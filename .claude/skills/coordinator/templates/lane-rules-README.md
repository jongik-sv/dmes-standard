# {업무 이름} 레인 공통 규칙

{작성 날짜} {업무 설명 한두 문장}을 세션 {N}개에 레인으로 나눠 진행한다.
조정 세션은 **{조정 세션 이름}** 이다. 질문·승인 요청·머지 요청은 모두 이 세션에 SendMessage 로 보낸다(사용자 화면에 묻지 않는다).

| 세션 | 레인 | 브랜치 |
|---|---|---|
| {세션 이름} | {레인 설명} | `{브랜치}` |

각 레인의 할 일·소유 파일·금지 파일은 조정 세션이 보낸 지시 메시지가 정본이다.

## 1. 작업 방식: Workflow 필수, 단계별 모델 지정

- 레인 작업은 **Workflow 도구**로 돌린다. 먼저 `workflow-authoring` 스킬을 읽는다.
- 모든 `agent()` 호출에 `model` 과 `effort` 를 명시한다.

| 단계 | model | effort |
|---|---|---|
| {설정 workflow.model_table 의 stage} | {model} | {effort} |

(표는 조정 설정 `workflow.model_table` 로 채운다. 기본 행: 조사·위치 찾기·문서 갱신·기계적 치환 sonnet/medium, 특성 테스트·구현·수정 opus/high, 리뷰·정합성 결함 수정 opus/high, 보안·트랜잭션 정합성 판정 opus/xhigh, 시험 실행·결과 확인 sonnet/medium)

- 항목마다 「구현 → 리뷰 → 지적 수정」 순서로 진행한다. 리뷰가 clean 이 아니면 다음 항목으로 넘어가지 않는다.
- 레인 안에서 파일이 겹치지 않는 항목은 병렬로 돌려도 된다. 겹치면 순서대로 돌린다.
- 동시 agent 수는 조정 세션이 지시문으로 정한다(기본은 현재 띠의 상한 G 4·Y 3·O 2).
- 셸 명령은 짧게 나눈다. heredoc·`sh -c`·변수·`$(…)` 를 섞은 복합 명령은 확인 창을 띄워 Workflow 를 멈춘다. 파일 수정은 Edit·Write 도구로 한다.
- 무거운 단계에는 시간 상한을 둔다(모듈당 15분, 전체 빌드 40분 등). 로그가 5분 넘게 늘지 않고 CPU 0% 이면 자기 트리만 종료하고 blocked 로 보고한다.

## 2. 작업 공간

- 레인마다 워크트리를 따로 쓴다. 기준은 `{integration_branch}` 최신 커밋이다. 브랜치 이름은 위 표를 따른다.
- {프로젝트 규칙: 이 리포 CLAUDE.md 와 RULE.md 의 작업 규칙을 따른다. PC별 실행 파일·경로는 각 PC 의 CLAUDE.md 와 `.coord.local.json` 이 정한다}
- {시험 규칙: 사용할 DB·도커 사용 여부 등}
- 메인 저장소에서 실행 중인 로컬 서버·FE 를 끄거나 재기동하지 않는다. 브라우저 확인이 필요하면 조정 세션에 요청한다. 직접 연 브라우저 작업 공간은 보고 전에 닫는다.
- 무거운 명령(gradle·전체 시험·빌드·E2E)은 레인당 한 번에 하나만 돌린다. 조정 세션의 `무거운 작업 금지` 통지를 받으면 풀릴 때까지 시작하지 않는다.

## 3. 규율

- {업무 원칙: 예) 동작 보존이 원칙이다. 바꾸기 전에 특성 테스트를 먼저 깔고, 바꾼 뒤 같은 테스트가 통과해야 한다}
- 결함 수정(동작이 바뀌는 것)은 다른 커밋과 섞지 않고 `fix(...)` 커밋으로 따로 둔다.
- **자기 레인의 소유 파일만 고친다.** 금지 파일을 고쳐야 하면 먼저 조정 세션에 묻는다.
- {소유 레인이 하나뿐인 공용 파일 목록과 소유 레인}
- **삭제하지 않는다.** 쓰지 않는 파일은 archive 로 옮긴다(`git mv`, 빌드·시험 대상에서 빠지게 설정).
- {사용자 승인이 필요한 변경: 예) shared 의 기존 공개 API·props·동작 변경은 조정 세션에 승인 요청을 보내고 기다린다. 새 export 추가는 승인 없이 한다}
- 커밋은 저장소 관례(Conventional Commits)를 따르고 작은 단위로 나눈다.
- 영역 규칙이 걸리면 리포의 무조건 적용 스킬을 따른다.

## 4. 머지 절차

1. **준비된 레인부터 머지한다.** 남는 의존은 다음과 같다.
   - {A 레인 항목은 B 레인이 들어간 뒤 머지한다. 의존 그래프를 그대로 옮긴다}
   - 머지 요청 직전에 `{integration_branch}` 최신을 자기 브랜치에 합치고 빌드·시험을 다시 돌린다.
2. 머지 직전, 조정 세션에 다음 형식으로 보낸다.
   `머지 요청: 세션 이름 / 원본 브랜치 / 대상 {integration_branch} / 커밋 수·변경 요약 / 겹칠 수 있는 파일·모듈 / 머지 전 시험 결과(명령과 통과·실패 수)`
3. 「머지 허가」 를 받은 뒤에만 머지한다. 「대기」 면 그 머지는 기다리되 놀지 않는다. 병목으로 기다리게 되면(다른 레인 머지·의존물·Oracle·heavy 슬롯·사용자 결정) 스스로 (a) 범위 안 의존 없는 다음 항목 (b) dev 미리 합치고 컴파일까지 확인 (c) 병목이 풀린 뒤 할 단계 준비(리허설·스크립트·런북·머지 요청 초안) (d) 문서·후속 목록 정리를 찾아 진행하고 무엇을 하는지 보고한다. 없을 때만 대기 보고를 보낸다. 머지는 {머지 방법: 메인 저장소에서 `--no-ff`. git 실행 파일은 PC 설정을 따른다} 로 한다.
4. 머지 뒤 `머지 완료: 머지 커밋 해시 / 트리 / 머지 뒤 빌드·시험 결과` 를 보낸다(충돌·실패도 그대로).
5. 이어 워크트리를 정리한다(`git worktree remove`, `git branch -d`. `--force`·`-D` 금지). 끝나면 `정리 완료: 지운 워크트리·브랜치 / 남긴 것과 이유` 를 보낸다.
6. 레인 일이 많으면 중간 단위로 여러 번 머지해도 된다. 매번 같은 절차를 따른다.
7. 레인은 push 하지 않는다. dev push·릴리스 반영과 반영 빌드는 조정자가 머지 뒤에 한다.

## 5. 보고

- 항목 하나가 끝날 때마다 조정 세션에 한 줄로 보낸다: `진행 보고: 항목 번호 / 커밋 / 시험 결과(명령과 통과·실패 수) / 진도율 N%(끝난 항목/전체) / 다음 항목`.
- 조정 세션의 지시마다 번호(`instr_id`)가 붙는다. 다음 보고 첫 줄에 그 번호를 적는다.
- 착수 때 한 번 신원을 보낸다: `신원: 이름 / 세션ID / Orca 핸들 / pid / 워크트리`.
- 정본 메모를 하나 두고 지금 상태·남은 순서·결정·조정 세션 이름·다음 단계를 유지한다. 「정본 갱신 요청」 이 오면 갱신하고 `정본 갱신 완료: 경로 / 남은 일 3줄` 로 답한다. compact 뒤에는 정본을 읽고 「재개 확인」 에 남은 일 3줄로 답한다.
- 측정할 수 있는 성능 항목은 전후 수치를 남긴다. 이 PC 는 측정 편차가 클 수 있으므로 반복 측정 없이 결론 내지 않는다.

## 6. 기록 문서

{필요한 경우만 둔다. 사용자가 전후를 직접 비교하려는 업무일 때.} 레인마다 아래 문서를 **자기 브랜치에서** 쓰고 머지에 함께 넣는다. 레인별 파일을 따로 두어 머지 충돌을 막는다.

| 문서 | 경로 |
|---|---|
| 구조 변경 기록 | `docs/{업무}/structure-{레인}.md` |
| 성능 비교 기록 | `docs/{업무}/perf-{레인}.md` |

머지 요청을 보낼 때 해당 머지에 든 항목이 문서에 들어 있어야 한다. 모든 머지가 끝나면 조정 세션이 두 문서를 모아 `SUMMARY.md` 로 정리한다.

### 6.1 구조 변경 기록

대상: 클래스·모듈 분리와 통합, 패키지 이동, 공개 API·진입점 변경, 호출 경로·계층 변경, 설정 조립 방식 변경, 의존성 변경, archive 이동. 이름 정리·서식·시험만 추가한 커밋은 적지 않는다.

```markdown
## S<번호>. <제목>
- 커밋: <해시들>
- 바뀌기 전: <구조>
- 바뀐 뒤: <구조>
- 바꾼 이유: <문제와 기대 효과>
- 동작 보존 근거: <특성 시험 이름·결과>
- 영향 범위: <호출부·설정·다른 레인·화면>
- 되돌리는 방법: <revert 대상 커밋, 주의점>
```

### 6.2 성능 비교 기록

대상: 성능을 기대하고 바꾼 항목 전부. 기준(before)은 {기준 태그} 에서 별도 워크트리로 잰다. 수치는 조정 세션이 「측정 시작」 을 알린 뒤에 잰다(다른 레인이 조용할 때 단독으로 재기 위해). 기준과 변경을 번갈아(A·B·A·B…) 각 3회 이상 재고, 회차마다 값과 load(`coord-status.sh` PC 줄의 `load1`, 윈도우는 `-` = 관측 불가)를 남기며 결론은 중앙값으로 낸다. 편차가 없는 지표는 1회로 충분하다.

```markdown
## P<번호>. <항목>
- 관련 구조 변경: S<번호> (있으면)
- 지표(단위): <예: 콜드 빌드 시간(초)>
- 측정 절차: <명령·데이터·화면 조작을 그대로 따라 할 수 있게>
- 기준 커밋: {기준 태그} / 변경 커밋: <해시>
- 측정 환경: <단독 여부, 전원 연결, 측정 일시>

| 회차 | 기준 | 변경 | load(1분) |
|---|---|---|---|
| 1 | | | |

- 중앙값: 기준 <값> → 변경 <값> (<증감 %>)
- 판정: <개선·차이 없음·악화, 그 근거>
```
