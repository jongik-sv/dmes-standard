## 작업 방식

[작업 방식] 시간·토큰·성능 최적. 모든 일은 최소 충분 등급에서 시작, 실패·막힘 근거가 있을 때만 한 칸 올림.
시작 전에 핵심 수정이 몇 파일·몇 줄인지 먼저 적고, 모든 단계를 그 크기에 비례시킴.
항목마다 실행 수단을 업무 크기로 고름
- 영향·범위·단계·시간 → D0 직접 · D1 검색 워커 · D2 agent 하나 · D3 병렬 agent · D4 Workflow (기준표 {sizing_doc})
- 낮은 단계부터 맞춰 보고, 부족하다는 근거가 나올 때만 올림
- 진행 보고에 고른 단계 기재(예: 실행: D2)
Workflow(D4) = 구현 → 리뷰 → 수정이 필요한 M/L 항목, 또는 같은 흐름을 여러 항목에 반복할 때만
- 먼저 workflow-authoring 스킬 읽기
- 단순 시험·조회·한 파일 수정 = Workflow 없이 직접
모든 agent() 에 model 과 effort 기재(크기 S/M/L = 항목 표 기준):
{workflow.model_table 의 각 항목을 한 줄씩: - {stage} [{size}]: {model} / {effort}. model 이 search 면 「검색 워커({search_cmd}: agy, 실패 시 opencode) → 두 워커가 모두 실패하면 sonnet/medium」 으로 적는다}
시험 실패 → 실패 사다리: {workflow.escalation.ladder 를 「model/effort → …」 로}
- 시간 초과·부하 연쇄 실패 = load 확인 뒤 같은 등급으로 한 번만 재실행
- 같은 원인으로 연속 두 번 실패 = 한 칸 건너뜀
- 사다리 끝에서도 실패(항목당 수정 시도 최대 {workflow.escalation.max_attempts}회) = 멈추고 blocked 보고
조사 = 영향에 비례
- 값 하나 확인·위치 찾기 = Workflow·agent 없이 {search_cmd} 한 번 또는 grep 한 번
- 조사·위치 찾기·사용처 집계 = agy·opencode 먼저({search_cmd}, agy 실패 시 opencode 로 자동 하강)
- 두 워커가 모두 실패했을 때만 grep 또는 sonnet/medium agent
무거운 시험 = PC 전체에서 한 번에 하나
- 파일 하나씩 옮기는 단계(리팩토링) = 해당 폴더 시험과 tsc 만
- 띄운 백그라운드(시험 입력·성능 측정·로컬 DB·감시) = 반드시 정리
- 진행 보고·정리 완료 보고에 「남은 백그라운드 0」 기재
- 성능 시험에는 시간 상한 부착
- 무거운 작업 금지 통지 중 = 단순 시험도 미룸
항목마다 구현 → 리뷰 → 지적 수정. 리뷰가 clean 이 아니면 다음 항목으로 넘어가지 않음.
**속도 규칙**
- 중간 단계 = 해당 모듈 tsc 와 바뀐 파일 시험만
- 리뷰 지적 수정 뒤 = 전체 재리뷰 없이 수정분만 확인(보안 리뷰 수정분 = opus 로 한 번)
- 동시 agent = {N}개까지(조정자가 사용량·부하 띠로 정함)
- 무거운 명령 = {heavy_env} 로 heavy.sh 경유
셸 명령 = 짧게 나눔
- heredoc·sh -c·변수·$(…) 섞은 복합 명령 금지
- 파일 수정 = Edit·Write 도구
- 확인 창이 뜨면 Workflow 가 멈춤
사람에게 묻는 선택 창(AskUserQuestion) 금지
- 물을 것 = 조정자에게 「질문: 배경 / 선택지 / 기본안」 메시지
- 기본안으로 계속할 수 있으면 계속
무거운 단계마다 시간 상한(모듈당 15분, 전체 빌드 40분 등)
- 로그가 5분 넘게 늘지 않고 CPU 0% → 자기 트리만 TERM 으로 끝내고 blocked 보고
- 긴 gradle 실행 = `--info` 금지, 출력은 파일로
보고 첫 줄에 지시 번호 {instr_id} 와 지금 돌고 있는 동시 agent 수 기재.

## 시험 시간 예산

(2026-10-09 사용자 지시. 「작업 방식」 의 시험 문장과 충돌하면 이 절이 우선)
- 시험 범위 = 바뀐 것만: 바뀐 파일·모듈 단위 시험, 바뀐 화면의 E2E 스펙만
- 단순 시험(단일 시험 파일·클래스, tsc, lint) = heavy.sh 없이 바로 실행

  - 경계값 전수·변이 시험·스냅샷 대량 추가 금지
- 실패 재실행 = 같은 명령 1회까지
  - 내 변경과 무관한 기존 실패 = 고치지 않고 보고만
- 항목당 시험 실행 시간 합계가 15분 초과 → 멈추고 진행 보고(원인·남은 시험)
- 리뷰 지적 수정 뒤 = 수정분 시험만

## 보고 방식

- 항목 하나가 끝날 때마다 한 줄: `진행 보고: 항목 번호 / 커밋 / 시험 결과(명령과 통과·실패 수) / 진도율 N%(끝난 항목/전체) / 다음 항목`
  - 첫 줄에 {instr_id}
- 머지 직전: `머지 요청: 세션 이름 / 원본 브랜치 / 대상 {integration_branch} / 커밋 수·변경 요약 / 겹칠 수 있는 파일·모듈 / 머지 전 시험 결과(명령과 통과·실패 수)`
  - 「머지 허가」 를 받은 뒤에만 머지
  - 머지 뒤 `머지 완료`, 정리 뒤 `정리 완료` 보고
- 머지 요청에 대상 SHA 기재
  - 브랜치에 다음 항목 커밋이 이미 쌓여 있으면 머지할 커밋을 7~12자 SHA 로 적고, 그 SHA 까지만 머지
  - 머지 요청·정리 완료 보고에 「남은 백그라운드 0」 병기
- 정본 메모: {경로}. 지금 상태·남은 순서·결정·조정 세션 이름·다음 단계 유지
  - 「정본 갱신 요청」 수신 → 갱신 후 `정본 갱신 완료: 경로 / 남은 일 3줄` 답장
- 병목으로 기다리게 되면(다른 레인 머지·의존물·Oracle·heavy 슬롯·사용자 결정) 무작정 기다리지 않음. 스스로 찾아 진행하고 진행 보고에 기재:
  - (a) 범위 안 의존 없는 다음 항목
  - (b) dev 미리 합치고 컴파일까지 확인
  - (c) 병목이 풀린 뒤 할 단계 준비(리허설·스크립트·런북·머지 요청 초안)
  - (d) 문서·후속 목록 정리
  - 넷 다 없을 때만 「대기」 보고
  - 다른 레인 소유 파일 수정 금지
  - 머지 요청을 낸 뒤 요청 SHA 를 바꾸는 합류 금지
  - 병목 레인을 돕는 일 = 조정자가 배정
- 무거운 작업 금지 통지 수신 → 풀릴 때까지 무거운 명령 시작 금지
- 조정자는 보고로 쌓인 state.json 요약으로 판단, 화면은 이상 감지 때만 읽음
  - 항목 완료·막힘·대기 같은 상태 변화 = 화면에 두지 말고 진행 보고로 알림
