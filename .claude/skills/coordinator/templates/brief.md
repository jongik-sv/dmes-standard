## 작업 방식

시간·토큰·성능 최적. 최소 충분 등급에서 시작.
- 한 칸 올림 = 실패·막힘 근거가 있을 때만(시험 실패·리뷰 지적 반복·20분 넘게 막힘)
- 시작 전에 핵심 수정 크기(파일·줄 수) 기재, 모든 단계를 그 크기에 비례
- 실행 수단 = 항목마다 업무 크기로 고름(기준표 {sizing_doc})
  - D0 직접 · D1 검색 워커 · D2 agent 하나 · D3 병렬 agent · D4 Workflow · D5 새 세션 · DP 풀(아래 「비-Claude 풀」)
  - 진행 보고에 고른 단계 기재(예: 실행: D2)
- Workflow(D4) = 같은 흐름(구현→리뷰→수정) M/L 항목이 {wf_min}개 이상일 때만
  - agent 2개 이하로 끝나는 일 → Agent 도구 직접(D2·D3)
  - Workflow 안에서 풀 호출 금지(풀은 레인이 Workflow 밖에서)
  - 먼저 workflow-authoring 스킬 읽기
  - 조회·한 파일 수정 = Workflow 없이 직접
- 모든 agent() 에 model·effort 기재(크기 S/M/L = 항목 표 기준):
  - opus 를 쓰면 근거 한 줄(L·동시성·판정 중 무엇). token 모드 opus = 판정 리뷰·L 구현만
  - 같은 단계 agent = 같은 모델로 함께 띄움. 지시문은 공통 부분 먼저, 항목별 내용 뒤(캐시 재사용)
{workflow.model_table 항목마다 한 줄: - {stage} [{size}]: {model} / {effort}}
- 시험 실패 → 실패 사다리: {workflow.escalation.ladder 를 「model/effort → …」 로}
  - 시간 초과·부하 연쇄 실패 → load 확인 뒤 같은 등급 1회만 재실행
  - 같은 원인 연속 2회 실패 → 한 칸 건너뜀
  - 사다리 끝 실패 또는 수정 시도 {workflow.escalation.max_attempts}회 도달 → 멈추고 blocked 보고
- 조사 = 영향에 비례
  - 값 하나·위치 찾기 → Workflow·agent 없이 {search_cmd} 또는 grep 한 번
  - 조사·사용처 집계 → {search_cmd}(agy 먼저, 실패 시 opencode)
  - 두 워커 모두 실패 → grep 또는 sonnet/medium agent
  - model 이 search 인 단계 = 위 순서대로
- 항목마다 구현 → 리뷰 1회 → 지적 수정 → 수정분만 확인
  - 수정분 확인이 clean 이 아니면 그 항목에 의존하는 항목만 대기(다른 항목은 계속)
  - 보안 리뷰 수정분 확인 = opus 로 1회
  - 몇 줄 수정·리팩토링 이동 단계 = 리뷰는 마지막 1회
- 회차 모드 = {mode} (token = 토큰 우선, time = 시간 우선)
- 병렬 배정(레인 안)
  - 착수 때 항목 표에 항목마다 `선행 항목`·`건드릴 파일` 기재({sizing_doc} 와 같은 폴더의 decompose.md §2.1 형식)
  - 선행이 끝났고 진행 중 항목과 건드릴 파일이 안 겹치는 항목 → 동시 상한까지 한꺼번에 시작
  - 동시 agent = {N}개까지(구현·리뷰·수정 합)
  - 구현 agent = 자기 항목 파일만 수정, 커밋 금지
  - 컨트롤러 = 그 항목 파일만 `git add <파일…>` 로 커밋
    - 커밋 전 `git status` 로 소유 밖 변경 확인 → 있으면 그 항목 멈추고 보고
  - 구현 끝난 항목 → 바로 커밋·리뷰 시작. 다른 항목 구현은 계속
  - 리뷰가 clean 될 때까지 그 항목 파일 = 그 항목 소유
  - 웨이브(함께 진행한 묶음) 끝 → 컨트롤러가 모듈 시험 1회(heavy.mjs)
- agent 보고 = `task-<번호>-report.md` 파일 + 컨트롤러에게 5줄 이하 요약
- 비-Claude 풀(절차 {pool_doc})
  - token 모드: S/M 구현·조사·문서 → 풀 먼저(`{pool_cmd} submit …`)
  - time 모드: Claude agent 와 풀 중 먼저 비는 쪽
  - 풀 결과 → 완료 조건 시험 1회 → Claude 리뷰
  - 풀 실패·리뷰 지적 → Claude agent 가 처리(풀에 다시 맡기지 않음)
  - 풀 금지: L·동시성·트랜잭션·보안·공유 API·원인 모를 결함
- 컨텍스트 {lane_max} 토큰 넘음 → 조정자의 정본 갱신 요청에 답하고 `/clear` 재개 대기
- 셸 명령 = 짧게 나눔
  - heredoc·sh -c·변수·$(…) 섞은 복합 명령 금지
  - 파일 수정 = Edit·Write 도구
  - 확인 창이 뜨면 Workflow 가 멈춤
- 사람에게 묻는 선택 창(AskUserQuestion) 금지
  - 물을 것 → 조정자에게 「질문: 배경 / 선택지 / 기본안」
  - 기본안으로 계속할 수 있으면 계속
- 무거운 명령 1회 시간 상한 = 모듈당 15분, 전체 빌드 40분
  - 로그 5분 넘게 불변 + CPU 0% → 자기 트리만 TERM, blocked 보고
  - 긴 gradle = `--info` 금지, 출력은 파일로

## 보고 방식

- 모든 보고 첫 줄 = 지시 번호 {instr_id} + 지금 도는 동시 agent 수
- 보고 문체 = 한국어 뼈대 + tech term·identifier 영어 원문, 조사·인사·군말 생략, 명사로 끝냄. 숫자·부정·추정 여부 유지
  - 프로젝트 문체 문서(CLAUDE.md 가 가리킴)가 있으면 그것 우선
  - 위 고정 문구(`진행 보고:`·`머지 요청:`·`머지 완료:`·`정리 완료:`)는 바꾸지 않음
- 상태 변화(항목 완료·막힘·대기) = 화면에 두지 않고 진행 보고로
- 항목 하나가 끝날 때마다: `진행 보고: 항목 번호 / 체크포인트 커밋(선택) / 시험 결과(명령과 통과·실패 수) / 진도율 N%(끝난 항목/전체) / 다음 항목`
  - 작업 중 commit = 체크포인트(자유). 통합 브랜치 모양 = 레인당 commit 1개, merge commit 없음(선형, 머지 = `git merge --ff-only`)
- 머지 직전 순서
  1. {integration_branch} 최신을 브랜치에 합치고 충돌·시험 확인
  2. `node .claude/skills/_shared/node/squash-branch.mjs --onto {integration_branch} --subject "<type(scope): 레인 전체 요약>" --rebase` → `SQUASH_OK`·`SQUASH_ALREADY_ONE`·`SQUASH_REBASED` 확인(결과 = {integration_branch} tip + commit 1개)
     - `SQUASH_REBASE_CONFLICT` → 원래 상태로 복원됨. {integration_branch} 를 브랜치에 합쳐 충돌을 풀고 시험 뒤 다시 실행
  3. 합친 commit 의 SHA 를 머지 요청에 적음. 합친 뒤 SHA 를 바꾸는 commit·합류 금지
- 머지 직전: `머지 요청: 세션 이름 / 원본 브랜치 / 대상 {integration_branch} / 커밋 수(1)·변경 요약 / 겹칠 수 있는 파일·모듈 / 머지 전 시험 결과(명령과 통과·실패 수) / 머지할 SHA(합친 커밋 1개, 7~12자)`
  - 커밋 수 ≠ 1 → 조정자가 `NOT_SQUASHED`, 기점 ≠ {integration_branch} tip → `NOT_REBASED` 로 되돌림
  - 요청 뒤 쌓인 다음 항목 커밋 = 다음 머지 몫. 이번 머지 = 그 SHA 까지만
  - 진행 보고·머지 요청·정리 완료 보고에 「남은 백그라운드 0」 병기
- 「머지 허가」 수신 뒤에만 머지
  - 머지 = 메인 저장소에서 `git merge --ff-only <SHA>`. {integration_branch} 가 그 사이 앞서 가 실패하면 위 2번을 다시 하고 머지 요청 재전송
  - 머지 뒤 `머지 완료: 커밋 / 트리 / 머지 뒤 빌드·시험 결과(충돌·실패도 그대로)`
  - 정리 뒤 `정리 완료: 지운 워크트리·브랜치 / 남긴 것과 이유`
  - 「대기: 사유」 수신 → 병목이면 아래 병목 대기대로, 수정·첨부 요청이면 그 일 먼저
- 정본 메모: {경로}. 지금 상태·남은 순서·결정·조정 세션 이름·다음 단계 유지
  - 「정본 갱신 요청」 수신 → 갱신 후 `정본 갱신 완료: 경로 / 남은 일 3줄` 답장
  - compact 뒤 「재개 확인」 수신 → 정본을 읽고 남은 일 3줄 답장
  - `/clear` 뒤 「재개:」 수신 → 문구가 가리키는 착수 지시 원문(이 메시지)과 정본을 읽고 이어서 진행
- 병목 대기(다른 레인 머지·의존물·Oracle·heavy 슬롯·사용자 결정) → 무작정 기다리지 않음
  - 아래에서 스스로 찾아 진행, 진행 보고에 기재
  - (a) 범위 안 의존 없는 다음 항목
  - (b) dev 미리 합치고 컴파일까지 확인
  - (c) 병목이 풀린 뒤 할 단계 준비(리허설·스크립트·런북·머지 요청 초안)
  - (d) 문서·후속 목록 정리
  - 넷 다 없을 때만 「대기」 보고
  - 다른 레인 소유 파일 수정 금지
  - 머지 요청 뒤 요청 SHA 를 바꾸는 합류 금지
  - 병목 레인을 돕는 일 = 조정자가 배정
