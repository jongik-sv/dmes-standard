# 업무 분해와 레인 할당

설계 절: §3.a(업무 분해·레인 할당), §5.2(레인 공통 규칙 문서 템플릿).

분해 초안은 조정자가 직접 쓰지 않고 `opus` / `high` 서브에이전트에 올린다(「판단 올리기」). 서브에이전트에는 아래 입력과 이 문서의 규칙을 넘기고, 항목 표·레인 묶기·의존 그래프를 돌려받아 사용자에게 확정받는다.

## 1. 입력

1. 큰 업무 설명(사용자 지시).
2. 조사 결과: 조정자가 Explore 등으로 만든 것(건드릴 파일·모듈·기존 구조).
3. 레인 수: 사용자가 띄운 세션 수 또는 사용량 띠가 허용하는 수(`usage.md`: 1주 사용률이 `usage.spawn_week_max` 미만이면 띠와 상관없이 허용). 입장 제어가 필요하면 dflow-team 의 `capacity.sh` 가 있는 PC 에서만 부른다(없으면 건너뛴다).

**회차는 조정 세션 하나에 하나만 둔다.** 열린 회차가 있는데 새 업무가 들어오면 `init` 으로 새 회차를 열지 않고, 그 회차에 레인을 `lane-add` 하고 `run.goal` 에 새 업무를 덧붙인다(`coord-state.sh set '.run.goal' '"<기존 목표> / <새 업무>"'`). 회차를 둘 열면 오피스에 팀장이 두 칸으로 보이고 slots·busy 가 합산된다(사용자 지적 2회). 앞 업무가 끝났다면 먼저 `close-run`(`closing.md` §6) 하고 새 회차를 연다.

## 2. 항목 표 만들기

항목마다 다음 칸을 적는다.

| 칸 | 내용 |
|---|---|
| id | 짧은 식별자(레인 안에서 유일) |
| 제목 | 한 줄 |
| 크기 | S / M / L (진도 가중치로 쓴다: S=1, M=2, L=3 이 기본) |
| 건드릴 파일·모듈 | 경로 또는 글롭 |
| 선행 항목 | 먼저 dev 에 들어가야 하는 항목 |
| 무거운 명령 여부 | 전체 시험·빌드·E2E 를 도는가 |
| 측정 대상 여부 | 벽시계 성능 측정이 들어가는가 |

마감 단계(측정, SUMMARY, 정리)도 항목으로 넣는다. 「코드 100%」인데 측정·정리가 남은 상태를 구분하기 위해서다.

## 3. 레인 묶기 규칙

- 건드릴 파일이 겹치는 항목은 한 레인에 둔다. 겹침을 못 피하면 **소유 레인**을 하나 정하고 다른 레인은 요청만 한다(예: 빌드 설정 파일은 빌드 레인만 고친다).
- 공용 자원(shared 공개 API, 공용 DB, 메인 서버)은 소유자를 지정하거나 조정자 전용으로 둔다. 서버 기동·브라우저 확인은 조정자만 한다.
- 레인 크기는 비슷하게 맞춘다. 의존이 긴 레인에는 기다리는 동안 할 수 있는 독립 일을 섞는다.
- 레인마다 `owned`(소유 글롭)와 `forbidden`(금지 글롭)을 적는다. `merge-gate.sh` 가 이 둘로 범위를 대조한다.

## 4. 의존 그래프

`항목 A → 항목 B`(B 는 A 가 dev 에 들어간 뒤) 형태로 state 의 `deps` 에 둔다: `["a8:3b", "a6:menu-cache"]`. 머지 순서·측정 순서·대기 작업 배정에 쓴다. 실제 예: 「1b 2차는 a8·a6 이 들어간 뒤」, 「a6 메뉴 캐시는 a8 3b 뒤 통합 시험 다시」.

**의존물은 따로 먼저 머지한다.** 결과는 한 덩어리씩 바로 머지하는 것이 기본이다. 그중 여러 레인이 기다리는 의존물(다른 레인이 쓰는 공개 prop·계약·공용 부품)은 다른 일과 묶지 않고 단독으로 먼저 머지한다. 항목 표의 「선행 항목」 칸에 이런 의존물을 따로 항목으로 둔다. 단독으로 먼저 머지한 레인(C1·c0)은 짝 레인이 바로 출발했고, 의존물(C5 prop)이 다른 항목(C2)과 묶이면서 짝 레인(grid-adopt)이 약 1시간 기다린 일이 있다. 대기 레인에 줄 일은 `monitor.md` §5.

## 5. state 에 넣기

```text
scripts/coord-state.sh lane-add <레인> '{"brief":"…","branch":"…","worktree":"…","memo":"<정본 메모 경로>","owned":[…],"forbidden":[…],"priority":2,"items":[{"id":"1","title":"…","weight":2,"done":false}],"queue":[…]}'
scripts/coord-state.sh set '.deps' '[["a8:3b","a6:menu-cache"]]'
```

- 레인 이름은 **40자 이하**다(오피스 팀원 키가 40자로 자른다. 넘으면 `lane-add` 가 거절한다).
- **첫 `lane-add` 에 `memo`(정본 메모 경로)를 함께 넣는다.** 비면 compact 문구가 「정본은 -」 로 나가고 `lane-add` 가 stderr 에 `WARN` 한 줄을 낸다. 경로는 착수 지시의 정본 메모 칸과 같은 값이다(`compact.md` §1).

분해 단계에서 각 레인의 「대기 중 할 일」 후보(의존 없는 항목·병목 풀린 뒤 준비 단계·문서 정리)를 미리 `backlog` 에 넣는다. 레인이 병목으로 기다리게 될 때 조정자가 곧바로 줄 수 있어야 한다(`monitor.md` 「병목 대기 레인」).

`priority` 는 머지 임박 > 측정 > 일반 구현 > 대기 작업 순으로 숫자가 낮을수록 높다(`heavy.md`).
`heavy_env` 는 전용 칸을 줄 때만 채운다(`heavy.md` 「예외 칸」).

## 6. 착수 지시

착수 지시는 `protocol.md` 3.1 과 `templates/brief.md` 로 만든다. 지시 메시지가 그 레인의 할 일·소유 파일·금지 파일의 정본이다. 원문은 `lanes/<레인>/brief.md` 에도 남긴다(compact 뒤 복구용).

## 7. 레인 공통 규칙 문서 쓰는 법

레인 공통 규칙(작업 공간, 규율, 머지 절차, 보고, 기록 문서)은 저장소 문서 하나(`docs/<업무>/README.md`)에 두고 착수 지시에서 링크한다. 뼈대는 `templates/lane-rules-README.md` 이고, 견본은 `docs/refactor-2026-10/README.md` 다.

절차:

1. `templates/lane-rules-README.md` 를 `docs/<업무>/README.md` 로 복사한다.
2. `{…}` 자리를 채운다: 업무 이름, 조정 세션 이름, 레인 표(세션·레인·브랜치), 워크트리 규칙, 소유·금지 규칙, 시험 규칙.
3. **Workflow 단계별 모델 표**는 설정 `workflow.model_table` 값으로 채운다(`workflow.md`).
4. PC별 도구 이름(git 실행 파일, JDK 경로, 브라우저 도구)은 이 문서에 쓰지 않는다. 필요하면 「프로젝트·PC 설정은 각 PC 의 CLAUDE.md 와 `.coord.local.json` 을 따른다」로 가리킨다. 리포 CLAUDE.md 가 이미 정한 규칙은 링크한다.
5. 기록 문서(구조 변경·성능 비교) 경로를 레인 이름으로 정한다. 머지 게이트의 `records_check` 가 이 경로를 본다.
6. 커밋은 사용자 지시가 없으면 하지 않는다(문서를 만들고 사용자에게 알린다).

## 8. 후속 리팩토링 레인 예시

큰 공용 파일(1,500줄 이상)이 기능 작업을 늦추면(여러 레인이 같은 파일을 기다리거나 충돌한다), 그 기능 작업을 머지한 **직후** 같은 레인에 분리 리팩토링 항목을 붙인다. 새 레인을 따로 띄우지 않는다(그 레인이 파일 맥락을 이미 안다). 항목 순서:

1. 특성 시험 고정: 지금 동작을 시험으로 먼저 박는다.
2. 순수 함수·타입 이동: 동작이 없는 것부터 새 파일로 옮긴다.
3. 훅 이동: 상태·부수 효과가 있는 부분을 옮긴다.
4. opus 리뷰 한 번(동작 보존 판정). 항목마다 리뷰하지 않는다.

옮기는 중에는 해당 폴더 시험과 `tsc` 만 돌리고 전체 시험은 머지 요청 직전에 한 번이다(`heavy.md` §7). 사례: AgDataGrid(2,091줄)를 기능 작업 머지 뒤 같은 레인에서 분리했다. 이 항목은 의존 그래프에서 기능 작업 항목 뒤로 두고, 같은 파일을 만지는 다른 레인의 항목은 분리가 머지된 뒤로 미룬다.
