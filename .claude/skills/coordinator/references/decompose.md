# 업무 분해와 레인 할당

- 분해 초안 = `opus` / `high` 서브에이전트가 작성 (「판단 올리기」)
  - 조정자 직접 작성 금지
- 넘길 것: 아래 입력, 이 문서의 규칙
- 돌려받을 것: 항목 표, 레인 묶기, 의존 그래프 → 사용자 확정

## 1. 입력

1. 큰 업무 설명(사용자 지시)
2. 조사 결과(건드릴 파일·모듈·기존 구조)
   - 조정자가 Explore 등으로 수집
3. 레인 수: 사용자가 띄운 세션 수 또는 사용량 띠 허용 수
   - 새 레인 상한 = `usage.md` §2 「새 레인 상한」
   - 입장 제어: dflow-team 의 `capacity.sh` 가 있는 PC 에서만 호출

**회차는 조정 세션 하나에 하나.** (회차 절차 정본 = `closing.md` §6)
- 열린 회차가 있는데 새 업무 수신 → 새 회차를 열지 않음
  - 그 회차에 `lane-add`
  - `run.goal` 에 덧붙임: `node scripts/coord-state.mjs set '.run.goal' '"<기존 목표> / <새 업무>"'`
- 앞 업무 종료 → 먼저 `close-run`, 그 뒤 새 회차

## 2. 항목 표 만들기

칸:
- id: 짧은 식별자(레인 안에서 유일)
- 제목: 한 줄
- 크기: S / M / L (진도 가중치 S=1, M=2, L=3)
- 건드릴 파일·모듈: 경로 또는 글롭
- 선행 항목: 먼저 dev 에 들어가야 하는 항목
- 무거운 명령 여부: 전체 시험·빌드·E2E 여부
  - 옆에 시험 범위(바뀐 모듈만 / 리포 전체) 병기
- 측정 대상 여부: 벽시계 성능 측정 여부

- 시험 범위 기본 = 바뀐 모듈만. 리포 전체는 예외
- 마감 단계(측정, SUMMARY, 정리)도 항목으로 둠
  - 「코드 100%, 측정·정리 남음」 구분용
- 화면 레인(`src/frontend` 의 `m-*` 화면을 만들거나 바꾸는 레인)
  - 머지 항목 앞에 「렌더 점검」 항목(크기 S)
  - 레인 행동 = `templates/brief.md` 「화면 레인」
  - `scripts/perf/render/screens.mjs` = 여러 레인 공용 파일
    - 등록은 한 레인만 담당
  - 프로파일링 측정 = 회차 마감 때 한 번 (`closing.md` §0)

## 3. 레인 묶기 규칙

- 건드릴 파일이 겹치는 항목 → 한 레인
  - 겹침 불가피 → **소유 레인** 하나 지정, 다른 레인은 요청만
  - 예: 빌드 설정 파일 = 빌드 레인
- 공용 자원(shared 공개 API, 공용 DB, 메인 서버) → 소유자 지정 또는 조정자 전용
  - 서버 기동·브라우저 확인 = 조정자만
- 레인 크기 비슷하게
- 의존이 긴 레인 → 대기 중 할 독립 일을 섞음
- 레인마다 `owned`(소유 글롭)·`forbidden`(금지 글롭) 기재
  - `merge-gate.mjs` 가 범위 대조

## 4. 의존 그래프

- 형태: `항목 A → 항목 B` (B 는 A 가 dev 에 들어간 뒤)
- 용도: 머지 순서·측정 순서·대기 작업 배정

**의존물은 단독으로 먼저 머지.**
- 기본: 결과를 한 덩어리씩 바로 머지
- 여러 레인이 기다리는 의존물(공개 prop·계약·공용 부품) → 다른 일과 묶지 않음
  - 「선행 항목」 칸에 별도 항목으로 둠
- 묶으면 짝 레인이 대기
- 대기 레인에 줄 일 = `monitor.md` §5

## 5. state 에 넣기

```text
node scripts/coord-state.mjs lane-add <레인> '{"brief":"…","branch":"…","worktree":"…","memo":"<정본 메모 경로>","owned":[…],"forbidden":[…],"priority":2,"items":[{"id":"1","title":"…","weight":2,"done":false}],"queue":[…]}'
node scripts/coord-state.mjs set '.deps' '[["a8:3b","a6:menu-cache"]]'
```

- 레인 이름 **40자 이하**
  - 오피스 팀원 키가 40자로 잘림
  - 넘으면 `lane-add` 거절
- **첫 `lane-add` 에 `memo`(정본 메모 경로) 포함**
  - 비면 compact 문구 「정본은 -」 + `lane-add` stderr `WARN` 한 줄
  - 경로 = 착수 지시의 정본 메모 칸 값 (`compact.md` §1)

대기 중 할 일 후보를 분해 단계에서 준비:
- 의존 없는 항목 → `queue` 앞 (`monitor.md` 「병목 대기 레인」 (a))
- 준비 단계·문서 정리·교차 리뷰 후보 → `backlog` 에 넣음
  - 형식 `{id, kind, fits:[레인], desc}`
- `priority`: 머지 임박 > 측정 > 일반 구현 > 대기 작업
  - 숫자 낮을수록 높음 (`heavy.md` §2)
- `heavy_env`: 전용 칸을 줄 때만 기재 (`heavy.md` §5)

## 6. 착수 지시

- 작성: `protocol.md` 3.1 + `templates/brief.md`
- 지시 메시지 = 그 레인의 할 일·소유 파일·금지 파일의 정본
- 원문은 `lanes/<레인>/brief.md` 에도 보관 (compact 뒤 복구용)

## 7. 레인 공통 규칙 문서 쓰는 법

- 내용: 작업 공간, 규율, 머지 절차, 보고, 기록 문서
- 위치: 저장소 문서 `docs/<업무>/README.md` 하나. 착수 지시에서 링크
- 뼈대 `templates/lane-rules-README.md`
- 견본 `docs/refactor-2026-10/README.md`

절차:

1. 뼈대를 `docs/<업무>/README.md` 로 복사
2. `{…}` 채움
   - 업무 이름, 조정 세션 이름
   - 레인 표(세션·레인·브랜치)
   - 워크트리·소유·금지·시험 규칙
3. Workflow 단계별 모델 표 = 설정 `workflow.model_table` 값 (`workflow.md`)
4. PC별 도구 이름(git 실행 파일, JDK 경로, 브라우저 도구) 기재 금지
   - 대신 「프로젝트·PC 설정은 각 PC 의 CLAUDE.md 와 `.coord.local.json` 을 따른다」
   - 리포 CLAUDE.md 가 정한 규칙은 링크
5. 기록 문서(구조 변경·성능 비교) 경로를 레인 이름으로 지정
   - 머지 게이트 `records_check` 가 참조
6. 커밋은 사용자 지시가 있을 때만
7. 문서 작성 후 사용자에게 알림

## 8. 후속 리팩토링 레인 예시

- 조건: 큰 공용 파일(1,500줄 이상)이 기능 작업을 지연(레인 간 대기·충돌)
- 시점: 그 기능 작업 머지 **직후**
- 위치: 같은 레인에 분리 항목 추가
  - 새 레인 금지 (파일 맥락 보유)

항목 순서:

1. 특성 시험 고정: 현재 동작을 시험으로 고정
2. 순수 함수·타입 이동: 동작 없는 것부터 새 파일로
3. 훅 이동: 상태·부수 효과 부분
4. opus 리뷰 1회(동작 보존 판정). 항목마다 리뷰하지 않음

- 이동 중 시험 = 해당 폴더 시험 + `tsc` 만
- 바뀐 모듈 전체 시험 = 머지 요청 직전 1회 (`templates/brief.md` 「시험」)
- 의존 그래프: 기능 작업 항목 뒤
- 같은 파일을 만지는 다른 레인 항목 = 분리 머지 뒤로 미룸
