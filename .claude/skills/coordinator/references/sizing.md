# 업무 크기 산정과 실행 수단 선택

SKILL.md 「시간·토큰·성능 최적화 원칙」의 실행 기준.
- 시점: 조정자가 일을 맡기기 전, 레인이 항목 하나를 시작하기 전
- 목표: 같은 결과를 가장 적은 시간·토큰으로 얻는 **실행 수단** 선택
- Workflow·여러 에이전트는 비용(스크립트 작성, agent 기동, 컨텍스트 전달)이 큼 → 비용을 넘는 이득이 있을 때만 사용

## 1. 네 가지 점수

| 기준 | 0 | 1 | 2 |
|---|---|---|---|
| **영향**: 결과가 바꾸는 것 | 참고용(틀려도 곧 드러나고 손해 작음) | 작업 방향 결정(고칠 파일, 방식) | 판정·머지·데이터·공개 API·보안에 닿음 |
| **범위**: 읽거나 고칠 곳 | 파일 1~2개 | 한 모듈 안 여러 파일 | 여러 모듈·계층 |
| **단계**: 필요한 흐름 | 한 번에 끝남(조회·확인·한 번 수정) | 두 단계(수정 → 확인) | 셋 이상 또는 반복(구현 → 리뷰 → 수정, 실패 사다리, 항목 여러 개) |
| **시간**: 예상 소요 | 10분 안 | 1시간 안 | 1시간 넘음 |

## 2. 실행 수단 여섯 단계

| 단계 | 수단 | 고르는 조건 | 예 |
|---|---|---|---|
| **D0 직접** | 세션이 직접 명령(grep·cat·git·단순 시험) | 합계 0~1, 답이 몇 줄 | 값 하나 확인, 파일 위치, git 상태, 단일 시험 파일 실행 |
| **D1 검색 워커** | `node scripts/search.mjs "<질의>"`(기본 agy, 실패 시 opencode. 새 탭 실행, 사용자가 진행을 봄). Claude 토큰 미사용. 조사·위치·영향 범위·사용처 목록의 기본 수단. 시간 초과 종료 또는 큰 범위(예: 100개 파일 분류) → 재시도 없이 sonnet Explore(D2, §3)로 | 합계 0~2, 여러 파일을 읽지만 결과가 참고용·방향 결정용, 코드 수정 없음 | "이 설정은 어디서 읽나", "이 함수 호출자는", "이 오류 문구는 어디서 나나" |
| **D2 서브에이전트 하나** | Agent 1개(기본 sonnet/medium, 판정은 opus/high) | 합계 2~3, 단계 하나, 출력이 많아 세션 컨텍스트 절약 필요 | 한 모듈 집중 조사, 파일 몇 개 수정, 긴 로그 요약 |
| **D3 서브에이전트 병렬** | Agent 2~4개 동시 | 합계 3~5, 서로 독립인 범위 둘 이상, 공유 상태 없음, 각자 단계 하나 | 모듈 셋 따로 조사, 서로 다른 파일 묶음 수정 |
| **D4 Workflow** | Workflow 도구(단계마다 model·effort 지정) | 단계 점수 2(구현 → 리뷰 → 수정, 실패 사다리, 항목 반복)이고 합계 4 이상, 또는 결정적 흐름·재개 필요 | M/L 크기 구현 항목, 항목 여러 개를 같은 흐름으로 처리 |
| **D5 새 세션(레인)** | `spawn-lane.mjs` 로 새 탭 세션 | 시간 2 이고 자기 브랜치·워크트리·머지 필요, 또는 몇 시간 넘게 독립 컨텍스트 필요 | 레인 하나 분량 업무, 긴 측정, 다른 레인과 병렬 구현 묶음 |

## 3. 고르는 순서

0. **핵심 수정이 몇 파일·몇 줄인지 먼저 한 줄로 기재.**
   - 단계 수·Workflow 사용·조사 깊이·시험 범위를 이 크기에 비례시킴
   - 몇 줄 수정에 금지: 영향 조사 Workflow, 여러 갈래 조사, 항목마다 리뷰, 전 모듈 시험
   - 대신: 조사 = grep·검색 워커, 리뷰 = 마지막 1회, 시험 = 영향 모듈만
   - 이미 아는 영향 지점은 지시에 적어 줌
1. 네 점수를 매기고 합계 산출. 한 줄 판단이면 충분(자세히 따지지 않음)
2. **낮은 단계부터** 조건 확인
   - 경계가 애매 → 낮은 쪽
   - 부족 근거(답이 틀림, 범위가 큼, 출력 넘침) 발생 → 한 단계 올림
   - 높은 쪽 선취 금지
3. 예외 적용
   - 영향 2 → 단계 무관, 판정 부분만 opus/high(D2 의 model 만 올림). 수집·실행 부분은 올리지 않음
   - 코드를 고치고 리뷰가 필요한 M/L 항목 = D4 (리뷰 없이 머지 금지)
   - S 항목 = D2 구현 + sonnet/high 리뷰 1회
   - D1 이 `SEARCH fail`(agy·opencode 모두 실패) → D0(grep) 또는 D2
   - `search.mjs` 탭 모드 시간 초과(`search.timeout_s` 가 워커마다 적용, 기본 최대 약 480초) → 같은 질의 재전송 금지, 바로 sonnet Explore(D2)
   - 조사 범위가 「100개 파일 분류」 처럼 큼 → D1 건너뛰고 처음부터 sonnet Explore
   - 사용량 띠 O → D4 동시 agent 를 띠 상한(2)으로 축소. Y 이하는 단계를 낮추지 않음
   - 사용량 띠 R → Claude 로 D4·D5 신규 시작 금지(opencode·agy 워커 일은 계속)
4. 고른 단계를 지시·보고에 한 단어로 기재(예: `실행: D1`). 같은 종류 일에 같은 판단 반복 방지

## 4. 흔한 과잉

- 설정값 하나·함수 하나 확인에 Workflow·병렬 조사 → D0·D1
- 참고용 조사에 opus → D1 또는 sonnet/medium
- 이미 나온 답을 다른 수단으로 재확인 → 근거가 의심될 때만 1회
- 단순 시험 실행·결과 집계를 Workflow 단계로 구성 → D0 (haiku/low 대신 세션이 직접 실행이 더 쌈)
