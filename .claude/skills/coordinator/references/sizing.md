# 업무 크기 산정과 실행 수단 선택

SKILL.md 「시간·토큰·성능 최적화 원칙」의 실행 기준이다. 조정자가 일을 맡기기 전, 그리고 레인이 항목 하나를 시작하기 전에 이 기준으로 **실행 수단**을 고른다. 목표는 같은 결과를 가장 적은 시간·토큰으로 얻는 것이다. Workflow 나 여러 에이전트는 비용(스크립트 작성, agent 기동, 컨텍스트 전달)이 크므로, 그 비용을 넘는 이득이 있을 때만 쓴다.

## 1. 네 가지 점수

| 기준 | 0 | 1 | 2 |
|---|---|---|---|
| **영향**: 결과가 무엇을 바꾸나 | 참고용(틀려도 곧 드러나고 손해가 작다) | 작업 방향을 정한다(어느 파일을 고칠지, 어떤 방식으로 할지) | 판정·머지·데이터·공개 API·보안에 닿는다 |
| **범위**: 읽거나 고칠 곳 | 파일 1~2개 | 한 모듈 안 여러 파일 | 여러 모듈·계층 |
| **단계**: 필요한 흐름 | 한 번에 끝난다(조회·확인·한 번 수정) | 두 단계(수정 → 확인) | 셋 이상이거나 반복(구현 → 리뷰 → 수정, 실패 사다리, 항목 여러 개) |
| **시간**: 예상 소요 | 10분 안 | 1시간 안 | 1시간 넘음 |

## 2. 실행 수단 여섯 단계

| 단계 | 수단 | 고르는 조건 | 예 |
|---|---|---|---|
| **D0 직접** | 세션이 직접 명령(grep·cat·git·단순 시험) | 합계 0~1, 답이 몇 줄 | 값 하나 확인, 파일 위치, git 상태, 단일 시험 파일 실행 |
| **D1 검색 워커** | `scripts/search.sh "<질의>"`(기본 agy, 실패하면 opencode. 새 탭에서 돌아 사용자가 진행을 본다). Claude 토큰을 쓰지 않는다. 조사·위치 찾기·영향 범위·사용처 목록은 Claude agent 대신 여기가 기본이다. 단 시간 초과로 끝났거나 범위가 크면(예: 100개 파일 분류) 재시도 없이 sonnet Explore(D2, 아래 3)로 간다 | 합계 0~2, 여러 파일을 읽어야 하지만 결과가 참고용이거나 방향 정하기용, 코드를 고치지 않는다 | "이 설정은 어디서 읽나", "이 함수 호출자는", "이 오류 문구는 어디서 나나" |
| **D2 서브에이전트 하나** | Agent 1개(기본 sonnet/medium, 판정이면 opus/high) | 합계 2~3, 단계 하나, 출력이 많아 세션 컨텍스트를 아껴야 할 때 | 한 모듈 집중 조사, 파일 몇 개 수정, 긴 로그 요약 |
| **D3 서브에이전트 병렬** | Agent 2~4개를 한 번에 | 합계 3~5, 서로 독립인 범위가 둘 이상이고 공유 상태가 없으며 각자 단계 하나 | 모듈 셋을 따로 조사, 서로 다른 파일 묶음 수정 |
| **D4 Workflow** | Workflow 도구(단계마다 model·effort 지정) | 단계 점수 2(구현 → 리뷰 → 수정, 실패 사다리, 항목 반복)이고 합계 4 이상, 또는 결정적 흐름·재개가 필요할 때 | M/L 크기 구현 항목, 항목 여러 개를 같은 흐름으로 처리 |
| **D5 새 세션(레인)** | `spawn-lane.sh` 로 새 탭 세션 | 시간 2 이고 자기 브랜치·워크트리·머지가 필요하거나, 몇 시간 넘게 독립 컨텍스트가 필요할 때 | 레인 하나 분량 업무, 긴 측정, 다른 레인과 병렬로 돌릴 구현 묶음 |

## 3. 고르는 순서

0. **핵심 수정이 몇 파일·몇 줄인가를 먼저 한 줄로 적는다.** 단계 수·Workflow 사용 여부·조사 깊이·시험 범위를 모두 이 크기에 비례시킨다. 몇 줄짜리 수정에 영향 조사 Workflow·여러 갈래 조사·항목마다 리뷰·전 모듈 시험을 넣지 않는다(조사는 grep·검색 워커 수준, 리뷰는 마지막 1회, 시험은 영향 모듈만). 이미 아는 영향 지점은 지시에 적어 준다.
1. 네 점수를 매기고 합계를 낸다. 시간을 아끼려고 자세히 따지지 않는다: 한 줄 판단이면 충분하다.
2. **낮은 단계부터** 조건에 맞는지 본다. 경계가 애매하면 낮은 쪽을 고르고, 부족하다는 근거(답이 틀림, 범위가 생각보다 큼, 출력이 넘침)가 나오면 한 단계 올린다. 높은 쪽을 미리 고르지 않는다.
3. 아래 예외를 적용한다.
   - 영향이 2 이면 단계와 상관없이 판정 부분만 opus/high 로 둔다(D2 의 model 만 올린다). 판정이 아닌 수집·실행 부분까지 올리지 않는다.
   - 코드를 고치고 리뷰가 필요한 M/L 항목은 D4 다(리뷰 없이 머지하지 않는다). S 항목은 D2 로 구현하고 sonnet/high 리뷰 한 번으로 끝낸다.
   - D1 이 `SEARCH fail`(agy·opencode 모두 실패)이면 D0(grep) 이나 D2 로 대신한다. 특히 `search.sh` 탭 모드가 시간 초과(`search.timeout_s` 가 워커마다 걸려 기본 최대 약 480초)로 끝났으면 같은 질의를 다시 보내지 말고 바로 sonnet Explore(D2)로 넘어간다. 조사 범위가 「100개 파일 분류」 처럼 크면 D1 을 건너뛰고 처음부터 sonnet Explore 를 쓴다.
   - 사용량 띠가 O 이면 D4 의 동시 agent 를 띠 상한(2)으로 줄인다. Y 이하에서는 단계를 낮추지 않는다. R 띠에서는 Claude 로 D4·D5 를 새로 시작하지 않는다(opencode·agy 워커 일은 계속).
4. 고른 단계를 지시·보고에 한 단어로 적는다(예: `실행: D1`). 같은 종류의 일에 같은 판단을 되풀이하지 않기 위해서다.

## 4. 흔한 과잉

- 설정값 하나, 함수 하나의 동작을 확인하려고 Workflow 나 병렬 조사를 띄운다 → D0·D1.
- 참고용 조사에 opus 를 쓴다 → D1 이나 sonnet/medium.
- 이미 답이 나온 질문을 다른 수단으로 다시 확인한다 → 근거가 의심될 때만 한 번.
- 단순 시험 실행·결과 집계를 Workflow 단계로 만든다 → D0(haiku/low 를 쓸 일도 세션이 직접 돌리면 더 싸다).
