# 머지 순서와 머지 게이트

설계 절: §3.b.

## 1. 순서 원칙

- 「준비된 레인부터」 가 기본이다. 의존 그래프(`deps`)가 막는 것만 뒤로 미룬다.
- dev 를 바꾸는 머지는 **한 번에 하나만** 허가한다(`merge.in_flight` 가 비어 있을 때만). 완료 보고를 받은 뒤 다음을 허가한다. 요청이 겹치면 `merge.queue` 에 넣고 준비된 순서로 처리한다.
- 머지와 정리 완료까지 받으면 `merge.in_flight` 를 `merge.history` 로 옮기고 닫는다.
- 머지 완료 처리(트리 대조) 뒤 조정자가 반영 빌드와 통합 브랜치 push·릴리스 반영을 사용자에게 묻지 않고 한다. 시점은 머지 묶음 뒤나 회차 마감 때 조정자가 정하고, 리포별 절차는 `closing.md` §7 이다. 레인은 push 하지 않는다.

## 2. 절차

1. `머지 요청` 을 받으면 첫 줄 종류를 확인하고 `coord-state.sh report <레인>` 으로 기록한다.
2. `scripts/merge-gate.sh <레인>` 을 돌린다(브랜치로 직접 부를 땐 `--branch <브랜치>`).
3. 출력으로 아래 표대로 행동한다. 「판단 올리기」 표시가 있는 줄이 하나라도 있으면 출력 전체와 요청 메시지를 `opus` / `high` 서브에이전트에 넘겨 판정을 받는다.
4. 허가면 `coord-state.sh set '.merge.in_flight' '{"lane":…,"branch":…,"expected_tree":"<hash>","granted_at":"<iso>"}'` 로 기록하고 `protocol.md` 3.12 로 `머지 허가` 를 보낸다. 허가 메시지에는 예상 트리, 조건, **머지 뒤 다음 일** 을 넣는다.
5. `머지 완료` 를 받으면 보고된 머지 커밋의 트리를 `expected_tree` 와 대조한다. 같으면 history 에 `merged`·`tree` 를 적는다. 다르면 사용자 확인 전에 다음 머지를 허가하지 않고 원인(그 사이 dev 가 바뀌었는지)을 확인한다.
6. `정리 완료` 를 받으면 `cleaned` 를 채우고 닫는다. 남긴 브랜치(squash 로 `-d` 가 거부된 것 등)는 `pending_user` 에 올린다.

### 2.1 허가 견본 보강

- **대상 SHA**: 레인 브랜치에 다음 항목 커밋이 이미 쌓여 있으면(머지할 것보다 앞서 간 브랜치) 머지 요청에 머지할 SHA(7~12자)를 적게 하고, 게이트도 `merge-gate.sh <레인> --branch <SHA>` 로 그 SHA 를 대조해 허가문에 「이 SHA 까지만 머지」 를 적는다. `expected_tree` 도 그 SHA 기준이다. 브랜치 끝이 아닌 SHA 를 머지하면 쌓인 다음 커밋은 다음 머지 몫으로 남는다.
- **건드리지 말 파일**: 메인 체크아웃에 사용자의 미커밋 파일(예: 메모 문서)이 있으면 허가문에 「<경로> 는 사용자 미커밋 파일이다. 건드리지 말고 커밋에 넣지 말 것(머지 뒤 `git add` 는 경로를 지정한다)」 을 넣는다. 허가 전에 메인 체크아웃의 `git status --short` 로 확인한다.
- **되돌리는 수단과 함께**: 화면이 바뀌면 사용자 동작이 바뀌는 기능(자동 저장·기본 동작 변경 등)은 되돌리는 수단(기본값 복원 화면·끄는 설정)과 함께 머지한다. 통합 브랜치 push 가 조정자 몫이라 늘 적용한다. 둘이 다른 레인에 있으면 허가를 묶는다(자동 저장 C2 는 기본값 복원 화면 C3 와 묶어 머지했다). 요청에 되돌리는 수단이 없으면 `대기: 되돌리는 수단(복원 화면·설정)과 함께 머지해 달라` 를 보낸다.

## 3. merge-gate.sh 출력별 조정자 행동

첫 줄 `GATE <ok|wait|conflict> branch=<b> base=<integration> tree=<hash|-> files=<n>`.

| 줄 | 뜻 | 조정자 행동 |
|---|---|---|
| `GATE ok` | 충돌 없음, 사유 줄 없음 | 시험 근거(아래 4)와 기록 문서만 확인하고 허가한다. 예상 트리 `tree=` 를 허가 메시지에 넣는다 |
| `GATE conflict` + `CONFLICT <경로>` | 병합 충돌 | 허가하지 않는다. `대기: dev 최신을 합쳐 충돌을 풀고 시험을 다시 돌려 달라(충돌 경로 목록)` 를 보낸다 |
| `FORBIDDEN <경로>` | 레인 금지 파일을 고침 | `대기: 금지 파일 <경로> 변경 사유를 설명하거나 되돌려 달라` 를 보낸다. 사유가 타당하면 소유 레인과 조정한 뒤에만 허가한다 |
| `OUTSIDE <경로>` | 레인 소유 밖 파일을 고침(판단 올리기) | 서브에이전트가 요청 설명과 대조해 정당성을 판정한다. 정당하면 허가, 아니면 대기 |
| `SHARED_API <경로>` | shared 공개 API·props·동작 변경 후보(판단 올리기) | **사용자 승인 기록**을 직접 확인한 뒤에만 허가한다: 그 세션 jsonl 의 사용자 입력이나 AskUserQuestion 답. 기록이 없으면 `대기: 사용자 승인 기록이 필요하다` 와 함께 `pending_user` 에 올린다. 새 export·새 컴포넌트 추가만이면 승인 없이 허가해도 된다(서브에이전트가 가린다) |
| `RESTART <note>` | 실행 중 서버가 물고 있는 산출물에 닿음(`restart_rules`) | 허가 메시지 조건에 note 를 그대로 붙인다(예: 세 서버 내린 뒤 jar 빌드·재기동) |
| `WINDOW <kind> until=<iso>` | 측정·이동 창이 열려 있음 | 머지 뒤 빌드·시험이 창을 깨므로 허가를 창 끝 뒤로 미룬다. `대기: 측정 창이 <until> 에 끝난다` 와 그동안 할 일을 보낸다. 창이 끝나면 틱에서 허가한다 |
| `INFLIGHT <레인>` | 다른 레인의 머지가 진행 중 | `대기: <레인> 머지 완료 뒤 허가한다` 와 그동안 할 일(`monitor.md` 「병목 대기 레인」)을 보내고 `merge.queue` 에 넣는다 |

## 4. 스크립트가 못 보는 것(조정자가 직접 확인)

1. **시험 근거**: 머지 요청에 명령과 통과·실패 수가 있는지, 요청 직전에 dev 최신을 합쳐 다시 돌렸는지 본다. 숫자가 없으면 `대기: 시험 결과(명령과 통과·실패 수)를 붙여 달라`.
2. **기록 문서**: `records_check` 가 `true` 이면 이번 머지 항목이 레인의 기록 문서(구조·성능)에 들어 있는지 본다. 기본은 꺼져 있다.
3. **레인 상태**: 그 레인이 Workflow 중이어도 머지 요청이 왔다면 세션이 직접 낸 것이므로 처리한다. 단 허가를 보내는 길은 SendMessage 이며 Workflow 하위 에이전트에는 보내지 않는다.

## 5. 재기동 판단표 형식

설정 `restart_rules` 는 `[{"glob":"src/backend/**","note":"세 서버 내린 뒤 jar 빌드·재기동"}]` 형식이다. `merge-gate.sh` 가 변경 파일을 각 glob 과 대조해 맞으면 `RESTART <note>` 를 낸다. 리포마다 `.coord.json` 에 둔다.
