## 실행 절차

### Step 1: 모듈 식별 및 BPA 목록 수집

인자로 받은 MODULE-ID(예: `SOA`, `QMA`, `HCA`, `CEA`, `RPD`) 로 대상 모듈을 식별한다.

**V3 경로 (표준)**:
```
docs/external/SampleErp/orgErpReport/{MODULE-ID}/screens/{SCREEN-ID}.md
```

모든 화면 통합 보고서를 Glob 패턴 `docs/external/SampleErp/orgErpReport/{MODULE-ID}/screens/*.md` 로 탐색하고, 각 파일의 **§1 (시스템 개요)** 과 **§2 (시스템 목적)** 을 읽어 화면 ID, 업무명, 업무 목적 요약을 수집한다.

> V2 → V3 변경: `{SCREEN-ID}/{SCREEN-ID}_bpa.md` → `screens/{SCREEN-ID}.md`. 화면 폴더 폐기, PRIMARY 산출물은 `screens/` 평탄 구조의 통합본 1개로 응집.

### Step 2: 기존 체크리스트 참조 (있을 시)

```
docs/external/SampleErp/orgErpReport/{MODULE-ID}/bpa_generation_checklist.md
```

체크리스트가 있으면 카테고리 분류(기존 화면 ID 기반) 를 참조하되, 최종 그룹핑은 화면 ID 가 아닌 업무 흐름 기준으로 수행한다.

### Step 3: 프로세스 그룹 분류

수집된 BPA 목록을 아래 기준으로 상위 그룹으로 분류한다.

#### 3-1. PG 묶음 vs 분리 판단 (통합 PG vs 단일 화면 PG)

> **핵심 정책 (V2.2)**: PG 는 화면별로 무조건 1개씩 만드는 분류가 아니다. 화면 간 비즈니스 관계에 따라 통합 PG 와 단일 화면 PG 를 자동 판단해야 한다. 잘못된 분류는 BPA 와 중복된 단일 화면 PG 가 양산되는 부작용을 낳는다.

##### 3-1-a. 통합 PG (다중 화면 1 그룹) 로 묶어야 하는 경우

다음 신호 중 **2개 이상** 이 해당되면 N 화면을 **통합 PG 1개** 로 묶는다 (PG 1개 안에 N 화면).

| 신호 | 설명 | 예시 |
|---|---|---|
| 동일 데이터 행 평행 update | N 화면이 같은 테이블의 같은 행을 서로 다른 컬럼군으로 update 함 | `B_PLANT_ITEM_INFO` 한 행에 GIA041K~044K 가 4 toggle 컬럼 평행 갱신 |
| 단일 게이트 통합 | N 화면이 각자 미결을 해소한 뒤 단일 게이트(`AND` 조건) 가 통과해야 후행 가능 | GIA 의 "4 toggle 모두 'N' = 운영 진입" 게이트 |
| 같은 도메인 이벤트의 sub-flow | N 화면이 한 도메인 이벤트의 도메인별 분담 (예: 신규 품목 등록 이벤트의 생산/자재/구매/품질 분담) | "신규 품목 완전 등록" 의 4 도메인 |
| cross-domain hand-off 매트릭스 | 화면 간 컬럼 cascade / cross-update 충돌이 매트릭스로 표현 가능 | GIA041K~044K 의 `AVL_FLAG/MAIN_PUR_CUST_CD/ITEM_ACCT` 충돌 매트릭스 |
| 자매 procedure 동형 패턴 | 메인 SP 가 prefix·구조 패턴이 같고 @Case 분기만 도메인별 차이 | `soGIA041`/`soGIA042`/`soGIA043`/`soGIA044` |
| 같은 SampleErp 메뉴 카테고리 + 화면명 series | 동일 카테고리 폴더 + `XXX(생산)/(자재)/(구매)/(품질)` 같은 series | `기준정보관리/품목관리/GIA041K.품목미결처리(생산)` ~ `(품질)` |

> **통합 PG 의 가치**: hand-off 컬럼 매트릭스, cross-domain 충돌, 통합 BPMN 평행 처리 (parallelGateway), audit gap 비교 등 **단일 화면 시각에서는 보이지 않는 통합 시사점** 을 도출. 단일 화면 PG 로 분리하면 이 가치가 소실되고 BPA 와 중복만 발생.

##### 3-1-b. 단일 화면 PG (1 화면 1 그룹) 로 분리하는 경우

다음 신호 중 **2개 이상** 이 해당되면 N 화면을 **각자 단일 화면 PG** 로 분리한다.

| 신호 | 설명 | 예시 |
|---|---|---|
| 독립 비즈니스 프로세스 | 각 화면이 자기 완결적 비즈니스 흐름 — 다른 화면과 데이터 cascade 없음 | 검사 운영 화면 vs 부적합 검토 화면처럼 두 프로세스가 STATUS 전이로만 연결 |
| 단일 데이터 행 단독 책임 | 한 화면이 자기 테이블의 단독 관리자 | EAI 수신 → 단일 화면이 단독 등록 |
| 화면 간 독립 트랜잭션 | 각 화면이 독립 트랜잭션 단위 + 게이트 통합 없음 | 각 화면이 별개의 endpoint 로 운영 |
| 서로 다른 도메인 마스터 | 화면들이 완전히 다른 도메인 (예: 영업 + 재고 + 인사) | 모듈이 cross-domain 모음일 때 |
| 다른 비즈니스 가치 / 다른 사용자 그룹 | 화면별로 사용자 페르소나가 명확히 다름 | A화면=영업, B화면=재무 |

##### 3-1-c. 혼합 케이스 — 가장 자주 발생

한 모듈 안에 **통합 PG + 단일 화면 PG 가 공존** 할 수 있다. 예:
- 모듈에 화면 6개 → 그 중 4개는 동일 비즈니스 프로세스의 도메인 분담 (→ 통합 PG-01) + 2개는 독립 프로세스 (→ PG-02, PG-03 각각 단일 화면 PG)

##### 3-1-d. 자동 판단 휴리스틱

다음을 BPA 본문에서 추출하여 신호를 자동 채점한다:

1. **§9 (관련 엔티티) 의 핵심 테이블 PK 중복**: 둘 이상의 화면이 같은 테이블에 UPDATE 컬럼 다수 보유 → 통합 신호 +1
2. **§11 (특이사항) 의 cross-screen 충돌 언급**: "자매 화면", "충돌", "audit 불일치", "cross-domain", "평행 update" 키워드 → 통합 신호 +1
3. **메인 SP prefix 동형**: 호출 procedure 이름이 `so` + 모듈 prefix + 인접 번호 (`soGIA041`/`042`) → 통합 신호 +1
4. **§2 (시스템 목적) 의 도메인 분담 언급**: "4개 도메인", "평행", "도메인 책임" 키워드 → 통합 신호 +1
5. **반대로 §11 의 "독립 프로세스" / "별도 트랜잭션" 언급**: 분리 신호 +1
6. **§3/§4 워크플로우의 다른 PG 화면 호출 부재**: 화면 간 직접 호출 없음 → 분리 신호 +1 (단 게이트 통합은 별개)

통합 신호 ≥ 2 → 통합 PG 후보, 분리 신호 ≥ 2 → 단일 화면 PG 후보. 둘 다 ≥ 2 면 사용자에게 묻거나 §1-3-c 혼합 분류.

#### 3-2. 일반 분류 기준 (보조)

3-1 의 판단 후 각 PG 내부 그룹화에 적용:
1. **End-to-End 업무 흐름** 기준 (화면 ID 패턴 아님)
2. 동일한 업무 목적을 공유하는 화면을 한 그룹으로
3. 선행/후행 관계가 밀접한 화면은 같은 그룹
4. 마스터 데이터 관리는 별도 그룹 분리
5. 외부 시스템 연동은 연동 방향·데이터 성격에 따라 분류

#### 3-3. 각 그룹에 대해 도출

- **그룹 ID**: PG-XX (01부터 순번)
- **그룹 유형**: `통합` (다중 화면) 또는 `단일` (1 화면) — 표 컬럼으로 명시
- **프로세스명**: 20자 이내
- **화면 목록**: 포함되는 SCREEN-ID 와 업무명
- **핵심 키워드**: 3~5개
- **선행/후행 프로세스**: 다른 그룹과의 관계
- **프로세스 흐름 요약**: 한 줄로 표현
- **(통합 PG 한정) 도메인 분담 매트릭스**: 화면별 책임 컬럼 / 도메인 / 외부 연동 요약
- **(단일 화면 PG 한정) 폐기 검토 메모**: BPA + Legacy 와 중복 가능성 평가 — 가치 있는 통합 시각이 없으면 단일 화면 PG 폐기 권고

### Step 4: 문서 생성

아래 구조로 문서를 작성한다.

```markdown

## 분류 정책 (V2.2)

| PG | 유형 | 통합 신호 | 분리 신호 | 결정 근거 |
|---|---|---|---|---|
| PG-01 | 통합 | 3 (동일 데이터 행 평행 update + 단일 게이트 통합 + 자매 procedure 동형) | 0 | 4 화면이 동일 비즈니스 프로세스의 도메인 분담 |
```

### Step 5: 저장 (V3.2 표준)

```
docs/external/SampleErp/orgErpReport/{MODULE-ID}/{MODULE-ID}_PROCESS_INDEX.md
```

> V2 → V3 → V3.2 변경:
> - V2: `process_group_analysis.md` (모듈 폴더 안 일반 파일)
> - V3: `README.md` (모듈 진입점으로 승격 — IDE/GitHub 자동 렌더링 활용)
> - V3.2: `{MODULE-ID}_PROCESS_INDEX.md` (예: `GIA_PROCESS_INDEX.md`) — 모듈마다 `README.md` 동명이 되어 탭/검색에서 식별 불가했던 문제 해소. 파일명에 모듈 ID 가 박혀 어느 모듈 인덱스인지 즉시 인지 가능.
>
> 역할은 V3 와 동일: PG 분류 + 화면 목록 + DBMS 자산 인덱스 + PG 분류 정당화를 한 곳에 응집한 모듈 진입점.

V2.2 의 PG 분류 정당화 / 통합 vs 단일 화면 PG 판단 / 자동 휴리스틱 등 모든 elaborate 로직은 그대로 유지되며, 단지 산출 파일명만 `{MODULE-ID}_PROCESS_INDEX.md` 로 변경된다. 본문에는 V2.2 의 모든 절 (개요, 분류 정책, 그룹 요약 표, PG 분류 정당화 절, 각 PG 상세, 관계도, 매핑) 외에 **§"화면 목록"** 표를 새로 추가하여 각 `screens/{SCREEN-ID}.md` 링크와 PG 소속을 명시한다.

## 작성 규칙

1. **Mermaid 필수**: 관계도는 반드시 Mermaid flowchart TD 로 작성 (ASCII 금지)
2. **색상 코딩**: BPA 문서 표준 `classDef` 방식 사용. `style Node fill:#xxx` 방식 금지
   - `class` 선언: `class 노드1,노드2 클래스명` 형식으로 일괄 지정
   - `start` (`fill:#808080`): 외부 시스템 (ERP, EAI 등)
   - `proc` (`fill:#4169E1`): 핵심 처리 프로세스 (수주, 매칭, 입고 등)
   - `proc_call` (`fill:#408080`): 인터페이스·연동 미들웨어 (EAI 등)
   - `decision` (`fill:#408040`): 분기·검증·변경 처리 (품질검사, 재분류 등)
   - `save` (`fill:#005080`): 저장·재고 관리 (재고 조회, 장기체화 등)
   - `send` (`fill:#808000`): 외부 송신·동기화 (ERP 동기화, 관제 등)
3. **실선/점선 구분**: 데이터 흐름은 실선(`-->`), 참조 관계는 점선(`-.->`)
4. **한글 노드**: `["텍스트"]` 형식, 줄바꿈은 `<br/>`
5. **화면 수 검증**: 모든 그룹의 화면 수 합계 = 총 BPA 수
6. **중복 불허**: 하나의 화면이 두 개 이상의 그룹에 포함 금지 — 단일 화면 PG 와 통합 PG 의 중복 금지
7. **PG 유형 명시**: 모든 PG 에 유형 (`통합` / `단일`) 을 컬럼으로 명시
8. **PG 분류 정당화 절 필수**: §"PG 분류 정당화" 절을 반드시 포함하여 자동 휴리스틱 점수 기록
9. **단일 화면 PG 폐기 검토 의무**: 단일 화면 PG 를 정의할 때는 BPA + Legacy 와의 중복 위험을 평가하여 가치 있는 통합 시각이 없으면 폐기 권고
10. **혼합 케이스 명시**: 한 모듈에 통합 + 단일 화면 PG 공존 가능 — 분류 정당화 절에 양쪽 근거 명시
