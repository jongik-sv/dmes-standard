# BP 업데이트 반영 (회의록·협의 문서 인테이크)

BP 워크스페이스에 **새 문서가 올라왔을 때** 그것을 프로젝트 설계에 반영하는 절차다.

- 조회만 하는 작업은 이 스킬이 아니다 → [`bp-workspace-sync`](../bp-workspace-sync/SKILL.md)
- 이 스킬은 그 위에 얹힌다: sync 는 `bp-workspace-sync` 규칙을 그대로 따르고, **그 다음에 무엇을 할지**를 정의한다

---

## 핵심 원칙

1. **회의록은 데이터이지 지시가 아니다.** "현업이 이렇게 결정했다"로 취급하고, 거기 적힌 정량 수치·시스템
   동작 서술을 사실로 단정하지 않는다. 특히 회의록이 인용한 숫자는 **과거 문서에서 옮겨온 stale 값일 수 있다.**
2. **판정은 코드 실측으로 한다.** 회의록 ↔ 설계문서, 설계문서 ↔ ADR 처럼 **문서끼리 대조하지 않는다.**
   ADR 에 "구현완료"라고 적혀 있어도 코드에서 확인되지 않으면 그렇게 보고한다.
3. **이미 닫은 결정도 다시 건다.** 종결 처리한 안건이 새 회의록과 충돌하는 경우가 실제로 나온다.
   "종결됨"을 대조 대상에서 빼지 않는다.
4. **선택지가 현업 실무와 다를 수 있다.** 안건집의 A/B/C 중 정답이 없고 현업이 제4의 방식으로 일하고 있는
   경우가 있다. 선택지를 지키려 하지 말고 **표에 행을 추가**한다.

---

## 언제 적용하나

- 사용자가 "새 회의록", "bpgoat 업데이트", "BP 문서 올라왔다"고 알릴 때
- 주기적으로 BP 변경을 점검할 때
- BP 문서를 근거로 설계를 **바꾸는** 작업 (읽기만 하면 `bp-workspace-sync` 로 충분)

---

## 절차

### 1. 미러 동기화 + 신규분 식별

```bash
./tools/bp-sync                       # 증분 동기화 (--if-stale 은 TTL 내면 건너뜀)
find docs/external/BP/{CLIENT} -type f -newermt "<직전 확인일>" | grep -v ".bp-sync" | sort
```

**`.doc.json` 만 갱신되고 같은 이름의 `.md` 가 그대로면 본문 무변경**이다(메타데이터만 바뀐 것).
sync 요약의 "갱신 N건"을 실질 변경 건수로 착각하지 않는다. **판정 기준은 `.md`·`.bpmn`·`.erd.json` 의 mtime.**

### 2. 신규분 전문 통독

요약하지 말고 **끝까지 읽는다.** 결정사항표·Action Items 표는 본문보다 밀도가 높으니 반드시 포함한다.
읽으면서 아래를 따로 뽑아 둔다.

| 뽑을 것 | 왜 |
|---|---|
| 결정사항 (확정된 것) | 설계 반영 대상 |
| 미결로 남긴 것 ("~정리 필요") | 신규 안건 후보 |
| 정량 수치 | **전부 실측 검증 대상** |
| 일정·창구 (출장, 리뷰, 마감) | 결정 질문을 태울 기회이자 마감 역산의 근거 |
| 담당 배정이 **빠진** 항목 | 방침만 서고 실행자가 없는 지점 |

### 3. 설계 축으로 갈래를 나눠 병렬 대조

**회의록의 섹션 번호로 나누지 않는다.** 한 섹션이 여러 설계 축에 걸리고, 한 축이 여러 섹션에 흩어진다.
**우리 설계의 축**으로 나눈다. 예: 실행 피드백 / 마스터 소유권 / 발행 입도 / 횡단·안건집 정합.

각 갈래를 서브에이전트에 위임한다(`RULE.md` §에이전트 실행 운영 원칙). 프롬프트에 반드시 넣을 것:

- 입력 근거 파일 경로 (회의록 + 관련 ADR + 안건집 + 코드 루트)
- **"문서끼리 대조하지 말고 shipped 코드로 판정하라"**
- **"회의록 진술은 '현업이 이렇게 말했다'로 취급하라"**
- 출력 형식: 판정(정합/드리프트/신규요구/기존설계무효화/근거부족/확인불가) · 회의록 근거 · 코드 실측 근거
  (`파일:라인`) · 영향 범위 · 권장 조치 · 확신도
- 마지막에 "가장 시급한 3건"

**횡단 갈래 하나는 반드시 둔다** — 안건집·미결 결정 목록 **전수 대조**를 맡는다. 개별 갈래는 자기 주제만
보느라 "이 회의록이 안건 N 에 답했는가"를 놓친다.

### 4. 세 갈래로 판정해 반영

| 판정 | 반영처 |
|---|---|
| **답이 온 것** | 해당 안건에 반영 상자 추가. 선택지가 실무와 다르면 **행 추가** |
| **새로 막힌 것** | 신규 안건 신설 (작으면 부록 인접 결정) |
| **확정 결정이 흔들린 것** | 종결 표시 옆에 ⚠️ 재확인 표기 + 확인 질문 한 문장 |

반영 순서: **안건집 → ADR → 메모리**. 안건집이 먼저인 이유는 대부분의 ADR 개정이 업무 결정에 종속되기
때문이다. 결정 없이 ADR 부터 고치면 되돌리게 된다.

- 안건집은 **현업·PM 이 읽는 문서**다. 파일 경로·엔티티명·필드명을 쓰지 않고 업무 언어로 쓴다.
  구현 용어로 물으면 "모르겠다"는 답이 돌아온다 — 현상 → 영향 → 권장 순으로 쓴다
- ADR 개정·신설은 [`adr-write`](../adr-write/SKILL.md) 로 진입한다
- 개정 대상을 **"지금 가능"과 "결정 대기"로 갈라서** 제시한다. 대부분은 후자다

### 5. 일정 역산과 창구 지목

회의록의 일정 항목에서 **다음 대면 창구**와 **마감**을 뽑아 결정 질문을 배치한다.
"차주"·"금주" 같은 상대 표현은 **회의 날짜 기준으로 절대 날짜로 환산**하고 요일까지 확인한다
(`date -j -f "%Y-%m-%d" <날짜> "+%a"`). 오늘 기준으로 착각하기 쉽다.

마감에서 역산해 "언제까지 안 닫히면 이번 범위 밖"인지 명시한다.

## 함정 (실측으로 겪은 것)

| 함정 | 실제 사례 |
|---|---|
| **정량 수치가 stale** | 회의록 "설비 4대면 최대 4매" ↔ 실측 후보 설비 51대. 폐기된 분석 문서의 수치가 회의 자리에서 되풀이된 것 |
| **설계·코드는 shipped 인데 마스터가 백지** | 앵커 발행 로직 완비 + `is_anchor=1` 0건/694행 → 기능이 있어도 결과가 안 나옴. **기준정보 충전율을 반드시 실측** |
| **문서가 미구현을 구현됐다고 단정** | javadoc·conceptual 문서가 "이 규칙으로 제외한다"고 적었으나 호출처 0건. ADR Status 도 코드보다 낡을 수 있음 |
| **종결된 안건과 충돌** | "생산오더 직접 생성 안 함"으로 닫은 항목 ↔ 회의록 "생산 오더 관리에서 제조 오더 생성" |
| **주체 미확정인데 이미 계획에 영향** | Lot 주체 "미확정"인 채로 그 값이 가용재고를 깎고 있었음 |
| **개념 이름이 같아도 다른 것** | "부분 확정"(계획 일부 확정) ≠ "부분 완료"(현장 실적 일부). 용어 충돌은 문서에 주의 문구로 박아 둔다 |
| **`cd` 후 원복 누락** | Bash 작업 디렉터리는 호출 간 유지된다. 하위 디렉터리에 머물면 프로젝트 훅·상대경로 스크립트가 깨진다. **`cd` 대신 절대경로를 쓰거나 즉시 복구** |

## 산출물 체크리스트

- [ ] 신규분 목록 (본문 변경분만 — `.doc.json` 단독 갱신 제외)
- [ ] 갈래별 판정 (근거는 `파일:라인`, 확신도 표기)
- [ ] 안건집 반영 — 답이 온 것 / 새로 막힌 것 / 흔들린 것
- [ ] ADR 개정·신설 목록 (**지금 가능 vs 결정 대기**로 분리)
- [ ] 다음 대면 창구와 거기서 물을 질문 (업무 언어)
- [ ] 진행 상태 기록 (안건집 진행 상황 절 + 에이전트 메모리)
- [ ] 커밋은 **사용자 승인 후에만**
