# STT 회의록 정리 (dmes-standard)

> 문체: 산출 문서 → `../_shared/style/Korean-STE-Writing-Guide.md`. 종결은 이 스킬의 명사형 종결 규칙 우선.

{CLIENT} 프로젝트 회의는 **화자 분리가 안 된 단일 트랙 STT 자막**으로 남는다. 자막 원문은
오인식률이 높고, 같은 사람이 한 회의 안에서 여러 호칭으로 튀며, 도메인 용어가 통째로
다른 단어로 바뀐다. 이 스킬은 그 자막을 **읽을 수 있고 근거를 추적할 수 있는 회의록**으로
바꾸는 절차다.

## 0. 불변 원칙

**정본 프롬프트를 따른다.** 회의록 작성 규칙의 정본은
[`docs/external/BP/{CLIENT}/회의록/회의 내용 요약 프롬프트.md`](../../../docs/external/BP/{CLIENT}/회의록/회의%20내용%20요약%20프롬프트.md) 다.
사용자가 자막 파일을 붙여넣으면 그 파일 안에 같은 프롬프트가 이미 들어있는 경우가 많다.
본 스킬은 그 규칙을 **대체하지 않고**, 프로젝트 부속 자료(단어집·명단)를 물려 정확도를 올린다.
정본과 본 스킬이 충돌하면 **정본이 우선**한다. (BP 미러는 `bp sync` 로 덮어써지므로 직접 수정 ✗)

**추측을 본문에 쓰지 않는다.** 확신이 낮은 코드 번호·인명·수치는 회의록 본문에서 **빼고**,
회의록 바깥에 "확인 필요" 로 따로 보고한다. 자막이 뭉개졌다는 이유로 그럴듯한 값을 지어내면
그게 그대로 정본이 된다.

**파일을 먼저 만들지 않는다.** 회의록은 대화에 텍스트로 출력하는 것이 기본이다.
사용자가 "파일로 저장해" 라고 하기 전에는 `Write` 하지 않는다. 저장 위치도 사용자가 정한다.

## 1. 진입 시 필수 로드

세 문서를 **먼저 읽고** 자막에 손댄다. 순서대로다.

| 순서 | 문서 | 용도 |
|---|---|---|
| 1 | [`docs/glossary/STT-회의록-교정-단어집.md`](../../../docs/glossary/STT-회의록-교정-단어집.md) | 도메인 용어 오인식 교정. §0 최우선 혼동쌍부터 본다 |
| 2 | [`docs/glossary/이해관계자-명단.md`](../../../docs/glossary/이해관계자-명단.md) | 인명·호칭 교정 + "이 주제는 누구 담당인가" 역추적 |
| 3 | 자막 파일 전문 | 아래 §2 규칙대로 **전량** |

사용자가 단어집·명단을 첨부하지 않아도 **스스로 읽는다**. 첨부되면 그것을 쓴다.

---

## 2. 자막은 전량 읽는다

⚠️ **가장 흔한 실패 지점이다.** 회의 자막은 100분 기준 1,000~1,500행 / 70k~90k 토큰이다.
`Read` 는 한 번에 25k 토큰에서 잘리므로 **부분만 읽고 회의록을 쓰면 뒷부분 주제가 통째로 누락**된다.

1. 먼저 `Read` 로 앞부분을 읽어 전체 행 수와 토큰 규모를 확인한다.
2. `offset` / `limit` 으로 **끝까지** 이어 읽는다 (경험상 340~400행 단위가 1회 한도에 맞는다).
3. 잡담·인사·전화 응대 구간도 읽는다. 그 안에 결정이 섞여 있는 경우가 실제로 있다.

전량 읽기 전에는 "핵심 요약" 을 쓰지 않는다. 회의 후반에 앞선 결정을 뒤집는 발언이 자주 나온다.

## 3. 교정 절차

### 3.1 도메인 용어 — 단어집 기준

우선순위대로 훑는다.

1. **최우선 혼동쌍** (단어집 §0) — 뜻이 완전히 뒤집히는 것. 페깅↔패킹, 교정↔고정, 발번↔발주, 수불↔수출.
2. **시스템·모듈명** — 자막에서 가장 심하게 뭉개진다.
   - `MS` / `MBS` / `메스` → **MES**
   - `EPS` / `ASP` / `ABS` / `AKS` / `IPS` / `WBS` / `AVS` → **APS**
   - `ERB` / `ELP` / `ARP` → **ERP**
3. **제조 고유 공정·품목** (단어집 §6) — 벨로우즈·DP·CV·캡슐·ID/OD/EF 용접·슬리팅·박판.
4. **재고/물류** (단어집 §5) — `제공창고` → **재공창고**, `수고`/`수굴`/`수부` → **수불**, `분출` → **불출**.

> 단어집에 없는 새 오류 패턴을 발견하면 **회의록 밖에 목록으로 보고**하고, 단어집에 추가할지
> 사용자에게 묻는다. 임의로 단어집을 고치지 않는다.

### 3.2 인명 — 명단 기준

1. 명단 §5.2 **자주 나오는 오인식 후보** 표를 먼저 본다. ✅ 확정 행은 그대로 치환한다.
2. 명단 §6.2 **확정된 STT 변이** 표를 본다. 예: `박재현` → **박재연**.
3. ⚠️ **성(姓)까지 바뀌는 오인식이 실재한다** (`김세현` → `박세현`). 성이 다르다는 이유로
   별개 인물로 단정하지 말고, **담당 업무가 겹치면 동일인을 의심**한다.
4. 명단에 없는 이름은 §4 역인덱스로 **담당 업무 → 인물** 역추적을 시도한다. 실패하면 §5 로 넘긴다.

### 3.3 호칭 — 명단 §5.3 기준

이름 없이 직책·호칭만 나오는 발화가 많다. 호칭도 뭉개진다.

- `부사장님` / `부수장님` / `정 부장님` → **부서장님**
- 맥락상 이름이 생략된 `이사님` → 기술연구소 최종환 이사 (BOM·라우팅·코드체계 문맥)

호칭만 있고 인물 비정이 안 되면 **역할 표기로만 쓰고 이름을 붙이지 않는다.**

## 4. 확신도 관리 — 본문 vs 별도 보고

| 확신도 | 처리 |
|---|---|
| 단어집·명단에 ✅ 확정으로 등재 | 본문에 바로 반영 |
| 문맥상 명백 (앞뒤 문장이 뜻을 확정) | 본문에 반영 |
| 발음 유사도만 근거 | 본문에서 **제외**, 회의록 밖에 "확인 필요" 로 보고 |
| 자막이 뭉개져 값 자체가 불명 (코드 번호·수량) | 본문에서 **제외**, 항목 존재만 서술 |

**응답 말미에 반드시 붙일 것**

1. 적용한 주요 교정 목록 (원문 → 교정, 근거 문서)
2. 확신이 낮아 본문에서 뺀 항목과 그 이유
3. 명단·단어집에 **역반영이 필요한 신규 확정 건** 제안

## 5. 작성 규칙 (정본 요약)

정본 프롬프트의 규칙 중 실무에서 자주 어기는 것만 추린다. 전문은 §0 링크 참조.

### 5.1 구조

```
# {회의 제목}
## 핵심 요약      (3~5개 불릿, 항목 사이 빈 줄 필수)
## 참석자         (입력에 없으면 섹션 생략)
## 논의 사항      (주제별 소제목)
## 결정사항       (표)
## Action Items   (표)
```

### 5.2 자주 어기는 규칙

| 규칙 | 흔한 위반 |
|---|---|
| **[최우선] 화자 익명** | 본문에 "~님이 말하길" 서술. → 내용·결정 중심으로만 쓴다. 이름은 Action Items 담당자 칸에만, 그것도 **명확할 때만** |
| **참석자 섹션** | 명단으로 참석자를 **추정해 채움**. → 입력에 없으면 **생략**한다 |
| **제목** | `새로운 녹음` 같은 녹음앱 플레이스홀더를 그대로 씀. → 내용 기반 제목으로 바꾸고 **바꿨다고 고지**한다 |
| **명사형 종결** | "~했습니다". → "~함 / 완료 / 예정" |
| **문장당 정보 1개** | "~이며, ~하고, ~라" 로 사실 여러 개를 한 문장에 이음. → 짧게 쪼갠다 |
| **분량** | 10,000자 한도 초과. → 이 한도는 **기존 내용 보존 규칙보다 우선**한다. 넘으면 오래된 세부부터 압축 |
| **단위 표기** | LaTeX `$g/m^2$`. → 유니코드 `g/m²`, `CO₂`, `≤ ± × →` |

### 5.3 Mermaid (회의록당 최대 2개)

프로세스·의사결정·시스템 구조처럼 표로는 안 되는 것에만 쓴다. **파싱 에러 = 빈 화면**이므로 아래는 예외 없다.

- 모든 노드 라벨을 큰따옴표로 감쌀 것 — `B{"조건 분기"}` (O) / `B{조건 분기}` (X)
- 줄바꿈은 `<br/>` — `A["첫째 줄<br/>둘째 줄"]` (O) / `\n` (X)
- 라벨 안쪽 큰따옴표 중첩 금지 — `D["MO 생성(현재 방식)"]` (O) / `D["MO 생성("현재")"]` (X)
- mindmap 은 잎 노드까지 `id["라벨"]` 형식 필수

## 7. 후속 제안 (회의록 출력 후)

회의록을 낸 뒤 아래를 **제안**한다. 사용자 승인 없이 실행하지 않는다.

1. **명단·단어집 역반영** — 이번 회의로 확정된 인명 변이·신규 인물·용어 오인식 패턴.
2. **업무결정 안건집 대조** — [`docs/aps/user-requirements/analysis/mpn-business-decision-briefing.md`](../../../docs/aps/user-requirements/analysis/mpn-business-decision-briefing.md)
   의 미결 안건 중 이번 회의에서 답이 나온 것 / 새로 막힌 것 / 확정 결정이 흔들린 것.
3. **BP 워크스페이스 반영** — BP 에 회의록을 올릴 필요가 있으면 `bp-update-intake` 스킬로 넘긴다.
4. **ADR 트리거** — 되돌리기 어려운 설계 결정이 확정되었으면 `adr-write` 로 넘긴다.

## 8. 체크리스트

회의록을 출력하기 전에 스스로 확인한다.

- [ ] 자막을 **끝까지** 읽었다 (마지막 행 번호 확인)
- [ ] 단어집·명단을 읽고 교정에 실제로 썼다
- [ ] 본문에 사람 이름이 없다 (Action Items 담당자 칸 제외)
- [ ] 참석자 정보가 입력에 없으면 섹션을 생략했다
- [ ] 확신 낮은 값을 본문에 넣지 않았다
- [ ] Mermaid 노드 라벨이 전부 큰따옴표다 · 다이어그램 2개 이하
- [ ] 10,000자 이내다
- [ ] 응답 말미에 교정 내역 + 확인 필요 항목 + 역반영 제안을 붙였다
