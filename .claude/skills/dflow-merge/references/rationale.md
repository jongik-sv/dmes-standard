# /dflow-merge 근거·이력

실행에는 불필요. SKILL.md 와 references/* 규칙을 **바꾸려 할 때** 읽음. 항목 머리 = 규칙이 있는 자리.

## 「절차」 1번 — 후보 식별

- **고정 glob `*/tasks/*/state.json` 금지 이유**: 이 repo 밖 어느 디렉터리든 이름이 `tasks` 면 걸림 (예 `src/tasks/…`) — 이 프로젝트의 작업 폴더 아님
- **`$dirs` 를 here-doc 으로 넘기지 않는 이유**: 이 블록은 목록 들여쓰기째 붙여 넣어질 수 있음 → 종결자 `EOF` 앞에 공백이 붙어 here-doc 이 안 끝나고 뒤 반복문 전체를 삼킨 채 exit 0 (후보 0건이 오류 없이 보고됨). 파이프 뒤 `{ … }` 는 들여쓰기 무관
- **`tasks-dirs` 실패·빈 값을 먼저 보는 이유**: `$dirs` 가 빈 줄 하나가 되어 `"$d/*/state.json"` 이 `"/*/state.json"` 으로 풀림. git 은 이런 pathspec 을 리포 바깥 경로로 보고 거부 ("outside repository") — `git diff` 자체가 실패해 원격 후보를 **조용히 0건**으로 만듦 (오류가 파이프 뒤로 사라져 안 보임)
- **원격 후보를 `phase != merged` 로 넓게 잡는 이유**: `reported` 커밋이 실패하면 tip 의 phase 가 `verify` 에 머무를 수 있음. 판정은 서버 `show` 로만 하므로 넓게 잡아도 안전. 일치하는 state.json 이 없는 브랜치 = 아직 state.json 커밋 전
- **중복 제거를 `api_base` 필터보다 먼저 하는 이유**: 필터를 먼저 걸면 같은 작업이 "건너뜀(다른 D'Flow)" 와 "머지됨" 으로 두 번 보고됨. 원격 사본 쪽을 남기면 `api_base` 없는 옛 로컬 후보가 원격 규칙에 걸려 건너뛰어져 수동 경로가 머지하던 작업을 놓침
- **head_sha 를 포함하는 쪽을 머지 대상으로 고르는 이유**: 사람이 승인한 코드 = 그 커밋까지. 그 커밋이 없는 쪽은 4번 승인 뒤 변경 확인을 통과 못 함
- **`api_base` 필터 이유**: 스테이징 D'Flow DB 는 운영 복제 → 스테이징 `api_base` (export 된 `DFLOW_API_BASE`) 로 실제 리포에서 스윕하면 운영에서 승인된 작업을 로컬·원격 후보로 머지할 수 있음. 값 없는 옛 로컬 후보는 출처 판별 불가 → 사람이 보는 수동 경로에만 남김
- **로컬 스캔에 glob 금지 이유**: zsh 는 매치가 없으면 `no matches found` 로 명령 전체가 죽음. `<TASKS>` 없는 리포에서도 `find` 는 조용히 아무것도 안 냄
- **승인 전 머지분 (`merged`+`unapproved`) 을 로컬 스캔이 늘 보는 이유**: 머지 뒤에는 원격 스캔 (`phase != "merged"`) 에도 `reported` 스캔에도 안 걸려 그 작업의 승인·반려를 아무도 못 읽음. 팀장 poll 에도 반려 신호 (exit 10) 가 안 옴 (`/dflow-team` 「2-3」)
- **원격 스캔이 `wait_pred` 를 빼는 이유** (2026-09-26 설계 선행): 설계만 끝내고 선행을 기다리는 작업은 agent 브랜치를 push 해 두지만 완료 보고 전. tip 의 phase 에 기대지 않는 원칙은 "보고했는데 마지막 push 가 실패한" 경우용인데, `wait_pred` tip 은 보고 뒤 push 가 이 값을 남길 수 없어 그 경우 아님. 안 빼면 선행이 끝날 때까지 모든 스윕 사전 검사가 후보를 내 「4-0」 절약이 사라짐
- **show 를 jq 로 줄이는 이유**: 스윕마다 spec 본문을 컨텍스트에 싣지 않으려고
- **사전 검사 스크립트가 생긴 이유**: 2026-09-24 실측 (약 17시간) — 팀장 스윕 38회 중 20회가 머지 0건인데 매번 이 스킬 본문을 문맥에 다시 실음. 스크립트는 팀장 체크아웃이 뒤처져도 `origin/<기본브랜치>` 트리의 승인 전 머지분을 보므로 정본의 상위 집합
- **정본을 셸 블록으로 둔 이유** (2026-09-25): 4번이 블록 출력의 경로·브랜치 칸 (`$p`·`$f`) 을 그대로 쓰는데 스크립트는 후보 id8 만 냄. 스크립트는 fail-open 상위 집합이라 정본으로 삼으면 판정이 넓어짐. 다른 스킬 테스트도 이 블록을 글자 그대로 봄
- **사전 검사 스크립트가 상위 집합인 이유**: 덜 내면 머지 누락, 더 내면 스윕 한 번이 늘 뿐

## 플래그

- **`--on-report`** (2026-09-19): 의존 사슬 WBS 에서 선행이 승인될 때까지 후속이 착수 못 하면 사람이 Task 마다 승인해야 진척됨 (2026-09-19 mdm-dict-v2 실측: 팀원 4명 중 3명이 `skipped 선행 승인 대기`). 자율로 돌고 사람은 사후 확인한다는 팀장 설계와 어긋남
- **`--resolve`**: 2026-09-23 머지 충돌 설계 §5.1. 플래그 없는 수동 사용과 팀장 스윕은 충돌 파일 목록 보고만 바뀜

## 「절차」 2번 — 판정

- **반려는 state.json 을 안 고치는 이유**: 수동 `/dflow-poll` 반려 감지 (exit 10) 가 로컬 state.json 의 `reported`·`merged` 를 재료로 씀 → `rejected` 로 바꾸면 감지가 사라짐
- **승인 반영 커밋 (`unapproved` 지우기) 이유**: 표식이 남으면 매 스윕이 같은 작업을 다시 show 함. 표식이 이미 없으면 커밋 안 하는 이유: 호출한 체크아웃이 옛 커밋에 머물러 표식을 계속 읽어도 기본 브랜치에 빈 커밋이 안 쌓이게
- **반려 (머지됨) 에서 state.json 안 고치고 안 되돌리는 이유**: 반려 재작업 (`/dflow-dev` Phase 01 1번) 은 로컬 `merged` 와 서버 `claimed` 로 반려를 알아보며, 승인 뒤 재작업처럼 기본 브랜치에서 새 agent 브랜치를 따 머지된 코드 위에 수정 커밋을 얹음. `git revert` 는 그 위에 이미 다른 작업이 올라갔을 수 있어 사람이 고름

## 「절차」 3번 — 순서

- **tip 아닌 `branch_base` 로 판정하는 이유**: `/dflow-dev` Phase 06 가 done 뒤 `reported` 를 커밋 → 선행 tip 이 후속 기점 커밋보다 앞서 있어 후속의 조상 아님. tip 으로 판정하면 스택을 못 알아봐, 승인 철회된 선행 위에 쌓인 후속만 승인됐을 때 선행 코드가 main 에 들어감
- **`branch_base` 가 커밋으로 안 풀릴 때 tip 으로 판정하는 이유**: 수동 경로가 판정하던 옛 후보를 거부하면 퇴행
- **차분 백스톱 이유**: `branch_base` 는 오케스트레이터가 적는 값이라 빠질 수 있음 → 빠지면 스택이 비스택으로 판정되어 미승인 선행 커밋이 main 에 들어감. 차분에 다른 작업의 state.json 이 보임 = 그 작업 커밋이 기본 브랜치에 없다는 구조적 증거. 기점이 main 에 없는데 그 기점을 가진 후보도 없으면 "건너뜀(기점 미반영)"

## 「절차」 4번 — 머지

- **머지 자리를 가르는 이유**: git 은 한 브랜치를 워크트리 하나에서만 체크아웃하게 함 → 기본 브랜치를 다른 체크아웃이 잡고 있으면 `git switch <기본브랜치>` 가 `already used by worktree` 로 실패. 링크드 워크트리에서 도는 두 번째 `/dflow-team` 팀장이 이 경우. 수동 사용자가 다른 브랜치에서 불렀을 때도 체크아웃을 안 옮기게 됨
- **승인 뒤 변경 확인 이유**: 원격 후보를 받으므로 승인 뒤 같은 agent 브랜치에 올라온 커밋까지 머지 대상이 되는데, 사람이 승인한 것은 증적의 head_sha 까지. tip = head_sha 인지만 보면 `/dflow-dev` Phase 06 의 `reported` 커밋 때문에 늘 다름
  - 확인 못 한 경우를 건너뛰는 이유: `git diff` 가 오류로 끝나면 출력이 비어 "비어 있으면 머지" 로 읽힘
  - 증적에 `head_sha` 없는 옛 완료 보고를 머지하는 이유: 수동 경로가 머지하던 후보를 거부하면 퇴행
- **강제 진행 스텁 관문** (스펙 2026-09-23 §4): 두 브랜치가 다르면 스텁은 개발 브랜치에 머지되는 것이 정상 (F5), 관문 = 운영 승격
- **충돌하면 `--abort` 하는 이유**: 충돌 상태로 남으면 체크아웃이 더러워져, 팀장이면 이후 모든 기상이 전제 검사에서 멈추고 수동이면 사람이 치워야 함
- **state.json 경로를 다시 구하지 않는 이유**: 서버 호출이 실패하거나 예상 밖 빈 값을 주면 `git add "/state.json"` 처럼 저장소 루트 바로 아래 엉뚱한 경로를 stage 하는 사고로 번질 수 있음 — 이미 아는 값을 그대로 쓰면 안 생김
- **`phase` 에 새 값을 안 만드는 이유**: `/dflow-dev` 「--worker」 행 G 의 기본 브랜치 반영 확인이 `phase` = `merged` 인지 보고, `poll.mjs` 반려 감지도 `reported|merged` 만 훑음. 새 값을 쓰면 후속이 여전히 `skipped` 로 끝나고 반려도 감지 안 됨
- **번호 매김 실패가 머지를 안 막는 이유**: 스크립트가 자기 변경을 되돌린 채 끝나고, 임시 ID 는 트리에 남아 다음 머지의 번호 매김이 트리 전체를 다시 훑어 매김. 단 전역 번호 중복 바로잡기는 다음 머지가 다시 안 해 줌 — 실패한 머지가 남긴 중복은 다음 머지에서 둘 다 개발 브랜치 쪽이 되어 `DUP_LEFT … dev-side` 로만 나옴
- **로컬 브랜치 삭제의 not found·checked out 건너뛰는 이유** (5번 뒷정리): 원격 전용 후보에는 로컬 브랜치가 없고, 팀원 워크트리가 그 브랜치를 잡고 있을 수 있음
- **트레일러 고정**: 부착이 우연에 맡겨지면 실제 반영된 선행도 후속 워커가 승인 대기로 오판 (2026-09-22 mdm-dict-v2 실측: 선행 4건 TSK-03-07·03-09·03-11·03-12 가 origin/main 에 머지됐는데 트레일러 0건이라 후속 3건 TSK-03-10·03-13·04-01 모두 막힘)

## push 실패(`references/push-fail.md`)

- **경합이면 멈추는 이유**: 다른 스윕이 먼저 머지한 것 → fetch 부터 다시 해야 후보가 맞음
- **훅 거부는 그 작업과 후손만 빼는 이유**: 훅이 막은 작업은 사람이 풀 때까지 매번 막힘 → 그 한 건이 뒤 승인분까지 막으면 안 됨. `/dflow-dev` Phase 01-가 원문도 이 작업만 건너뛰고 스윕 계속. 로컬 pre-push 훅은 고정 문구 없이 훅 출력과 `failed to push some refs` 만 남김
- **그 밖의 실패에서 멈추는 이유**: 원인 모르는 실패에서 머지를 계속 시도하지 않는 것이 현재 동작
- **`origin` 으로 리셋 금지 이유**: 수동 사용자의 기본 브랜치에 있던 미push 커밋 보호

## 임시 머지 워크트리(`references/merge-worktree.md`)

- **가드 줄 이유**: 빈 `$W` 로 `git -C "" …` 를 부르면 git 은 호출한 체크아웃에서 돎 — 사용자 브랜치에 머지하고, 그것을 `HEAD:<기본브랜치>` 로 push 하고, 실패하면 `reset --hard` 로 그 체크아웃을 되돌림
- **스크립트를 호출한 체크아웃의 스킬 경로로 부르는 이유**: `<W>` 에 스킬이 없을 수 있음 (gitignore 된 심링크로 배포한 리포)
- **`pull` 대신 detach 하는 이유**: `<W>` 는 브랜치를 안 잡음
- **`--keep` 대신 `--hard` 쓰는 이유**: `<W>` 는 이 스윕만 쓰는 임시 트리라 지킬 미커밋 변경 없음
- **`git branch -d` 를 `<W>` 에서 하는 이유**: `-d` 는 브랜치가 현재 HEAD 에 머지됐는지 보는데, 머지 커밋은 `<W>` HEAD 에만 있음
- **지워도 되는 이유**: 로컬 브랜치 저장소는 모든 워크트리가 공유 → `<W>` 를 지워도 머지·삭제 결과 유지

## 방언 검증

- **스윕 끝에 한 번만 도는 이유**: 2026-09-24 dmes-standard 에서 워커마다 같은 방언 검증 컨테이너를 따로 띄워 16GB PC 가 load 52 까지 밀림. 같은 목적 컨테이너는 한 곳에 모아 한 번만 띄움
- **exit 126·127·128 이상을 실패로 기록하지 않는 것** = `baseline.mjs` 가 같은 exit 를 저장하지 않는 것과 같은 규칙
- **문서뿐 이월** (2026-09-25): 문서만 머지된 스윕마다 도커 슬롯을 잡고 Testcontainers MSSQL 을 띄우면 이미 통과한 코드를 다시 검증하는 일. 판정은 `last_pass` 와 끝 커밋의 트리 차이로 함 (커밋 이력이 아니라 트리라 중간에 되돌린 코드도 맞게 봄)
  - 기준을 `last_pass` 로 좁힌 이유: `--sweep-base` 는 판정받은 적 없는 트리. 앞 스윕이 도커 꺼짐으로 보류한 코드 머지 D 뒤에 문서만 머지되면 sweep-base=D 기준으로는 문서뿐이 되어 D 가 검증 없이 넘어감 (BUSY·오류도 같음). 통과 기록이 없으면 실행
  - `last_pass` 를 안 옮기는 이유: 옮기면 다음 실제 검증의 since 가 이월 커밋이 되어 그 사이 머지된 Task 가 tasks·unverified 에서 빠짐
    - 대신 상태 `docs_only=<sha>` 를 남겨 `sweep-check.mjs` 가 그 끝 커밋을 판정된 것으로 봄 — 없으면 틱마다 `SWEEP_DIALECT_PENDING` 이 나와 팀장이 매번 깨어남
    - `last_result` 도 안 덮음 — 백그라운드로 옮겨져 놓친 실패를 `status` 가 그대로 내야 함
  - `DIALECT_UNVERIFIED` 가 있어도 이월하는 이유: 코드가 통과한 트리와 같아 다시 돌려도 결과 같음. 그 표시를 남기는 Task 는 보통 코드도 바꿔 문서뿐에 안 걸리고, 문서만 바꾼 Task 의 표시는 since 가 그대로라 다음 실제 검증에 실림
  - `--no-renames`: 이름 바뀜을 찾으면 `src/X → docs/X` 가 새 경로만 나와 문서뿐으로 오판. `core.quotePath=false` 는 한글 파일명이 따옴표·8진수로 나와 문서 규칙에 안 걸리는 것 (안전하지만 이월이 조용히 꺼짐) 을 막음
  - 작업 폴더 문서를 이름 목록 (`state.json`·`decisions.json`·`.issues`·`.result`, 그 밖은 `*.md`) 으로만 보는 이유: 작업 폴더에 SQL·스크립트가 들어올 수 있음. `tasks-dirs` 를 못 읽으면 이 규칙만 빠짐 (더 엄격해질 뿐)

## 결정 번호 매김

- **머지 때 매기는 이유**: 번호 = 개발 브랜치에 들어가는 순서로만 결정 (2026-09-24 dmes-standard: 병렬 워커가 같은 다음 번호를 골라 머지마다 충돌)
- **`.claude/` 를 참조 치환에서 빼는 이유**: 킷 복사형 리포에서 스킬 문서의 예시 ID 가 실제 Task ID 와 겹쳐도 킷이 안 바뀌게
- **같은 임시 ID 머리가 둘이면 그 ID 만 건너뛰는 이유**: 개발 브랜치에 남은 잘못 하나가 뒤 머지를 모두 막지 않게
- **전역 번호 중복 바로잡기** (2026-09-24): dmes-standard TSK-08-01·TSK-04-03 이 둘 다 D-050~052 — `merge-conflicts` 가 두 쪽 블록을 그대로 붙였고 팀장이 손으로 고침 (86baa20)
  - 다른 파일 참조를 리포 전체가 아니라 머지 대상이 바꾼 파일에서만 바꾸는 이유: 같은 문자열이 개발 브랜치 쪽 결정도 가리킴. Task 폴더 기록은 자기 번호를 씀
  - 겹치지 않은 직접 번호를 안 고치는 이유: 번호를 바꾸면 겹치지 않은 결정의 참조까지 흔들리고, 블록을 옮기면 추가만 하는 기록의 순서가 바뀜
- **`merge=union` 을 안 거는 이유**: 샌드박스 실측 (wbs-web 리포 `tests/skills/dflow-merge-decisions.test.ts`) — 같은 필드 줄을 공유하는 블록이 줄 단위로 합쳐져 한 블록의 줄이 사라지고 두 머리가 붙음

## 해소 머지(`references/resolve.md`)

- **agent 브랜치를 안 건드리는 이유**: 건드리면 다음 스윕 「승인 뒤 변경 확인」 이 그 작업을 "건너뜀(승인 뒤 변경)" 으로 냄. rebase 는 force push 금지와 `merge-base --is-ancestor <head_sha>` 검사에 모두 걸림
- **임시 머지 워크트리를 안 쓰는 이유**: 팀장 스윕의 임시 워크트리와 경로 겹침
- **`RESOLVE_BASE_MOVED` 로 멈추는 이유**: 기준선과 머지 기점이 어긋나면 게이트가 개발 브랜치의 새 실패를 해소 탓으로 돌리거나 그 반대가 됨
- **해소·stage → 게이트 → 기록 → 커밋 순서** (2026-09-24): 게이트를 커밋 뒤에 돌리면 커밋에 담을 게이트 결과가 아직 없음. 해소 워커 셋이 이 모순을 연달아 `skill-unclear` 로 보고하고 저마다 다르게 우회
- **rerere 를 `-c` 로만 켜는 이유**: 워크트리의 `git config` 는 공용 `.git/config` 에 써져 사람 체크아웃까지 바뀜. rerere 기록 (`rr-cache`) 은 공용 디렉터리에 남으므로 push 경합 뒤 재머지와 다음 시도가 같은 해소 재사용
- **충돌 없어도 게이트 도는 이유**: 의미 충돌은 텍스트 충돌 없이 옴 (2026-09-21 가드 Task: 텍스트 충돌 한 줄에 시험 85건이 401)
- **작업 트리 = stage 트리 확인 이유**: 시험은 작업 트리에서 돌고 커밋되는 것은 index
- **게이트 실패에 `merge --abort` 쓰는 이유**: 커밋 전이라 되돌릴 커밋 없음 (HEAD 는 이미 기준 HEAD). 머지 도중 `reset --keep` 은 `Cannot do a keep reset in the middle of a merge` 로 거부되어 해소 편집과 `MERGE_HEAD` 가 그대로 남음. `merge --abort` 는 stage 한 새 파일까지 치움
- **게이트 뒤 `resolution.md` 만 더 stage**: 게이트가 본 트리와 커밋된 트리는 그 파일 하나만 다름. 번호 매김은 decisions.md 머리와 참조 문자열만 바꾸므로 게이트 재실행 안 함
- **결과 줄에 전체 sha 를 넘기는 이유**: 팀장이 이 값으로 조상 확인을 하는데 짧은 sha 는 저장소가 커지면 모호해져 확인이 실패할 수 있음
- **호출한 워크트리 안만 쓰는 이유**: 팀장 체크아웃을 안 건드리므로 해소가 `RESOLVE_BLOCKED` 로 멈춰도 팀장의 전제 검사가 안 깨짐
