# dflow-dev 규칙의 이유와 사고 이력

실행 중에는 안 읽는 문서. 규칙 고치거나 "왜 이렇게 하나" 따질 때 읽음. 규칙 본문 = SKILL.md·dev-discipline.md·
Phase 파일·worker-mode.md·e2e.md. 여기에는 규칙을 만든 이유·사고·실측만 둠. 제목 = 규칙이 있는 곳.

## SKILL.md

- **상태 모델 `model`**: heartbeat 훅이 60초 안에 새 값을 실어 좌석표 에이전트 보기의 명찰·등급(Fable·Opus·Sonnet·Haiku …)이
  Phase 마다 바뀜(2026-09-18, 0100). 빠뜨리면 이전 Phase 의 모델이 계속 보임. Phase 01·06 에서 안 지우는 이유: 마지막
  Phase 의 값이 "누가 일했나" 에 가까움.
- **`order` 전체 UUID**: 주문이 approved 가 되면 목록에서 빠져 id8 접두 해석이 죽음. poll 의 승인 감지(exit 9)와 merge 판정이
  그 주문을 영영 못 봄(2026-08-25 실증).
- **`api_base`**: 스테이징 D'Flow DB 는 운영 복제. 스윕(Phase 01-가, `/dflow-merge`)이 이 값으로 로컬·원격 후보 중
  자기 인스턴스의 것만 고름. 재작업 branch 도 다시 push 되어 원격 후보가 됨. 값이 없으면 같은 인스턴스의 branch 가
  "다른 D'Flow" 로 건너뛰어짐.
- **재claim 격리의 예외**: 재개에서 격리가 잘못 발동하면 그 작업의 design.md 가 통째로 `.prev-` 로 밀림. 재개한 세션이 설계
  없는 상태에서 Design 부터 다시 하게 됨. scaffold 예외가 없으면 팀장이 시작할 때 미리 만든 폴더(`dflow.mjs scaffold`)를
  모든 신규 claim 이 `.prev-` 로 밀어냄.
- **Phase 01-가 후보를 원격까지 보는 이유**: Phase 06 가 `reported` 를 commit 하므로 다른 branch 로 옮긴 뒤에는 작업트리에서 그
  state.json 이 빠짐. 로컬만 보면 승인분을 놓침. 스테이징 DB 는 운영 복제라 다른 인스턴스의 후보도 approved 로
  보임. 2-5번을 `/dflow-merge` 에 맡기는 이유: 같은 merge 절차를 두 곳에 적으면 한쪽만 고쳐져, 스윕이 충돌 상태나 push
  안 된 commit 을 checkout 에 남기는 결함이 되살아남. 스윕을 claim 앞에 흡수한 이유: 사람이 D'Flow 웹에서 승인해 놓고 아무도
  main 에 반영하지 않는 병목(2026-08-24).
- **Phase 01-가 0번 사전 검사**: 수동 `/dflow-dev` 가 호출마다 `/dflow-merge` 전체(약 31K 토큰)를 읽었는데 대부분 후보 없음.
  팀장 쪽도 같은 이유로 「4-0」 을 둠(2026-09-24 실측 약 17시간: 스윕 38회 중 20회가 merge 0건). 판정 불가를 후보
  없음으로 뭉개면 승인된 작업이 merge 안 되고 그 후속이 선행 반영 확인에 걸려 섬. 한 번 더 스윕하는 쪽이 쌈.
- **착수 가능 판정을 스킬이 하는 이유**: 2026-08-22 실증 — 선행 미승인·spec 부재 작업의 claim 이 서버에서 전부 조용히
  통과. `d.reached` 를 그대로 쓰는 이유: 실적 100 축은 위임 안 한 사람 Task 가 선행일 때 풀리는 길. 옛 규칙으로
  판정하면 서버는 claim 을 통과시키는데 스킬만 막음.
- **강제 진행 스텁**: 공유 등록 목록의 같은 줄을 안 고치는 규칙은 2026-09-21 충돌에서 나옴(스펙 2026-09-23 §3.4).
- **claim 전 기점 이동**: claim 의 선행 도달 검사(`check_depends_local`)가 현재 HEAD 를 봄. 수동 사용자가 무관한 branch 에
  있으면 exit 4. 기점 이동이 실패하면 claim 안 하는 이유: 미commit 변경이 기점과 부딪쳐 switch 가 거부된 상태로
  claim 하면 서버에는 claimed 가 남고 작업은 엉뚱한 HEAD 에서 시작. `PROJECT_MISMATCH` 를 재시도 안 하는 이유: 한
  사람이 여러 프로젝트에 속하면 서버 목록에 남의 프로젝트 작업이 섞임. 같은 TSK 번호끼리는 겉으로 구분 안 됨.
  exit 4 재시도에서 merge 안 하는 이유: fetch 로 바뀌는 것은 기점. merge 는 기본 branch 를 사용자의 현재 branch 나
  detached HEAD 에 섞음. `git switch -` 를 안 쓰는 이유: "직전 위치" 가 기록한 위치와 다를 수 있음. 수동 사용자를
  엉뚱한 곳에 남기면 수동 동작의 퇴행.
- **`prepare` phase(2026-09-24)**: 훅은 `prepare`·`design`·`build`·`verify`·`refactor`·`rejected` 만 보내고 scaffold 값
  `ready` 는 안 보냄(ready 는 claim 전 모든 배정 작업에 있는 자리표라 받으면 남의 주문으로 신호가 샘). 그대로 두면
  Phase 01 내내 신호가 안 나감(dmes-standard 2026-09-24 실측: 착수 5분이 넘도록 `last_heartbeat_at=null`). 훅은
  PostToolUse 라 5분 넘는 단일 호출(기준선 testAll 등) 동안 좌석이 무응답으로 보임. 호출이 끝나면 되살아남. claim
  직후가 아니라 branch 생성 뒤에 쓰는 이유: 그 사이 실패하면 원래 위치로 돌아가야 하는데 고친 state.json 이 복귀 switch 를
  막을 수 있음.
- **Phase 에이전트 회수**: 끝난 에이전트가 세션을 붙들어 사이클 하나에 4개 쌓임(2026-08-25 사용자 보고).
  실측(2026-08-25, mes-runlog TSK-01-02): 완료 에이전트 4개에 TaskStop → 전부 성공, `ListAgents` 에서 즉시 소멸 = "완료 후 idle 로 세션 붙듦" 진단과 일치.
- **서브에이전트 종료 뒤 오지 않을 알림(종료 5번)**: 2026-09-24 dmes-standard TSK-03-01 사고. 상세 = 아래 Phase 프롬프트 「포그라운드」.
  Build 서브에이전트가 run_in_background 변이 스윕의 알림을 기다리며 턴을 끝냄. 종료와 함께 백그라운드 프로세스도 사라짐.
  오케스트레이터가 47분간 입력 대기로 멈췄다가 TICK 무응답 점검에서 발견됨.
- **Phase 06 `reported` commit·push**: 원격 agent branch tip 에도 `reported` 를 남기고, 미commit state.json 이 다음 branch 전환을
  막지 않게 하려는 것.

## dev-discipline.md

- **설계 배경**: 러너 설계(결과 게이트)와 dflow-dev(과정 규율)의 2026-08-21 상호 적대 검토에서 "산출물 품질 = 과정 규율 ×
  결과 게이트의 곱" 으로 판정 — 이 규율 문서들은 그중 과정 규율 절반.
- **게이트 기준선**: 차분 판정인 이유: 기준선이 빨간 리포(예: wbs-web 의 기존 실패 42건)에서도 게이트가 성립해야 함.
  빨간 기준선 위에 안 쌓는 것은 러너 설계 §4-3 ⑥ 과 같은 원칙.
- **기준선 캐시(2026-09-24)**: 같은 기점에서 뜬 팀원 셋이 똑같은 backend testAll·mssqlMigrationTest 기준선을 각자 몇 분씩
  돌림(dmes-standard). 동시 측정을 한 쪽만 하는 이유: 둘 다 재면 시간을 못 줄이고, testAll·migration test 는 같은
  DB·포트를 두고 부딪칠 수 있음. 대기를 짧게 끊는 이유: heartbeat 가 안 끊기게. 오래된 결과를 버리는 이유: 키가 commit 이라
  코드는 안 낡지만 DB 상태·포트·도구 버전처럼 commit 밖 환경이 결과를 바꿀 수 있음. exit 126·127·128+ 을 저장 안 하는
  이유: 설치 누락 같은 일회성 고장이 모든 팀원의 기준선이 되어 각자의 새 실패를 가리면 안 됨.
- **research/docs 특례**: 2026-08-22 TSK-00-01-01 리허설에서 현장 재량으로 적용한 판단을 명문화.
- **도커 사용 규칙(2026-09-24 dmes-standard 사고)**: 팀원 6명이 기준선 단계에서 `mssqlMigrationTest`(Testcontainers MSSQL)를
  동시에 돌림. 한 팀원은 꺼져 있던 OrbStack 을 `orb start` 로 스스로 켬. RAM 16GB 장비가 스왑 17GB·load 52 까지 밀림.
  같은 날 두 워커가 OrbStack 을 켜서 사용자의 다른 container 까지 함께 올라옴. 같은 날 오전의 첫 규칙(팀원 4명 이상이면
  금지)은 3명 이하일 때 워커마다 같은 목적(DB 방언 검증)의 container 를 못 막음. 그래서 "같은 목적은 한 곳에 모은다" 로 원칙을
  바꿈. 옛 `NO_DOCKER=0` 을 허용으로 안 보는 이유: 인원 기준 시절의 값이라 태그를 안 보고 적힘. build 파일로 안 빼는
  이유: 산출물에 섞이고 금지 모드가 아닌 실행에서도 빠짐.
- **무거운 명령 줄 세우기(2026-09-24)**: dmes-standard 에서 팀원 6명이 기준선·게이트의 Gradle testAll(워커마다 데몬 JVM +
  test JVM), Testcontainers MSSQL(container 마다 약 730MB), E2E 용 Spring 서버와 프런트 dev 서버를 동시에 돌림. 10코어·
  16GB PC 에서 load 52, 스왑 18GB 중 17GB, 압축 메모리 약 45GB 까지 올라 PC 전체가 멈추다시피 함. 점검에서 `heavy.mjs` 밖의
  Gradle 실행 때문에 JVM 이 최대 10개까지 동시에 떠 Gradle·Maven 은 단일 test 도 감쌈. 대기에 상한(처음 240초, 2026-09-26
  부터 90초)을 둔 이유: 워커의 heartbeat 는 도구 호출 때 훅이 보냄. Bash 한 번으로 오래 기다리면 팀장이 무응답(약 5분)으로
  오판. 교착 불변식이 막는 순환: "일반을 쥐고 도커를 기다리는 쪽"(예: E2E 서버 슬롯을 쥔 세션)과 "도커를 쥐고 일반을
  기다리는 쪽".
- **대기 90초·분리 실행·독점·E2E 풀(2026-09-26 dmes-standard 성능 감사)**: 백그라운드로 넘어가 멈춘 호출 16건, 시간이
  기록된 4건은 47분-1.5시간씩 멈춤. timeout 없이 부른 무거운 명령은 대기 240초만으로도 Bash 기본 timeout(120초)을 넘어
  하네스가 호출을 백그라운드로 옮김. Phase 서브에이전트는 오지 않을 알림을 기다리며 턴을 끝냄. 그래서 대기를 90초로 줄여 기본
  timeout 안에서 `HEAVY_BUSY` 로 돌아오게 함. 10분 넘는 명령은 worktree 밖 잡 폴더로 떼어 내 240초 이하의 `wait` 로
  폴링(한 번의 Bash 는 heartbeat 상한 아래). 벽시계 성능 test 는 다른 팀원의 build 와 겹쳐 약 10회
  blocked 로 끝남 — 슬롯 하나로는 겹침을 못 막아 K개를 한꺼번에 잡는 독점을 두고, 슬롯이 빌 틈이 없게 양보 표식으로
  새 take 를 멈춤. 부분 보유로 안 기다리는 이유 = 교착(둘이 반씩 쥐고 서로를 기다림). E2E 서버의 hold 가 일반
  슬롯을 한 시간씩 쥐어 다른 팀원의 게이트가 굶음 — E2E 를 따로 세는 풀로 옮김. 그 대가(동시 스택 K+1)는
  `DFLOW_HEAVY_E2E_SLOTS=0` 으로 되돌릴 수 있음. 새 파일 이름(`e2e-*`·`excl-*`)은 같은 잠금 폴더를 함께 쓰는 옛
  heavy.mjs 가 모르는 이름. 옛 프로세스는 이들을 무시할 뿐 지우거나 잘못 세지 않음.
- **부하를 보고 슬롯 주기(2026-09-26 성능 감사 P12)**: K 는 RAM 기준이라 게이트가 몰린 구간에는 10코어 PC 의 부하가
  20-30(최대 62)까지 오름. 그 부하에서 벽시계 성능 test 가 실패해 blocked 발생 — 슬롯이 남아도 1분 부하가 코어 수 × 1.5 를
  넘으면 새 일반 슬롯을 미룸. 보유자 0명이면 주는 이유: heavy.mjs 밖의 부하(LLM 세션·E2E 서버)만으로 상한을 넘을 때
  아무것도 못 도는 기아를 막기 위해.
- **포그라운드 실행(2026-09-24 dmes-standard TSK-03-01)**: `/dflow-team` 「제1 제약」 과 같은 구조가 Phase 한 단계 아래에서 재발.
  상세 = 위 SKILL.md 「종료 5번」 · 아래 Phase 프롬프트 「포그라운드」.
- **공용 결정 기록의 번호**: 병렬 워커가 같은 기점에서 같은 다음 번호(D-020 부터)를 골라 merge 마다 충돌. 해소 워커를 띄워야
  했음(2026-09-24 dmes-standard TSK-01-02·TSK-02-03).
- **마이그레이션 버전**: 2026-09-24 dmes-standard mdm 에서 병렬 branch 가 같은 Flyway 번호를 골라 git 충돌 없이 merge 되고
  개발 branch 의 서버 start 가 깨짐.
- **모델 배정 — Verify 는 처음부터 sonnet**: 실측에서 haiku Verify 의 54% 가 변이 검증·E2E 를 건너뛴 부실 PASS 로 sonnet
  재시도가 됨.

### 전체 스위트 실행 횟수 (2026-09-24 개정)

점검에서 한 Task 가 전체 스위트를 12-17회 돌림. `heavy.mjs` 밖의 Gradle 실행 때문에 JVM 이 최대 10개까지 동시에 뜸.
Build·Verify·Refactor 개정과 「무거운 명령 줄 세우기」 의 감쌀 범위 확대가 이것을 줄임. 아래 수는 **추정**(불변
규칙 3-5개, 워커 기준).

| 어디서 | 개정 전 | 개정 후 |
|---|---|---|
| 기준선 | 1 | 1(같은 기점을 이미 쟀으면 0) |
| Build 서브에이전트(완료 확인·변이 검증) | 4-7(변이마다 전체) | 0(관련 test·대상 test 만. 구현 단위가 여럿이어도 0) |
| Build 게이트 | 1 | 1(실패 재시도 때 +1) |
| Verify 서브에이전트(전체 재실행·변이 재검) | 4-6 | 0(감사·E2E 만) |
| Verify 게이트 | 1 | 0(코드를 고쳤을 때만 1) |
| Refactor 서브에이전트 + 게이트 | 2 | 0(워커), supervised 는 commit 있을 때만 |
| 합계 | 약 12-17 | 약 2-3 |

### 게이트 범위 대응표·강제 재실행·게이트 기록 (2026-09-26 개정)

- **왜**: 성능 감사에서 test 약 3,500건의 실제 검사 시간 합은 약 70초인데 전체 한 번은 약 3분. Task 하나의
  게이트·검증 구간이 40-80분. 한 모듈만 바꾼 Task 도 Build 게이트·변이 검증·재실행마다 전체를 돎. UP-TO-DATE 를
  못 믿어 `--rerun-tasks`·`cleanTest` 로 전체를 다시 도는 일이 반복됨. 원인 하나(변이 복원 때 mtime 까지 되돌려
  재컴파일 누락)는 phase-build.md 의 백업 사본 방식 통일로 고침. 강제 재실행은 부분 실행 상태가 남았을 때만 씀.
- **대응표를 킷이 아니라 리포가 소유**: 모듈 구조와 명령(Gradle 모듈 이름, pnpm 패키지 이름)은 리포마다 다름. 킷에는
  일반 규칙과 판정 스크립트(`gate-scope.mjs`)만 두고, 대응은 리포의 `.dflow-gates` 가 정함. `.dflow` 키 하나로 안 둔
  이유: `.dflow` 는 key=value 한 줄 형식이라 여러 줄 표가 안 들어감. 옛 `dflow-config.sh` 가 모르는 키를 안 만나게 하려는
  것도 이유. 파일이 없으면 지금 동작 그대로(하위 호환).
- **의존 모듈은 명령이 스스로 포함**: 별도 의존 문법을 두면 스크립트가 그래프를 풀어야 하고 리포의 build 도구가 이미 아는
  관계를 두 곳에 적게 됨. pnpm `...<패키지>`, Gradle 의 명시적 태스크 나열로 충분.
- **대응표는 기점의 것을 읽음**: 기준선과 게이트는 같은 명령이어야 차분 판정이 됨(「게이트 기준선」). Task 가 대응표를
  고치면 그 Task 는 전체로 판정.
- **모듈 기준선은 Design 뒤에 잼**: Phase 01 에는 바꿀 모듈을 모름. Build 게이트 직전에는 트리에 이 Task 의 변경이 있어
  잰 값이 기준선 아님. Design 직후는 트리가 기점과 코드가 같고 design.md 의 변경 파일 목록으로 범위를 예측할 수 있음.
  예측 밖 모듈을 건드리면 그 게이트만 전체로 돎. `baseline.mjs` 가 Task 문서 commit 만 얹힌 HEAD 를 기점으로 보는 것도 이
  때문(같은 기점의 다른 팀원이 재사용).
- **전체는 Verify 에서 한 번**: merge 전 최종 증거는 전체 실행이어야 함. Build 게이트가 이미 전체였으면 같은 트리를 두 번
  안 돌게 종전 재실행 생략 규칙을 씀. done 전에 개발 branch 를 다시 merge 하고 전체를 도는 절차는 킷 문서에 없음
  (워커는 기점 이후 개발 branch 를 merge 안 함) — 킷에서 없앨 중복 지점 없었음. 리포 문서가 그런 절차를 뒀다면
  Verify 게이트의 전체 실행과 겹치므로 리포 쪽에서 정리.
- **게이트 기록**: 개선 효과를 Task 단위로 비교할 수 있게 명령·범위·경과·부하를 build-log.md 에 남김. 부하는 같은 PC 의
  다른 팀원 때문에 경과 시간이 흔들리는 것을 가려 보려고 적음.

## 읽기 규율과 구현 단위(Phase 파일)

- 2026-09-25 dmes-standard 팀 실행 기록을 단가 가중치(입력 1, 캐시 생성 1.25, 캐시 읽기 0.1, 출력 5)로 집계하니 Build
  서브에이전트 35%, Design 13%, Verify 11%, 팀원 메인 10%. Build 는 design.md 를 10-27회 다시 읽고(서브에이전트당
  약 110K자) 소스를 통째로 읽음(180-275K자). 그때는 누적이 호출 수의 제곱에 비례한다고 봄(아래 09-26 실측으로 고침).
- BE·FE 분할만으로는 안 줄음(TSK-08-02: 단위마다 200회 넘게 호출, 누적 88-90M). 그래서 단위를 나누고 단위마다
  새 컨텍스트에서 시작, 상한을 넘으면 인계로 끊음.
- **단위 크기 50-100회, 상한 120회, 작업 전체 120회 이하면 단위 1개(2026-09-26 개정)**: dmes-standard 팀원 6건(TSK-06-05·07-02·
  07-04·08-04·08-06·09-01)의 Build 단위 32개(33-195회)를 곡선에 맞추면 W ≈ 0.028M × calls + 0.000024 × calls². 거의
  직선. 제곱 항은 120회에서 0.35M(선형 항 3.4M 의 약 10%)라 약 120회를 넘을 때부터 눈에 띔. 종전 상한 80회는 곡선상
  절감이 거의 없는데 단위마다 spec·design 을 새로 읽는 고정비와 인계 비용만 늘림. 195회까지 간 단위는 제곱 항이 0.9M 으로
  커지므로 상한 자체는 둠. 50회 미만 단위는 고정비 비중이 커서 이웃과 합침.
- 인계 횟수를 트레일러로 세는 이유(2026-09-25 검토): 세션 기억으로 세면 압축·재개 뒤 0 으로 돌아가 상한이 무력해짐. 단위
  하나짜리도 트레일러를 붙여야 셀 수 있음. 재시도 중 인계를 상한에 넣는 이유: 안 넣으면 게이트 재시도가 인계를 거듭하며 끝없이
  이어짐. 이어 띄운 에이전트에 실패 목록을 다시 안 넣으면 재시도가 새 Build 로 바뀌어 1회 재시도 규칙이 깨짐.
- 게이트 재시도에서 단위 범위를 푸는 이유: 신규 실패는 앞 단위의 파일에서 나기 쉬움. 마지막 단위 에이전트는 phase-build 의
  "다른 단위의 파일은 고치지 않는다" 를 따르면 못 고쳐서 재시도가 헛돎.
- 회수 이름에 `-c<n>` 을 넣는 이유: 이어 띄운 에이전트는 그 이름으로만 TaskStop 가능. `<TSK>-build-<단위>` 로 부르면 이미
  회수된 앞 에이전트를 가리켜 이어 띄운 쪽이 세션을 붙든 채 남음.

## 구현 단위 순차와 병렬 묶음

설계: wbs-web 리포 docs/superpowers/specs/2026-09-26-build-unit-parallel-design.md(킷에는 미동봉).

- **순차가 기본인 이유**: 모든 단위가 한 worktree·한 agent branch 를 씀. 병렬이면 한 단위의 "관련 test 초록" 판정 때 작업
  트리에 다른 단위의 반쯤 쓴 코드가 섞임. 동시 `git add`·`commit` 이 index.lock 에서 부딪침. 뒤 단위가 앞 단위의
  API·타입 위에서 쓰는 경우가 많음. 재개·인계는 트레일러 순서를 전제. 팀이 이미 Task 여럿을 병렬로 돌리고 병목이
  메모리·무거운 검증 슬롯이라 팀 처리량 이득도 작음.
- **병렬 조건을 컴파일 범위로 거는 이유**: 파일이 안 겹쳐도 같은 Gradle 모듈·tsc 프로젝트면 한쪽의 반쯤 쓴 파일이 다른 쪽
  컴파일을 깨 자기 잘못 아닌 빨강이 남. 범위가 갈리면 변이 검증의 변이도 형제의 관련 test 에 안 닿음. E2E 는
  마지막 단위 혼자라 병렬 구간에 없음.
- **commit 을 묶음이 끝난 뒤로 미루는 이유**: 형제가 도는 중의 commit 은 `git status` 등이 잡는 index.lock 과 부딪침. 대상
  리포에 lint-staged 같은 commit 훅이 있으면 commit 이 형제의 작업 중 파일을 stash 로 치웠다 되돌림. 단위마다 따로 commit 하는 이유:
  `DFlow-Unit` 트레일러 계수(재개·인계 2회)를 그대로 쓰기 위해.
- **변이 되돌리기를 백업 사본으로 하는 이유**: `git checkout -- <파일>` 은 그 파일의 미commit 구현까지 지움. 변이 스윕이
  무효가 되어 다시 돈 사례 여러 번(2026-09-26 dmes-standard 성능 감사). 병렬 단위에서는 index 까지 써서 형제 단위의
  git 과 부딪침 — 병렬 단위의 git 쓰기를 0 으로 두면 index 경합이 원천적으로 없음. 되돌릴 때 `cp -p`·`touch -r` 로 mtime 을
  맞추면 크기·mtime 이 같은 파일을 Gradle 이 재컴파일 없이 건너뛴 사고도 있음. 그래서 평범한 `cp` 로 되돌려 mtime 을 새로 찍음.
- **게이트 명령을 좁히는 이유**: 2026-09-26 감사에서 프런트 단위 게이트 38초 중 31초가 대상 패키지가 안 쓰는 라이브러리
  build. 명령을 Task 도중에 안 바꾸는 이유: 기준선 캐시 키와 차분 판정 기준이 명령에 묶여 있음.
- **파일 목록·범위 검사와 commit 뒤 깨끗함 검사**: 병렬 단위는 스스로 commit 안 하므로 보고에서 빠진 파일이 트리에 남을 수
  있음. 남기면 Phase 06 마감 commit 에 섞여 어느 단위의 것인지 사라짐.

- **같은 모듈 안의 단위를 worktree 로 갈라 병렬로 안 돌리는 이유(2026-09-26 검토 후 제외)**: 단위마다 worktree 를 주면 같은
  모듈이라도 동시에 돌 수 있지만 worktree 마다 컴파일과 test JVM 부하가 따로 생김. 대상 PC(M5 10코어·16GB·팬 없는 MacBook
  Air)는 부하가 오래 이어지면 열로 클럭이 떨어짐. 무거운 명령 슬롯도 2개뿐이라 test 끼리는 결국 줄을 서 이득이 작다고
  사용자가 판단.

## Verify 감사 분할과 변이 표본(phase-verify.md)

설계: wbs-web 리포 docs/superpowers/specs/2026-09-26-dflow-parallel-token-design.md(킷에는 미동봉).

- **근거(2026-09-26 dmes-standard 팀원 6건 집계, 가중치 입력 1·캐시 생성 1.25·캐시 읽기 0.1·출력 5, 합계 139M)**: Build 52.6%,
  Verify 19.9%, 팀원 메인 11.5%, Design 10.6%, 조사 에이전트 5.3%. Verify 6건 324분, 도구 시간 179분 중 변이 재실행 60분.
  Verify 한 건은 호출 166-251회, 비용 5-8.8M 으로 작업마다 가장 큰 단일 에이전트.
- **감사자 셋과 작성자 하나로 나누는 이유**: 한 에이전트가 스펙 대조·코드 리뷰·test 품질·실행·수정을 줄지어 하면 호출마다 앞선
  읽기가 누적 컨텍스트로 다시 실림. 판단만 하는 일은 새 컨텍스트의 좁은 감사자에 나눠 동시에 돌림. 작업 트리를 고치는
  에이전트는 하나로 둬 쓰기 경합을 없앰. 목표: Verify 비용 약 절반, 작업당 Verify 시간 약 54분 → 25분(추정. 실측으로
  확인할 항목).
- **감사자가 commit 된 내용만 읽는 이유**: 같은 시각 작성자가 작업 트리에 변이를 넣음. 작업 트리를 읽으면 넣어 둔 변이를 결함으로
  지적.
- **감사자를 general-purpose 로, 이름 없이 띄우는 이유**: Explore 는 위치 찾기용이라 리뷰가 얕아짐. 이름 붙인 에이전트는 실행
  환경에 따라 별도 pane·프로세스로 뜸. 대상 PC(16GB·팬 없음)에서 Verify 한 번에 넷이 동시에 뜨는 부담을 피함. 감사자는
  SendMessage·TaskStop 할 일이 없고 보고하면 스스로 끝남.
- **감사자에 haiku 를 안 쓰는 이유**: 2026-09-24 게이트 절감 때 haiku Verify 의 54% 가 변이 검증·E2E 를 건너뛴 부실 PASS.
  감사는 판단이 핵심.
- **작성자 첫 보고를 `VERIFY_EXEC` 로 따로 두는 이유**: `PHASE_RESULT` 를 받으면 오케스트레이터가 게이트 판정 뒤 곧바로
  회수하므로 감사 지적을 넘길 대상이 사라짐. 지적 왕복을 재시도에 안 세는 이유: 세면 감사 뒤 실제 실패가 한 번만 나도
  재시도가 바닥남.
- **변이 재실행을 표본으로 줄이는 이유**: Build 가 같은 변이를 이미 돌림. Verify 의 역할은 재측정이 아니라 기록의 신뢰성
  감사. 의심 행은 전부, 나머지는 서로 다른 규칙의 2행만 다시 넣음. 표본이 기록과 어긋나면 전수로 넘어감. 표본은 작성자가
  고르고 이유를 보고에 남김(무작위보다 추적이 쉬움).

- **왜**: 서버 claim 관문은 선행이 `reached` 가 아니면 claim 을 거부. WBS 사슬 때문에 팀 슬롯 3개 중 2개가 놂. 설계는
  선행 코드 없이도 대부분 할 수 있음. 선행이 구현 중일 때 먼저 해 두고, 구현만 선행을 기다림.
- **계약 2.9 이상이면 늘 `--design-first` 로 claim 하는 이유**: 선행이 모두 충족된 작업도 `ds` 를 거쳐야 `ds` 가 "설계 중" 이라는 뜻을
  일관되게 가짐. 서버 버전은 `contract-ge` 로 칸마다 숫자로 봄 — 문자열 비교는 2.10 을 2.9 보다 작게 봄.
- **선행 단계를 스킬이 판정 안 하는 이유**: 착수 전 선행(`as`·`ds`·미착수)에 설계 선행을 허용 안 하는 규칙은 서버가
  `design_first_too_early` 로 집행. 스킬이 같은 판정을 따로 하면 두 판정이 어긋나는 날 "서버는 통과시키는데 스킬만 막는다" 가
  됨(선행 검사가 `reached` 를 그대로 쓰는 것과 같은 이유).
- **build-start 를 모드와 무관하게 늘 부르는 이유**: 선행이 충족된 채 claim 한 작업도 `ds` 에 있음. 옛 서버는 404 라 스크립트가
  `BUILD_START_UNSUPPORTED` 로 넘김. 스킬을 서버보다 먼저 deploy 해도 종전 동작으로 물러남. 404 를 옛 서버로 보는 것은 `/me` 의
  계약이 2.9 미만일 때뿐 — 새 서버도 프로젝트 게이트·PAT 범위로 404 를 내고, 그것을 넘기면 선행 관문을 건너뜀(버전을
  모르면 실패로 봄).
- **`wait_pred` heartbeat 를 직접 보내는 이유**: 킷 heartbeat 훅은 진행 중 phase(`prepare`·`design`·`build`·`verify`·`refactor`·
  `rejected`)만 보냄(`blocked` 도 같은 이유로 직접 보냄). 훅에 `wait_pred` 를 더하면 PC 마다 훅을 다시 설치해야 함. state.json
  을 먼저 바꾸는 이유: 그 사이 훅이 `design` 을 한 번 더 보내 좌석을 덮지 않게. 좌석이 WAIT 로 안 보이면 멈춘
  주문이 STALE·OFFLINE 으로 보임(서버에 자동 회수 없음).
- **멈출 때 push 하는 이유**: 재개는 다른 PC·새 worktree 에서 일어날 수 있음. 원격 스윕 후보는 `wait_pred` tip 을 빼므로
  (`/dflow-merge` 「절차」 1번) push 가 스윕을 안 부름.
- **재개가 Phase 01 기점 선정을 그대로 다시 타는 이유**: `reached` 는 완료 보고 뒤(`im`)나 승인 뒤 merge 전에도 참. 선행 코드가
  기본 branch 에 없을 수 있음. 기본 branch 끝을 merge 하면 선행 코드 없이 Build 가 시작됨. 기점 규칙을 두 곳에 안 적음.
- **선행 반영 merge 를 재merge 허용 한 번으로 보는 이유**: agent branch 에는 Task 문서 commit 뿐이라 충돌 없고 코드는 새 기점과 같음.
  그래서 기준선을 이 트리에서 다시 잴 수 있음. 기점(`baseline.base`·`branch_base`)을 안 바꾸면 게이트 범위와 Verify 감사가
  선행의 코드까지 이 작업의 변경으로 봄.
- **`## 선행 기준` 을 파일 단위로 적는 이유**: 재확인이 `git diff --name-only <sha>..<새 기점> -- <파일>` 로 기계적으로 돌게
  하려고. 미충족 선행에는 서버 `head_sha` 가 없고(승인된 선행에만 있음) 구현 중인 선행은 원격 branch 도 대개 없어 "읽을 곳
  없음(가정)" 이 흔함. 그때는 재개할 때마다 검토 모드 Design 을 한 번 더 돎 — 가정이 맞았는지 볼 방법이 그것뿐.

## 변이 기록 패치 형태·슬롯 대기 초·부하 민감 테스트(2026-09-26)

- **변이를 패치 형태(`mutations/<ID>.mut`)로 남기고 드라이버(`mutate.mjs`)로 넣는 이유**: TSK-08-05 Verify 가 변이 위치를 찾는 데
  약 23분 씀(Explore 11.1분 + 변이 스크립트 작성 12분 + 원문 없는 7행 재작성 4분). 표본 재실행 규칙은 넣을 행 수만 줄이고
  위치 찾기라는 고정비는 남김. 원문·치환문을 파일로 남기면 Verify 는 ID 만 골라 드라이버에 넣음. 원문이 파일에 정확히 한 번
  있어야 넣는 이유: 두 곳 이상이면 기록이 가리키는 곳을 확정할 수 없음(기록 결함으로 보고). Build 도 같은 드라이버를
  쓰게 해 "Build 가 돌린 변이 = Verify 가 다시 넣는 변이" 가 글자 그대로 같게 함.
- **Verify 의 E2E 변이 재실행을 1행으로 묶는 이유**: E2E 변이는 행마다 re-build·서버 restart 라 한 행에 약 7분. Build 가 이미
  돌린 E2E 변이를 Verify 가 다시 다 돌리면 표본 감사의 이득이 사라짐.
- **슬롯을 얻은 줄에 `waited=<초>s` 를 붙이는 이유**: 포기(`HEAVY_BUSY … wait=Ns`)만 시간이 남아, 기다려 얻은 대기는 잴 수 없었음.
  7건 분석에서 포기 대기 34회·133.5분, 단일 gradlew 128회의 "Gradle 밖 시간" 74분은 성공한 대기로 추정(미확인).
  끝에만 붙이는 이유: 기존 판독(test·사람의 grep)을 안 깨려고. `HEAVY_STATUS` 는 안
  바꿈(capacity.mjs·앱이 읽음).
- **부하 민감 test 를 단독으로 한 번 더 돌리는 이유**: TSK-07-04(27.5분 지연)와 TSK-09-01(44.4분 지연) 모두 evalex-perf NFR-1(1만
  레코드 100ms)과 sections-render 가 부하 24-32 에서 실패, 단독으로는 통과. 두 번 다 팀장이 같은 판단(env 인정).
  기준선에서는 통과(m-mdm 760/0)였으므로 기준선 차분 규칙의 빈틈이 아니라 부하가 만든 거짓 실패. 판별을 "경과 시간 상한
  단언" 으로 좁게 둔 이유: 넓히면 부하가 드러낸 진짜 동시성 결함까지 env 로 덮음. 단독에서도 실패하면 진짜 실패로 봄.

## advisor 호출 정책·Build 모델 시험·opus 승급(2026-09-26)

- **advisor 는 기본이 막혔을 때만, 정해진 시점 호출은 Build sonnet 시험 단위에만 두는 이유**(phase-prompt.md 공통 규칙 9, dev-discipline
  「advisor 호출(실행 모델별)」): 7건 분석에서 advisor 82회 호출, 회당 약 2분(대부분 advisor 출력 약 1만 토큰을 기다리는
  시간). advisor 입력은 캐시 없이 한 번에 약 15만 토큰이라 가중 합계 23M(+14%)이 advisor 몫. Opus Build 단위 26개가 약 52회를
  불렀는데 같은 모델끼리의 중복 검토. Sonnet Build 단위 11개는 약 7회, Sonnet Verify 7건은 12회. 완료 전 호출의 절반은 보이는
  변화 없이 그대로 보고로 넘어감. 처음에는 sonnet·haiku 에 정해진 시점 호출을 두려 했으나(2026-09-26 첫 안) 사용자 결정으로 바꿈 —
  같은 7건에서 코드 품질 때문에 생긴 게이트 실패·Verify 실패·반려 0건(sonnet 작업 3건 포함). sonnet 작업의 문제는 모두 환경·
  절차(부하 민감 성능 test, Verify 가 백그라운드 Gradle 을 기다리며 멈춤). sonnet 에 강제 호출을 두면 7건 추정으로 건당
  +11-15분, +1.3-2.2M 늘기만 함. 그래서 opus·sonnet 모두 기본은 막혔을 때만. 정해진 시점 호출은 원래 opus 였을 작업을
  sonnet 이 대신 도는 시험 단위에만 둠 — 그 단위는 배정표가 "어렵다" 고 본 작업이라 착수 전·완료 전 검토의 값이 있고, 시험이
  그 비용까지 함께 재야 비교가 공정. 하네스의 일반 지시("착수 전·완료 전에 부른다")보다 우선한다고 적는 이유: 두 지시가 같이

  안 서는 것은 advisor 대신 지적으로 올림(작성자가 판정). 서브에이전트가 자기 모델과 호출 시점을 모르면 이 규칙을

  몫을 따로 세는 이유: 시험의 비용 비교에 advisor 가 가장 큰 변수.

  게이트 신규 실패·재작업·Verify 지적·시간·토큰·승급률을 나란히 모으려는 것. 비율을 TSK ID 의 cksum 으로 정하는 이유:

- **sonnet Build 실패 시 opus 승급**(dev-discipline 「sonnet Build 의 opus 승급」): 같은 sonnet 에이전트에 실패를 이어 붙이면 같은
  모델이 같은 맹점으로 다시 도는 일이 많음. 시험으로 sonnet 을 늘리는 만큼, 막혔을 때 opus 가 받아 주는 안전판이 있어야 시험의
  실패 비용이 한 번의 재시도로 묶임. 횟수를 안 늘리고 기존 자리(게이트 재시도 1회, 인계 2회)의 모델만 바꾸는 이유: 전체
  스위트 실행 횟수(위 「전체 스위트 실행 횟수」)와 인계 상한을 그대로 지키기 위해. 초록 없이 끝난 sonnet 단위를 오케스트레이터가
  인계 commit 으로 바꾸는 이유: 인계 계수를 트레일러 하나로 유지해 재개가 기억 없이 셀 수 있게. 단위 모델을 state.json
  `model` 이 아니라 트레일러로 정하는 이유: 승급 뒤 `model` 이 opus 로 남아 재개한 오케스트레이터가 남은 단위까지 opus 로 띄우는
  것을 막기 위해. 승급 progress 를 state.json `model` 을 바꾸기 전에 보내는 이유: 보고 행이 그 시점의 heartbeat 모델을
  남기므로(0105) 진행표에서 sonnet 구간과 opus 구간이 행으로 갈림. heartbeat `--note` 는 blocked 일 때만 저장되므로
  (heartbeat 라우트) 승급 기록에 안 씀.
- **읽기 전용 위치 조사의 기본 모델을 haiku 로**(phase-prompt.md 공통 규칙 6, dev-discipline 「공통 금지」 토큰 항목): 종전 문구는

  작업당 3-8분이 임계 경로에 있음. 조사는 읽기 전용이라 haiku 의 과거 문제(Verify 에서 변이 검증·E2E 같은 실행 단계를 건너뜀)가
  생길 자리 없음. 결과를 해석·판단해야 하는 조사(설계 대안 비교, 코드 의미 검토)는 판단의 질이 산출물로 이어지므로 sonnet 을
  둠. Verify 감사자 셋은 조사가 아니라 리뷰라 sonnet 유지(사용자 결정). Phase 실행 모델의 haiku 금지(배정표)와는 대상이
  다름. 조사 서브에이전트의 모델은 Agent 호출 기록으로 확인할 수 있어 따로 기록 안 함.
