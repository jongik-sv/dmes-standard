# 전문 수신(Inbound, API) 설계

> 작성일: 2026-06-01
> 범위: **Serai → MES 로 HTTP(API) 수신하는 부분**. (Kafka 직접 consume 은 Serai 담당, 우리는 Serai 가 쏘는 API 만)
> 위치: **cactus-core 공통 제너릭 리시버** (`com.dongkuk.dmes.cactus.dmom.receiver`)
> 송신 설계: [01_전문송신_설계.md](./01_전문송신_설계.md) 와 대칭. 포맷 조회(`DmomFormatRepository`)·직렬화 규칙 재사용.

## 1. Serai → MES 수신 body (소스 검증 완료)

Serai `HttpOutboundHandler` 가 Kafka 원본 메시지 맵(`getRawMessageMap()`) 전체를 JSON POST. (caravan `KafkaMessageContext` 표준 5필드)

```http
POST <OUTBOUND config.HTTP_URL>      (HTTP_METHOD, 기본 POST)
Content-Type: application/json; charset=UTF-8
Accept: application/json
```
```json
{
  "TRANSACTION_CODE":  "PQR02012",
  "INTERFACE_ID":      "MMQCMMCMTT01",
  "INTERFACE_MSG":     "PQR02012|P|S|5A|20260130111245",
  "INTERFACE_PROTOCOL":"IF_KAFKA",
  "KAFKA_KEYDATA":     "b77b3447-..."
}
```
- **성공 계약**: HTTP **2xx** → 성공. 그 외 → Serai `failRetryable` → 재시도(최종 실패 시 컨테이너 pause).
- **인증 헤더 없음** (Serai 는 Content-Type/Accept 만). → 무인증 수신. 보안은 네트워크 또는 별도 헤더 정책으로(후속).
- `INTERFACE_MSG` = 파이프 구분 전문. FORMAT_LAYOUT 으로 **역파싱** 필요.

## 2. 수신 흐름
```
외부/타시스템 → Kafka(topic=INTERFACE_ID) → Serai consume
  → OutboundRouter.selectOutboundConfig(topicId)   [SERAIUSER.TB_MCM_MOM_KAFKA_SERAI_CONFIG]
  → INTEGRATION_TYPE=HTTP → HttpOutboundHandler → POST {JSON}
  → ★ MES cactus-core 수신 API (DmomReceiveController) ★
      1) DTO 수신 (TC / IF / INTERFACE_MSG[raw 전문] / KAFKA_KEYDATA)
      2) TC_SKIP 체크 (선택)
      3) serviceId=TC → serviceStarter.start(TC, ServiceContext[inputs={TC, IF, raw 전문}]) 백엔드 직접 기동 (웹 미경유)
  → ★ BPMN 서비스(TC) 실행 ★
      4) 첫 태스크 dmomParseMessageTask: (TC,IF)→FORMAT_LAYOUT 조회 + raw 전문 역파싱 → Map → context output(parseData)
      5) 후속 BPMN 태스크가 parseData(ITEM_ID 키 Map)로 업무 처리 (수신 BPMN이 다시 송신 시 createMsg → 송신 버퍼/afterCommit)
      6) 커밋 → 리시버 2xx / 실패(예외·ServiceResult 에러) → rollback → 리시버 5xx + TC_ERROR('R') → Serai 재시도
```

**설정 전제**: 현재 `TB_MCM_MOM_KAFKA_SERAI_CONFIG` OUTBOUND 행은 대부분 DB 타입. **API 수신하려면** 토픽별 **OUTBOUND + INTEGRATION_TYPE=HTTP + HTTP_URL=우리 엔드포인트** 설정 필요.

## 3. 컴포넌트 설계 (`com.dongkuk.dmes.cactus.dmom.receiver`)

| 클래스 | 책임 | 레거시 대응 |
|---|---|---|
| `DmomReceiveController` | `POST /dmomApi/v1/receive` — Serai JSON 수신, **파싱 안 함**(raw 전달), 디스패처 호출, 2xx/5xx 반환 | `DMomRecvServiceController` |
| `DmomReceiveRequest` (record) | `transactionCode/interfaceId/interfaceMsg/interfaceProtocol/kafkaKeyData` (@JsonProperty 대문자) | (신규) |
| `DmomReceiveDispatcher` | serviceId=TC → `ServiceContext[inputs={TC,IF,raw 전문}]` 구성 + 시스템 audit → `serviceStarter.start(TC, sc)` | `DMomRecvServiceController.createService/runService` |
| **`DmomParseMessageTask`** (빈+method) | **BPMN 첫 태스크**. context inputs(TC/IF/raw)로 `(TC,IF)→FORMAT 조회 + MessageParser 역파싱 → Map` 출력 | `DMomParseMessageTask`(Wow) — 위치 동일, 메커니즘은 빈+method |
| `MessageParser` | FORMAT_LAYOUT + pipe → `Map` 역직렬화 (E/G/GE, DATA_TP 1~5 역변환). **`DmomParseMessageTask` 가 호출** | `DMomParseMessage`+`DMomRecvUtil.getMsgFromRecvFormat` |
| `DmomReceiveResponse` (record) | 결과 코드(SUCCESS/ERROR) — 2xx body | `IntegrationResponse` 대칭 |
| (재사용) `DmomFormatRepository` | (TC,IF) → FORMAT_LAYOUT — **파싱 태스크가 사용**(리시버 아님) | 송신과 공유 |
| (재사용) `DmomErrorLogger` | 실패 시 TC_ERROR (ERROR_TYPE='R') | `DMomLogger` |

### 역변환 규칙 (`getMsgFromRecvFormat` 이식 — 송신 DATA_TP 의 역)
| DATA_TP | 송신(직렬화) | 수신(역파싱) |
|---|---|---|
| 1 String | 그대로 | `trim` 후 그대로 |
| 2 Number | 고정폭 zero-pad(소수점없음) | prec>0·"."없음 → `값/10^prec` (BigDecimal, prec 자리) / 그 외 BigDecimal 정규화(앞 0 제거) |
| 3 Date | 숫자+0패딩+절단 | "1900"<값<"9999" 면 구분자 제거 후 `substring(0,DataLen)`, 아니면 "" |
| 4 String2 | trim | ※ 레거시 미구현(빈값) → **신규는 trim 처리로 보강** |
| 5 Number2 | 원형 | BigDecimal 정규화 |
- E/G/GE 토큰 매핑·그룹 반복 알고리즘 = `DMomParseMessage.msgParsing` 이식. (신규는 TC/IF 를 JSON 에서 받으므로 메시지에서 추출 불요)

> ✅ **역파싱 위치 = BPMN 첫 태스크 (AS-IS 동일, R6 확정 2026-06-01)**
> - **AS-IS**: 컨트롤러가 raw 파이프 메시지를 context `MOM_RECV_CDATA` 로 넣고 서비스 시작 → BPMN **첫 태스크 `DMomParseMessageTask`(Wow)** 가 `msgParsing` → 결과를 context `MOM_PARSE_DATA` 로 출력 → 후속 태스크가 사용.
> - **신규**: 동일하게 **BPMN 첫 태스크에서 파싱**. 단 메커니즘은 **빈+method 태스크 `dmomParseMessageTask`**(Wow 아님 — OASIS `WowJavaServiceTaskExecutable` 이 `newInstance` 라 DI 불가; 송신 `DmomMessageTask` 와 동일 이유). 리시버는 raw 전문/TC/IF 를 inputs 로만 전달.
> - 입출력: 첫 태스크가 inputs(TC/IF/raw)로 `DmomFormatRepository.getActiveLayout(TC,IF)` + `MessageParser.parse(layout, raw)` → Map 을 task `output`(예: `parseData`) 으로 context 에 적재 → 후속 태스크가 ITEM_ID 키 Map 사용. (AS-IS `MOM_PARSE_DATA` 대응)

## 4. 디스패치 (TC → OASIS BPMN) — 확정

- **serviceId = TRANSACTION_CODE** (R4): 별도 매핑테이블 없이, OASIS BPMN 저장경로(`cactus.oasis.service-path`)에서 **TC 명과 매칭되는 BPMN** 을 실행. (OASIS `ServiceProvider` 가 serviceId→BPMN 해석. `group^^name` 형태면 그대로 사용)
- **웹 미경유 백엔드 직접 기동** (R5): 리시버는 `CactusRequest`/`OasisServiceExecutor`(웹 진입) 를 거치지 않고, **raw 전문 + TC + IF** 를 inputs 로 **`ServiceContext` 를 직접 구성**해 `serviceStarter.start(TC, sc)` 호출. (역파싱은 리시버가 아닌 BPMN 첫 태스크 — R6)
  - inputs(예): `{ transactionCode, interfaceId, interfaceMsg(raw), kafkaKeyData }` → OASIS `Map<String,TypedObject>` 로 변환해 `DefaultServiceContext` 에 주입. (AS-IS 는 context `MOM_RECV_CDATA` 에 raw 적재)
  - audit: 웹 사용자 컨텍스트가 없으므로 **시스템 audit**(예: userId=SYSTEM, svcId=TC, pgmId=수신) 을 `AuditHolder` 에 세팅(수신 INSERT/UPDATE 감사 컬럼용). `OasisServiceExecutor` 의 audit 세팅 패턴 참고.
- **트랜잭션**: 기동된 BPMN 이 OASIS Spring tx(`transactional:true`) 안에서 실행 → 커밋 성공 = 처리 완료. (수신 BPMN 이 다시 dmom 송신을 하면 동일 afterCommit 메커니즘 적용 — 송수신 대칭)
  - 성공 → 리시버 HTTP **200**. 실패(예외/`ServiceResult` 에러) → OASIS rollbackAll → 리시버 **5xx** → Serai 재시도.
- 구현 상세(`ServiceContext` 구성·audit 세팅의 정확한 API)는 `OasisServiceExecutor`/`CoreServiceStarter` 패턴을 따른다(수신 구현 Phase 에서 코드화).

**레거시 대조 (`DMomRecvServiceController.runService`) — R4/R5 확정 근거:**
- `String serviceId = momTransactionCode;` → `serviceController.start(serviceId, null, context)` — **serviceId=TC 정확히 일치**.
- `action = DEFAULT_GROUP_NONUI`(비-UI), `audit.getUser().setUserType(UserType.NUI)` — **비-UI 액션 + 시스템(NUI) audit**. 신규도 동일하게 비-UI 액션 + 시스템 audit 로 기동.
- 레거시는 `momSendList`/`momSendForcedList` 를 context 에 init(수신 서비스가 다시 송신 시 사용) → **신규는 tx-스코프 버퍼라 불요**(수신 BPMN 이 `createMsg` 호출하면 자동 버퍼/afterCommit).
- 레거시는 OASIS 자체 tx(`transactionHandler.rollbackAll`) 수동 정리 → **신규는 Spring tx 자동**.

## 5. 응답·계약·기타
- **성공**: 서비스 커밋 성공 → HTTP 200 `{resultCode:SUCCESS, ...}`.
- **실패**: 5xx (Serai 재시도 유발) + `TC_ERROR`(ERROR_TYPE='R') 적재. 포맷 부재/파싱 오류도 실패.
- **TC_SKIP** (`TB_MCM_MOM_TC_SKIP`, 레거시 `momSkipTc` 정합): 두 레벨 구분 —
  - `SKIP_LEVEL='Y'` (SKIP-1): **200 응답 + 서비스 미실행**(전문 무시·종료).
  - `SKIP_LEVEL='T'` (SKIP-2): **200 조기 응답 + 서비스는 그래도 실행**.
  - (선택 기능 — 1차 구현에서 생략 가능)
- **멱등성**: `KAFKA_KEYDATA` 로 중복 수신(재시도) 식별 가능 → 멱등 처리 여부 결정(후속).
- **인증**: Serai 무인증 → 네트워크 격리 또는 공유키 헤더 도입 검토(후속).

## 8. 레거시(cactus-section) 대조 종합

소스: `cactus-section` `controllers/DMomRecvServiceController`, `dmom/receiver/DMomParseMessage`, `dmom/util/DMomRecvUtil`.

| 설계 항목 | 레거시 | 판정 / 조치 |
|---|---|---|

| **역파싱 위치** | BPMN 첫 태스크 `DMomParseMessageTask` 가 파싱(컨트롤러는 raw 전달) | ✅ **위치 일치**(R6 수정): 신규도 BPMN 첫 태스크 `dmomParseMessageTask`. 메커니즘만 빈+method(Wow→DI불가) |
| 역변환 규칙 | `getMsgFromRecvFormat`(DATA_TP 1/2/3/5; 4 미구현) | ✅ 이식, type4 trim 보강 |
| getFormatLayout | TC+IF 로 조회(`DMomMapper.getFormatLayout`) | ✅ 동일 매퍼 재사용 |
| TC_SKIP | SKIP1(Y)=200+미실행, SKIP2(T)=200+실행 | ⚠️ 정정 반영(§5) |
| 송신 버퍼 init | context `momSendList`/`ForcedList` | ➕ 불요(tx-스코프 버퍼) |
| Tx 정리 | `transactionHandler.rollbackAll()` 수동 | ➕ Spring tx 자동 |
| 실패 응답 | EAI 401 / JCM·LOC 500 | ✅ 신규 5xx(=Serai 재시도) |
| 중복 방지 | `isProcessing()` stub(비활성) | ➕ KAFKA_KEYDATA 멱등(후속) |
| 진입 프로토콜 | EAI XML(CDATA)·JCM·LOC 다중 엔드포인트 + immediateReturn/Direct-HTTP quirk | ➖ 신규는 Serai JSON 단일 엔드포인트(quirk 불요) |

**결론**: 핵심 디스패치(serviceId=TC·백엔드 기동·시스템 audit)·**역파싱 위치(BPMN 첫 태스크)** 모두 레거시(AS-IS)와 일치(R6 수정으로 정합). 유일한 메커니즘 차이는 파싱 태스크가 **Wow → 빈+method**(OASIS Wow DI 불가, 송신 `DmomMessageTask` 와 동일 이유)인 점뿐. 나머지는 신규 인프라(tx-스코프 버퍼·Spring tx·Serai JSON 단일 엔드포인트)로의 정합한 단순화.

### 🔴 필수 — 수신을 실제 동작시키려면 반드시 필요
1. **Serai 측 헤더 전송 기능 (별도 모듈, 미구현)** — 인증 확정안(고정키 `X-Client-Key` + `X-Authenticated-User`)을 Serai 가 실어보내야 cactus 보안체인(`.anyRequest().authenticated()`)을 통과. 미구현 시 **401/403 → non-2xx 무한 재시도**.
   - ① **DDL**: `TB_MCM_MOM_KAFKA_SERAI_CONFIG.HTTP_HEADERS NVARCHAR(MAX) NULL` 추가 — NULL 이면 기존 동작(헤더 0개) 유지 → 완전 옵셔널·목적지별.
   - ② **Mapper**: `SeraiConfigMapper.xml` 의 `selectOutboundConfig` SELECT 목록에 `HTTP_HEADERS` 추가.
   - ③ **Handler**: `HttpOutboundHandler`(현재 `L106-160`)가 `HTTP_HEADERS` non-blank 시 JSON→`Map<String,String>` 파싱 후 `setRequestProperty(k, resolveEnv(v))`. `${ENV}`→`System.getenv` 치환(실 시크릿은 DB 아닌 Serai 환경변수).
2. **cactus/모듈 키 설정** — `BACKEND_CLIENT_KEY`(env, 1순위) 또는 `cactus.security.client-key`(yml) 설정만. 보안체인/스킵경로 변경 불요.
3. **OUTBOUND HTTP config 시드** — 수신 토픽 행 추가(`DIRECTION=OUTBOUND, INTEGRATION_TYPE=HTTP, HTTP_URL=<MES>/dmomApi/v1/receive`) + `HTTP_HEADERS` 헤더 JSON:
   ```json
   {"X-Client-Key":"${BACKEND_CLIENT_KEY}","X-Authenticated-User":"SERAI","X-Authenticated-Role":"SYSTEM"}
   ```

### 🟡 검증 — 파일럿 (현재 테스트 1 skip)
4. **E2E 파일럿** — 실 Serai/Kafka: OUTBOUND HTTP 토픽 → Serai → MES API → BPMN 파싱 → 처리.
   - `dmomParseMessageTask` BPMN 메서드 인자 바인딩(`parse(TC,IF,raw)` ↔ context inputs) 실 BPMN 검증.
   - `RECEIVE_ACTION("nonui")` ↔ 수신 BPMN actionGateway 정합(또는 게이트 없음) 확인.

5. **영구 업무오류 무한재시도 회피** — Serai 는 모든 non-2xx 재시도 → 비재시도 4xx 업무거절도 재시도. "비재시도 오류 → TC_ERROR 적재 후 2xx" 정책 검토.
