## 4. 핵심 컴포넌트 상세

### 4.1 `DmomMessageService` / `DefaultDmomMessageService`

```java
public interface DmomMessageService {
    /** 전문 생성 → 버퍼 적재 → (최초) 동기화 등록. @return 직렬화된 전문 문자열. */
    String createMsg(DmomSendRequest request);
}
```

`createMsg` 처리 순서:
```java
@Override
public String createMsg(DmomSendRequest req) {
    // 1) 활성 트랜잭션 전제 검증 (D7) — DB 즉시INSERT 원자성 + HTTP afterCommit 등록 모두 필요
    if (!TransactionSynchronizationManager.isActualTransactionActive()) {
        throw new DmomException("createMsg requires an active Spring transaction. "
            + "OASIS: cactus.oasis.transactional=true, 또는 호출 메서드에 @Transactional.");
    }
    // 2) 포맷 조회 (biz-template, MCMAPUSER cross-schema SELECT)
    FormatLayout layout = formatRepository.getActiveLayout(req.formatLookupTc(), req.interfaceId());
    if (layout.isEmpty()) {
        throw new DmomException("FORMAT_LAYOUT 없음: TC=" + req.formatLookupTc() + ", IF=" + req.interfaceId());
    }
    // 3) 직렬화
    String interfaceMsg = serializer.serialize(layout, req.data());   // "값|값|값|"
    // 4) transport 분기
    switch (req.transport()) {
        case DB -> dbWriter.insert(req, interfaceMsg);    // 즉시 업무 tx 커넥션 INSERT (원자적). 실패 시 예외 전파→롤백
        case HTTP -> {                                    // 버퍼 적재 + 최초 1회 afterCommit 등록
            boolean first = !DmomSendBuffer.isActive();
            List<DmomMessage> buffer = DmomSendBuffer.openIfAbsent();
            if (first) {
                TransactionSynchronizationManager.registerSynchronization(
                    new DmomDispatchSynchronization(buffer, httpSender, errorLogger));
            }
            buffer.add(new DmomMessage(req.transactionCode(), req.interfaceId(), interfaceMsg));
        }
    }
    // 5) 직렬화 문자열 반환 (D9)
    return interfaceMsg;
}
```
협력자(주입): `DmomFormatRepository`, `MessageSerializer`, `DmomHttpSender`, `DmomDbOutboundWriter`, `DmomErrorLogger`.

### 4.2 `DmomSendBuffer` — bindResource 기반 tx-스코프 버퍼 (D8)

```java
public final class DmomSendBuffer {
    private static final Object RESOURCE_KEY = DmomSendBuffer.class;
    private DmomSendBuffer() {}

    public static boolean isActive() {
        return TransactionSynchronizationManager.hasResource(RESOURCE_KEY);
    }
    @SuppressWarnings("unchecked")
    public static List<DmomMessage> openIfAbsent() {
        if (!isActive()) {
            List<DmomMessage> list = new ArrayList<>();
            TransactionSynchronizationManager.bindResource(RESOURCE_KEY, list);
            return list;
        }
        return (List<DmomMessage>) TransactionSynchronizationManager.getResource(RESOURCE_KEY);
    }
    public static void close() {                  // afterCompletion 에서 호출
        if (isActive()) TransactionSynchronizationManager.unbindResource(RESOURCE_KEY);
    }
}
```
- **OASIS / 비-OASIS 양쪽 공용 — 단일 버퍼.** Spring 트랜잭션 인프라에만 의존하므로 진입 경로와 무관하게 동일 동작(OASIS Context 미사용).
- 스레드/트랜잭션 단위 격리(동기화 콜백은 동일 스레드). 중첩 createMsg 는 같은 버퍼 공유.
- 누수 방지: `afterCompletion` 에서 반드시 `close()` (커밋·롤백 무관).

### 4.3 `DmomDispatchSynchronization` — afterCommit HTTP 디스패치 (HTTP 전용)

> DB는 `createMsg`에서 이미 in-tx INSERT 되므로 동기화는 **HTTP만** 담당. `beforeCommit` 없음.
> (검증 결과: OASIS 멀티 PTM + 단일 동기화 리스트 + `commitAll` 역순 커밋 때문에 `beforeCommit` 의 "업무 tx 합류" 타이밍이 선언순서 의존 → 취약. DB는 createMsg 즉시 INSERT로 회피.)

```java
public class DmomDispatchSynchronization implements TransactionSynchronization {
    private final List<DmomMessage> buffer;       // HTTP 메시지만 (등록 시 캡처)
    private final DmomHttpSender httpSender;
    private final DmomErrorLogger errorLogger;
    // 생성자 생략

    @Override
    public void afterCommit() {                    // 커밋 성공 시에만 (D2)
        for (DmomMessage m : buffer) {
            try { httpSender.send(m); }
            catch (Exception e) {
                errorLogger.log(m, e, "S");        // 커밋 후라 롤백 불가 → TC_ERROR (ERROR_TYPE='S')
            }
        }
    }

    @Override
    public void afterCompletion(int status) {
        DmomSendBuffer.close();                    // 버퍼 unbind (누수 방지)
    }
}
```
- **순서**: 버퍼 적재 순서대로 send(FIFO). 개별 try/catch — 한 건 실패가 다른 건을 막지 않음, 실패분만 `TC_ERROR`.
- 등록은 `registerSynchronization` 1회(HTTP 최초 적재). `afterCommit` 미발동 = 커밋 실패 = 미전송(정상).
- (멀티tx 엣지케이스 — 동기화 소유 tx 롤백 시 afterCommit 미발동 등 — §14-5 한계 참조.)

### 4.5 `DmomDbOutboundWriter` — EAIUSER.IF_* INSERT (업무 tx 커넥션, 원자적)

> **별도 EAIUSER DS / REQUIRES_NEW 안 씀.** `createMsg` 에서 직접 호출되어 **활성 업무 트랜잭션 커넥션**으로 INSERT → 같은 로컬 tx 에 합류(원자적). 따라서 `@Transactional` 부착 안 함(이미 활성 tx 안). 사용 템플릿 = **업무 tx DataSource 에 바인딩된 SqlSessionTemplate** (기본 `sqlSessionTemplateBiz`, OASIS SQL ScriptTask 와 동일 패턴). 대상 테이블만 `EAIUSER.` schema-qualified.

```java
@Component
public class DmomDbOutboundWriter {
    private final SqlSessionTemplate bizTemplate;        // 업무 tx DS 템플릿 (기본 sqlSessionTemplateBiz)
    private final DmomFormatRepository formatRepository; // SEND_TABLE_ID 조회용

    // @Transactional 없음 — createMsg 가 활성 업무 tx 안에서 호출 (원자적). 실패 시 예외 전파→롤백.
    public void insert(DmomSendRequest req, String interfaceMsg) {
        String table = formatRepository.resolveSendTable(req.interfaceId(), req.transactionCode());
        Map<String, Object> p = new HashMap<>();
        p.put("tableName", table);                      // 동적 테이블 (화이트리스트 검증)
        p.put("transactionCode", req.transactionCode());
        p.put("interfaceId", req.interfaceId());
        p.put("interfaceMsg", interfaceMsg);
        p.put("ifFlag", "N");                           // 미처리 (Serai 폴러 대상)
        // 감사 컬럼은 CactusMybatisAuditInterceptor 가 자동 주입 (cUsrId/cAt/...)
        // IF_SEQ = DB 시퀀스/DEFAULT 자동 채번, IF_DATE/IF_TIME = Serai 가 처리시 채움, KEY_DATA = 미사용 → INSERT 컬럼 제외
        bizTemplate.insert("DmomMapper.insertIfOutbound", p);   // 업무 tx 커넥션 → 원자적
    }
}
```
- **원자적**(D1): `createMsg` 가 활성 업무 tx 안에서 즉시 INSERT → 업무데이터와 함께 커밋/롤백. INSERT 실패 시 예외 전파 → 전체 롤백.
- **전제 GRANT**: 업무스키마 USER 에 `EAIUSER.IF_*` INSERT 권한 필요(§6). (MCMAPUSER 부여 완료)
- 타깃 테이블: `TB_MCM_MOM_INTERFACES.SEND_TABLE_ID`, 미지정 시 `IF_<INTERFACE_ID>`. **동적 테이블명은 정규식 화이트리스트 `^[A-Za-z_][A-Za-z0-9_]*$` 검증**(SQL injection 방지, Serai `isValidTableName` 패턴 동일).
- **실측 컬럼**(`EAIUSER.IF_MMQCMMCMTT01`): `TRANSACTION_CODE / INTERFACE_ID / INTERFACE_MSG / IF_FLAG / KEY_DATA1~3 / C_*·U_*(audit) / VER / IF_SEQ / IF_DATE / IF_TIME`. 우리 INSERT 가 채우는 건 `TRANSACTION_CODE / INTERFACE_ID / INTERFACE_MSG / IF_FLAG('N') / audit / VER(0)`. **IF_SEQ=DB채번, IF_DATE/IF_TIME=Serai, KEY_DATA=미사용** 이므로 제외. (`U_AT` NOT NULL → audit 인터셉터가 항상 set)

### 4.6 `DmomErrorLogger` — TB_MCM_MOM_TC_ERROR INSERT (REQUIRES_NEW, HTTP 실패 전용)

> HTTP 방식은 `afterCommit`(업무 tx 종료 후) 실패 → 독립 트랜잭션으로 적재해야 함. `error-tx-manager`(프로퍼티) 기반 `TransactionTemplate(REQUIRES_NEW)` 사용(§7.2). (DB 방식 실패는 `beforeCommit` 예외 → 업무 롤백이라 별도 로그 불필요.)

```java
@Component
public class DmomErrorLogger {
    private final SqlSessionTemplate bizTemplate;        // TC_ERROR(MCMAPUSER) — biz-template
    private final TransactionTemplate dmomErrorTxTemplate; // REQUIRES_NEW (error-tx-manager)

    public void log(DmomMessage m, Throwable error, String errorType) {   // HTTP 실패 전용
        dmomErrorTxTemplate.executeWithoutResult(s -> {
            Map<String, Object> p = new HashMap<>();
            p.put("transactionCode", m.transactionCode());
            p.put("interfaceId", m.interfaceId());
            p.put("interfaceProtocol", "SERAI_HTTP");               // HTTP 실패만 적재 (DB는 롤백)
            p.put("interfaceMsg", m.interfaceMsg());
            p.put("errorType", errorType);                          // 'S'(송신)
            p.put("errorCode", shortCode(error));
            p.put("errorMsg", truncate(error.getMessage(), 1000));
            p.put("errorStatusCode", "N");                          // 미처리
            bizTemplate.insert("DmomMapper.insertTcError", p);      // SQ_VAL = NEXT VALUE FOR SEQ
        });
    }
}
```
- 독립 트랜잭션 → 업무/전송 결과와 무관하게 에러 로그 보존. **HTTP 실패 전용**(DB 실패는 createMsg 예외→업무 롤백이라 로그 불요).
- KEY_DATA 미사용 → TC_ERROR 의 KEY_DATA 컬럼은 NULL.
- 비-mcm 모듈은 `biz-template`/`error-tx-manager` 를 `cactus.dmom.*` 로 재지정(§7).

### 4.7 `DmomFormatRepository`

```java
@Component
public class DmomFormatRepository {
    private final SqlSessionTemplate bizTemplate;       // = sqlSessionTemplateBiz (MCMAPUSER)

    public FormatLayout getActiveLayout(String tc, String interfaceId) {
        Map<String,Object> param = Map.of("transactionCode", tc, "interfaceId", interfaceId);
        List<Map<String,Object>> rows = bizTemplate.selectList("DmomMapper.getFormatLayout", param);
        // ★ mapUnderscoreToCamelCase=true → 결과 키는 camelCase:
        //   formatId/formatVer/itemSeq/itemTp/itemId/itemNm/dataTp/dataLen/dataDecimalPrec
        // rows → FormatItem 리스트 → FormatLayout (camelCase 키로 read)
    }
    public String resolveSendTable(String interfaceId, String tc) {
        String t = bizTemplate.selectOne("DmomMapper.getSendTableId",
                       Map.of("interfaceId", interfaceId, "transactionCode", tc));
        return (t != null && !t.isBlank()) ? t : "IF_" + interfaceId;   // bare 테이블명, 매퍼가 EAIUSER. prefix
    }
}
```
- ★ **Phase 0 확인(0.5)**: `cactus-mybatis-config.xml` `mapUnderscoreToCamelCase=true` → resultType=map 결과 키 camelCase. Repository 가 camelCase 키로 읽음.
- 캐싱(후속): `cactus.dmom.format-cache.*` 로 FORMAT_LAYOUT 캐시(레거시 미적용, 성능 시 도입).

### 4.8 `MessageSerializer` — `값|값|값|` 직렬화 (D11, E/G/GE + DATA_TP 1~5)

```java
@Component
public class MessageSerializer {
    private static final String SEP = "|";

    public String serialize(FormatLayout layout, Map<String,Object> data) {
        StringBuilder sb = new StringBuilder();
        List<FormatItem> items = layout.items();
        for (int i = 0; i < items.size(); i++) {
            FormatItem it = items.get(i);
            switch (it.itemTp()) {
                case "E" -> sb.append(field(it, data.get(it.itemId()))).append(SEP);
                case "G" -> i = appendGroup(sb, items, i, data);   // 반복 그룹 처리
                // "GE" 는 G 처리 내부에서 소비
                default  -> { /* 알 수 없는 ITEM_TP → 검증단계에서 차단 */ }
            }
        }
        return sb.toString();
    }
    // appendGroup: G.dataLen=반복수, data.get(groupId)=List<Map>, 후속 GE 항목들을 반복수만큼 직렬화
    // field: DATA_TP 1~5 변환 (아래 표)
}
```

**DATA_TP 변환 규칙 — Phase 0 에서 레거시 소스로 확정** (정본: [Phase0_조사결과.md](./Phase0_조사결과.md) §0.1):

| DATA_TP | 의미 | 변환 |
|---|---|---|
| 1 | String | 값 그대로 (패딩/trim 없음) |
| 2 | Number | 정수부 `(DataLen-DataPrec)`자리 + 소수부 `DataPrec`자리 zero-pad, **소수점 미포함** (예 12.5/len8/prec2→`00001250`) |
| 3 | Date | `-,/,:,공백,.` 제거 → 뒤에 0 채움 → `substring(0,DataLen)` |
| 4 | String2 | `trim()` |
| 5 | Number2 | 값 원형 유지 |

- 구분자 `|` 는 **각 항목값 뒤에 부착**(마지막 포함 = `값|값|값|`). `G`(그룹헤더)는 append 안 함, `GE` 만 출력.
- `null` → `""`. 값에 `"NULL"`+`,[]` 만 있으면 → `""` (레거시 quirk).
- 특수: `SNDR_INFORM_EDIT_PGM_ID` >14 → 14자 절단. 변환결과 `"ERROR"` 시작 → `UserException`.
- **반드시** 레거시 산출물과 byte 동등성 단위테스트 작성(§13). 그룹 반복 알고리즘 = Phase0 §0.1.

## 5. MyBatis 매퍼 (`persistence/dmom/DmomMapper.xml`, MSSQL)

> namespace=`DmomMapper`. XML은 `cactus.mybatis.mapper-locations` 패턴에 포함되어 biz/if/cmn 모든 factory에 로드됨. DS는 호출 SqlSessionTemplate으로 결정.

```xml
<mapper namespace="DmomMapper">

  <!-- ① 포맷 레이아웃 조회 (biz-template = MCMAPUSER).
       MSSQL: Oracle 의 (A,B)=(subquery) tuple 비교 미지원 → JOIN + TOP 1(최신 활성 FORMAT_VER) 로 작성 -->
  <select id="getFormatLayout" resultType="map">
    SELECT L.FORMAT_ID, L.FORMAT_VER, L.ITEM_SEQ, L.ITEM_TP, L.ITEM_ID, L.ITEM_NM,
           L.DATA_TP, L.DATA_LEN, L.DATA_DECIMAL_PREC
    FROM MCMAPUSER.TB_MCM_MOM_FORMAT_LAYOUT L
    INNER JOIN (
        SELECT TOP 1 F.FORMAT_ID, F.FORMAT_VER
        FROM MCMAPUSER.TB_MCM_MOM_FORMAT_LIST F
        INNER JOIN MCMAPUSER.TB_MCM_MOM_TC_LIST T ON T.FORMAT_ID = F.FORMAT_ID
        WHERE T.TRANSACTION_CODE = #{transactionCode}
          AND (T.START_ACTIVE_DATE IS NULL OR T.START_ACTIVE_DATE &lt; GETDATE())
          AND (T.END_ACTIVE_DATE   IS NULL OR T.END_ACTIVE_DATE   &gt; GETDATE())
          AND (F.START_ACTIVE_DATE IS NULL OR F.START_ACTIVE_DATE &lt; GETDATE())
          AND (F.END_ACTIVE_DATE   IS NULL OR F.END_ACTIVE_DATE   &gt; GETDATE())
        ORDER BY F.FORMAT_VER DESC          <!-- 최신 활성 버전 -->
    ) FV ON FV.FORMAT_ID = L.FORMAT_ID AND FV.FORMAT_VER = L.FORMAT_VER
    ORDER BY L.ITEM_SEQ
  </select>

  <!-- ② 송신 테이블 ID 조회 -->
  <select id="getSendTableId" resultType="string">
    SELECT SEND_TABLE_ID FROM MCMAPUSER.TB_MCM_MOM_INTERFACES
    WHERE INTERFACE_ID = #{interfaceId} AND TRANSACTION_CODE = #{transactionCode}
  </select>

  <!-- ③ DB 방식 아웃박스 INSERT (bizTemplate=업무 tx 커넥션, EAIUSER schema-qualified). 테이블명 화이트리스트 검증 후 ${}
       제외 컬럼: KEY_DATA1~3(미사용), IF_SEQ(DB 채번), IF_DATE/IF_TIME(Serai 처리시 채움) -->
  <insert id="insertIfOutbound">
    INSERT INTO EAIUSER.${tableName}
      (TRANSACTION_CODE, INTERFACE_ID, INTERFACE_MSG, IF_FLAG,
       C_USR_ID, C_AT, C_SVC_ID, C_PGM_ID, U_USR_ID, U_AT, U_SVC_ID, U_PGM_ID, VER)
    VALUES
      (#{transactionCode}, #{interfaceId}, #{interfaceMsg}, #{ifFlag},
       #{cUsrId}, #{cAt}, #{cSvcId}, #{cPgmId}, #{uUsrId}, #{uAt}, #{uSvcId}, #{uPgmId}, 0)
  </insert>

  <!-- ④ 에러 로그 INSERT (bizTemplate = MCMAPUSER). SQ_VAL = SEQUENCE. KEY_DATA 미사용 → 컬럼 제외(NULL) -->
  <insert id="insertTcError">
    INSERT INTO MCMAPUSER.TB_MCM_MOM_TC_ERROR
      (SQ_VAL, TRANSACTION_CODE, INTERFACE_ID, INTERFACE_PROTOCOL, INTERFACE_MSG,
       ERROR_TYPE, ERROR_CODE, ERROR_MSG, ERROR_STATUS_CODE,
       C_USR_ID, C_AT, C_SVC_ID, C_PGM_ID, U_USR_ID, U_AT, U_SVC_ID, U_PGM_ID, VER)
    VALUES
      (NEXT VALUE FOR MCMAPUSER.SEQ_MCM_MOM_TC_ERROR,
       #{transactionCode}, #{interfaceId}, #{interfaceProtocol}, #{interfaceMsg},
       #{errorType}, #{errorCode}, #{errorMsg}, #{errorStatusCode},
       #{cUsrId}, #{cAt}, #{cSvcId}, #{cPgmId}, #{uUsrId}, #{uAt}, #{uSvcId}, #{uPgmId}, 0)
  </insert>
</mapper>
```
> 감사 컬럼(`cUsrId` 등)은 `CactusMybatisAuditInterceptor` 가 Map에 주입하므로 placeholder만 두면 됨. `IF_FLAG`/`IF_*` 실제 컬럼 구성은 Serai 폴러(`InterfaceMapper.selectPendingMessages`)가 기대하는 스키마에 맞춰 확정(§14-3).

## 7. 트랜잭션 / DataSource 매핑 & 설정

### 7.1 `DmomProperties` (`cactus.dmom.*`)
```yaml
cactus:
  dmom:
    enabled: true
    biz-template: sqlSessionTemplateBiz         # 업무 tx 커넥션 템플릿 (DB 아웃박스 INSERT + 포맷/TC_ERROR 조회)
    error-tx-manager: transactionManager        # TC_ERROR REQUIRES_NEW 대상 (HTTP 실패 적재용)
    default-send-table-prefix: "IF_"            # SEND_TABLE_ID 미지정 시
```
- **DB 아웃박스**는 별도 DS/tx매니저 설정이 없음 — `biz-template`(=활성 업무 tx 의 DataSource)로 `createMsg` 시점에 즉시 INSERT 하여 **업무 tx 에 합류**(원자적).
- **포맷/SEND_TABLE 조회**도 `biz-template` 사용(MCMAPUSER cross-schema SELECT).
- **TC_ERROR(HTTP 실패)** 만 `afterCommit` 후 별도 트랜잭션 필요 → `error-tx-manager` 로 `REQUIRES_NEW`.
> 비-mcm 모듈에서 MCMAPUSER가 primary가 아니면 cross-schema GRANT(§6)로 동일 `biz-template` 에서 접근. (DB가 분리된 환경이면 별도 가이드 필요 — §14-4)

### 7.2 동적 tx 매니저 (TC_ERROR 전용, 모듈 이식성)
`@Transactional(transactionManager="...")` 는 컴파일 고정이므로, `DmomErrorLogger` 의 `REQUIRES_NEW` 는 **`TransactionTemplate` 주입 방식**으로 구현(빈 이름 프로퍼티):
```java
// DmomAutoConfiguration
@Bean TransactionTemplate dmomErrorTxTemplate(BeanFactory bf, DmomProperties p) {
    return new TransactionTemplate(
        bf.getBean(p.getErrorTxManager(), PlatformTransactionManager.class),
        requiresNew());
}
// DmomErrorLogger.log(): dmomErrorTxTemplate.executeWithoutResult(s -> bizTemplate.insert("DmomMapper.insertTcError", p));
```
- DB 아웃박스(`DmomDbOutboundWriter`)는 `createMsg` 시점에 활성 업무 tx 에 합류(즉시 INSERT)하므로 **별도 tx매니저/TransactionTemplate 불필요**.

> Wow 인스턴스를 직접 생성 → **Spring DI 불가**(DmomMessageService 주입 못함). 반면 `PlainJavaServiceTaskExecutable`

BPMN에 Java 작성 없이 송신을 추가하려는 경우:
```xml
<bpmn:serviceTask id="sendTask" name="전문송신" camunda:class="dmomMessageTask">

    <camunda:property name="method" value="createMessage"/>
  </camunda:properties></bpmn:extensionElements>

</bpmn:serviceTask>

// 빈 이름 "dmomMessageTask" (DmomAutoConfiguration 등록). DmomMessageService 주입됨.
public class DmomMessageTask {
    private final DmomMessageService dmomMessageService;
    public String createMessage(String transactionCode, String interfaceId, String transport,
                                Map<String,Object> data) {
        return dmomMessageService.createMsg(DmomSendRequest.builder()
            .transactionCode(transactionCode).interfaceId(interfaceId)
            .transport(SeraiTransport.valueOf(transport.toUpperCase())).data(data).build());

}
```
> 메서드 인자(transactionCode/interfaceId/transport/data)는 BPMN inputs 로 바인딩(StrictMethodInvoker, `-parameters` 컴파일). 실제 BPMN 바인딩은 Phase 5 파일럿에서 검증.
> **권장 1순위는 §9.2(업무 서비스 빈이 DmomMessageService 직접 주입)** — 별도 태스크 불요.

## 14. 미해결 / 후속 확정 & 한계

**확인 완료 (검증 결과 반영):**
- IF 테이블 실측: `EAIUSER.IF_MMQCMMCMTT01` 컬럼 확인 → insertIfOutbound 컬럼 확정(§4.5/§5). `IF_SEQ`=DB 채번, `IF_DATE/IF_TIME`=Serai, `KEY_DATA`=미사용.
- 매퍼 경로 = `persistence/dmom/DmomMapper.xml` (mapper-locations 기본값 정합).
- **(2차 검증) DB 즉시 INSERT 원자성 성립 확인**: mcm `cactus.oasis.transactional: true` + `primary-alias: biz` + `cactus.tx.default-manager: txBiz`(data-source=biz=MCMAPUSER). `pilotDefaultTx` 문서 명시 — tx 미명시 서비스는 txBiz(=biz=primary) tx 로 실행, biz DataSource→`sqlSessionTemplateBiz` 매핑. 즉 **기본 서비스 업무tx = bizTemplate DataSource** 일치 → DB 즉시 INSERT 가 업무 tx 합류 + GRANT(MCMAPUSER) 정합. ✓
- **(2차 검증) getFormatLayout MSSQL 정정 완료**: Oracle `(A,B)=(subquery)` tuple 비교 미지원 → JOIN + `TOP 1 ORDER BY FORMAT_VER DESC`(최신 활성 버전) 로 재작성(§5).

**KAFKA_KEYDATA 처리 (검증 결론):** IF 행/KEY_DATA1 에 **넣지 않음**.
- DB: KAFKA_KEYDATA 는 Serai 가 폴링 시(커밋 후, 비동기) 생성 → INSERT 시점 부재. Serai `updateSuccess` 도 IF 행에 안 씀. `selectPendingMessages` 가 KEY_DATA 를 읽지만 `send()` 에 전달 안 함.
- HTTP: `SeraiSendResult.kafkaKeyData()` 로 동기 수신되나 afterCommit(업무 커밋 후) + HTTP 는 IF 행 없음.
- **트랜잭션상 불가**: KAFKA_KEYDATA 는 커밋 이후 생성값이라 업무 tx 에 포함 불가(별도 REQUIRES_NEW 필요). 필수 아니므로 미저장, 추적은 로그.

**한계 (멀티 tx / 부분커밋 — 문서화만, 파일럿은 단일 tx 권장):**
- HTTP `afterCommit` 동기화는 **첫 시작 tx(소유 tx)** 커밋 시 발동. `commitTx`(alwaysCommit)로 업무는 커밋됐는데 소유 tx 가 롤백되면 afterCommit 미발동 → HTTP 누락 가능.
- `CommitTransactionAskedEvent`(commit-and-restart)로 태스크가 중간 커밋 시, DB 즉시 INSERT 가 의도보다 일찍 커밋될 수 있음.
- **DB transport 는 업무 tx 가 biz(txBiz, 기본) tx 매니저일 때만 원자적** — `bizTemplate`(biz DS) 고정 사용. 서비스가 biz 외 tx 매니저(txIF 등)에서만 돌면 INSERT 가 그 tx 에 합류 못함(별도 biz 커넥션→autocommit/비원자 위험). 기본 서비스는 txBiz 라 정상.
- **병렬 실행(`ParallelExecutionScope`) 태스크에서 createMsg 금지** — 병렬 워커 스레드엔 활성 tx 없음 → `isActualTransactionActive()==false` → fail-fast.
- → **파일럿 및 권장 사용은 단일(biz) tx 서비스, 비병렬**. 멀티 tx 부분커밋 서비스에서의 dmom 사용은 위 동작 숙지 후.

**미해결:**
1. `MessageSerializer` DATA_TP 패딩·null 의 **정확한 레거시 규칙** — 레거시 소스 확보 후 테스트로 고정 (Phase 0).
2. `WowContext` 의 task property/입력 Map 접근 API — 기존 cactus Wow 구현 컨벤션 확인 (Phase 0).
3. `IF_SEQ` DB 채번 방식(테이블 DEFAULT/시퀀스 존재 여부) Phase 0 확인 — 없으면 DEFAULT 추가 또는 NULL 허용.
