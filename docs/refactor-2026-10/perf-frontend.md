## P1. MessageProvider context 값 고정
- 관련 구조 변경: 없음(구조 변경이 아니므로 S 에 넣지 않았다)
- 지표(횟수): 모달을 열고 닫을 때 `useMessage` 를 쓰는 memo 소비자의 다시 그리기 횟수. 편차가 없는 결정적 지표라 1회로 충분하다.
- 측정 절차: 기준 커밋과 변경 커밋에서 `src/frontend/shared/tests/unit/message-provider-stable-value.unit.test.ts` 와 같은 방식으로 렌더 횟수를 센다. 기준 워크트리에는 해당 시험 파일이 없으므로 같은 코드를 임시로 복사해 돌린다(커밋 안 함).
- 기준 커밋: refactor-2026-10-base / 변경 커밋: 46b21c9b(시험 정리 e0f3fa54)
- 측정 환경: 시험 결과로 이미 확인된 사실이다. 단독 측정이 필요 없다.
- 영향 범위: `useMessage` 를 import 하는 파일은 64개다(시험·정의 파일 포함, `grep -rlE useMessage src/frontend`, node_modules·dist 제외, 2026-10-04).

## P2. m-mdm 빌드 시간·메모리
- 관련 구조 변경: S2
- 지표: 콜드 빌드 시간(초)·최대 RSS(GB), 증분 빌드 시간(초)·최대 RSS(GB)
- 측정 절차:
  1. 기준 워크트리(refactor-2026-10-base)와 변경 워크트리를 각각 둔다. 둘 다 shared 를 먼저 빌드한다.
  2. 각 워크트리의 `m-mdm` 폴더에서 `/usr/bin/time -l pnpm build` 를 잰다.
  3. 콜드: `m-mdm/dist` 와 lib-dev 캐시(`m-mdm/node_modules/.cache/`, `scripts/lib-dev.mjs` 의 `cacheDir`, `.tsbuildinfo` 포함)를 지운 뒤 1회 잰다.
  4. 증분: 소스 변경 없이 콜드 직후 바로 1회 더 잰다.
  5. 기준(A)과 변경(B)을 A·B·A·B 로 번갈아 각 3회 이상 재고, 회차마다 `uptime` 의 load 를 남긴다. 결론은 중앙값으로 낸다.
- 기준 커밋: refactor-2026-10-base / 변경 커밋: e8cd73b3(문서 ccbcfa10, 머지 4f335f12)
- 측정 환경: 단독 여부, 전원 연결, 측정 일시를 기록한다(비워 둠).
