## P2. m-mdm 빌드 시간·메모리
- 관련 구조 변경: S2
- 지표: 콜드 빌드 시간(초)·최대 RSS(GB), 웜(증분) 빌드 시간(초)·최대 RSS(GB). RSS 는 `/usr/bin/time -l` 의 maximum resident set size(자식 가운데 가장 큰 단일 프로세스)를 10⁹ 으로 나눈 값이다.
- 측정 절차(스크립트로 돌렸다):
  1. 측정용 워크트리 두 개를 detached 로 둔다. 기준 A 는 refactor-2026-10-base(b557ccbd), 변경 B 는 dev(efb39f2c)다. 둘 다 `pnpm install --offline --frozen-lockfile` 뒤 shared 를 먼저 빌드한다(재지 않음).
  2. 각 워크트리의 `m-mdm` 폴더에서 `LIB_DEV_FORCE_BUILD=1 /usr/bin/time -l pnpm build` 를 잰다(dev watch 가 있어도 직접 빌드하게 한다).
  3. 콜드: `m-mdm/dist`, `m-mdm/node_modules/.cache/`(lib-dev 지문·tsc 빌드 정보), `m-mdm/*.tsbuildinfo` 를 지운 뒤 잰다. OS 페이지 캐시는 sudo 없이 비울 수 없으므로, 본 측정 전에 A·B 를 한 번씩 빌드해 버리는 예열로 양쪽을 맞춘다.
  4. 웜: 아무것도 지우지 않고 콜드 직후 바로 한 번 더 잰다.
  5. 본 측정 4회. 홀수 회차는 A→B, 짝수 회차는 B→A(ABBA)로 번갈아 순서 편향을 줄인다. 빌드마다 직전 `uptime` load 를 남기고, load(1분)가 5 를 넘은 쌍은 버리고 다시 잰다. 결론은 중앙값으로 낸다.
- 기준 커밋: refactor-2026-10-base(b557ccbd) / 변경 커밋: dev efb39f2c(6번 본체 e8cd73b3, 문서 ccbcfa10, 머지 4f335f12 포함)
- 측정 환경: 2026-10-04 12:18:06~12:22:36, 조정 세션이 다른 레인의 새 무거운 명령을 멈춘 상태에서 `heavy.sh --exclusive` 로 단독 실행, 전원 연결(AC). MacBook Air M5(팬 없음).
- 버린 측정: 예열의 A 콜드 1회(load 5.08). 다시 잰 값은 load 2.90 이었다.

- 중앙값:
  - 콜드 시간: 기준 15.23초 → 변경 4.14초 (-73%)
  - 콜드 RSS: 기준 3.35GB → 변경 0.67GB (-80%)
  - 웜 시간: 기준 15.52초 → 변경 1.51초 (-90%)
  - 웜 RSS: 기준 3.12GB → 변경 0.46GB (-85%)
- 판정: 개선. 두 쪽의 범위가 겹치지 않는다(콜드 기준 12.84~17.12초, 변경 3.54~4.84초). 모든 빌드가 성공(rc 0)했다.
- 해석:
  - 기준은 웜이 콜드와 거의 같다. tsup 의 rollup-plugin-dts 는 진입점마다 처음부터 묶고 증분이 없기 때문이다. 변경은 tsc 증분(빌드 정보 `node_modules/.cache/lib-dev-dts.tsbuildinfo`) 덕분에 웜이 1.5초다.
  - 변경 커밋은 dev 이므로 6번 밖의 변경(2·3·4번 등)도 섞여 있다. 그래도 기준의 웜이 콜드와 같다는 점에서, 차이의 대부분은 .d.ts 생성 방식에서 온다고 본다.
  - 회차가 지날수록 A·B 모두 조금씩 느려졌다(팬 없는 기기의 열 영향으로 본다). ABBA 순서라 비교 결론은 바뀌지 않는다.
- 측정 전 비공식 참고값(결론에 쓰지 않음): 리뷰 때 부하 아래에서 잰 값이다. lib-dev `build --force` 1.75초·RSS 0.47GB, tsc 처음부터 8.1초·RSS 0.68GB.
