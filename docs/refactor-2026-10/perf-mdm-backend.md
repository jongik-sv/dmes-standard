#### 측정 방법

PC 부하가 측정마다 크게 달라 전후 커밋을 따로 잰 값은 비교할 수 없었다(아래 "참고 — 전후 커밋을 따로 잰 첫 측정" 소절). 그래서 한 JVM 안에서 두 경로를 번갈아 재어 부하 변화가 양쪽에 똑같이 걸리게 했다.

- PC: MacBook Air M5(팬 없음, P4+E6, 16GB), JDK 21.0.12.1, 코어 10.
- 시험: `RuleSetPrepareBenchTest`. `MDM_BENCH` 가 있을 때만 돈다.
- 명령: `MDM_BENCH=1 JAVA_HOME=/opt/homebrew/opt/openjdk@21/libexec/openjdk.jdk/Contents/Home ../gradlew test --rerun --tests '*RuleSetPrepareBenchTest' --console=plain -i` (`src/backend/maru-mdm-engine` 에서 실행)
- 세트 정의: 룰 9개·노드 17개다. 샘플 LS_A3 의 BASE_SPD_LKP → SPD_EXC(COLLECT) → SPD_JOIN 뒤에 IF·PARALLEL·INPUT_ERROR 받기를 붙였다. 4행 중 1행은 받는 노드로 간다. 평가기는 시험 설정이다.
- 반복: 1,000행 × 세트 N개(N=1·5·20, ID 만 다르다). 예열 3회 뒤 9회를 잰다.
- 세 경로를 **100행 블록마다 번갈아** 잰다. 블록마다 순서를 돌린다(A→B→C, B→C→A, C→A→B …). 한 회차의 각 경로 시간은 블록 시간의 합이다.
  - **A(기억 적중)**: 지금 조회기를 쓰는 엔진이다. 같은 세트 정의 객체가 와서 기억이 적중한다. 운영 cactus `MdmValidator` 처럼 오래 사는 엔진에 해당한다.
  - **B(기억 놓침)**: 감싼 조회기(`FreshSetLookup`)를 쓰는 별도 엔진이다. `ruleSet()` 을 부를 때마다 값이 같은 새 `RuleSetDefinition` 사본을 돌려준다.
    - 엔진은 세트 정의 객체 동일성(`MdmRuleEngine.cachedPlan` 의 `p.set == set`)으로 기억을 고르므로 B 는 매번 놓친다. 매 호출 흐름 파싱과 `new FlowKeys` 를 한다.
    - 룰 조회는 원래 조회기에 넘기므로 A 와 같은 룰 정의 객체를 받는다.
    - A 와 B 는 엔진을 따로 둔다. 한 엔진이면 B 가 넣은 준비가 A 의 기억을 덮어쓴다.
  - **C(준비 몫 기준값)**: 같은 호출 수만큼 `FlowParser.parse` 와 `new FlowKeys` 만 한다. 기억으로 아낄 수 있는 몫의 같은 시각 값이다.
- 시험은 재기 전에 두 경로가 정상 판정이고 결과가 같음을 확인한다. 세트마다 8행에서 `assertEquals(A 결과, B 결과)` 이고, 4행 중 1행은 받은 오류가 1건이다.
- B 는 바꾸기 전(`262ca6df`) 비용보다 조금 크다. 그래서 B − A 는 실제 절약보다 조금 크게 나온다.
  - B 에만 더 드는 것: 세트 정의 사본 생성, 룰 정의 snapshot(`LinkedHashMap` 복사·읽기 전용 감싸기), 기억 `ConcurrentHashMap.put`.
  - A·B 모두 드는 것: 판정마다 `FlowKeys.forRun` 사본이다. 바꾸기 전에는 이 비용이 없었다.
  - 그러므로 실제 절약(바꾸기 전 − 바꾼 뒤)은 대략 C 에서 `forRun` 비용을 뺀 값이고, B − A 보다 작다.
- 회차마다 1분 load average(`OperatingSystemMXBean.getSystemLoadAverage`)를 찍는다. 다른 레인 세션들의 gradle 이 함께 돌았다.
- 같은 시험을 2번 돌렸다(1차 09:02~09:06, 2차 09:08~09:12, 2026-10-04).

#### 해석

- 같은 조건에서 기억 적중(A)이 놓침(B)보다 54회 모두(2번 × N 3가지 × 9회) 빨랐다. 방향은 확정이다.
- 크기: 짝 차이 중앙값은 호출당 13~41µs 이고, A 의 4~10% 다.
  - 같은 시각 기준값 C(파싱 + `new FlowKeys`)는 15~25µs 다. 짝 차이는 C 와 같은 자릿수이고 대체로 조금 크다. B 에만 드는 사본·snapshot·put 비용이 더해진 결과로 보인다.
  - 회차별 짝 차이는 1.4~102.7µs 로 흩어진다. 그래서 퍼센트 하나로 못 박지 않는다.
- 실제 절약(바꾸기 전 − 바꾼 뒤)은 B − A 보다 작다. 대략 C 에서 `forRun` 비용을 뺀 값이다. 그러므로 호출당 C(15~25µs, 같은 회차 A 중앙값의 4.7~5.4%)보다 조금 작다고 본다. 판정 비용의 대부분은 식 평가다.
- 판정: 개선은 측정으로 확인됐다. 크기는 판정 한 번에 수십 µs 이하로 작다.
  - 운영(cactus MdmValidator)처럼 오래 사는 엔진에 같은 세트·룰 정의 객체가 계속 오면, 세트 판정 한 번마다 파싱과 검사기 생성이 빠진다.
  - mdm 쪽 `StoredDefinitionLookup` 은 판정 시각마다 새 세트 객체를 만든다. 그래서 시각이 다른 호출끼리는 적중하지 않고 B 와 같은 비용이 든다.


#### 참고 — 전후 커밋을 따로 잰 첫 측정(조건이 달라 결론에 쓰지 않음)

- 처음에는 `262ca6df`(바꾸기 전)와 `d56dde59`(바꾼 뒤)를 각각 2번씩, 다른 시간대에 쟀다.

- 정의 객체 동일성을 키로 쓴다. 정의 객체를 만든 뒤 그 안의 List·Map 을 고치는 생산자가 있으면 옛 트리를 다시 쓰게 된다.
