### 공통 원칙 (MUST)
- DB 컬럼명은 대문자 SNAKE_CASE (`ORDER_NO`), 화면 표시명은 한글, API JSON은 camelCase 3계층 표기를 지킨다.
- 기능/디자인/BPMN 3종 설계서는 **화면 식별자·필드ID·버튼ID·팝업ID·DB 컬럼·상태코드·action** 이 일치 키로 정합되어야 한다.
- 설계 결정이 개발가이드와 충돌하면 **개발가이드를 따른다**. 불일치는 설계서 §11 특이사항에 기록.

**원칙 (MUST)**
- 설계서 작성 시 위 자료를 **근거로 명시**한다 (예: "참조: `tables/MES_WORK_ORDER.sql`", "참조: `procedures/USP_WORK_ORDER_SAVE.sql`").
- 기존 ERP에 동일/유사 기능이 존재하면 **As-Is 분석 → To-Be 설계** 순서를 따른다.
- 기존 자료와 설계가 달라야 할 경우 §11 특이사항(또는 §10 검증·이슈)에 **차이와 사유를 명시 기록**한다.
- 위치 미확인 상태에서 추정으로 설계하지 않는다.

### 설계 산출물 저장 위치 (MUST)

본 가이드로 작성한 설계 산출물은 **모듈(체인)별 폴더로 분리하여 저장**한다. 한 화면당 기능/디자인/BPMN 3종 산출물이 같은 모듈 폴더 내에서 동일 `{화면식별자}` prefix 로 묶여야 한다.

**저장 규칙**
- 위치: `docs/{moduleId}/design/{화면식별자}/` — **화면별 하위 폴더** 아래에 3종 산출물(기능/디자인/BPMN)을 함께 저장한다. (MUST)
- **폴더 미존재 시 자동 생성** (Agent가 산출물을 작성하기 전에 `docs/{moduleId}/design/{화면식별자}/` 폴더 존재 여부를 먼저 확인하고, 없으면 생성한 뒤 저장한다)
- 파일명: `{화면식별자}_기능설계서.md`
- 절대경로 예: `docs/mqc/design/inspectionResult/inspectionResult_기능설계서.md`

**moduleId 산출 규칙**
- 화면이 속한 **모듈 식별자** (`mls`, `mqc`, `mpp`, `aps`, `mas`, `mes`, `master`) 를 그대로 사용 — §A.2-0-1 체인 사전 참조
- 모듈은 **화면 식별자에 포함되지 않으므로** §A.2-2-1 "모듈" 행 또는 저장 경로에서 표현된다

**모듈 예시**
| 모듈 | moduleId | 화면 식별자 예 | 산출물 절대경로 예 |
|---|---|---|---|
| 자재/주문 | `mls` | `orderRegistration` | `docs/mls/design/orderRegistration/orderRegistration_기능설계서.md` |
| 품질 | `mqc` | `inspectionResult` | `docs/mqc/design/inspectionResult/inspectionResult_기능설계서.md` |
| 생산실적 | `mpp` | `workReport` | `docs/mpp/design/workReport/workReport_기능설계서.md` |
| 생산계획 | `aps` | `productionPlan` | `docs/aps/design/productionPlan/productionPlan_기능설계서.md` |
| 마스터 | `master` | `item` | `docs/master/design/item/item_기능설계서.md` |
| 시스템 | `mes` | `user` | `docs/mes/design/user/user_기능설계서.md` |

**한 화면당 산출물 3종 (같은 `{화면식별자}/` 폴더에 함께 저장)**
- `{화면식별자}_기능설계서.md` — 본 가이드(01) Part B 템플릿 기반
- `{화면식별자}_디자인설계서.md` — 02 가이드 Part B 템플릿 기반

### 개발체크리스트 (6번째 산출물 — 개발 단계 진입 시 생성, MUST)

설계 5종(분석리포트 + 기능/디자인/BPMN + 정합체크)이 완료되어 **라우터 분기 3 (MES 개발, [`Mes-Guide.md`](../../MES/Mes-Guide.md) §3)** 으로 진입할 때, 해당 화면의 **개발 진행 체크리스트** 를 6번째 산출물로 생성한다. "설계서 보고 알아서 개발" 을 막고 **실제 개발 단위마다 객관적 증거(빌드/테스트 로그)로 완료를 판정** 하기 위한 장치다.

**저장 규칙 (MUST)**
- 위치: **5종 설계 산출물과 동일한 화면 폴더** (`docs/{moduleId}/.../{화면식별자}/`). 별도 폴더 생성 ✗.
- 파일명: **`{화면식별자}_개발체크리스트.md`** (예: `plateSlittingMgmt_개발체크리스트.md`)
- 템플릿: [`templates/개발체크리스트.template.md`](../templates/개발체크리스트.template.md) 단일 정본.

**생성 규칙 (MUST)**
- 단일 원천 = **같은 폴더의 5종 설계 산출물**. 설계서에 없는 요구사항을 체크리스트에 임의 추가하지 않는다 (필요 시 설계로 환송 → 정합체크 재통과 → 체크리스트 갱신).
- 구조: §0 운영 규칙 → §1 선행 결정 게이트(P0 차단) → §2 BE 기반 → §3 BE 서비스·BPMN → §4 검증·비즈니스 규칙 → §5 FE → §6 정합·회귀 게이트(= 정합체크 §K) → §7 변경 이력.
- §1 선행 결정 게이트는 정합체크서 §G(확인필요 집계)·§K(코드 구현 정합) 와 설계서 4종 간 충돌을 그대로 추출한다. open Q-NNN·정합 불일치가 있으면 [`Mes-Guide.md`](../../MES/Mes-Guide.md) §4 "개발 진입 가드" 표에 따라 **사용자 결정 전 구현 진입을 차단**한다.
- 각 체크 항목은 `근거(설계서 출처) / DoD(객관적 완료 정의) / 검증(실행 명령 + 로그)` 3요소를 갖는다. **검증 로그 없이 `[x]` 금지.**
- `/implement <ITEM-ID>` · `/progress` · `/check` 스킬과 연동한다.

**정합 검증 대상에서 제외 (중요)**
- 개발체크리스트는 **개발 단계 산출물** 이며, 정합체크서가 검증하는 **"4종 설계 산출물(분석/기능/디자인/BPMN)"·"5종 산출물" 집계에 포함되지 않는다.** 정합체크 §A 누락검증·§E.2 templates drift 의 "5종/4종" 카운트에 본 산출물을 더하지 않는다 (별도 6번째 산출물로 취급).

# Part A. 설계 표준 규칙

## A.1. 문서 사용 규칙

### A.1-0. 적용 범위 (매우 중요 · MUST)

본 가이드는 **MES 하위 업무 모듈**(MLS · MPP · MQC · MAS · 시스템 MES 등)의
화면 설계에만 적용한다. 아래 대상은 본 가이드의 적용 범위가 **아니다**:

| 대상 | 적용 가이드 | 체계 |
|---|---|---|
| **APS** (공정계획) — `src/backend/{aps-core, mpn}`, `src/frontend/m-mpn` | [`docs/aps/Aps-Guide.md`](../../../aps/Aps-Guide.md) | 구 체계 (Phase 1~6 기반 TDD) |
| MES 하위 업무 모듈 | **본 3종 설계가이드** + [`docs/guide/MES/Mes-Guide.md`](../../MES/Mes-Guide.md) | 신 체계 (마이그레이션) |

- **APS 화면은 본 가이드로 설계하지 않는다.** APS 관련 작업은 별도의 [`docs/aps/Aps-Guide.md`](../../../aps/Aps-Guide.md) 를 따른다. (MUST NOT)
- 한 PR 에 APS 와 MES 가 섞이면 섹션별로 각 가이드를 분리 적용한다. 임의로 한쪽 규칙을 반대쪽에 적용 금지. (MUST NOT)
- 식별 규칙: 화면 식별자 prefix 가 `APS_` 이거나 경로가 `src/backend/{mpn, aps-core}` / `src/frontend/m-mpn` 면 Aps-Guide 대상. 그 외 MES 모듈 경로이면 본 가이드 대상.

#### "MES" 라는 단어의 중의적 사용 — 반드시 구분 (MUST)

| 표기 | 의미 | 사용 예 |
|---|---|---|
| **프로젝트 MES** (대문자, 고유명사) | 전사 ERP → 신규 MES 마이그레이션 프로젝트 전체 | 본 가이드 line 5 "신규 MES 마이그레이션" |

두 의미가 같은 문서에 공존하므로 설계서 작성 시 문맥으로 구분한다. 애매한 경우 "프로젝트 MES" / "moduleId `mes`" 처럼 병기한다.

### A.1-1. 규칙 등급
| 등급 | 의미 |
|---|---|
| MUST | 반드시 지켜야 하는 규칙 |
| SHOULD | 특별한 사유가 없으면 따라야 하는 규칙 |
| MAY | 필요한 경우 선택적으로 적용할 수 있는 규칙 |

### A.1-2. 기본 원칙
- 기능설계는 **"이 화면이 무엇을 하는가(WHAT)"** 를 정의한다. "어떻게 보이는가"는 디자인설계, "어떻게 동작하는가"는 BPMN 설계에서 다룬다.
- 기능설계서는 **화면 단위**로 작성한다. 하나의 화면 식별자에 하나의 기능설계서가 대응한다.
- 설계는 **코드 수준**이 아닌 **명세 수준**에서 작성한다. 실제 SQL/함수 시그니처는 금지한다.
- 표준 템플릿(Part B) 밖의 섹션을 임의 추가하지 않는다. 필요 시 §11(특이사항)에 기록한다.
- **[마이그레이션 원칙]** 본 프로젝트는 마이그레이션이므로 설계는 아래 입력 자료들을 교차 참조하여 작성한다.
  1. **화면 캡처** (As-Is 화면) — 조회조건/그리드/버튼의 실제 요소 *(SHOULD — 있으면 정확도 크게 향상, 없으면 As-Is 소스 + 테이블 설계서로 대체 가능)*
  2. **As-Is 테이블 설계서** — 기존 시스템의 컬럼·제약·관계 (MUST)
  3. **To-Be 테이블 설계서** — 신규 MES의 컬럼·제약 (매핑 대상) (MUST)
  4. **기존 소스 코드** — 비즈니스 로직·상태 전이 규칙·검증 규칙의 숨은 로직 (MUST)
- 자료 2~4 중 **하나라도 누락된 상태로 설계 시작 금지**. (MUST NOT)
- 자료 1(캡처) 누락 시 §11 에 "캡처 미제공 — 소스 기반 추정" 명시 + 추정 항목에 `[확인필요]` 마커 부여 (MUST)
- 자료 간 불일치 발견 시 `[확인필요]` 마커 + §11 특이사항 기록. (MUST)

### A.1-2-1. Agent 의사결정 원칙 (MUST)

본 프로젝트의 설계서는 Agent 가 작성한다. Agent 가 사용자에게 결정을 묻기 전에, 본 가이드의 **MUST/MUST NOT 으로 이미 답이 정해진 항목** 과 **진짜 가이드 공백** 을 분리해야 한다. **MUST/MUST NOT 항목을 트레이드오프 선택지로 사용자에게 제시하면 가이드 위반의 책임을 사용자에게 전가하는 것이며, 이는 금지된다. (MUST NOT)**

#### A.1-2-1-1. 묻지 말고 가이드 기본값을 채택해야 하는 항목 (MUST — 카탈로그)

### A.1-3. 작성 순서

**0. As-Is 자료 전수 분석 (Phase 0 — MUST)**
   - As-Is 소스(컨트롤러/SQL/designer.cs) + 테이블 설계서 전수 확보 (MUST). 화면 캡처 / 운영 인터뷰 자료는 있으면 추가 확보 (SHOULD)
   - 조회조건 필드 **전수** 식별 (몇 개인지 명시)
   - 그리드 컬럼 **전수** 식별 (**가로 스크롤 영역 포함**)
   - 버튼 **전수** 식별 (아이콘 + 텍스트)
   - 상태/플래그 표기 및 색상 규칙 확인 (초도품 Y, 진행상태 뱃지 등)
   - 다중 그리드 / 탭 / 팝업 / 하위 화면 존재 여부 확인
   - **읽히지 않거나 불명확한 항목은 추측 대신 `[확인필요]` 마커로 표기 (§A.6-1)**

1. 화면 식별자·모듈·주 사용자 확정 (§A.2 시작 전 결정 항목)
2. 화면 영역 정의 (A-FILTER / A-GRID / A-DETAIL / A-BTN — 필요 시 A-TOOLBAR, 다중 그리드)
3. 조회조건·조회결과 필드 정의 (§A.5 명명 규칙 적용) — **전수 반영 MUST**
4. 상세 영역 필드 정의 (폼 / 서브그리드 / **그리드 인라인 편집** 중 선택)
5. 버튼 및 동작 정의 (케이스 선택표 §A.10 참조)
6. 입력값 검증 규칙 정의
7. 상태 정의·상태 전이·상태별 제어 정의 — **다계층 중첩 가능성 검토 MUST**
8. 권한 정의
9. 연동 화면/팝업 정의
10. BPMN/디자인 설계서 연계 확인 (§A.9)

### A.1-4. 정합성 체크 (Consistency Check) — 용어 정본 (MUST)

본 프로젝트·본 가이드에서 **"정합성 체크"** 또는 **"정합 체크"** 라고 부르는 절차는 아래 세 층위의 **여러 산출물이 서로 어긋나지 않는지 일치 키 기준으로 교차 확인**하는 작업을 뜻한다. 맥락에 따라 셋 중 하나 이상을 가리킨다.

#### A.1-4-1. 3종 설계서 간 정합성 (가장 기본)
화면 단위로 **기능설계서 / 디자인설계서 / BPMN설계서 3종이 동시 산출**되며, 아래 **일치 키** 가 세 문서 모두에서 동일해야 한다. (MUST)

| 일치 키 | 기능 | 디자인 | BPMN |
|---|---|---|---|
| 화면 식별자 | §1 | §1 | §1 |
| 필드ID (S-/G-/D-/L-) | §3, §4 | §3, §4 | §2 payload |
| 버튼ID (B-) | §5 | §3.4 | §1.1, §2 |
| 팝업ID (P-) | §9 | §6 | - |
| DB 컬럼명 | §3, §4 | §4 | §2, §4.2 |
| 상태코드 | §7 | - | §2.7, §4.1 |
| action / serviceId | §5 | - | §1.1, §2 |

- 하나라도 어긋나면 개발 시 매핑이 깨진다. 설계서 작성 완료 시 본 표로 **크로스 체크** 필수. (MUST)
- 기능설계서 §A.9(연계/정합 확인) · 디자인 §A.7 · BPMN §A.7 에 정합 확인 표를 둔다.

#### A.1-4-2. 설계 ↔ 구현 정합성 (개발 진입 시)
설계서의 이름 체계가 **구현 계층**까지 동일 루트로 이어져야 한다. (MUST)

```
DB 컬럼 (SNAKE_CASE)  ↔  JPA Entity @Column(name=...)  ↔  DTO (camelCase)  ↔  FE apiRequest payload
ORDER_NO             ↔  @Column(name="ORDER_NO")       ↔  orderNo           ↔  { orderNo: ... }
```

- **3자 일치** 규칙 (§A.5-4-3): 저장 Body 최상위 키 = 서버 DTO 필드명 = FE 전송 키.
- 위반 시 FE → BE 매핑 실패 → 런타임 에러 또는 null 직렬화. 컴파일러가 잡지 못한다.

#### A.1-4-3. 화면별 정합체크 산출물 (선택 · SHOULD)
복잡한 화면은 **`{화면식별자}_정합체크.md`** 를 별도 산출물로 남길 수 있다. 예: `docs/mpp/design/workReport/workReport_정합체크.md`.

- 내용: A.1-4-1 + A.1-4-2 를 **행별 체크리스트**로 실증 검증한 리포트.
- 저장: `docs/{moduleId}/design/{화면식별자}/{화면식별자}_정합체크.md`.
- 작성 시점: 설계 3종 완료 직후 또는 구현 착수 직전. (SHOULD)
- 필수는 아니나, 마이그레이션 특성상 As-Is/To-Be/화면/코드 간 어긋날 지점이 많으므로 **복잡 화면**(다단 그리드·상태 전이·부수효과 多)은 강력히 권장.
