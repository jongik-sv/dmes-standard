### A.6-1. `[확인필요]` 마커 사용 규칙

설계 중 운영/업무팀 확인이 필요한 부분은 `[확인필요]` 마커를 사용한다.

- **사용 조건 (MUST)**:
  - 이미지/자료에서 명확히 읽히지 않는 필드/버튼/상태
  - 업무 규칙이 추론 가능하지만 확정 필요한 케이스
  - 연계 모듈의 동작 방식이 추측 단계인 경우
  - 코드값의 실제 영문 문자열이 확정되지 않은 경우
- **금지 (MUST NOT)**:
  - 추측을 `[가정]` 등으로 감추고 그냥 넘어가기
  - 명확한 것을 불필요하게 `[확인필요]` 로 표기
- **관리 원칙 (MUST)**:
  - 모든 `[확인필요]` 항목은 §11 특이사항의 **"미확정 사항 리스트"** 에 전수 집계
  - 각 항목은 **구체적 질문 형태**로 작성 (예: "상태 A와 B의 전이 조건이 무엇인가?", "~가 자동 생성인가 수동 입력인가?")
  - 설계 확정 전 운영 리뷰에서 반드시 해소
- **표기 예시**:
  ```
  | D-005 | ORDER_TYPE | 주문유형 | 드롭다운 | Y | MTO | MTO/MTS/MTPO **[확인필요: 3종 외 추가 유형 존재?]** |
  ```

## A.8. 작성 규칙

### A.8-1. §1 화면 개요
- 화면명/코드/모듈/목적/사용자/접근 경로 6개 항목 모두 채움. (MUST)
- "화면 목적"은 1~2문장. (MUST)

### A.8-2. §2 화면 영역 정의
- 영역ID는 §A.5-2의 `A-` 체계. (MUST)
- 화면에 없는 영역은 표에서 제외. (MUST)

### A.8-3. §3 조회조건/조회결과
- 조회조건 열: `필드ID | DB 컬럼명 | 화면 표시명 | 입력 방식 | 필수 | 기본값 | 설명` (MUST)
- 조회결과 열: `컬럼ID | DB 컬럼명 | 화면 표시명 | 데이터 설명 | 정렬 | 비고` (MUST)
- DB 컬럼 없는 표시 컬럼(순번 등)은 `-`. (MUST)
- 코드값 컬럼은 §3.3 코드값 변환에 반드시 등록. (MUST)

### A.8-4. §4 상세 영역 / 품목 라인
- 열: `필드ID | DB 컬럼명 | 화면 표시명 | 입력 방식 | 필수 | 기본값 | 설명` (MUST)
- 품목 라인은 `§4.2 품목 라인` 서브섹션으로 분리. (MUST)
- 계산 필드(금액 = 수량 × 단가)는 `설명` 에 명시. (MUST)

### A.8-5. §5 버튼 및 기능 동작

#### A.8-5-1. 버튼 목록
- 열: `버튼ID | 버튼명 | 위치 | 설명` (MUST)
- 위치는 §2 영역ID 참조 (예: `A-FILTER 우측`). (MUST)

#### A.8-5-2. 버튼별 동작 상세
```
#### [버튼명] 버튼 (B-NNN)

```
트리거: (클릭/엔터/자동)
선행 조건: (없으면 "-")
동작:
  1. ...
  2. ...
```
```

#### A.8-5-3. 버튼 패턴 카탈로그
화면 유형별 자주 쓰이는 버튼 패턴. 해당 화면에 필요한 패턴을 선택해 반영한다. (SHOULD)

| 패턴 | 대표 버튼 | 언제 사용 |
|---|---|---|
| 기본 CRUD | 조회 / 초기화 / 신규 / 저장 / 삭제 | 단일 레코드 관리 |
| 그리드 행 편집 | 행 추가 / 행 삽입 / 행 복사 / 행 삭제 / 일괄 저장 | 그리드에서 다건 인라인 편집 |
| 상태 전이 | 확정 / 취소 / 반려 / 승인요청 | 상태 기반 워크플로우 |
| **다계층 상태 전이** | 검사완료 / 검사보류 / 검사재시작 / 판정확정 | **3계층 상태 체계**가 있는 화면 (§A.8-7) |
| 팝업 경유 액션 | 배정 / 이관 / 승인 / 특채처리 | 추가 입력 → 팝업 → 저장 |
| 선택 기반 일괄 처리 | 일괄 확정 / 일괄 삭제 | 체크박스 다건 선택 |
| 연계 이동 | 상세 보기 / 생산지시 이동 | 다른 화면 이동 |
| **업무 특화 연계 조회** | 오더자재조회 / 보류이력조회 / QP조회 / 수주명세Note | 현재 선택 건의 **연관 데이터** 를 별도 팝업에서 조회 (읽기만) |
| **업무 특화 연계 편집** | 성적서관리 / 부적합내역조회 | 선택 건의 연관 데이터를 **별도 화면**으로 이동하여 편집 |
| **분할/합치기** | 검사분할 / 주문 통합 / 공정 분리 | 한 건을 여러 건으로 쪼개거나 합침 |
| 파일 I/O | 엑셀 다운 / 엑셀 업로드 / 템플릿 다운 / 인쇄 | 파일/출력 |
| 재조회 | 새로고침 | 조회조건 유지 재조회 |

> **업무 특화 버튼 설계 원칙**:
> - As-Is 화면의 업무 버튼은 **이름을 그대로 유지** (오더자재조회 → 오더자재조회). 현업이 익숙한 용어 존중.
> - 각 업무 특화 버튼은 **트리거 / 선행 조건 / 반환 데이터 / 연관 API-ID** 를 §5.2에 명시.
> - 업무 특화 버튼이 10개 넘으면 A-TOOLBAR 영역 분리 검토 (디자인설계 §A.3-2).

### A.8-6. §6 입력값 검증 규칙
- 필드별(§6.1) 열: `규칙ID | 대상 필드 | 검증 내용 | 에러 메시지` (MUST)
- 대상 필드는 `DB 컬럼명 (필드ID)` 병기. (MUST)
- 에러 메시지는 **사용자 노출 한글 문구**. (MUST)
- 연관 검증(§6.2)은 `ORDER_TYPE='MTO' AND DUE_DATE < ORDER_DATE + 14일` 조건식. (MUST)
- §6.3 검증 실행 순서 반드시 명시. (MUST)

### A.8-7. §7 상태 정의
- 상태 표 열: `상태코드 | 한글명 | 설명 | 수정 가능 | 삭제 가능` (MUST)
- 전이 규칙은 `WAIT → CONF` 화살표 형식. (MUST)
- 상태별 필드 편집 표 + 버튼 활성 표 **모두** 포함. (MUST)

#### A.8-7-1. 다계층 중첩 상태 체계 (MUST 검토)

실제 업무는 단일 계층 상태만으로 표현 불가한 경우가 있다. 다음 조건 중 **하나라도 해당되면 다계층 상태**로 설계한다.

- 전체 프로세스 단계(예: 미검사 / 검토중 / 판정)와 세부 진행 상태(예: 진행 / 보류 / 재시작 / 완료)가 **독립적으로 전이**되는 경우
- 최종 결과(예: 합격 / 불합격 / 특채)와 결과 확정 상태(예: Release완료 / Release보류)가 **별개 축**인 경우
- 상태 전이 규칙이 단일 DAG(방향 그래프)로 표현 불가능하고 복수 DAG가 필요한 경우

**다계층 설계 예시 (검사결과등록)**:

| 계층 | 상태 컬럼 | 값 | 축의 의미 |
|------|-----------|-----|----------|
| 1 | INSPECTION_STATUS | 미검사 / 검토중 / 판정 | 전체 프로세스 진행도 |
| 2 | PROGRESS_STATUS | 진행 / 보류 / 재시작 / 완료 | 검사 작업 자체 진행 상태 |
| 3 | JUDGMENT | 합격 / 불합격 / 특채 | 최종 판정 결과 |
| 3' | JUDGMENT_STATUS | Release완료 / Release보류 | 판정 확정 상태 |

- 각 계층은 **독립 전이 규칙**을 가진다. (MUST)
- 계층 간 연동(예: 계층2의 '완료' + 계층3의 '합격' 확정 시 계층1이 '판정'으로 자동 전환)은 **별도 표** 로 명시. (MUST)
- 다계층 상태 시 BPMN 설계서에서도 **계층별 API 엔드포인트 분리**. (MUST)
- 다계층 설계 이유를 §11 특이사항에 기록. (SHOULD)

**단일 계층 유지 조건 (MUST NOT 다계층화)**:
- 상태 전이가 선형(A→B→C)이고 분기/중복 없음
- 업무 요구사항에 "여러 축의 독립 진행" 표현이 없음
- → 이 경우 억지로 다계층화 금지

### A.8-8. §8 권한 정의

- **표 축 (MUST)**: **행 = 기능, 열 = 역할**. 화면 간 비교·정합 검증 시 형태 일관성을 위해 축을 뒤집지 말 것. (예: "조회 / 신규등록 / 수정 / 삭제 / 상태 변경" 등이 행, "ADMIN / MANAGER / USER" 등이 열)
- **역할 열 순서 (MUST)**: 권한이 큰 것부터 작은 것 순. (예: `ADMIN → MANAGER → USER`, 도메인 역할은 `QC_MANAGER → QC_INSPECTOR` 식)
- **셀 값 (MUST)**: `O` (허용) / `X` (거부) / `△` (조건부 — 비고 열에 조건 명시 필수). 그 외 표기 금지.
- **기능 행 (행 라벨, MUST)**: §5.1 버튼 또는 데이터 동작 단위. 버튼ID 가 있는 경우 `(B-NNN)` 같이 병기 가능. (예: `조회 (B-001)`, `저장 (B-003)`)
- **기본 역할**: `ADMIN / MANAGER / USER` 3종. (SHOULD) — 도메인 특화 역할(예: `QC_MANAGER`, `QC_INSPECTOR`, `POMGR`, `POUSER`)을 추가하거나 대체 가능.
- **조건부 권한** (`△`): 비고 열에 조건을 명시. (MUST) — 예: `INSP_CLASS_CD ∈ {M,O} 인 경우만 활성`.
- **필드/컬럼 가시성 권한** (예: `BP_NM` 표시 여부): 별도 행으로 추가 — 행 라벨에 `(필드ID)` 또는 `(컬럼ID)` 병기. (예: `BP_NM 표시 (G-016, D-014)`)

### A.8-9. §9 연동 화면/팝업
- 팝업은 `P-` 체계. (MUST)
- 주고받는 데이터는 `보내기: X / 받기: Y` 형식, 영문 DB 컬럼명. (MUST)

### A.8-10. §10 기타 열거형
- §3.3과 범위 겹치면 중복 허용. (MAY)
- 열 헤더: `열거형 (DB 컬럼) | 코드값 | 화면 표시명 | 설명` (MUST)

### A.8-11. §11 특이사항

**마이그레이션 프로젝트 필수 기록 항목** (MUST):

1. **As-Is → To-Be 매핑 요약**: 주요 필드/상태/로직의 변경점
2. **마이그레이션 전환점**: 신규 추가 필드 / 제거된 As-Is 필드 / 이름 변경
3. **기존 소스와 의도적으로 달라진 로직**: 변경 이유 명시
4. **발견된 As-Is 제약/버그**: To-Be에서 개선한 부분
