# 원칙과 산출물 게이트

> 상위 문서: [최우선 원칙, 게이트, Auto Manifest](../01-principles-gates-manifest.md)

## 0. 최우선 원칙

Claude는 설계서부터 작성하지 않는다.

반드시 아래 순서를 지킨다.

```text
1. 분석리포트 작성
2. 분석완료 게이트 통과 여부 판정
3. 기능설계서 작성
4. 디자인설계서 작성
5. BPMN설계서 작성
6. 정합체크서 작성
7. 확인필요 항목 집계
```

분석리포트 없이 기능/디자인/BPMN 설계서를 먼저 작성하는 것은 금지한다.

## 0.1 표준 산출물 생성 게이트

Claude는 설계서를 자유 생성하지 않는다.
본 지시서, 부속서, 템플릿을 기준으로 정해진 절차에 따라 산출물을 생성한다.

### 0.1.1 최상위 실행 규칙

Claude는 다음 규칙을 반드시 따른다.

| # | 규칙 | 처리 |
|---:|---|---|
| 1 | `00_Agent지시_가이드`는 최상위 실행 지시로 적용한다. | MUST |
| 2 | 5개 템플릿 파일은 절대 변경 불가 원본으로 사용한다. | MUST |
| 3 | 분석리포트 작성 전에는 기능설계서, 디자인설계서, BPMN설계서를 작성하지 않는다. | MUST NOT |
| 4 | 기능설계서, 디자인설계서, BPMN설계서는 분석리포트의 표를 기준으로 파생 작성한다. | MUST |
| 5 | 분석리포트에 없는 조회조건, 그리드 컬럼, 버튼, 팝업, 상태값, action을 임의 추가하지 않는다. | MUST NOT |
| 6 | 정합체크서 §A / §B / §C / §D / §E / §F / §H / §I / §J 및 §D.4 12 행 중 하나라도 ✗이면 설계 완료로 판정하지 않는다. | MUST NOT |
| 7 | 동일 As-Is 자료로 반복 생성 시 S-NNN, G-NNN, B-NNN, P-NNN, statusCodes, action 목록이 동일해야 한다. | MUST |
| 8 | 확정 불가능한 항목은 추정하지 않고 `[확인필요: Q-NNN]`으로 등록한다. | MUST |

### 0.1.2 템플릿 잠금 규칙

Claude는 다음 템플릿을 산출물의 단일 정본으로 사용한다.

| 산출물 | 템플릿 |
|---|---|
| 분석리포트 | `분석리포트.template.md` |
| 기능설계서 | `기능설계서.template.md` |
| 디자인설계서 | `디자인설계서.template.md` |
| BPMN설계서 | `BPMN설계서.template.md` |
| 정합체크서 | `정합체크서.template.md` |

다음 항목은 변경할 수 없다.

| 항목 | 규칙 |
|---|---|
| frontmatter 6개 필드 | 삭제, 추가, 이름 변경 금지 |
| 절 순서 | 템플릿 순서 유지 |
| 표 헤더 | 컬럼명, 컬럼 수, 컬럼 순서 변경 금지 |
| “해당 없음” 문구 | 적용 대상이 없어도 절과 표를 삭제하지 않음 |
| 임의 섹션 | 템플릿 외 `##` 헤더 추가 금지 |
| 자유 서술 | 템플릿에서 허용한 위치에만 작성 |

> **개발체크리스트(6번째 산출물)는 위 잠금 규칙 대상이 아니다.** `templates/개발체크리스트.template.md` 는 **설계 완료 후 개발 단계(분기 3)** 에서 생성하는 별도 산출물의 템플릿이며, 위 §0.1.2 표의 "단일 정본 5종"·frontmatter 6필드 잠금·절 순서 잠금에 포함되지 않는다 (개발 진행에 따라 frontmatter 보조 필드·체크 항목이 가변). 생성·저장 규칙은 [`02_화면_기능설계_가이드.md`](../../02_화면_기능설계_가이드.md) §"개발체크리스트 (6번째 산출물)" 가 정본이다.

### 0.1.3 분석리포트 단일 원천 원칙

분석리포트는 기능설계서, 디자인설계서, BPMN설계서의 단일 원천이다.

| 분석리포트 항목 | 후속 산출물 반영 위치 |
|---|---|
| §4.2 조회조건 S-NNN | 기능설계서 §3, 디자인설계서 §3.2 |
| §4.3 그리드 컬럼 G-NNN / GE-NNN | 기능설계서 §3.2, 디자인설계서 §4 |
| §4.4 상세/라인 필드 D-NNN / L-NNN | 기능설계서 §4, 디자인설계서 §3.3 |
| §4.5 버튼 B-NNN / GB-NNN | 기능설계서 §5, BPMN설계서 §1.1 / §2 |
| §4.6 팝업 P-NNN | 기능설계서 §9, 디자인설계서 §6 |
| §4.7 상태값 ST-NNN | 기능설계서 §7, BPMN설계서 §2 / §4 |
| §9 코드값/LoV LV-NNN | 기능설계서 §3.3, 디자인설계서 §4.2 |
| §11 C1~C6 API 패턴 판정 | BPMN설계서 §1.2 |

후속 설계서는 분석리포트에 없는 항목을 새로 만들 수 없다.
추가 필요성이 발견되면 분석리포트로 돌아가 해당 항목을 먼저 추가하고, 그 근거를 기록한 뒤 후속 산출물을 다시 작성한다.

### 0.1.4 완료 판정 규칙

Claude는 산출물 작성 후 반드시 정합체크서를 작성한다.

설계 완료 판정 조건은 다음과 같다.

| 조건 | 완료 여부 |
|---|---|
| 정합체크서 §A~§F 모두 ✓ | 완료 가능 |
| §A~§F 중 1개라도 ✗ | 완료 불가, 재작성 필요 |
| 확인필요 Q-NNN 존재 | 완료 가능하나 미확정 항목으로 별도 보고 |
| 분석리포트 없이 설계서 작성 | 완료 불가 |
| 템플릿 절 순서 또는 표 헤더 변경 | 완료 불가 |
| 분석리포트에 없는 항목을 후속 설계서에 추가 | 완료 불가 |

### 0.1.5 반복 생성 결정성 검증

동일 화면을 동일 As-Is 자료로 다시 생성하는 경우, 아래 항목은 이전 산출물과 동일해야 한다.

| 항목 | 검증 기준 |
|---|---|
| 조회조건 | S-NNN 수, 순서, 화면 표시명, To-Be 컬럼 |
| 그리드 컬럼 | G-NNN / GE-NNN 수, 순서, 화면 표시명, To-Be 컬럼 |
| 상세/라인 필드 | D-NNN / L-NNN 수, 순서 |
| 버튼 | B-NNN / GB-NNN 수, 순서, action |
| 팝업 | P-NNN 수, 순서 |
| 상태값 | ST-NNN 목록 |
| 코드값/LoV | LV-NNN 목록 |
| API 패턴 | C1~C6 판정 결과, OASIS/Phase 7 채택 결과 |
| 산출물 구조 | 절 순서, 표 헤더, “해당 없음” 유지 여부 |

위 항목이 달라지면 Claude는 변경 사유를 임의 작성하지 말고, 정합체크서 §D를 ✗로 판정한 뒤 재분석한다.

### 0.1.6 Q-NNN 해소 라이프사이클 (MUST)

확인필요 Q-NNN 항목의 라이프사이클은 다음 4 단계로 강제한다. 사용자 결정이 완료된 Q-NNN 은 ~~취소선~~ 처리만 하고 §12 표에 잔존시키지 않는다.

| # | 단계 | 처리 |
|---:|---|---|
| 1 | 확인필요 항목 식별 | 분석리포트 §12 "확인필요 항목 (Q-NNN)" 표에 등재 (`\| Q-NNN \| 영역 \| 내용 \| 처리 후보 \| 영향 \|`) |
| 2 | 사용자 결정 수신 | 결정 내용을 본 세션 컨텍스트에 누적 |
| 3 | 설계 업데이트 | 분석리포트 본문 §6 / §9 / §10 / §11 + 기능설계서 + 디자인설계서 + BPMN설계서 + 정합체크서 5 산출물 모두 결정 내용 반영 (file:line cite 100%) |
| 4 | §12 표에서 행 **물리 제거** | 해당 Q-NNN 행을 §12 표에서 **삭제** (취소선 ✗) + §12 제목/intro 를 "결정 누적 (사용자 결정 완료 — 활성 N 건)" 으로 갱신 + 표 구조를 결정 누적 형태로 재구성 |

**§12 변환 패턴**:

| 단계 | §12 표 구조 |
|---|---|
| 초기 (활성 Q 잔존) | `\| Q-NNN \| 영역 \| 내용 \| 처리 후보 \| 영향 \|` 5 컬럼 (Q-NNN 번호 행 포함) |
| 해소 완료 | `\| 결정 영역 \| 결정 내용 \| 본문 반영 \|` 3 컬럼 (Q-NNN 번호 ✗ — 의미있는 "결정 영역" 텍스트) + 활성 = 0 명시 |

**(MUST NOT)**

| 사례 | 처리 |
|---|---|
| `~~Q-NNN~~` 취소선만 처리하고 행 잔존 | ✗ — 행 자체 삭제 + 결정 누적 표로 재구성 |
| "해소됨" 표시만 추가 + 본문 미반영 | ✗ — 본문 §6/§9/§10/§11 갱신이 선결 |
| 결정 내용을 §12 본문에만 적고 4 설계서 동기화 누락 | ✗ — 5 산출물 동시 갱신 |
| 정합체크서 §G Q-NNN 활성 카운트 미갱신 | ✗ — §G 도 동일하게 결정 누적 패턴 변환 |

근거: cma 4 화면 (masterCodeMng / masterCategoryMng / masterCodeSelPop / masterCodeUploadFilePopup) 정본 패턴 — `§12. 결정 누적 (사용자 결정 완료)` + 3 컬럼 표 + 활성 0 명시.

### §0.1.7 개발 단계 결정 사항 변경 시 설계서 동시 update (MUST)

개발 단계 (BE / FE 구현, 빌드, 통합 테스트, 운영 검증) 에서 설계 결정이 변경되거나 신규 결정 사항이 추가되면 **해당 cycle 내에 5종 설계서 (분석리포트 / 기능설계서 / 디자인설계서 / BPMN설계서 / 정합체크) 의 본문을 같이 update** 한다.

**MUST**:
- 컬럼/메서드/BPMN 액션/FE 컴포넌트 의 추가/제거/변경
- 데이터 시드 정책 변경
- audit / 트랜잭션 / 권한 정책 변경
- legacy 자산 제거 / 신규 자산 SoT 전환
- RBAC chain 재설계 등 시스템 구조 변경

위 어느 항목이라도 **개발 cycle 중에 결정되면 설계서 본문 § 갱신 + §12 결정 누적 표 등재 + §G(정합체크) sync** 의 3 단계 작업을 같은 PR 에 포함한다.

**MUST NOT**:
- "후속 PR 에 설계서 update" 형태로 cycle 분리
- 코드만 변경하고 설계서는 그대로 두기
- 변경 사항을 메모리 / 커밋 메시지에만 기록

**근거**: 설계서는 As-Is/To-Be 의 정본. 코드와 설계서가 분리되면 다음 cycle 의 Q-NNN 해소 / 후속 worker 가 설계서 기준으로 작업 시 정합 깨짐.

**적용 예시**:
- W6 commPermMng 개발 중 `BIZ_SYSTEM_CODE` 폐기 결정 → 분석리포트 §11.1 / §12 + 기능설계서 §4.2 + 디자인설계서 §G-005 / DS-005 + BPMN설계서 §1 (lov action 제거) + 정합체크 §K 본문 모두 동시 update
- legacy mcm-core 자산 제거 + 신규 9 화면 SoT 전환 (2026-06-01 사용자 결정) → 9 화면 모두의 분석리포트 §11 정책 항목에 본 결정 등재 (이 결정은 9 화면 cross-cutting)

**적용 시점**: 본 규칙은 2026-06-01 사용자 결정 이후 신규 / 보완 cycle 에 적용. 기존 산출물 (W1~W9 1차 사이클) 의 소급 update 는 별도 후속 PR 후보.

### §0.1.8 모듈 설계 결정 레퍼런스 선참조 (MUST — Q-NNN 재질문 방지)

화면 설계 착수 시, 해당 `moduleId` 의 **설계 결정 레퍼런스가 존재하면 반드시 먼저 읽는다**.

| 자산 | 위치 |
|---|---|
| 모듈 레퍼런스 파일 | `docs/guide/reference/{moduleId}-reference.md` (모듈 공통/도메인 공통/화면 고유/미결 결정 누적) |
| 모듈 레퍼런스 메모리 | 자동 메모리 `reference_{moduleId}_design_decisions` (있으면 system-reminder 로 노출) |

**규칙 (MUST)**:
1. 신규 화면의 확인필요(Q-NNN)가 레퍼런스의 **기결정(resolved) 항목과 일치하면 사용자에게 재질문하지 않고 `resolved` 처리 + 레퍼런스 cite** (정합체크 §G / 분석 §13). — §0.1.6 Q-NNN 라이프사이클의 "사용자 결정 수신" 을 레퍼런스 인용으로 갈음.
2. 신규 결정이 확정되면 §0.1.7(개발 단계 동시 update)과 동일하게 **같은 cycle 내에** 화면 `정합체크 §G`/`분석 §13` 갱신 + `{moduleId}-reference.md` 추가 + 메모리 갱신을 함께 수행한다.
3. 레퍼런스에 없거나 충돌하는 신규 항목만 사용자에게 확인한다.
4. 레퍼런스 미존재 모듈은 빈 템플릿(`A~D` 섹션 + "결정 없음")을 `docs/guide/reference/` 에 두고, 첫 결정 확정 시부터 누적한다.

**(MUST NOT)**: 레퍼런스에 이미 결정된 항목을 화면마다 다시 open 으로 등재하거나 사용자에게 재질문 ✗. 결정 내용을 레퍼런스 동기화 없이 화면 본문에만 적기 ✗.

> 정본 예시: `docs/guide/reference/mls-reference.md` (lsa 슬리팅 5 화면 결정 누적 — 관리번호/PDA/Kafka I/F/금액컬럼 미보유/폐폭 N 판정/전역 DATE 룰 등).

### §0.1.9 시스템 간 I/F(Kafka) 명세 등재 (MUST — 토픽/payload 단일 정본)

화면 설계에서 시스템 간 I/F(Kafka 토픽 발행/수신)가 신설·변경되면 **모듈 interface 명세에 등재**한다.

| 자산 | 위치 |
|---|---|
| 모듈 I/F 명세 파일 | `docs/{moduleId}/interface/{MODULEID}_INTERFACE_명세.md` (정본 예시: `docs/mls/interface/MLS_INTERFACE_명세.md`) |

**규칙 (MUST)**:
1. I/F 1건 = 명세의 **IF-ID 1행** (방향 OUTBOUND/INBOUND, 토픽, 송신→수신, 발행 트리거, 송수신 내용, 근거 Q-NNN).
2. 토픽·payload 미확정 단계에서는 **샘플로 등재**한다 — 토픽 명명: `SAMPLE_{송신모듈}_{수신모듈}_{NN}` (예: `SAMPLE_MLS_ERP_01`, `SAMPLE_ERP_MLS_01`), payload 는 샘플 JSON 스키마. 실명 확정 시 **명세 파일에서만 일괄 치환**한다.
3. 화면 설계서(분석 §13 / 정합 §G / BPMN §4.1 / 기능 P-NNN)는 토픽·payload 를 본문에 재기술하지 않고 **IF-ID 를 cite** 한다 (§E 가이드 중복 제거와 동일 원칙).
