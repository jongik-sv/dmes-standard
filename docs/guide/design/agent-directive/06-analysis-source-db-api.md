### 6.13 속도 vs 품질 기준 (신설 — Wave G-1)

본 절은 설계서 5종 산출물 생성 시 에이전트가 따르는 작업 속도와 품질의 우선순위를 명시한다.

| 항목 | 기준 | 위반 사례 (금지) |
|---|---|---|
| 표준 | **"느려도 꼼꼼하게"** 가 정본. 시간이 더 걸려도 As-Is 1:1 보존 (§17.2) · 추측 금지·인용 필수 (§17.3) · 결함 전부 처리를 우선한다. | "빠르게 가려고 대충" / 발췌 처리 / "주요 / 대표 / 등" 요약화 |
| 누락 정당화 금지 | "사소한 것은 생략" / "△ skip — 토큰 한계" / "분량이 많아 일부만 발췌" 같은 표현으로 본문에 누락을 정당화하지 않는다. | "토큰 절약을 위해 일부만" / "임시 placeholder" / "추후 보완" 처리 후 종료 |
| 토큰 한계 발견 시 처리 | Stage 분할 (예 §17 후반부 별도 Stage / 화면 단위 분할 / 산출물 종류 분할) 로 회피. 누락으로 두지 말 것. | 누락된 채로 phase 종료 / "다음 phase 에서 처리하겠다" 메모만 남기고 종료 |
| 충실 작성 의무 | 각 § 본문은 행위 / 조건 / 예시 / 실패 시 대응을 모두 명시한다 (§16 분량 회피 금지). | 표 헤더만 있고 본문 비어 있음 / 1줄 요약만 남김 |

**(MUST)** 본 § 위반 시 §6.14 Phase 종료 자동 고해성사 Q4 ("임의 합리화한 결과가 있는가?") 에서 즉시 적발되어 phase 재진입 처리된다.

### 6.14 Phase 종료 자동 고해성사 + 재진입 (신설 — Wave G-1)

본 절은 에이전트가 phase 종료 직전 스스로 누락 / 위반 / 임의 합리화 여부를 점검하는 자동 고해성사 프로토콜을 정의한다. 사용자가 "고해성사 할 거 있냐" 묻기 전에 에이전트가 먼저 수행하는 게 본 § 의 핵심 행동 강제 사항이다.

#### 6.14.1 Phase 종료 4 질문 자체 점검

각 phase 종료 직전 에이전트 본인이 스스로 다음 4 질문을 점검한다. 누구도 묻지 않아도 본인이 먼저 수행한다.

| # | 질문 | 점검 방식 | 통과 기준 |
|---|---|---|---|
| **Q1** | 이번 phase 에 사용자 요구 14 항목 (§2.5.2 의 14 항 prepend) 중 위반한 게 있는가? | 14 항 1~14 를 grep 또는 본인 행동 회상으로 1:1 대조 | 위반 0 건 |
| **Q2** | 검증 안 한 핵심 자산이 있는가? | 작업 대상 designer.cs / cs / SQL / 스크린샷 (제공 시) / 가이드 본문 처음~끝 읽기 완료 여부 확인 | 미독파 자산 0 건 |
| **Q3** | 에이전트 (서브-) 보고를 그대로 수용하고 직접 검증 안 한 부분이 있는가? | 서브 워커 보고 vs 산출물 실제 상태 spot-check (§2.5.3 인용 검증 / 산출물 실제 상태 / 14 항 위반 자체 점검 3 단계) | 보고 == 실제 상태 100% |
| **Q4** | 임의로 합리화한 결과가 있는가? | "△ skip — 토큰 한계" / "사소" / "다음에" / "추후 보완" / "일단 placeholder" 같은 표현 grep | hit 0 건 |

#### 6.14.2 4 질문 결과 분기

| 결과 | 행동 |
|---|---|
| **4 질문 모두 No** (위반 / 미검증 / 그대로 수용 / 임의 합리화 모두 0) | 다음 phase 진행 |
| **하나라도 Yes** | 즉시 정정 후 4 질문 재점검 (재귀 — 정정으로 인해 새 위반이 생기지 않았는지 다시 확인) |
| **정정 불가** (예: 자료 자체 부재 / 환경 제약) | 사용자에 보고 (fail-fast) — 임의 합리화 금지 |

#### 6.14.3 재진입 트리거

정정 후에도 잔존 결함이 0 이 아니면 해당 Phase 자체를 재진입한다. 재진입은 동일 작업 단위 / 동일 14 항 prepend / 동일 자료 인벤토리로 phase 를 처음부터 다시 수행하는 것으로, **에이전트 본인이 직접 실행한다** (사용자 요청 불필요).

| 재진입 횟수 | 행동 |
|---|---|
| 1 회차 (최초 재진입) | 잔존 결함 보완 후 4 질문 재점검 |
| 2 회차 (1 회차에도 잔존 시) | 다른 접근 (Stage 분할 / 자료 추가 수집 / 서브에이전트 분산 변경) 으로 재진입 |
| 3 회차 (2 회차에도 잔존 시) | **사용자 보고** — 임의 종료 금지. 잔존 결함 목록 + 시도한 접근 2 회차 내역 + 막힌 지점 명시 |

**(MUST)** Phase 종료 자동 고해성사는 사용자가 묻기 전에 **에이전트가 먼저** 수행한다. 이를 누락하고 phase 종료를 보고한 경우, 본 가이드 위반 + §17.2 결함 처리 대상이 된다.

#### 6.14.4 본 가이드 통합 작업에의 자기 적용

본 §6.14 는 **본 가이드 자체의 통합 작업** (Wave G-1 ~ G-6) 에도 적용된다. 각 wave 워커는 Edit 완료 후 4 질문 자체 점검을 거쳐야 한다. 메인 에이전트는 워커 보고 수용 시 §2.5.3 3 단계 종합 규칙으로 검증한다.

### 6.15 스크린샷 / Redline 처리 프로토콜 (제공 시 조건 — 신설 Wave G-1)

본 절은 As-Is 화면 스크린샷 또는 Redline 마크업이 **제공된 경우에만** 적용되는 시각 검증 프로토콜이다. 부재 시 처리 방식과 경로 추측 금지 원칙도 함께 명시한다.

#### 6.15.1 제공 시 시각 검증 절차

스크린샷 또는 Redline 이 제공된 경우, 에이전트는 다음 1:1 대조를 수행한다.

| 대조 항목 | 비교 대상 | 결과 처리 |
|---|---|---|
| **3자 1:1 대조** | designer / cs (As-Is 소스) + .jpg / .png (스크린샷) + 디자인설계서 §10 (To-Be 설계) | 차이 발견 시 Q-NNN 등재 (§13) + 디자인설계서 §6 특이사항에 기록 |
| 컴포넌트 좌표 / 크기 | designer Visible=true 컨트롤 좌표 vs 스크린샷 시각 위치 | 시각적으로 동일 → 통과 / 차이 → Q-NNN |
| 컴포넌트 라벨 / 텍스트 | resx PropBag vs 스크린샷 텍스트 vs 디자인설계서 라벨 정의 | 3자 일치 → 통과 / 1자라도 다름 → Q-NNN |
| 색상 / 강조 / 분기 표시 | Redline 마크업 (제공 시) vs designer 속성 vs 디자인설계서 §3 | Redline 우선 → 디자인 갱신 |

#### 6.15.2 부재 시 처리

스크린샷이 제공되지 않은 경우 강제 시각 검증은 적용하지 않는다. 다음 2 처리 중 하나를 선택한다.

| 선택지 | 조건 | 후속 조치 |
|---|---|---|

#### 6.15.3 경로 추측 금지

스크린샷 / Redline / designer / cs 의 모든 파일 경로는 작업 초기 `ls` 또는 `Glob` 으로 **실제 경로** 를 확인한 후 사용한다.

| 항목 | 금지 행위 | 정본 행위 |
|---|---|---|
| 스크린샷 경로 | `docs/external/KsmErpK/screenshots/{화면식별자}.jpg` 같은 패턴 추측 후 직접 Read 시도 | `Glob "**/{화면식별자}*"` 또는 `ls docs/external/KsmErpK/screenshots/` 로 실제 파일 목록 확인 |
| designer 경로 | `Tasks/{prefix}/{화면식별자}/{화면식별자}.Designer.cs` 패턴 추측 | `Glob "**/{화면식별자}.Designer.cs"` 로 실제 파일 위치 확인 |
| 한글 / 공백 / 중첩 경로 | 패턴 그대로 따옴표 없이 명령 실행 | 따옴표로 감싸기 + 백슬래시 / 슬래시 OS 정합 확인 (`feedback_no_path_inference` 메모리 인용) |

#### 6.15.4 스크린샷 변경 감지 시 자동 고해성사

이전 분석 사이클에서 사용한 스크린샷의 파일 mtime / hash 가 변경된 경우, 분석리포트 §-1 R14-Step0 의 manifest hash 도 영향받는다. 다음 자동 절차를 거친다.

| 단계 | 행동 |
|---|---|
| 1. 변경 감지 | manifest 9 파일의 hash 비교 (R14-Auto 정책 — §0.2.10) 시 스크린샷 input source 의 hash 변경 발견 |
| 2. 영향 평가 | 변경된 스크린샷의 화면 식별자 / 컴포넌트 영역 식별 |
| 3. Q-008 (또는 차순위 Q-NNN) 등재 | §13 에 "스크린샷 변경 — 시각 검증 재수행 필요" 기록 |
| 4. 재시각검증 | §6.15.1 3자 1:1 대조 재수행 |
| 5. §6.14 4 질문 재점검 | Q2 ("검증 안 한 핵심 자산") 통과 여부 확인 |
