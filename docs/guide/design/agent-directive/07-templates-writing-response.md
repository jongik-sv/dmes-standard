## 8. 템플릿 사용 규칙

### 8.1 공통 규칙

각 설계서는 해당 가이드의 Part B 템플릿 구조를 그대로 사용한다.

Claude는 다음을 하지 않는다.

1. 섹션 삭제
2. 섹션 병합
3. 섹션 순서 변경
4. 섹션명 임의 변경
5. 템플릿 밖 신규 상위 섹션 추가
6. 적용 대상이 없다는 이유로 섹션 생략

## 15. `[확인필요]` 표기 규칙

Claude는 근거 없는 확정 표현을 쓰지 않는다.

### 15.1 표기 형식

```text
[확인필요: 사유]
```

예:

```text
[확인필요: To-Be 테이블 정의서에 LOT_NO 대응 컬럼이 없음]
[확인필요: As-Is 프로시저와 화면 이벤트의 상태 전이 조건이 서로 다름]
[확인필요: moduleGroup이 체인별 모듈 사전에 미등재]
```

### 15.2 사용해야 하는 경우

| 상황 | 처리 |
|---|---|
| 필수 자료 접근 불가 | `[확인필요]` + 설계 차단 이슈 기록 |
| As-Is와 To-Be 불일치 | `[확인필요]` + 차이 기록 |
| 컬럼 매핑 불가 | `[확인필요]` + 매핑 문서에 기록 |
| 운영 정책 미확정 | `[확인필요]` + 권한/상태 섹션에 기록 |
| 화면 캡처 미제공 | 소스 기반 추정 후 `[확인필요]` 표시 |
| 개발가이드와 충돌 | 개발가이드 우선, 충돌 내용 기록 |

### 15.3 사용하지 말아야 하는 경우

가이드에 MUST/MUST NOT으로 정해진 항목에는 `[확인필요]`를 남발하지 않는다.

| 항목 | 잘못된 처리 | 올바른 처리 |
|---|---|---|
| body root key | `[확인필요: master 또는 rows 선택]` | 단일 Grid면 `master` 확정 |
| HTTP method | `[확인필요: GET/POST 선택]` | OASIS는 `POST` 확정 |
| PortalShell 영역 | `[확인필요: Header 설계 여부]` | 설계 대상 아님으로 확정 |
| 외부 아이콘 라이브러리 | `[확인필요: lucide 사용 여부]` | 사용 금지로 확정 |

## 16. 금지 사항

Claude는 다음을 하지 않는다.

1. 분석리포트 없이 설계서부터 작성하지 않는다.
2. As-Is 자료 확인 없이 신규 기능을 창작하지 않는다.
3. 분석리포트에서 발견한 항목을 설계서에 반영하지 않고 누락하지 않는다.
4. 발견 수와 반영 수가 맞지 않는데 완료 처리하지 않는다.
5. To-Be 테이블에 없는 컬럼을 확정 컬럼처럼 쓰지 않는다.
6. Part B 템플릿 구조를 임의 변경하지 않는다.
7. 기능/디자인/BPMN 간 필드ID, 버튼ID, 팝업ID를 다르게 쓰지 않는다.
8. DB 컬럼명을 한글 표시명으로 대체하지 않는다.
9. JSON 필드를 snake_case로 쓰지 않는다.
10. DB 컬럼을 camelCase로 쓰지 않는다.
11. OASIS URL에 복수형, 하이픈, `/api/backend/` prefix를 쓰지 않는다.
12. BPMN설계서에 FE 경로(`/api/{moduleId}/...`)만 쓰고 BE 경로(`/oasis/...`)를 누락하지 않는다.
13. 디자인설계서에서 PortalShell 영역을 재설계하지 않는다.
14. shared에 없는 컴포넌트를 있는 것처럼 쓰지 않는다.
15. 외부 아이콘 라이브러리를 제안하지 않는다.
16. CSS hex, px, 임의 색상값을 설계 표준처럼 쓰지 않는다.
17. 화면 캡처만 보고 기존 소스/프로시저 확인을 생략하지 않는다.
18. 일부 조회조건·그리드 컬럼만 발췌하고 전수 반영한 것처럼 쓰지 않는다.
19. 사용자에게 가이드 기본값을 선택지로 떠넘기지 않는다.
20. `확정`, `반드시`, `정본` 같은 표현을 근거 없는 값에 사용하지 않는다.
21. 분석 내용에 `기타`, `등`, `주요 항목만`, `대표 컬럼` 같은 표현으로 누락 가능성을 숨기지 않는다.

## 17. 완료 기준

Claude는 산출물 생성 완료 전 아래 기준을 모두 확인한다.

### 17.1 산출물 완료 기준

| 항목 | 완료 조건 |
|---|---|
| 저장 경로 | `docs/{moduleId}/design/{화면식별자}/` 하위에 5종 산출물 존재 |
| 파일명 | `{화면식별자}_*.md` 규칙 준수 |
| 분석리포트 | §1~§16 모두 존재, 분석완료 게이트 결과 존재 |
| 기능설계서 | §1~§11 모두 존재 |
| 디자인설계서 | §1~§10 모두 존재 |
| BPMN설계서 | §1~§6 모두 존재 |
| 정합체크서 | 분석 반영 체크, 일치 키, 확인필요 항목 집계 존재 |
| 자료 근거 | As-Is/To-Be 참조 근거 기록 |
| 확인필요 | 모든 `[확인필요]` 항목 집계 |
| 불일치 | 불일치가 있으면 영향도와 후속 조치 기록 |

### 17.2 분석 품질 완료 기준

| 항목 | 완료 조건 |
|---|---|
| 전수성 | 조회조건, 그리드 컬럼, 버튼, 팝업, 상태, 코드값 수량이 기록됨 |
| 근거성 | 각 주요 항목에 As-Is/To-Be 근거가 있음 |
| 재현성 | 검색/탐색 기준이 기록되어 같은 분석을 반복 가능함 |
| 연결성 | 소스 이벤트가 버튼/action/BPMN 프로세스와 연결됨 |
| 매핑성 | 화면 요소가 To-Be 컬럼 또는 `[확인필요]`로 분류됨 |
| 커버리지 | 발견 수 = 반영 수 + 확인필요 수 + 제외 수 |
| 차이 관리 | As-Is와 To-Be 차이가 숨겨지지 않고 기록됨 |

### 17.3 설계 품질 완료 기준

| 항목 | 완료 조건 |
|---|---|
| 구조 일관성 | 동일 유형 설계서의 템플릿 구조 유지 |
| 사람 가독성 | 표, 섹션, 근거, 특이사항이 명확함 |
| Agent 가독성 | ID, action, serviceId, body key가 기계적으로 추적 가능 |
| 추가 의사결정 최소화 | 가이드 기본값은 자동 적용, 진짜 결정만 확인필요 처리 |
| 개발 착수 가능성 | FE/BE/BPMN 구현자가 URL, payload, 상태, 버튼, 필드를 바로 확인 가능 |
