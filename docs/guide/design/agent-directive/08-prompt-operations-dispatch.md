## 19. Claude 실행 프롬프트 템플릿

아래 프롬프트를 Claude에게 그대로 입력하여 화면 설계서 생성을 지시할 수 있다.

```markdown

- `docs/guide/design/03_화면_디자인설계_가이드.md`
- `docs/guide/design/04_백단_BPMN_기능설계_가이드.md`
- `docs/guide/design/01_Agent부속_가이드.md`
- `docs/guide/design/00_Agent지시_가이드.md`

가장 중요한 원칙:

1. 설계서부터 작성하지 말고, 반드시 `{화면식별자}_분석리포트.md`를 먼저 작성한다.
2. 분석리포트에는 자료 수집 인벤토리, 검색/탐색 기준, 화면 요소 전수 목록, 소스 로직 분석, DB/SQL 분석, To-Be 분석, 매핑 분석, API 패턴 분석, 커버리지 매트릭스, 분석완료 게이트 결과를 포함한다.
3. 분석리포트의 발견 수와 설계서 반영 수가 맞지 않으면 완료 처리하지 않는다.
4. 조회조건, 그리드 컬럼, 버튼, 팝업, 상태, 검증, 코드값, 연동, 부수효과는 전수 식별한다. 일부 대표 항목만 작성하지 않는다.
5. 가로 스크롤 그리드 우측 컬럼, 아이콘 버튼, 숨은 이벤트, 프로시저 분기, 트리거 부수효과를 누락하지 않는다.

8. 기능설계서, 디자인설계서, BPMN설계서, 정합체크서를 모두 작성한다.
9. 각 설계서는 해당 가이드의 Part B 템플릿 구조를 그대로 사용한다.
10. 섹션을 삭제, 병합, 이름 변경, 순서 변경하지 않는다.
11. 적용 대상이 없으면 섹션을 삭제하지 말고 `해당 없음`이라고 작성한다.
12. MUST/MUST NOT으로 정해진 항목은 사용자에게 묻지 말고 기본값을 채택한다.
13. 업무 정책 또는 자료 부족으로 확정 불가능한 항목만 `[확인필요: 사유]`로 표기한다.
14. 모든 `[확인필요]` 항목은 분석리포트, 정합체크서, 최종 응답에 집계한다.
15. 기능/디자인/BPMN 간 화면 식별자, 필드ID, 버튼ID, 팝업ID, DB 컬럼명, 상태코드, action, serviceId를 반드시 일치시킨다.
```

## 20. 운영 권장 사항

### 20.1 분석리포트 고정 운영

분석 내용이 매번 달라지는 것을 막기 위해, 같은 화면의 기능/디자인/BPMN 설계서는 항상 동일한 `{화면식별자}_분석리포트.md`를 근거로 작성한다.

설계서 수정 시에도 먼저 분석리포트를 갱신하고, 그 다음 3종 설계서를 갱신한다.

### 20.2 moduleGroup 사전 관리

체인별 moduleGroup은 설계 착수 전 사전에 등재되어 있어야 한다.

미등재 상태에서 Claude가 임의로 moduleGroup을 확정하면 FE 경로, pageId, tsup entry key, 메뉴 등록 기준이 흔들릴 수 있다.

권장 관리 방식:

```text
docs/guide/design/module-group-registry.md
```

### 20.3 정합체크서 필수 운영

가이드상 복잡 화면은 정합체크서가 권장일 수 있으나, Claude 자동 생성에서는 모든 화면에 대해 정합체크서를 작성한다.

V2에서는 정합체크서에 “분석리포트 → 설계서 반영 체크”를 추가한다.

이유:

1. Agent가 분석에서 발견한 항목을 설계서에서 누락할 수 있다.
2. 필드ID, 버튼ID, action, serviceId 불일치는 개발 단계에서 즉시 오류로 이어진다.
3. 정합체크서는 사람 리뷰와 Agent 재수정 모두에 유리하다.

### 20.4 설계서 리뷰 기준

리뷰어는 설계서 본문보다 먼저 아래를 확인한다.

1. 분석리포트가 존재하는가
2. 분석리포트의 발견 수와 설계 반영 수가 맞는가
3. 적용 가이드가 APS/MES에 맞는가
4. 저장 경로와 파일명이 맞는가
5. 화면 식별자, moduleId, moduleGroup, pageName, pageId가 일관되는가 (MES 룰: `screenId == pageName == pageId == serviceId` 단일 camelCase 값 / APS `mpn`: kebab-case + `-page.tsx` 컨벤션 유지 — §3.1 / §3.1.1 정본)
6. 기능/디자인/BPMN의 일치 키가 맞는가
7. `[확인필요]` 항목이 숨겨져 있지 않고 집계되어 있는가
8. As-Is 근거와 To-Be 매핑 근거가 명시되어 있는가
9. 개발 착수 가능 여부 판단이 명확한가

## 21. 최종 원칙

Claude는 설계서 생성 시 다음 문장을 기준으로 판단한다.

> 설계서보다 분석리포트가 먼저다.
> 가이드에 답이 있으면 묻지 않고 따른다.
> 자료에 근거가 없으면 확정하지 않는다.
> 확정하지 못한 항목은 숨기지 않고 `[확인필요]`로 남긴다.
> 분석에서 발견한 항목은 설계서에 빠짐없이 반영하거나 제외 사유를 남긴다.
> 발견 수와 반영 수가 맞지 않으면 완료가 아니다.
> 3종 설계서는 같은 화면을 설명하는 하나의 설계 세트이므로, 모든 일치 키를 끝까지 맞춘다.

## 22. 메인-워커 1계층 디스패치 패턴 (2026-06-05 사용자 결정)

> **(MUST)** 본 § 은 §2.5 "멀티에이전트 조율" 의 1계층 분산 운영을 *복수 단위 작업 일반* 으로 확장한 정본 패턴이다. 화면 설계 5종 산출물 외에도 **모듈 시드 / 코드 일괄 갱신 / 설계서 일괄 동기화 / Round-N 전파** 같이 독립 단위가 다수인 작업에 동일 패턴을 적용한다. §2.5 와 본 § 이 충돌하면 본 § 이 우선한다 (2026-06-05 결정 정본).

### 22.1 패턴 개요

**패턴 이름**: 메인-워커 1계층 디스패치 패턴 (Main-Worker 1-Tier Dispatch Pattern).

**적용 조건**:

| 조건 | 처리 |
|---|---|
| 사용자가 "여러 작업" / "복수 항목" 을 한 번에 지시 | 메인이 분해 + 워커 병렬 dispatch |
| 작업이 **3 + 개의 독립 단위** 로 분해 가능 (예: 9 화면 × 2 문서 / 10 모듈 시드 / 다수 코드 일괄 갱신) | 워커 병렬 dispatch 강제 |
| 단순 단건 (1 ~ 2 파일 수정) | 메인이 직접 수행 (워커 dispatch ✗ — 오버헤드 회피) |

**메인 Claude 의 책임** (5 단계):

| # | 책임 |
|---:|---|
| 1 | 사용자 지시 분해 → 독립 단위 N 개 식별 |
| 2 | 단위별 worker prompt 작성 (각 워커가 자기 단위만 처리하도록 self-contained 지시문) |
| 3 | `parallel()` 또는 다중 Agent 동시 dispatch 로 launch |
| 4 | 결과 수집 → grep / Read / 커맨드 출력으로 **마커 검증** (실제 갱신 여부 확인) |
| 5 | 검증 결과 종합 보고 (사용자에게 단일 응답) |

**워커 책임** (3 단계):

| # | 책임 |
|---:|---|
| 1 | 자기 단위 작업만 처리 (다른 단위 침범 ✗) |
| 2 | 작업 완료 후 plain text 또는 schema 강제 응답으로 보고 (변경 라인 수 / § 명 / 신규 row 등) |
| 3 | 메인이 검증 가능하도록 명확한 마커 (코드 주석 / § 명 / row label) 남김 |

**금지** (MUST NOT):

| # | 금지 사례 |
|---:|---|
| 1 | 메인이 직접 워커 작업까지 수행 (메인은 분해 + 검증 + 종합만) |
| 2 | 워커가 다른 워커의 단위 침범 |
| 3 | 워커가 사용자 추가 결정이 필요한 사항을 추측 — 결과 보고에 "사용자 결정 필요" 명시해야 함 |

### 22.2 적용 절차 (5 단계)

| Step | 메인 행동 | 산출물 |
|---:|---|---|
| 1 | 사용자 지시 분해 (N 개 독립 단위 식별) | 단위 목록 (예: 9 화면 / 10 시드 / 2 문서) |
| 2 | 단위별 self-contained prompt 작성 (§2.5.2 14 항 prepend 강제) | N 개 worker prompt |
| 3 | parallel dispatch (다중 Agent tool 호출을 단일 메시지에 묶음) | N 개 워커 launch |
| 4 | 결과 수집 + grep / Read 마커 검증 (워커 보고 ↔ 실제 산출물 차이 확인) | 검증 결과 (마커 occurrence count) |
| 5 | 메인이 종합 보고 (사용자에 단일 응답) | 사용자 최종 응답 |

> **Step 3 의 "parallel dispatch" 구현**: 본 환경에서는 메인 Claude 가 단일 응답 내에서 다수의 Agent / Task tool 호출을 동시 발행한다 (직렬 dispatch ✗). 환경이 다중 호출 미지원이면 §2.5.1 환경 제약 fallback 으로 메인 직접 수행 전환 — 강제 2계층 시도 ✗.

### 22.3 적용 예시 (본 세션 실적 — 2026-06-04 ~ 06-05)

| 사례 | 워커 수 | 워커 단위 | 검증 마커 |
|---|---:|---|---|
| 9 화면 설계서 동기화 (Round 1 ~ 5 전파) | 9 | 1 화면당 분석리포트 + 정합체크 = 2 문서 | 18 파일 §J / W5 / Round 1 ~ 5 grep occurrence ≥ 1 / 각 |
| Round 6 + 7 + Phase 1 ~ 4 일괄 동기화 | 10 | 8 화면 + 1 개발가이드 + 1 메모리 | 32 + grep occurrences (Round 6 / Round 7 / Phase 1 ~ 4) |

**총 누적 실적**: 11 worker 병렬 × 2 cycle = 32 + grep 마커 검증 통과 / 워커 침범 0 건 / 메인 우회 수행 0 건.

### 22.4 금지 사항 (재강조)

| # | 금지 사례 | 위반 시 처리 |
|---:|---|---|
| 1 | 메인이 워커 단위 작업까지 수행 (메인 = 분해 / 검증 / 종합 only) | 발견 시 §6.14 4 질문 재점검 + 메인 역할 재정의 |
| 2 | 워커 간 단위 침범 (워커 A 가 워커 B 의 화면을 수정) | 워커 재호출 + prompt 의 "작업 단위" 절 강화 |
| 3 | 워커가 사용자 추가 결정 사항 추측 (예: 정책 결정 / 명명 결정) | 워커 산출물에 "[확인필요: Q-NNN]" 또는 "사용자 결정 필요" 명시 강제 |

### 22.5 §2.5 와의 관계

| 항목 | §2.5 멀티에이전트 조율 | §22 메인-워커 1계층 디스패치 |
|---|---|---|
| 정본 영역 | 화면 설계 5종 산출물 생성 시 | 복수 단위 작업 일반 (시드 / 갱신 / 동기화 / 전파 / 5종 산출물) |
| 분할 임계치 | ≥ 5 화면 / ≥ 5 산출물 (§2.5.1) | **≥ 3 독립 단위** (본 §22.1 — 더 낮은 임계치) |
| 14 항 prepend | 강제 (§2.5.2) | 강제 (§2.5.2 인용) |
| 결과 종합 3 단계 | 인용 검증 / 산출물 상태 확인 / 14 항 위반 점검 (§2.5.3) | grep / Read 마커 검증 (Step 4) — §2.5.3 의 3 단계 포함 |
| 컨텍스트 분산 | 작업 노트 파일 + 250자 요약 (§2.5.1) | 동일 (§2.5.1 인용) |

> §2.5 가 화면 설계 한정이면 본 §22 는 *모든 복수 단위 작업의 정본 패턴*. 작업 종류와 무관하게 3 + 단위면 본 §22 적용.
