## 0. 요약

1. **exERD 동작 가정 6가지 중 5가지가 사실로 확인됐다**[원문]. 도움말 원문 211개 토픽과 제품 메타모델(`exerd.ecore`)을 읽었다. 키보드 연속 입력만 일부 확인이다(Ctrl+Enter 로 컬럼 추가는 확인, Tab·방향키 이동 규칙은 도움말에 없다).
2. **논리명→물리명 변환은 이미 우리 서버에 있다**[원문·실측]. `columnMng/compare` 는 물리명, 모호한 단어의 후보, 추천 도메인, 중복 여부를 한 번에 돌려주고, 응답 시간은 0.19~0.32초다. ERD 도구는 이 API 를 그대로 쓰면 된다.
3. **관계선이 가장 큰 새 문제다**[실측]. 로컬 DB 의 FK 는 MDM 스키마에만 53개 있고, MCM 을 비롯한 다른 스키마는 0개다. 칼럼 코멘트는 전 스키마가 0% 다. git 이력에도 MCM 의 FK·코멘트가 있었던 적이 없다. 따라서 "DB 를 읽어 오면 ERD 가 된다"는 1단계 전제는 MDM 에서만 성립한다. 칼럼명 규칙과 SQL 조인으로 관계를 추정하면 MCM 에서 후보 102쌍이 나오고, 그중 사람이 확인할 것은 약 75쌍이다.
4. **포크할 만한 오픈소스는 없다**[원문]. MIT 인 ERD Editor 는 React 가 아니라 자체 프레임워크와 Konva 캔버스로 만들어져 있다. drawDB·ChartDB 는 AGPL 이다. 대신 ERD Editor 의 MCP 설계(tool 56개, 전부 성공하거나 전부 실패하는 batch, 해결 방법을 담은 오류 메시지), drawDB 의 "고정 id 로 짝지어 RENAME 을 만드는 diff" 는 그대로 참고할 만하다.
5. **정본은 중간안이 근거가 가장 많다**[추론]. 모델은 설계 정본, Flyway V 파일은 적용 정본으로 둔다. 모델의 변경은 V 파일 초안으로 떨어지고 사람이 확정한다. drift 검사는 템플릿 PDB 에 V 파일을 적용한 결과와 모델을 비교한다.
6. **MDM 버전 엔진은 객체 ID 하나를 키로 쓴다**[원문]. 그래서 모델 전체를 버전 객체 하나로 두면 DRAFT 편집자가 한 명뿐이고, 표 단위 버전은 엔진에 맞지 않는다. 모듈(스키마) 하나를 모델 하나로 두는 절충안이 엔진에 맞는다[추론].
7. **가져오기는 exERD 파일이 1순위 후보다**[원문]. `.exerd` 는 EMF XMI 한 파일이고, 논리명·물리명·도메인·업무영역·좌표가 우리 모델과 거의 1:1 로 대응한다. 2순위는 Oracle SQL Developer Data Modeler, 3순위는 DBML(주로 내보내기)이다.
8. **구상 문서에 사실 오류가 있다**[실측·원문]. `TB_MDM_DICT_SYSTEM` 은 단어 사전이 아니고, 표 수(350/136)는 재현되지 않으며, 룰 세트 부품 경로가 다르다. 구상 문서는 이번에 함께 고쳤다(1절).

## 2. exERD 실제 동작

자료: 도움말 원문(일반판 211개 토픽 영어·한국어, SAM Edition 115개 토픽), 공개 업데이트 사이트(`exerd.com/update/exerd/3.x`, 3.3.56)의 jar 8개에 든 `exerd.ecore`, GitHub 에 커밋된 실물 `.exerd`·`.erdx` 파일. 프로그램은 설치·실행하지 않았다. 메모: [A2](research-2026-10-09/A2-exerd-deep.md), [I §exERD](research-2026-10-09/I-formats-deep.md).

### 2.1 구상 문서 가정 판정

| # | 가정 | 판정 | 근거 |
|---|---|---|---|
| 1 | 논리명·물리명을 버튼 하나로 전환 | 확인 | F3 전환, F4 논리, F5 물리. 논리 모드는 푸른 배경, 물리 모드는 붉은 배경. 모드 전환은 데이터 변환이 아니라 같은 객체의 두 필드 중 어느 쪽을 보여줄지 정하는 것이다 |
| 2 | 관계를 그으면 FK 가 생기고 PK 가 자식으로 옮겨진다 | 확인 | 부모 클릭 → 자식 클릭이면 "자동으로 자식 테이블에 참조 컬럼이 생성"된다. 자식에 같은 이름의 컬럼이 있으면 선택 창이 뜬다 |
| 3 | 식별·비식별 관계 구분 | 확인(일부 동작은 미확인) | 도구가 나뉘어 있다(4=비식별, 5=식별). 모델에 `identifying` 플래그가 있다. 식별 관계는 자식의 같은 이름 일반 컬럼을 PK 로 바꿔 FK 로 재사용한다 |
| 4 | 그리드에서 키보드만으로 연달아 입력 | 일부 확인 | 셀 인라인 편집(F2·더블클릭), Ctrl+Enter 컬럼 추가, Ctrl+Shift+Enter PK 컬럼 추가(이름 편집 중에도 동작). Tab·방향키 이동 규칙은 도움말에 없다 |
| 5 | 주제 영역 다이어그램 여러 개, 같은 표가 여러 다이어그램에 | 확인 | 업무영역 > 다이어그램 > 표 계층. 한 다이어그램에 같은 표를 두 번 놓을 수는 없고, 여러 다이어그램에는 놓을 수 있다 |
| 6 | 논리명 → 단어 사전으로 물리명, 도메인 → 타입·길이 | 확인 | "학번" → STUD_ID, "학생이름" → STUD_NM. 후보가 하나일 때만 자동으로 채우고, 여럿이면 선택 목록을 띄운다. 도메인을 바꾸면 그 도메인을 쓰는 컬럼에 일괄 반영된다 |

### 2.2 메타모델에서 배울 점 [원문]

- 모든 요소가 UUID 를 가진다. 모델 비교와 이름 변경 추적이 UUID 로 이루어진다.
- 구조는 Document > DatabaseModel > Schema > Table > Column 이다. 업무영역(BusinessArea)은 표를 **소유하지 않고 참조**하며, 그 아래에 Diagram 을 둔다.
- 표의 좌표·테마·컬럼 표시 필터는 표가 아니라 `TableDiagram`(다이어그램에 놓인 표)이 가진다. 같은 표를 여러 다이어그램에 다른 위치로 놓을 수 있는 이유다.
- PK·UK·FK·인덱스가 모두 `ColumnGroup` 계열이고, 컬럼은 `membership`(순서·정렬 포함)으로 여러 그룹에 속한다.
- `Relation` 은 `identifying`, 부모·자식 카디널리티(기본 EXACTLY_ONE / ZERO_OR_MORE)를 가지고, Document 의 `RelationManager` 에 따로 모인다.
- 도메인은 트리이고 `suggestedDataType`, `suggestedDefaultValue`, `suggestedNotNull` 을 가진다. 용어 사전은 Term(논리명, 물리명, 동의어, 설명, 태그)이다.
- 파일 버전별 ecore(0.0.0~3.0.0)를 남겨 두고 버전마다 마이그레이션한다.
- 주의: 제품 파일은 서명된 상용 배포물이므로 구조 참고로만 쓴다. ecore 를 복제하지 않는다.

### 2.3 따라 할 만한 편집 동작 (우선순위 순) [원문]

1. F3 로 논리·물리 전환, 배경색으로 현재 모드를 늘 구분한다.
2. 보기 프리셋 4종: 기본, 엔티티 모드, E-R 개요(표 이름·주석만), 논리·물리 동시 편집.
3. 비식별(4)·식별(5) 도구로 부모 → 자식 클릭 시 FK 를 자동 생성한다. 충돌이나 삭제 영향은 상황을 그림으로 보여 주는 "솔루션 대화상자"로 사용자 의도를 묻는다.
4. `` ` `` 키로 논리명·물리명·주석을 한 번에 편집한다.
5. 논리명 입력 → 용어 사전으로 물리명을 채우되 후보가 하나일 때만 자동으로 채운다.
6. 일괄 적용은 계획 → 검토 → 모호한 항목 선택 → 실행 순서다. 처음에는 체크가 비어 있어 사람이 확인해야 반영된다.
7. Ctrl+O 표 개요(컬럼 점프), Ctrl+T 표 찾기(물리명·주석 포함), Ctrl+↑/↓ 부모·자식 표 선택.
8. 표 접기(표만 / PK·FK 만), 확대율 50% 미만이면 이름만 표시, 다이어그램 생성 마법사, 자동 배치.
9. 삭제를 두 가지로 나눈다: Delete 는 다이어그램에서만 빼고, Alt+Delete 는 모델에서 지운다.
10. 모델 검사 후 Ctrl+1 로 문제를 자동 수정한다.
11. 모델 비교: UUID 로 같은 요소를 찾고, 위치·테마 같은 시각 변경은 따로 구분하며, 방향을 지정해 병합한다.
12. 협업(SAM Edition): 마지막 동기화 시점 기준 3-way 병합. 양쪽이 같은 곳을 바꾸면 묻지 않고 내 변경을 유지한다. 잠금은 편집 중이 아니라 **제출하는 순간**에 걸린다. 제출 전 정합성 검사는 건너뛸 수 없다.

## 3. 우리 리포에 이미 있는 자산

메모: [F](research-2026-10-09/F-codebase.md).

### 3.1 MDM 표준 사전과 변환 API

| 표 | 행 수 | 역할 |
|---|---|---|
| `TB_MDM_TERM` | 8,158 | 단어(용어) 사전. 영문 약어 `ENG_ABBR` 가 있는 행은 5,811 |
| `TB_MDM_DOMAIN` | 171 | 도메인 |
| `TB_MDM_COLUMN` | 7,951 | 컬럼 사전. `PHYS_NAME`·`COLUMN_NAME` 각각 UNIQUE, 구성 용어를 `TERM_IDS`(JSON)로 가진다. **표 구분 없는 전역 사전**이다 |
| `TB_MDM_COLUMN_SYSTEM` | 11,250 | 시스템별 물리명 별칭 |

- `ColumnNameComposer.forward/reverse` 가 왼쪽부터 최장 일치로 단어를 자르고, 사전에 없는 토막은 `***` 로 표시한다. 도메인 추천(`DomainSuggester`)도 있다[원문].
- `POST /api/mdm/oasis/columnMng/compare` 실측[실측]:

  | 입력 | 시간 |
  |---|---|
  | 고객주문일자 | 0.32초(첫 호출), 0.20초(다시) |
  | 사용자아이디 | 0.26초 |
  | 작업지시번호 | 0.19초 |
  | 설비가동시작일시 | 0.23초 |

  "고객주문일자" 응답은 `physName: CUS_ORD_DT`, 토막별 상태(고객 MATCHED, 주문 AMBIGUOUS 후보 2개, 일자 MATCHED), `recommendedDomainId: 30(일자)`, `duplicates: []` 였다. ERD 화면에 필요한 정보가 이미 다 있다.
- 판단[추론]: 0.2~0.3초면 입력을 멈춘 뒤(디바운스 300ms 안팎) 부르는 방식으로 "입력하는 순간 경고"를 할 수 있다. 키 입력마다 부르기는 무겁다. 서버가 요청마다 사전을 새로 읽는다고 코드 주석에 적혀 있으므로, 수백 컬럼을 한꺼번에 검사하는 일괄 검사에는 묶음 API 나 캐시가 필요하다.
- 표준 위반 검사는 값 검증(필수·타입·길이·허용 코드·룰 세트)만 있다. **"DB 칼럼명이 사전에 맞는가" 검사는 없다**[원문]. ERD 도구가 새로 만들 부분이다.
- 사전과 실제 DB 칼럼명의 일치율[실측]: 서로 다른 칼럼명 547개 중 `PHYS_NAME` 일치 79개(14%), 별칭까지 합치면 317개(58%). MDM 밖 스키마는 행 기준 70.5% 다(감사 칼럼 9개처럼 흔한 칼럼이 많아 행 기준이 높다).

### 3.2 MDM 객체 버전 관리와 잠금 [원문]

- 버전 대상은 `MASTER_CODE`, `BUSINESS_RULE`, `RULE_SET`, `LAYOUT` 4종이다(`VersionTarget.java:10-13`).
- 실제 쓰는 상태는 DRAFT 와 RELEASED 이고, 번호는 `1.000` 형식의 major/minor 다.
- 잠금 표는 따로 없다. DRAFT 소유자 선점(`DraftOwnershipService.acquire/release/handover`)과 낙관적 `ROW_VERSION` 을 함께 쓴다.
- ERD 를 얹으려면 `VersionTarget` 에 `ERD_MODEL` 을 추가하고, 확정 검사와 DRAFT 삭제 SPI 를 구현하고(없으면 fail-closed 로 막힌다), `TB_MDM_ERD_MODEL` 과 `_VER` 표를 새 V 파일로 만들고, 권한 시드를 넣고, `VersionActionBar` 를 재사용하면 된다.
- 엔진이 **객체 ID 하나를 키로** 쓴다. 모델 전체를 한 객체로 두면 DRAFT 편집자가 한 명이고, 표 하나를 한 객체로 두는 방식은 엔진에 맞지 않는다.

### 3.3 DB 메타 읽기 [원문·실측]

- analog DB 뷰어(`DbViewerController`, `/db/tables`, `/db/columns`)가 칼럼별 PK 여부, FK 여부, FK 참조 표(`FK_REF`)를 이미 돌려준다. ERD 1단계 가져오기의 바탕으로 쓸 수 있다.
- 부족한 것: 코멘트, 복합 FK 의 칼럼 짝, 인덱스, 기본값. 그리고 200건 제한·민감 칼럼 차단이 걸려 있다.

## 4. 관계선 복원 문제 (새로 드러난 쟁점)

메모: [J](research-2026-10-09/J-relation-inference.md). 수치는 모두 로컬 L_MAIN 기준이다. 운영 DB 는 확인하지 못했다.

### 4.1 현황 [실측]

- MDMAPUSER: FK 제약 53개(칼럼 짝 62개, 표 쌍 51개). 일부는 PK 가 아니라 UNIQUE 키를 참조한다(예: `COLUMN_PHYS → PHYS_NAME`).
- MCMAPUSER: 표 56개(`flyway_schema_history` 포함, 업무 표 55개), FK 0개. 그중 3개(`TB_MCM_CODE_CATEGORY`, `CODE_DETAIL`, `CODE_MASTER`)는 PK 도 없다.
- 다른 스키마도 FK 0개.
- SQLite→Oracle 전환 때 빠진 것이 아니라 처음부터 없었다. 근거는 두 가지다. git 이력 전체를 대소문자 구분 없이 `references (tb_mcm|tb_sec|tb_mca)` 로 검색해도 이번 보고서 커밋 말고는 나오지 않는다. 옛 SQLite 파일(`src/backend/data/mcm.db` 표 58개, `mls.db`, `caravan-console.db`)에도 `REFERENCES` 를 가진 표가 0개다. 이전 도구가 CHECK·FK 를 옮기지 않는다는 가이드 문장(`oracle-26ai-test-guide.md:294`)은 있지만, 옮길 FK 자체가 없었다.

### 4.2 정책 확인 [원문]

- 금지된 것은 **JPA 연관관계 매핑**이다(`02-structure-naming-constraints.md:267`, ArchUnit 시험 `MdmEntityArchitectureTest.java:40-56`). DB FK 자체를 금지한 규칙은 없다.
- MDM 은 DB FK 를 적극적으로 건다. 다만 선분 참조(`CODE_CATE_ITEM → CATE·ITEM`)와 `RULE_SET.RULE_IDS` 는 일부러 FK 를 걸지 않는다.
- 모듈 사이 FK·JOIN·뷰는 금지다(`adr/0003-module-boundary-screens-roles.md:34`).
- "MCM 에 DB FK 를 걸지 마라"는 명시 규칙은 없다. MCM 에 FK 가 없는 것은 정책이 아니라 관행으로 보인다.

### 4.3 추정 방법 실측 [실측]

MDM 의 FK 를 정답으로 놓고 잰 값이다.

| 방법 | 후보 | 정밀도(표 쌍) | 재현율(표 쌍) | 비고 |
|---|---|---|---|---|
| A. 칼럼명 규칙(다른 표의 PK 와 같은 이름, 감사 칼럼 제외) | MDM 70 | 0.57 | 0.78 | PK 기준이 필수. 같은 이름 전부를 잡으면 13,868쌍(정밀도 0) |
| B. JPA 엔티티 | 0 | - | 0 | 연관 어노테이션이 0건(금지 정책) |
| C. SQL 조인(Java 문자열·mapper XML 의 `a.X = b.Y`) | MDM 8 | 0.88 | 0.14 | 이름이 다른 참조를 잡는다. 별칭 해석률 56% |
| D. MDM 컬럼 사전 | 거의 0 | - | 거의 0 | `REF_KIND` 가 채워진 행이 1개뿐 |

- MCM 에 적용하면 A 94쌍, C 19쌍, 사람이 쓴 dbml 29쌍이 나온다. 합치면 104쌍이고, 56표(`flyway_schema_history` 포함) 중 49표에 관계가 하나 이상 걸린다.
- dbml 이 덮는 24표 안에서 A 는 정밀도 0.57·재현율 0.93, C 는 0.89·0.28 이다.
- 사람이 확인할 후보는 A 또는 C 에 있으면서 dbml 에 없는 75쌍이다. `USER_ID` 처럼 부모 후보가 여러 개인 허브 칼럼이 많다(후보 있는 자식 칼럼의 42%). 허브 칼럼을 접으면 40~50쌍으로 줄 것으로 추정한다(시험 안 함).

### 4.4 ERD 설계에 주는 시사점 [추론]

1. 모델에 **관계 상태**가 필요하다: DB 확정 / 추정 / 사람 확정 / 기각. 추정 관계는 점선으로 그리고 근거(PK 이름 일치, SQL 파일:줄, 문서)를 툴팁으로 보여 준다.
2. 사람의 확정·기각은 모델에 저장해서 다시 가져올 때도 유지한다.
3. 후보 생성 순서는 DB FK → 사람이 쓴 문서(dbml·mermaid 가져오기) → SQL 조인 → 칼럼명 규칙이다.
4. 허브 칼럼은 이름이 가장 가까운 부모 하나만 점선으로 그리고 나머지는 "다른 후보 n개"로 접는다. 부모 후보에 UNIQUE 키를 포함한다.
5. ERD 에서 확정한 관계를 **DB FK 로 실제로 걸지**, 논리 관계로만 둘지는 정책 결정이다(10.2절).

### 5.2 ERD Editor 에서 가져올 설계 [원문]

- 저장 구조: `collections` 에 table·column·relationship·index·memo 를 id 맵으로 평평하게 두고, 순서와 소속은 id 배열(`table.columnIds`)로 나타낸다.
- 관계: `start`/`end` 에 `{tableId, columnIds[]}` 를 두어 복합키 FK 를 칼럼 짝으로 표현한다. `onDelete`/`onUpdate` 를 따로 둔다.
- 식별 여부, 표 높이 같은 파생값은 저장하지 않고 계산한다.
- 편집: 액션(`table.add`, `column.changeName` 등) 단위, 실행 취소는 스냅샷이 아니라 **역액션**이다. id 는 클라이언트가 만든다.
- 협업: CRDT 라이브러리가 아니라 액션 로그 + 필드별 최종 기록 우선(LWW, Lamport 시계)이다.
- 버릴 점: 컬럼 타입이 문자열 하나라 길이·정밀도가 구조화되어 있지 않다. 논리명·도메인·용어 칸이 없다. 옵션을 비트 플래그로 저장해 JSON 을 읽기 어렵다.

  - 고정 ID 기반 V 파일 초안 생성, Oracle 함정 경고, 템플릿 PDB 검증, drift 검사
  - exERD·Data Modeler 파일 가져오기, DBML·Mermaid 내보내기
  - 표 정의서(HTML·CSV·엑셀) 출력
  - 모델 비교·병합, 문제 자동 수정(Ctrl+1 방식)
  - 보기 프리셋, 논리·물리·주석 동시 편집
- **넣지 않을 것**
  - 여러 DBMS 방언 지원(Oracle 하나)
  - CRDT 기반 동시 편집(명령 + revision 으로 충분)
  - CWM·XMI 같은 교환 표준 직접 구현
  - 서브타입 같은 고급 논리 모델링(수요가 생기면 다시 본다)

### 6.2 권장 [추론]

- **저장 모델은 자체 구조로 한다.** 위 포맷 중 논리명·도메인·주제 영역·좌표·고정 ID 를 모두 담는 텍스트 포맷은 없다. 뼈대는 exERD 메타모델(표와 "다이어그램에 놓인 표"를 분리)과 ERD Editor 의 정규화 구조(id 맵 + 순서 배열)를 합친 형태가 맞다.
- **가져오기 우선순위:** ① exERD(논리명·물리명·도메인·업무영역·좌표가 거의 1:1. 사내에 exERD 파일이 얼마나 있는지는 확인하지 못했다) ② Oracle Data Modeler(Oracle 전용, GUID) ③ DBML(이미 MCM dbml 문서 29관계가 있다) ④ 나머지는 수요가 있을 때.
- **내보내기:** Oracle DDL, DBML, Mermaid(문서 삽입용), 표 정의서(HTML·CSV·엑셀).
- **Claude 가 읽는 형식:** DBML 과 비슷하되 논리명·도메인·용어 ID·관계 상태를 담는 자체 텍스트. DBML·DDL·Mermaid 의 정확도와 토큰을 같은 스키마로 비교한 공개 연구는 찾지 못했으므로 우리 스키마로 실측해서 고른다. 칼럼 설명을 넣으면 Text-to-SQL 정확도가 20% 이상 오른다는 연구는 있다[2차].
- **git 에 둘 경우의 파일 구성:** 객체당 파일(표 하나에 파일 하나, 파일명은 고정 ID), 좌표·다이어그램은 별도 파일, 키·속성 정렬 고정. Oracle Data Modeler 가 이 구조의 실물 사례다. 매핑을 한 파일에 몰아넣지 않는다.

## 7. 정본과 마이그레이션 생성

메모: [C](research-2026-10-09/C-diff-sot.md)(웹, 대부분 [2차]), [H §7](research-2026-10-09/H-erd-editor-src.md).

### 7.1 diff → ALTER 도구

| 도구 | Oracle | 이름 변경 처리 |
|---|---|---|
| Atlas | 지원하나 Oracle 드라이버는 Pro(유료)[2차] | `renamed_from` 힌트를 명시한다. 힌트가 없으면 비대화형에서는 DROP+CREATE 로 데이터가 사라진다 |
| Redgate Flyway 비교 | 지원 | 이름·위치·타입 유사도로 추정한다. 누락·오탐이 있다고 문서에 적혀 있다 |
| Liquibase diffChangeLog | diff 계열은 Pro | 확인 안 됨 |
| Oracle `DBMS_METADATA_DIFF.COMPARE_ALTER` | 내장 | 객체 단위. 스키마 단위 API 는 없다 |
| drawDB `generateMigrationSQL` | 분기는 있음(정확성 미검증) | **고정 id 로 짝지어** 이름만 바뀌면 RENAME 으로 낸다[원문] |

결론[추론]: 모델에 고정 ID 를 두면 이름 변경 판별에 휴리스틱도 힌트도 필요 없다. 구상 문서 7절 P3 의 "모델에 고정 ID" 방향이 맞다. 외부 도구를 들이지 않고 고정 ID 기반 diff 를 직접 만드는 쪽이 비용 대비 낫다. Atlas 는 유료이고 Flyway 형식 출력도 확인되지 않았다.

### 7.2 Oracle ALTER 에서 사람이 판단해야 하는 것 [2차·원문]

- 컬럼 길이 축소: 값이 있으면 ORA-01441.
- NOT NULL 추가: NULL 이 있으면 ORA-02296. 값을 채운 뒤 MODIFY 한다.
- 컬럼 순서 변경 명령이 없다. INVISIBLE 토글로 맨 뒤로 보내는 우회만 있다.
- 표 이름 변경(`RENAME TO`)은 제약·인덱스 이름을 바꾸지 않는다. 명명 규칙(`PK_<표>`)을 지키려면 따로 바꿔야 한다.
- DDL 은 참조하는 뷰·프로시저를 무효화한다.
- 큰 표의 구조 변경은 `DBMS_REDEFINITION` 이 필요할 수 있다.

이 항목들은 자동으로 확정할 수 없다. 그래서 생성기는 "초안 + 경고"를 내고 사람이 확정하는 단계가 필요하다. 생성한 V 파일은 `pdb.mjs template-schema` 로 템플릿 PDB 에 적용해 검증할 수 있다.

### 7.3 정본 안 비교 [추론]

| 안 | 장점 | 단점 |
|---|---|---|
| (가) Flyway 정본, ERD 는 보기·초안 | 지금 체계를 바꾸지 않는다. 운영 적용이 명확하다 | ERD 를 거치지 않은 변경 때문에 모델이 늘 뒤처진다. 결국 매번 DB 를 다시 읽어 와야 한다 |
| (나) ERD 정본, V 파일은 결과물 | 설계가 한곳에 모인다. 이름 변경을 모델에서 명시할 수 있다 | 머지된 V 파일은 고칠 수 없어 과거 이력은 모델로 재현되지 않는다. 생성기 오류가 바로 운영 위험이 된다 |
| 중간안: 모델은 설계 정본, V 파일은 적용 정본 + drift 검사 | 기존 V 파일을 그대로 둔다. 모델 변경은 V 초안으로 떨어지고 사람이 확정한다. 둘이 어긋나면 drift 검사가 잡는다 | "어긋나면 V 파일이 이긴다"는 규칙을 문서로 정해야 한다. drift 검사를 만들어야 한다 |

조사 근거는 중간안 쪽이 가장 많다. drift 검사는 "V 파일을 템플릿 PDB 에 적용한 결과"와 "모델에서 만든 기대 스키마"를 비교하는 방식이 우리 환경에 맞다.

## 8. Claude Code 연동

메모: [D](research-2026-10-09/D-ai-mcp.md)(웹, [2차] 위주), [H §3](research-2026-10-09/H-erd-editor-src.md)([원문]).

### 8.1 기존 사례

- 스키마를 **명령 단위로 편집**하는 공개 MCP 서버는 ERD Editor 의 `packages/mcp-server` 하나뿐이다[원문]. 나머지(Supabase, Prisma, Oracle SQLcl `sql -mcp`, DBHub, SchemaCrawler)는 조회나 SQL 실행 위주다[2차].
- ERD Editor MCP 의 특징[원문]:
  - stdio, tool 56개(세션 8, 표 8, 컬럼 11, 관계 6, 인덱스 8, 메모 6, 설정 3, 가져오기 5, `erd_batch` 1).
  - 에디터 창이 열려 있으면 로컬 소켓으로 협업 상대처럼 합류해 화면에 바로 보이고, 없으면 파일을 직접 고친다.
  - `erd_batch` 는 최대 100개 연산을 사본에 먼저 시험한 뒤 전부 적용하거나 전부 버린다. 앞 연산이 만든 id 를 `$name` 으로 참조한다. 실행 취소 한 번에 묶음 전체가 되돌아간다.
  - 오류 코드는 `unknownTool`, `invalidArgs`, `notFound`, `tooLarge` 4가지이고, 메시지에 해결 방법이 들어 있다.
  - 읽기 응답은 40,000자 상한, `erd_list` 는 표 100개씩 페이지로 나눈다.
  - 약점: `erd_add_column` 이 빈 컬럼만 만들어 이름·타입마다 호출이 따로 필요하다. 이름 중복·예약어·길이 같은 의미 검증이 없다.

### 8.2 우리 설계 권장 [추론]

- 구상 문서 4절의 "세 입구가 같은 명령 API" 구조가 맞다. 상태는 서버가 가지고, MCP 와 CLI 는 얇게 감싼다. CLI·스킬만으로는 열린 캔버스에 실시간 반영이 안 된다.
- `addColumn` 은 논리명 하나로 부를 수 있게 한다. 서버가 `columnMng/compare` 로 물리명·도메인을 채우고, 모호하면 후보를 오류가 아닌 결과로 돌려준다.
- 표준 검증 결과는 프로토콜 오류가 아니라 tool 결과로 돌려준다: `{ok:false, errors:[{code, path, message, candidates?, suggestedAction}]}`. MCP 명세도 입력 검증 오류를 tool 실행 오류로 돌려주라고 권한다[2차].
- `batch` 는 전부 성공하거나 전부 실패하게 하고, `$name` 참조와 dry-run(검증만 하고 저장하지 않음)을 둔다. dry-run 기본, `--apply` 로 저장하는 `register-columns.mjs` 패턴과 같다.
- 모든 명령에 기준 revision 을 싣고, 다르면 충돌 오류와 최신 변경 요약을 돌려준다(낙관적 잠금).
- 명령 로그를 정본 기록으로 두고 행위자(사람 / Claude + 세션 ID)를 남긴다. 실행 취소, 행위자 구분, SSE 재생이 같은 기록에서 나온다.
- 실시간 반영은 SSE(마지막 revision 이후 재생)로 충분하다. 관계형 스키마 편집에 CRDT(Yjs)는 과하다. Yjs 의 실행 취소 관리자는 사용자별 기록 구분에 맞지 않는다[2차].
- MCP SDK 는 `@modelcontextprotocol/sdk` 다. 최근 패키지가 나뉘었다는 자료가 있어 설치 버전에서 import 경로를 확인해야 한다[2차].
- **인증 공백:** 로컬은 client-key 헤더로 충분하다. 운영에서 사용자별로 Claude 의 편집을 막거나 기록하려면 토큰 방식이 필요하다. 개발 기간 보안 정비는 보류 중이므로 1단계는 로컬 전용으로 시작하는 것이 현실적이다.

## 9. 데이터 표준화

메모: [E](research-2026-10-09/E-standards.md)(웹, [2차]).

- 행정안전부 공공데이터 공통표준은 표준단어·표준용어·표준도메인으로 구성된다. 포털 메타데이터는 8차 제·개정(2025.11) 기준이다[2차]. 우리 MDM 의 용어·도메인·컬럼 3단 구조와 같은 틀이다.
- 변환 알고리즘 권장안(표준용어 통째 일치 → 표준단어 최장 일치 → 후보 점수화 → 사용자 선택, 미등록 토막은 등록 요청으로)은 우리 `ColumnNameComposer` 가 이미 하는 방식과 같다. 다른 점은 "후보가 여럿이면 자동 확정하지 않는다"는 exERD 규칙이다. ERD 화면이 이 규칙을 지키면 된다.
- 위반 유형 목록(ERD 검사 규칙 후보): 비표준 단어, 분류어(일자·명·코드·여부·금액) 누락, 분류어와 도메인 불일치, 타입·길이가 도메인과 다름, 동음이의어, 이음동의어, 금칙어, 물리명 길이·문자·예약어, 한 단어에 약어 둘.
- Oracle 식별자 한도는 12.2 이상 128바이트다. 30자 제한은 조직 규칙으로 따로 정해야 한다. ERD Editor 의 Oracle DDL 생성기도 30바이트 초과를 경고한다[원문].
- 한글이 섞이는 칸은 `VARCHAR2(n CHAR)` 가 안전하다는 것이 관례다[2차]. 도메인의 길이 단위(BYTE·CHAR) 규칙을 확인해야 한다.
- 표준용어 등록 요청 흐름은 공공 절차 원문을 찾지 못했다. 일반 흐름(신청 → 형식 검토 → 중복 검토 → 심의 → 반영)을 MDM 에 이미 있는 등록 화면과 맞춰 보면 된다.

## 10. 결정 거리

결정을 재촉하지 않는다. 근거와 조사 쪽 판단만 적는다.

### 10.1 구상 문서의 기존 결정 3건

1. **정본은 어디인가?**
   - 조사 쪽 판단: 중간안(7.3절). 고정 ID 기반 diff 로 V 초안을 만들고, 사람이 확정하고, 템플릿 PDB 로 검증하고, drift 검사로 어긋남을 잡는다.
   - SQL Developer Data Modeler 와의 관계: 이 도구를 쓰더라도 MDM 용어·도메인 연동과 Claude 편집은 안 된다. 다만 `.dmd` 가져오기를 지원하면 함께 쓰는 길도 열린다.
2. **ERD 모델을 MDM 버전 객체로 둘 것인가?**
   - 핵심 제약: 버전 엔진은 객체 ID 하나를 키로 쓴다(3.2절).
   - 선택지:
     - (a) 모델 전체 = 객체 하나: 편집자 한 명.
     - (b) 모듈(스키마) = 객체 하나: 모듈별로 DRAFT 를 따로 잡을 수 있다. 모듈 사이 FK 금지 규칙(ADR 0003)과도 경계가 맞는다.
     - (c) 버전 객체로 두지 않고 명령 로그 + revision 만 쓴다.
   - 조사 쪽 판단: (b) 가 엔진과 모듈 경계에 맞는다[추론].
3. **exERD 동작 중 꼭 필요한 것과 뺄 것은?** 2.1절 판정표와 2.3절 목록에서 고른다. 조사 쪽 판단으로 1단계 필수 후보는 2.3절 1·3·5·7·8·9번이다.

### 10.2 조사로 새로 생긴 결정 거리

4. **모델 저장 위치:** 구상 3절은 Flyway 로 만든 Oracle 표에 둔다. 포맷 조사는 git 에 객체당 파일로 두는 방식을 권한다.
   - DB 표: 화면·MCP 실시간 반영, MDM 버전 엔진 재사용이 쉽다. 대신 V 파일 PR 과 모델 변경을 함께 리뷰하기 어렵다.
   - git 파일: 코드 리뷰·브랜치와 함께 움직인다. 대신 실시간 편집·잠금을 따로 만들어야 한다.
   - 절충: DB 를 작업 정본으로 두고, V 초안을 만들 때 모델의 결정적 텍스트 스냅샷(객체당 파일)을 함께 커밋한다[추론].
5. **MCM 등 FK 없는 스키마의 관계:** ERD 에서 확정한 관계를 DB FK 로 실제로 걸지, 논리 관계로만 둘지 정해야 한다. 지금은 금지 규칙도 권장 규칙도 없다(4.2절).
6. **1단계에서 추정 관계를 다룰 것인가:** 다루지 않으면 MCM ERD 에는 관계선이 없다. 다룬다면 관계 상태(DB 확정 / 추정 / 사람 확정 / 기각)를 모델에 넣어야 한다.
7. **가져오기 우선순위:** exERD → Oracle Data Modeler → DBML(6.2절). 사내에 exERD 파일이 실제로 얼마나 있는지가 판단 근거다.
8. **DDL 서식 규칙:** oracle-sql-rules 에 DDL 서식이 없다. 생성기를 만들기 전에 정해야 한다. ADR 0001(이름 규칙)도 PROPOSED 상태다.
9. **CLI·MCP 운영 인증:** 1단계를 로컬 전용으로 할지 정한다.

### 10.3 단계 안 보완 제안 [추론]

구상 7절 단계에 조사 결과를 반영하면 다음과 같다.

- **P1 가져오기와 뷰어**
  - DB 가져오기는 analog 뷰어 API 를 넓혀 코멘트·복합 FK·인덱스·기본값까지 읽는다.
  - 관계 후보를 생성한다(DB FK → dbml 문서 → SQL 조인 → 칼럼명 규칙). 추정 관계는 점선으로 그린다.
  - 논리명은 `COLUMN_SYSTEM` 별칭까지 포함한 사전 대조로 채운다(행 기준 70% 안팎).
  - 표준 위반을 표시한다.
  - MCP 읽기 tool 과 DBML 비슷한 읽기 텍스트를 만든다.
- **P2 편집:** exERD 동작 필수 항목, `compare` API 연동(후보가 하나일 때만 자동), 명령 API·batch·revision·명령 로그, MCP·CLI 쓰기.
- **P3 V 초안 생성:** 고정 ID 기반 diff, Oracle 함정 경고, 템플릿 PDB 검증, drift 검사.
- **P4 그 뒤:** exERD·Data Modeler 파일 가져오기, 표 정의서 출력, 모델 비교·병합.

## 11. 확인하지 못한 것

- exERD 그리드의 Tab·방향키 이동 규칙, Oracle 용 `.exerd` 실물, 설명(comment) 속성 이름.
- 운영 DB 의 FK·코멘트 현황. 이번 수치는 모두 로컬 L_MAIN 기준이다.
- 허브 칼럼 규칙의 실제 효과, SQL 파서를 도입했을 때의 개선 폭.
- `compare` API 를 수백 컬럼에 일괄로 부를 때의 시간. 한 번 부르는 시간만 쟀다.
- Atlas 의 Oracle·Flyway 지원 범위(유료 여부), Liquibase 의 이름 변경 처리 원문.
- DBML·DDL·자체 텍스트 중 Claude 가 가장 정확하게 읽는 형식. 우리 스키마로 실측해야 한다.
- 사내에 exERD·ERwin·Data Modeler 파일이 얼마나 있는지.
