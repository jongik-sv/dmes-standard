# 화면 성능 audit 경고 분류표

audit 가 낸 화면 성능 경고를 진짜 위반과 오탐으로 가른 결과다. 코드는 읽기만 했고 고친 것은 없다. 다음 수정 작업의 목록과 audit 규칙 개선의 근거로 쓴다.

- **기준 커밋**: dev `070ca0fd`
- **실행 명령**: `python3 .claude/skills/mantine-aggrid-ui/scripts/aggrid_docs.py audit src/frontend/m-mdm src/frontend/m-mcm src/frontend/m-mls src/frontend/shared/src` (1185개 파일 점검, 성능 경고 50건)
- **제외**: P-R12b 2건(`dma/unitMng`·`dmd/dataItemMng`)은 다른 세션이 고치는 중이라 표에 넣지 않았다. 나머지 48건 중 P-R1 28건·P-R6 19건·P-R14 1건을 판정했다.
- **방법**: 영역별 조사 3갈래(m-mdm dma·dmd·dmc, m-mdm dmb·dme, m-mcm·m-mls)로 초안을 만들고, audit 재실행 결과 47건(P-R1·P-R6)과 파일·줄 단위로 빠짐없이 대조했다. 표본으로 `ruleConfirm`·`query-table`·`noticeMgmt`·`unitMng` 의 코드를 다시 읽어 근거를 확인했다.

- **P-R6**: 19건 전부 실제로 0건을 조건으로 그리드를 내리는 3항 구조라 오탐이 없다. 대부분 그리드에 같은 문구의 `emptyMessage` 가 이미 있어 3항만 걷으면 된다. 재생성 빈도가 높은 것(목록 조회 결과·확정 대기 목록·위젯)과 카드·모달 안의 부수 그리드(경량)로 나뉜다.
- **P-R14**: 가이드가 확정한 잠재 위치 1건이다.

## 위반 우선순위 상위 5건

데이터 규모와 사용 빈도 기준이다.

1. **공지사항 관리 `searchNotices`**(P-R1, `m-mls/pages/lsh/noticeMgmt/page.tsx:191`): 유일한 중대 위반이다. 서버 LIMIT 이 없고 목록 행마다 본문(최대 20만 자)을 실어 보낸다. 공지가 누적되면 응답이 수 MB 까지 커진다. 목록에서 본문을 빼고 상한과 `GridLimitNotice` 를 넣는다.
2. **홈 쿼리표 위젯 `query-table`**(P-R6, `m-mcm/widget-types/query-table/renderer.tsx:41`): 홈 진입마다 모든 사용자가 거치는 경로이고, 0건과 N건이 오갈 때마다 그리드를 새로 만든다. 3항을 걷고 `emptyMessage` 로 안내한다.
3. **마루 코드·마루 데이터 빈 조건 조회**(P-R1 애매, `dmc/codeMng/page.tsx:173`·`dmd/dataMng/page.tsx:146`): 마루 코드는 외부 코드까지 포함해 수천 건이 될 수 있다. 먼저 운영 `TB_MDM_CODE`·`TB_MDM_DATA` 행 수를 확인하고, 1,000건을 넘으면 상한·`truncated`·`GridLimitNotice` 를 적용한다. handoff 진입의 자동 빈 조건 목록 조회는 상세만 열도록 바꾼다.
4. **조회 결과를 직접 그리는 목록 3형제**(P-R6, `dmb/headerMng/components/HeaderList.tsx:32`·`dmb/layoutMng/components/LayoutList.tsx:32`·확정 화면 4곳): `HeaderList` 는 가이드 R6 의 확정 근거 사례다. 확정 화면(`layoutConfirm`·`ruleConfirm`·`ruleSetConfirm`·`codeConfirm`)은 진입 자동 조회와 확정 뒤 재조회마다 0건과 N건이 오간다. 기계적으로 고칠 수 있다.
5. **코드 편집 IdPicker `searchCodes`**(P-R1 애매, `dmc/codeItemEdit/page.tsx:50`): 클라이언트는 20건으로 자르지만 서버는 빈 키워드에 전체 마루 코드를 반환한다. `search` action 이 `limit` 을 받아 서버에서 자르면 동작을 바꾸지 않고 응답만 줄일 수 있다.

## audit 규칙 개선 제안

1. **조건 검색 호출 제외(P-R1)**: 호출부가 사용자 조작 핸들러(버튼·Enter·`onChange`) 안에 있고 서버가 빈 키워드를 조기 반환하거나 상한으로 자르는 경우다. `IdPicker`·`DomainField` 의 `search={fn}` 전달 패턴과 `typeahead` 호출을 경고 밖으로 둔다(오탐 `ruleSetEdit`·`ColumnSettingsSection`·`domainMng` 부모 후보·`layoutMng` 영향도).
2. **클라이언트 상한 인식(P-R1)**: 호출 결과를 `.slice(상수)` 로 자르거나 `*_LIMIT` 상수와 안내 문구를 가진 경우는 상한이 있다고 보되, 서버 응답이 무제한이면 정보성으로 남긴다(`codeItemEdit`·`domainMng`).
3. **콤보 옵션 전용 조회 제외(P-R1)**: 결과가 그리드 `data` 가 아니라 `Select`·`MultiSelectComboBox` 옵션 상태로만 쓰이면 제외한다(`commObjMng` `searchSystemLov`·`noticeMgmt` `searchRoles`).
4. **필수 인자가 있는 호출 제외(P-R1)**: `searchXxx(필수 인자)` 처럼 비어 있지 않은 첫 인자를 넘기는 호출은 조건 있는 조회로 본다(`termRegPop`).
5. **서버 상태 필터 목록의 판정 근거(P-R1)**: 확정 대기 목록처럼 서버가 `status='DRAFT'` 만 돌려주는 조회는 자연 상한으로 보는 기준을 가이드에 적고, 정적 분석으로 못 보는 것은 수동 예외 목록으로 관리한다(`codeConfirm`·`layoutConfirm`·`ruleConfirm`·`ruleSetConfirm`).
6. **`&&` 조건부 렌더로 확장(P-R6)**: 3항뿐 아니라 `{cond && <AgDataGrid/>}` 와 빈 상태 형제 `<p>` 조합도 잡는다. `layoutMng/components/ImpactPanel.tsx:51-66` 이 같은 문제를 가졌는데 3항이 아니라서 걸리지 않았다.
7. **P-R14 잠재 위치(P-R14)**: 가이드가 이미 확정하고 코드를 고치지 않기로 한 `WidgetFrame` 의 `refreshSec` 타이머는 경고 대신 정보성으로 낮춘다. 그렇지 않으면 audit 를 돌릴 때마다 같은 경고가 남는다.
8. **운영 행 수 확인 표시**: 애매 6건이 모두 운영 DB 행 수에 달렸다. 마스터 행 수를 모아 두는 표나 설정을 audit 가 읽을 수 있으면 사람이 판정하는 비용이 줄어든다.
