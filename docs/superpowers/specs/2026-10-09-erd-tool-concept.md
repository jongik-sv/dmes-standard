# DB 설계 도구(ERD) 구상

- 작성일: 2026-10-09
- 상태: 구상(설계 전). 아래 "설계 전에 정할 것" 3건이 정해지면 brainstorming 으로 설계에 들어간다.
- 출발점: 마음에 드는 ERD 도구가 없다. dbdiagram.io 정도의 화면은 직접 만들 수 있고, 우리 MDM 의 도메인·컬럼·용어를 쓸 수 있으니 다른 도구보다 낫다고 본다. 편집 사용성은 exERD 방식을 따른다. Claude Code 와 연결되어 MCP·CLI 로도 편집할 수 있어야 한다.

## 0. 처음 생각에서 바뀐 점

- 처음에는 dbdiagram 처럼 왼쪽 텍스트(DBML)를 쓰면 오른쪽에 도면이 그려지는 방식을 생각했다. 그래서 "텍스트에서 도면으로 가는 한 방향부터", "2단계는 용어 자동 완성이 붙은 DBML 편집기"를 제안했으나, 이 두 가지는 철회한다.
- exERD 방식은 캔버스와 컬럼 그리드를 직접 편집하므로 도구의 중심은 **구조화된 모델**(표, 컬럼, 관계, 다이어그램, 위치)이다. DBML 같은 텍스트 형식은 가져오기·내보내기용, 그리고 Claude 가 모델을 읽는 형식(4절)으로 쓴다.
- 자동 배치는 룰 세트 편집기의 dagre 로 해결된다. 진짜 어려운 부분은 **모델과 DB 의 차이를 Flyway ALTER 파일로 만드는 일**이다.
- 2026-10-07 에 Oracle SQL Developer(Data Modeler) 를 설계 도구로 쓸 예정이라고 했다. 이 도구를 만들면 그 계획을 접을지는 아래 결정 1번에 따라 달라진다.

## 1. 따라 할 exERD 사용성

아래는 exERD 동작에 대한 가정이다. 실제 확인한 사실이 아니므로 꼭 필요한 것과 뺄 것을 사용자가 골라야 한다(결정 3번).

- 논리명과 물리명을 버튼 하나로 전환해서 본다.
- 부모 표에서 자식 표로 관계를 그으면 FK 가 생기고 PK 컬럼이 자식으로 옮겨진다.
- 식별 관계와 비식별 관계를 구분한다(식별 관계면 옮겨진 컬럼이 자식 PK 가 된다).
- 표를 고르면 옆 패널의 그리드에서 컬럼을 키보드만으로 연달아 입력한다.
- 모델 하나에 주제 영역 다이어그램을 여러 개 둔다. 같은 표가 여러 다이어그램에 나올 수 있다.
- 논리명을 입력하면 단어 사전으로 물리명을 만들고, 도메인을 고르면 타입과 길이가 정해진다.

## 2. MDM 연동 (직접 만드는 이유)

필요한 MDM 표는 이미 있다.

| 기능 | 근거가 되는 표 |
|---|---|
| 논리명 → 물리명 자동 변환 | `TB_MDM_TERM`, `TB_MDM_DICT_SYSTEM` |
| 도메인 → 타입·길이 | `TB_MDM_DOMAIN` |
| 표준 컬럼 재사용, 코멘트 | `TB_MDM_COLUMN`, `TB_MDM_COLUMN_SYSTEM` |
| 사용자가 확정한 서식으로 Oracle DDL 생성 | oracle-sql-rules 4장 |
| 실제 DB 를 거꾸로 읽어 표준 위반 표시 | `ALL_TAB_COLUMNS` 와 MDM 대조 |

- 표준 위반을 나중에 검사하는 데서 그치지 않고 **입력하는 순간 막거나 경고**한다. 상용 도구와 가장 크게 차이 나는 점이다.
- 사전에 없는 단어를 쓰면 그 자리에서 표준용어 등록 요청으로 이어 붙일 수 있다.
- 걸리는 점: 2026-10-09 기준 리포 SQL 파일에 `CREATE TABLE` 은 350건(중복 제거 표 136개)인데 `COMMENT ON COLUMN` 은 54건뿐이다. 기존 DB 를 거꾸로 읽어도 논리명은 거의 얻을 수 없다. 논리명은 컬럼 사전과 물리명을 맞춰 보는 방식으로 채우고, 사전에 없는 컬럼은 1단계에서 바로 "표준 위반"으로 드러낸다.

## 3. 모델 저장 위치와 동시 편집

- 모델은 Flyway 로 만든 새 Oracle 표에 둔다. 다이어그램별 위치는 룰 세트의 `view.positions` 와 같은 방식으로 따로 저장한다.
- 여러 사람이 편집하는 경우 새 장치를 만들지 않고 MDM 객체 버전 관리와 잠금 방식을 다시 쓴다.
- Claude 의 편집도 같은 잠금을 거친다(4절).

## 4. Claude Code 연동 (MCP·CLI)

편집 명령을 화면 밖 서버 API 한 곳에 둔다. 화면, MCP, CLI 가 모두 이 API 를 쓴다.

```
화면(캔버스·그리드) ─┐
MCP 서버 ───────────┼─→ 모델 편집 API (명령 단위) ─→ 표준 검증 ─→ 모델 표
CLI (.mjs) ─────────┘
```

- 세 입구가 같은 명령(`addTable`, `addColumn`, `addRelation`, `renameColumn`, `moveToDiagram` 등)을 쓴다. 그래야 Claude 의 편집도 표준 검증과 잠금을 똑같이 거친다. 화면에만 있는 편집 로직을 만들면 Claude 쪽이 따라가지 못한다.
- 읽기 도구: 모델 전체나 주제 영역을 DBML 비슷한 간결한 텍스트로 돌려준다. Claude 가 토큰을 적게 쓰고 구조를 파악할 수 있다.
- Claude 가 편집하는 동안 열려 있는 캔버스에 변경이 바로 보여야 한다(SSE 나 폴링). 실행 취소 기록에는 누가 고쳤는지(사람인지 Claude 인지) 남긴다.
- CLI 는 윈도우 사용자도 쓰므로 node `.mjs` 로 만든다. MCP 서버는 같은 API 를 감싸기만 한다.
- 기대하는 흐름: "이 화면 요구사항으로 표 설계해 줘" 를 Claude 가 표준을 지키며 모델에 넣고, 사람은 캔버스에서 검토한다.

## 5. 규모

- 2026-10-09 기준 표 136개(MDM 57, MCM 47, SEC 10 등). APS·MES 가 붙으면 수백 개가 된다.
- 모듈별 주제 영역은 필수다.
- 컬럼 행마다 관계선 손잡이를 두면 화면 요소가 크게 늘어난다. 축소하면 표 이름만 보이게 하는 처리가 필요하다.

## 6. 룰 세트 편집기 재사용

`src/frontend/m-mdm/pages/dme/ruleSetEdit/` 에서 가져다 쓸 수 있는 것:

| ERD 에 필요한 기능 | 룰 세트 편집기에 있는 것 |
|---|---|
| 캔버스, 노드 | `@xyflow/react` (`canvas/react-flow.ts` 진입점) |
| 자동 배치 | `@dagrejs/dagre` (`flow-layout.ts`), 저장 위치가 자동 배치를 덮는 구조(`view.positions`) |
| 관계선 꺾기·둥근 모서리 | `canvas/route-path.ts` |
| 정렬, 찾기, 단축키 | `canvas/align.ts`, `FindWidget.tsx`, `shortcuts.ts` |
| 우클릭 메뉴, 화면 이탈 방지 | `ContextMenu.tsx`, `ViewportGuard.tsx` |

- 새로 만들 것: 컬럼 목록을 보여 주는 표 노드, 컬럼 행끼리 잇는 관계선 손잡이와 1:N 끝 모양.
- 위 부품은 화면 폴더 안에 있다. 업무와 무관한 부품은 CLAUDE.md 공통 컴포넌트 규칙에 따라 `@dk-oasis/shared` 로 옮겨 함께 쓴다.
- 1단계는 필요한 부품만 shared 로 복사해서 시작한다. 룰 세트 편집기가 shared 부품을 쓰도록 옮기는 리팩토링은 별도 후속으로 남긴다. 당분간 같은 코드가 두 곳에 있지만, 잘 돌아가는 룰 세트 편집기를 건드리지 않는다.

## 7. 단계 (안)

1. **P1 가져오기와 뷰어:** DB 를 읽어 모델에 넣고 컬럼 사전과 맞춰 논리명을 채운다. 표준 위반을 표시한다. 모델 편집 API 의 읽기 부분과 MCP 읽기 도구도 여기서 만든다.
2. **P2 exERD 방식 편집:** 캔버스와 그리드로 편집하고, 용어로 물리명을, 도메인으로 타입을 정한다. 쓰기 API 와 MCP·CLI 쓰기 도구를 함께 만든다.
3. **P3 Flyway 초안 생성:** 모델과 DB 의 차이를 새 V 파일로 만든다. 이미 머지된 V 파일은 고치지 않고 모듈 폴더별 번호 규칙(`flyway-migration-add` 스킬)을 따른다. 이름 변경을 "삭제 후 추가"로 오인하지 않도록 모델에 고정 ID 를 둔다.
4. **P4 그 뒤:** DBML 가져오기·내보내기, drift 감지(ERD 를 거치지 않고 Flyway 를 직접 쓴 경우).
