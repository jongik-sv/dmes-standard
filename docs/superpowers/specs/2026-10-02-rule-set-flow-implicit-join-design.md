## 0. 범위와 승인된 결정

사용자와 브레인스토밍을 마치고 승인받은 방향이다(팀장 전달, 2026-10-02). 이 문서는 승인 내용을 다시 논의하지 않고 정확한 규칙으로 옮긴다.

| ID | 승인된 결정 |
|---|---|
| A1 | 합류(MERGE) 노드는 병렬(PARALLEL)에만 둔다. 병렬 분기는 지금처럼 채운 막대로 그리고, 병렬 합류는 같은 크기의 **이중선 막대**(가는 선 두 줄)로 그린다. 의미(모든 갈래를 기다린 뒤 갈래 순서대로 결과를 합침)는 바꾸지 않는다 |
| A2 | IF 에는 합류를 두지 않는다. 갈래는 다음 노드로 바로 들어가고, IF 블록의 끝(**모이는 자리**)은 갈래가 처음 다시 만나는 노드로 계산한다(직후 후지배자). 들어오는 선이 2개 이상인 노드는 계산된 모이는 자리(IF, 또는 A3 의 돌아오는 자리)이거나 병렬 합류여야 한다. 한 노드가 중첩된 IF 블록 여러 개를 함께 닫을 수 있다 |
| A3 | 받는 노드(CATCH)의 처리 갈래는 돌아오는 MERGE 없이 받은 노드의 정상 경로 위 노드로 바로 돌아온다(**돌아오는 자리**). 한 노드에 붙은 돌아오는 처리 갈래는 모두 같은 노드로 들어가야 한다. 처리 갈래가 END 로 가면 지금처럼 끝냄(`endedBy`)이다. `CATCH_*` 는 돌아오는 자리에 들어갈 때 뺀다(받는 노드 계획 R3·R4 의 순서 그대로). 돌아오는 자리의 경로 상태 규칙은 지금 MERGE 뒤에 쓰던 교집합 규칙이다 |
| A4 | 받는 노드를 빈 단계(TASK)에도 붙일 수 있다. TASK 에 룰을 지정해도 붙은 받는 노드는 남는다. TASK 인 동안은 예외가 날 수 없다는 경고를 낸다(`CATCH_NEVER` 와 같은 수준) |
| A5 | 저장된 흐름에는 IF 합류와 돌아오는 합류(`splitId` = RULE)가 있을 수 있다. 엔진(Java)과 TS 해석기는 옛 형식을 **계속 받아** 그대로 실행·검사한다. 편집기는 열 때 옛 형식을 새 형식으로 바꾸고(합류를 지우고 들어오던 선을 합류 출구 도착으로 잇는다) 새 형식으로 저장한다 |
| A6 | 결정 기록 번호는 D-136 이다(D-134 = 받는 노드, D-135 = 하위 세트 호출 스펙 예약) |
| B1 | (추가 결정) IF 갈래 중간 끝내기를 허용한다. IF 의 어떤 갈래는 END 로 가서 그 자리에서 실행을 끝내고, 나머지 갈래는 다음 노드에서 다시 만나 계속 갈 수 있다. 결과 표기 여부, 블록 끝 계산, 경로 상태(END 로 간 갈래는 교집합에서 뺀다), 병렬 안 IF 에서 END 로 가는 경우(받는 노드의 병렬 안 끝냄과 맞춘다), 엔진 실행, 디버거를 이 문서가 정한다 |
| B2 | (추가 결정) 빈 갈래는 한 IF 에 하나만 허용한다. 같은 출발·도착 선 두 개는 지금처럼 막는다 |

제외(§16): 모이는 자리 강조 표시, 접힌 블록 뒤에 끼우기, 서버 일괄 변환, IF 조건식 오류 받기, 끝내는 갈래와 블록 뒤 노드의 관계 계산 개선.

## 1. 저장 형식

`FLOW_JSON` 모양(노드·선 칸)은 바뀌지 않는다. 쓰는 방법만 바뀐다.

```json
{
  "version": 1,
  "nodes": [
    { "id": "start", "kind": "START" },
    { "id": "r1", "kind": "RULE", "ruleId": "QD_R_GRADE" },
    { "id": "if1", "kind": "IF", "label": "조건" },
    { "id": "r2", "kind": "RULE", "ruleId": "QD_R_PRICE" },
    { "id": "c1", "kind": "CATCH", "attachTo": "r2", "catches": ["NO_RESULT"], "label": "단가 없음" },
    { "id": "r9", "kind": "RULE", "ruleId": "QD_R_PRICE_DEFAULT" },
    { "id": "r3", "kind": "RULE", "ruleId": "QD_R_AMOUNT" },
    { "id": "par1", "kind": "PARALLEL", "label": "병렬" },
    { "id": "r4", "kind": "RULE", "ruleId": "QD_R_TAX" },
    { "id": "r5", "kind": "RULE", "ruleId": "QD_R_FEE" },
    { "id": "m1", "kind": "MERGE", "splitId": "par1" },
    { "id": "end", "kind": "END" }
  ],
  "edges": [
    { "id": "e1", "from": "start", "to": "r1" },
    { "id": "e2", "from": "r1", "to": "if1" },
    { "id": "e3", "from": "if1", "to": "r2", "order": 1, "cond": "GRADE = \"A\"", "label": "갈래 1" },
    { "id": "e4", "from": "if1", "to": "r3", "otherwise": true, "label": "그 외" },
    { "id": "e5", "from": "r2", "to": "r3" },
    { "id": "e6", "from": "c1", "to": "r9" },
    { "id": "e7", "from": "r9", "to": "r3" },
    { "id": "e8", "from": "r3", "to": "par1" },
    { "id": "e9", "from": "par1", "to": "r4", "order": 1 },
    { "id": "e10", "from": "par1", "to": "r5", "order": 2 },
    { "id": "e11", "from": "r4", "to": "m1" },
    { "id": "e12", "from": "r5", "to": "m1" },
    { "id": "e13", "from": "m1", "to": "end" }
  ]
}
```

- `r3` 은 `if1` 의 모이는 자리이면서 `r2` 에 붙은 `c1` 처리 갈래의 돌아오는 자리다. 들어오는 선이 셋(`e4`·`e5`·`e7`)이다. `e4` 는 빈 갈래(IF 에서 모이는 자리로 바로 가는 선)다.
- MERGE 의 `splitId` 는 새 형식에서 PARALLEL 노드만 가리킨다. 옛 형식(IF·받는 노드가 붙은 노드)은 §12 대로 받는다.
- 새 형식 IF 에서 같은 노드로 가는 갈래 선은 하나만 둔다. 그래서 빈 갈래(모이는 자리로 바로 가는 갈래)는 한 IF 에 하나뿐이다(J-D7). 옛 형식 IF(짝 MERGE 가 있음)는 지금처럼 MERGE 로 가는 선이 여럿이어도 받는다.

갈래 중간 끝내기(B1)는 갈래 선이나 갈래 안 마지막 노드의 선을 END 로 이어 그린다.

```json
{
  "nodes": [
    { "id": "start", "kind": "START" },
    { "id": "r1", "kind": "RULE", "ruleId": "QD_R_PRICE" },
    { "id": "if1", "kind": "IF", "label": "단가 확인" },
    { "id": "r8", "kind": "RULE", "ruleId": "QD_R_LOG_NO_PRICE" },
    { "id": "r2", "kind": "RULE", "ruleId": "QD_R_AMOUNT" },
    { "id": "end", "kind": "END" }
  ],
  "edges": [
    { "id": "e1", "from": "start", "to": "r1" },
    { "id": "e2", "from": "r1", "to": "if1" },
    { "id": "e3", "from": "if1", "to": "r8", "order": 1, "cond": "PRICE = NULL", "label": "단가 없음" },
    { "id": "e4", "from": "r8", "to": "end" },
    { "id": "e5", "from": "if1", "to": "r2", "otherwise": true, "label": "그 외" },
    { "id": "e6", "from": "r2", "to": "end" }
  ]
}
```

- `e3` 갈래(`r8`)는 **끝내는 갈래**다. `r8` 을 실행하고 세트를 끝낸다. `e5` 갈래는 **이어지는 갈래**이고 빈 갈래다. `if1` 의 모이는 자리는 `r2` 이고, `r2` 는 IF 블록 뒤 바깥 순차의 노드다.
- `version` 은 1 그대로 둔다(받는 노드 X-D7, D-125 와 같은 판단). 읽는 쪽이 엔진·화면 한 벌씩이고 함께 배포된다.
- 엔진 계약(`FlowNode`·`FlowEdge`·`NodeKind`)의 모양은 바뀌지 않는다. `MERGE` 종류도 남는다. 바뀌는 것은 설명 문구와 실행 기록의 항목 수다(§7).

## 2. 구조 규칙과 모이는 자리

### 2.1 용어

| 용어 | 뜻 |
|---|---|
| `next(x)` | 나가는 선이 하나인 노드 x 의 그 선 도착 |
| `after(x)` | 블록 단위로 본 x 의 다음 노드. 아래 표 |
| 줄기 `spine(x, stop)` | x 에서 시작해 `after` 를 따라간 노드 목록. `stop` 이나 END 에 닿으면 그 노드까지 넣고 멈춘다. `stop` 이 없으면 END 까지 간다 |
| 모이는 자리 `join(s)` | IF 블록이 끝나는 노드(§2.2). 병렬은 짝 MERGE |
| 돌아오는 자리 `J` | 받는 노드 블록이 끝나는 노드(§2.3). 돌아오는 처리 갈래가 없으면 없다 |
| 둘러싼 끝 `stop` | 지금 만드는 순차가 멈출 노드. 루트는 END, IF 의 이어지는 갈래는 그 IF 의 모이는 자리, IF 의 끝내는 갈래는 END, 병렬 갈래는 짝 MERGE, 정상 갈래는 `J`, 처리 갈래는 그 갈래의 도착(`J` 또는 END) |
| 끝내는 갈래·이어지는 갈래 | IF 갈래 가운데 다른 갈래와 만나지 않고 END 로 가서 세트를 끝내는 갈래가 끝내는 갈래, 나머지가 이어지는 갈래다(§2.2) |

| 노드 x | `after(x)` |
|---|---|
| IF | 옛 형식 짝 MERGE 가 있으면 그 MERGE, 없으면 `join(x)` |
| PARALLEL | 짝 MERGE |
| END | 없음(줄기가 멈춘다) |
| 그 밖(RULE·TASK·MERGE·START·CATCH) | `next(x)`. 받는 노드가 붙은 노드도 정상 선의 도착이다. 처리 갈래는 줄기에 들어가지 않는다(받는 노드는 선이 아니라 `attachTo` 로 붙는다) |

줄기를 걷다가 같은 노드를 두 번 만나면 순환이다. 그 노드에서 `FLOW_STRUCTURE` "{id}를 두 번 지난다. 순환이 있거나 갈래가 모이는 자리 밖에서 만난다" 로 멈춘다(§3.3 S6).

### 2.2 IF 의 모이는 자리

1. IF s 에 `splitId = s` 인 MERGE 가 있으면(옛 형식) 그 MERGE 가 모이는 자리다. 계산하지 않고, 끝내는 갈래도 없다(모든 갈래가 그 MERGE 로 닫혀야 한다).
2. 없으면 s 의 갈래를 실행 순서(`ordered()` — "그 외"가 아닌 선을 `order` 오름차순, 그 뒤 "그 외") b0…bk 로 늘어놓고 갈래마다 줄기 `spine(e.to, 없음)` 을 만든다. 줄기에서 END 를 뺀 노드 집합을 N(bi) 라 한다.
3. **끝내는 갈래**: N(bi) 가 다른 모든 갈래의 N(bj) 와 겹치지 않는 갈래다. 다른 갈래와 한 노드도 함께 지나지 않고 END 로 간다는 뜻이다. END 로 바로 가는 갈래(N 이 빔)도 여기에 든다. 나머지가 **이어지는 갈래**다.
4. 이어지는 갈래가 있으면, 실행 순서로 첫 이어지는 갈래의 줄기를 앞에서부터 보면서 다른 모든 이어지는 갈래의 N 에 들어 있는 첫 노드를 모이는 자리로 한다.
   - 그런 노드가 없으면(이어지는 갈래끼리 둘씩만 만나고 모두가 만나는 노드가 없음) 모이는 자리를 END 로 하고 끝내는 갈래는 없는 것으로 본다. 이 흐름은 갈래를 만들 때 S6 이나 S5 로 거부된다.
5. 이어지는 갈래가 없으면(모든 갈래가 서로 겹치지 않고 따로 END 로 감), 실행 순서 **마지막 갈래 가운데 END 로 바로 가지 않는 갈래** 하나를 이어지는 갈래로 하고 그 갈래 선의 도착을 모이는 자리로 한다. 그 갈래는 빈 갈래가 되고 나머지는 끝내는 갈래다. 갈래가 둘 이상이고 같은 노드로 가는 선은 하나뿐이므로(§3.1 f4) END 로 바로 가는 갈래는 많아야 하나라서 이 갈래는 늘 있다.
6. 결과(모이는 자리와 끝내는 갈래 목록)는 해석 한 번 동안 IF ID 로 기억한다. `join(s)` 를 계산하는 도중에 다시 `join(s)` 가 필요하면(줄기가 s 로 되돌아옴) s 에서 S6 으로 멈춘다.
7. 계산은 블록 트리를 만들다가 그 IF 에 **닿을 때** 한다(미리 모든 IF 를 계산하지 않는다). 그래서 "어느 오류를 먼저 내는가"가 지금처럼 트리를 만드는 순서로만 정해지고, 기억해 둔 값을 다시 쓰는 것은 첫 오류를 바꾸지 않는다.

DAG 에서 줄기의 공통 노드는 모든 줄기에 같은 순서로 나온다(어느 줄기에서 c1 이 c2 앞이면 c2 는 c1 에서 닿고, 다른 줄기에서 순서가 뒤집히면 순환이다). 그래서 이어지는 갈래 기준 "첫 공통 노드"는 끝내는 갈래를 뺀 그래프의 직후 후지배자와 같다.

5번 규칙을 둔 까닭: 끝내는 갈래와 이어지는 갈래가 모두 따로 END 까지 가면(예: §1 둘째 예의 `e3`·`e5`) 그래프만으로는 어느 쪽이 "흐름을 잇는" 갈래인지 정할 수 없다. 실행 결과는 어느 쪽으로 정해도 같고, 블록 범위(배치·지우기·관계 계산)만 달라진다. 둘러싼 끝을 보고 정하면 바깥 IF 의 모이는 자리 계산이 안쪽 IF 의 모이는 자리를 먼저 알아야 해서 순환이 생긴다. 그래서 그래프 밖 정보 없이 정해지는 실행 순서 규칙을 쓴다. 편집기 기본 모양(`insertSplit` 의 "그 외")이 흐름을 잇는 쪽이고 — END 앞에 끼울 때도 모이는 자리 빈 단계를 두어 두 갈래가 그 빈 단계에서 모이므로 이 규칙에 기대지 않는다(§8.2, 수정 판정 2026-10-02) — 사용자가 "갈래 1" 을 END 로 다시 이으면 바로 맞는 모양이 된다. 규칙에 어긋나게 그리면(이어질 갈래를 조건 갈래로 두고 "그 외" 에 노드를 두어 END 로 보냄) 루트에서는 뒤 흐름이 끝내는 갈래 안으로 들어가고(실행 결과는 같다), 안쪽 갈래에서는 바깥 모이는 자리를 지나므로 S5 로 거부된다. 조건을 뒤집어 흐름을 잇는 쪽을 "그 외" 로 두면 풀린다. 이 안내는 S5 문구에 넣지 않고(같은 문구가 다른 원인에도 나온다) 화면 도움말·가이드에 적는다.

### 2.3 받는 노드 블록의 돌아오는 자리

받는 노드가 붙은 노드 R(RULE 또는 TASK)에 둘러싼 끝 `stop` 인 순차에서 닿으면 다음 순서로 만든다.

1. 정상 줄기 `S = spine(next(R), stop)` 을 만든다. `stop`(또는 END)까지 넣는다.
2. 받는 노드 c 마다(노드 배열 순서) 처리 줄기 `spine(next(c), 없음)` 을 만들고, 그 가운데 처음으로 S 에 들었거나 END 인 노드를 c 의 도착 `t(c)` 로 한다. 줄기만 계산하고 노드를 방문 처리하지 않는다.
3. `t(c) = END` 인 갈래는 끝내는 처리 갈래, 나머지는 돌아오는 처리 갈래다. 돌아오는 갈래의 첫 도착을 `J` 로 하고, 뒤 갈래의 도착이 `J` 와 다르면 그 받는 노드에서 S7 로 멈춘다. 돌아오는 갈래가 없으면 `J` 는 없다.
4. `J` 가 `splitId = R` 인 MERGE 면(옛 형식) 그것을 블록의 `mergeId` 로도 둔다.
5. 정상 갈래를 `seq(next(R), J)` 로 만든다. `J` 가 없으면 정상 갈래는 비고, R 의 나가는 선은 바깥 순차가 그대로 잇는다(지금과 같다).
6. 처리 갈래를 받는 노드 배열 순서로 `seq(next(c), t(c))` 로 만든다. 처리 갈래 c 를 만드는 동안은 (R, c, `S` 에서 END 를 뺀 집합)을 "지켜보는 정상 줄기" 묶음에 넣는다(§2.4 1). 그 갈래를 다 만들면 뺀다.
7. 바깥 순차에 돌려주는 다음 노드: `J` 가 없으면 `next(R)`, 옛 MERGE 면 `next(mergeId)`, 그 밖이면 `J`.

`J` 는 `S` 의 아무 노드나 될 수 있다. 룰 바로 뒤 노드(정상 갈래가 빈다), 정상 경로 중간 노드, 둘러싼 끝(그 IF 의 모이는 자리나 병렬 합류)도 된다. END 는 `J` 가 될 수 없다. END 로 가는 처리 갈래는 늘 끝냄이다.

### 2.4 블록 트리 만들기(2단계)

지금 `Builder.step`·TS `step` 에 둘러싼 끝 `stop` 을 넘긴다. 노드 하나를 처리하는 순서는 다음과 같다.

1. **정상 경로 침범 검사(새로 둠)**: 지켜보는 정상 줄기 묶음을 안쪽(가장 나중에 넣은 것)부터 보고, cur 가 그 집합에 들어 있으면 S8 로 멈춘다.
2. **방문 검사**: 이미 방문했으면 S6.
3. **종류 검사**: START·END·MERGE 면 "{앞 문구}{cur}로 나간다"(S5·S9).
4. RULE·TASK: 받는 노드가 붙었으면 §2.3, 아니면 한 칸(`RuleStep`·`TaskStep`). RULE 은 `ruleSteps` 에 넣는다.
5. IF: 모이는 자리와 끝내는 갈래를 정하고(§2.2) 실행 순서대로 갈래를 만든다. 이어지는 갈래는 `seq(e.to, join)`, 끝내는 갈래는 `seq(e.to, END)` 이고 `ends = true` 다. 끝내는 갈래 순차의 앞 문구는 "갈래가 end에서 닫히지 않고 " 다(S5). 옛 MERGE 면 그 MERGE 를 방문 처리하고 `next(MERGE)` 를, 아니면 `join` 을 돌려준다.
6. PARALLEL: 지금과 같다(짝 MERGE 까지 갈래를 만들고 `next(MERGE)` 를 돌려준다).

루트는 `seq(next(START), END)` 다. 다 만든 뒤 방문하지 않은 노드가 있으면 "{id}에 도달할 수 없다"(지금과 같다).

### 2.5 "들어오는 선 2개 이상은 모이는 자리만" 이 지켜지는 까닭

따로 검사하지 않는다. 블록 트리를 오류 없이 만들었다면 다음이 늘 참이다.

- 모든 선 u→v 는 u 를 담은 순차가 만든다(RULE·TASK·MERGE 는 `next`, IF·PARALLEL 은 갈래 선, 받는 노드는 처리 갈래 첫 선).
- 그 순차는 v 를 한 칸으로 방문하거나(방문은 흐름 전체에서 한 번뿐, 두 번이면 S6), v 가 그 순차의 둘러싼 끝이라 멈춘다.
- 둘러싼 끝은 IF 의 모이는 자리, 병렬 합류, 돌아오는 자리, END(루트·끝내는 IF 갈래·끝내는 처리 갈래)뿐이다.

그래서 들어오는 선이 2개 이상인 노드는 둘러싼 끝이고, 바깥 순차에서 한 번 더 방문될 뿐이다. 모이는 자리가 아닌 노드로 선이 하나 더 들어오면 S6 또는 S5 가 난다. 코퍼스 사례로 이 성질을 고정한다(§14.2 N5·N6).

### 2.6 경우별 규칙

| 경우 | 규칙 |
|---|---|
| 빈 갈래 `IF → X` | X 가 그 IF 의 모이는 자리일 때만 빈 갈래다. X 가 모이는 자리가 아니면 X 는 그 갈래의 첫 노드다 |
| 빈 갈래 둘(같은 노드로 가는 IF 선 둘) | 1단계 오류 f4(§3.1, J-D7). 빈 갈래는 한 IF 에 하나다 |
| END 로 바로 가는 갈래 `IF → END` | 끝내는 갈래다(그 IF 의 모이는 자리가 END 가 아닐 때). 빈 갈래로 세지 않는다. 노드 없이 그 자리에서 끝낸다 |
| 끝내는 갈래 하나 + 이어지는 갈래 여럿 | 이어지는 갈래들이 처음 만나는 노드가 모이는 자리다. 끝내는 갈래는 몸(END 앞까지 노드)을 가질 수 있다 |
| 끝내는 갈래 여럿 | 받는다. 끝내는 갈래끼리도 노드를 함께 지나면 안 된다(함께 지나면 둘 다 이어지는 갈래가 되어 §2.2 4 로 간다) |
| 모든 갈래가 따로 END 로 감 | §2.2 5 의 실행 순서 규칙으로 이어지는 갈래 하나를 정한다 |
| 끝내는 갈래가 다른 갈래와 노드를 함께 지남 | 끝내는 갈래가 아니다. 이어지는 갈래로 보고 모이는 자리를 계산한다 |
| 중첩 IF 의 끝내는 갈래 | 받는다. 안쪽 IF 의 끝내는 갈래는 바깥 블록과 상관없이 그 자리에서 세트를 끝낸다 |
| 병렬 갈래 안 IF 의 끝내는 갈래 | 받는다. 실행은 받는 노드의 병렬 안 끝냄(X-D11)과 같다(§5) |
| 처리 갈래 안 IF 의 끝내는 갈래 | 받는다. 그 갈래를 타면 처리 갈래가 끝냄이 된다(`endedBy` = 그 받는 노드, §5). 이어지는 갈래는 처리 갈래 안에서 모이거나 돌아오는 자리로 간다 |
| 받는 노드의 정상 갈래 안 IF 의 끝내는 갈래 | 받는다. 그 갈래를 타면 세트가 정상으로 끝난다(`endedBy` 없음) |
| IF 의 모이는 자리가 END | 갈래끼리 END 말고는 모두가 만나는 노드가 없을 때만 생긴다(§2.2 4). 올바른 흐름에서는 생기지 않는다 |
| 중첩 IF 가 같은 노드에서 모임 | 받는다. 안쪽 IF 의 모이는 자리가 바깥 갈래의 둘러싼 끝과 같으면 두 블록이 그 노드에서 함께 닫힌다 |
| 처리 갈래가 룰 바로 뒤 노드로 돌아옴 | `J = next(R)`, 정상 갈래는 비어 있다 |
| 처리 갈래가 정상 경로 중간 노드로 돌아옴 | `J` 앞까지의 정상 경로 노드가 정상 갈래다 |
| 돌아오는 자리가 IF 의 모이는 자리와 같음 | 받는다. 받는 노드 블록이 먼저 닫히고(`CATCH_*` 를 뺀다) 이어서 IF 블록이 닫힌다 |
| 돌아오는 자리가 병렬 합류 | 받는다. 병렬 갈래 안 받는 노드 블록이 합류에서 닫힌다. 병렬 합류는 그 뒤에 갈래를 합친다 |
| 처리 갈래 안 IF 의 갈래가 모두 따로 END 로 감 | 받는다. §2.2 5 로 이어지는 갈래가 정해지고 처리 갈래는 끝내는 처리 갈래다. 받는 노드 X-D6(처리 갈래 안 IF 갈래는 END 로 못 감)은 없어진다(J-D9) |
| 처리 갈래 안 IF 의 일부 갈래만 END 로 가고 나머지는 정상 경로로 돌아옴 | 받는다. END 로 가는 갈래는 끝내는 갈래이고 처리 갈래는 돌아오는 처리 갈래다 |
| 처리 갈래 안 갈래가 정상 경로 노드를 지남 | 오류 S8. 예: 처리 갈래 안 IF 의 이어지는 갈래들이 돌아오는 자리보다 뒤에서 만난다 |
| 처리 갈래 안 PARALLEL | 지금과 같다. 짝 합류로 닫혀야 한다 |
| 정상 갈래가 `J` 에 닿지 않고 END 로 빠짐 | 오류 S5 "갈래가 {J}에서 닫히지 않고 end로 나간다"(지금 문구) |
| 정상 다음 노드가 END 인 노드의 처리 갈래 | END 로 가면 끝냄이다. 돌아올 자리가 없으므로 돌아오게 하려면 노드 뒤에 빈 단계를 둔다(J-D10) |
| 처리 갈래가 받은 노드 자신이나 그 앞으로 감 | 오류 S6(순환) |

### 2.7 빈 단계(TASK)에 받는 노드

- 받을 수 있는 노드 종류는 RULE·TASK 다(`FlowParser.catchable`, TS `CATCHABLE`). 하위 세트 호출 스펙이 SET 을 더한다.
- TASK 블록의 구조 규칙은 RULE 과 같다(§2.3).
- 실행: TASK 는 실패하지 않으므로 처리 갈래는 실행되지 않는다(§5).
- 검사: 받는 노드마다 `CATCH_NEVER` 경고 한 줄(§6).
- 편집: `assignRule` 은 노드 ID 를 바꾸지 않으므로 붙은 받는 노드가 그대로 남는다(지금 코드 그대로 맞다).

### 3.2 2단계 순서

1. 루트 `seq(next(START), END)` 를 만든다. 노드에 닿을 때마다 §2.4 의 1→2→3→4/5/6 순서로 본다.
2. IF 에 닿으면 모이는 자리와 끝내는 갈래를 계산하고(S6 가능), 갈래를 실행 순서대로 만든다(끝내는 갈래도 실행 순서 자리에서 만든다).
3. 받는 노드가 붙은 노드에 닿으면 정상 줄기 → 처리 줄기들(받는 노드 배열 순서, S6 가능) → 도착 비교(S7) → 정상 갈래 → 처리 갈래 순서로 만든다.
4. 마지막에 도달할 수 없는 노드를 노드 배열 순서로 본다.

## 4. 블록 트리 모양

Java `flow` 패키지와 `flow-model.ts` 가 같은 모양을 갖는다. 엔진 계약 밖이라(`flow` 는 `spi` 만 본다) 계약 대조표는 바뀌지 않는다.

| 대상 | 지금 | 바뀜 |
|---|---|---|
| `Step`(새 sealed interface / TS 합 타입) | — | `RuleStep`·`TaskStep`. 하위 세트 호출 스펙이 `SetStep` 을 더한다. `Block permits Seq, Step, Split, Guarded` |
| `Split` | `(nodeId, kind, mergeId, branches)` | `(nodeId, kind, @Nullable mergeId, joinId, branches)`. `mergeId` 는 PARALLEL 과 옛 IF 의 MERGE, 새 IF 는 null. `joinId` 는 이어지는 갈래가 모이는 노드(MERGE 가 있으면 MERGE, §2.2 4 의 예외에서만 END) |
| `Branch` | `(edgeId, cond, otherwise, label, body)` | `ends` 를 더한다. 끝내는 IF 갈래면 true(몸은 END 앞까지), 그 밖(이어지는 갈래·병렬 갈래·옛 IF 갈래)은 false. `Guarded.Handler.ends` 와 같은 뜻이다 |
| `Guarded` | `(rule: RuleStep, normal, handlers, @Nullable mergeId)` | `(step: Step, normal, handlers, @Nullable mergeId, @Nullable joinId)`. `joinId` 는 `J`(돌아오는 갈래가 없으면 null), `mergeId` 는 옛 돌아오는 MERGE 일 때만 `J` 와 같다. 필드 이름을 `rule` → `step` 으로 바꿔 RULE 만 가정한 코드를 컴파일이 모두 찾게 한다(지금 TS 주석이 쓰는 방법과 같다) |
| `FlowTree.ruleSteps` | 받는 룰 포함 RULE 깊이 우선 | 그대로. TASK 블록은 넣지 않는다 |
| `FlowTree` 노드 위치·관계 | 받는 룰은 갈래 0 = 정상, k+1 = 처리 | 그대로. TASK 블록도 같은 방식이다 |

## 5. 실행과 기록

`FlowRun` 은 블록 트리만 보므로 새 형식에서 바뀌는 것은 MERGE 기록이 없어지는 것, `CATCH_*` 를 빼는 자리, 끝내는 IF 갈래 세 가지다.

| 블록 | 지금 | 바뀜 |
|---|---|---|
| IF | 고른 갈래 실행 → `merge()` 로 MERGE 기록(path·trace) | 고른 갈래 실행으로 끝. `mergeId` 가 있을 때(옛 형식)만 지금처럼 MERGE 기록. 고른 갈래가 끝내는 갈래면 몸을 실행한 뒤 끝냄 신호 `Ended(null)` 을 던진다 |
| PARALLEL | 갈래 실행 → 합치기 → MERGE 기록 | 그대로 |
| 받는 노드 블록 | 끝에 `mergeId` 가 있으면 `restoreCatch(ctx, outer)` → MERGE begin·고친 값·path·trace | 끝에 `joinId` 가 있으면 `restoreCatch(ctx, outer)`. `mergeId` 가 있을 때(옛 형식)만 이어서 MERGE 기록 |
| TASK 블록 | 없음 | `plain(TASK)` → 정상 갈래. 처리 갈래는 실행하지 않는다. `caught` 에 넣을 것도 없다 |

- **`CATCH_*` 를 빼는 순서(R3·R4 유지)**: 블록이 끝날 때 `CATCH_*` 를 룰 직전 값(중첩이면 바깥 값)으로 되돌린다. 그다음 바깥 순차가 돌아오는 자리 노드를 시작하면서(`begin`) 그 노드의 고친 값을 넣는다. 지금 "되돌림 → MERGE 시작 → 고친 값" 과 같은 순서다. 한 노드가 블록 여럿을 함께 닫으면 안쪽 블록부터 차례로 되돌린다. 마지막 상태는 가장 바깥 블록의 룰 직전 값이다.
- **끝냄 신호 하나로 묶기**: 지금 `Ended(catchNodeId)` 를 `Ended(@Nullable catchNodeId)` 로 넓힌다. 처리 갈래가 END 에 닿으면 지금처럼 `Ended(c)`, 끝내는 IF 갈래가 끝나면 `Ended(null)` 이다.
- **처리 갈래 안에서 난 IF 끝냄**: `guarded()` 가 처리 갈래 몸을 실행하다 `Ended(null)` 을 받으면 `Ended(c)`(그 처리 갈래의 받는 노드)로 바꿔 다시 던진다. 이미 받는 노드 ID 가 있으면 그대로 던진다. 그래서 `endedBy` 는 끝난 지점을 감싼 **가장 안쪽 처리 갈래**의 받는 노드다. 처리 갈래 안에서 끝났다는 것은 예외를 처리하다 세트를 끝냈다는 뜻이므로, 처리 갈래가 END 에 바로 닿은 것과 같게 본다(J-D18).
- **병렬 갈래 안 끝냄**: 신호 종류와 상관없이 지금 X-D11 규칙 그대로다. 남은 형제 갈래는 실행하지 않고, 끝난 형제 갈래와 지금 갈래의 결과를 갈래 순서대로 합친 뒤 다시 던진다. 그래서 `finalValues` = 분기 직전 ctx + 끝난 형제 결과(order 순) + 지금 갈래 결과다.
- **세트 끝**: `run()` 은 지금처럼 신호를 받아 `endedBy = 신호의 받는 노드 ID`(IF 끝냄이면 null)로 두고, `CATCH_*` 를 지운 뒤 END 를 기록한다. 끝내는 IF 갈래로 끝난 실행은 **정상 완료**다. `RuleSetResult`·`RunTrace` 에 새 칸을 두지 않는다(J-D17). `path` 에는 IF 의 `chosenEdgeId` 와 END 가 남아 어느 갈래로 끝났는지 알 수 있다.
- **입력 키 검사**: 끝내는 갈래로 들어갈 때도 지금처럼 `keys.check(chosen.body(), …)` 를 한다.
- **없어지는 기록**: 새 형식 흐름에서는 IF 와 돌아오는 처리 갈래마다 있던 MERGE 의 `PathStep` 과 `NodeTrace` 가 없다. `RunTrace.nodes` 의 `seq` 가 그만큼 당겨진다. 고친 값(`TraceEdit.beforeSeq`)은 같은 흐름의 기록에서만 만들고 저장하지 않으므로(디버거 `local-store` 는 입력·식·중단점만 저장한다) 옛 기록과 섞이지 않는다.
- **결과 불변**: `steps`·`finalValues`·`caught`·`endedBy`·`warnings` 는 옛 형식과 새 형식(§12 변환 결과)이 같다. 다른 것은 `path`·`RunTrace.nodes` 에서 MERGE 항목이 빠지는 것과, 변환이 빈 단계를 넣은 자리(J-D10 의 END 앞 합류, §12.2 의 남는 빈 갈래)에 TASK 항목이 생기는 것뿐이다. 옛 형식에는 끝내는 IF 갈래가 없다.
- `FlowKeys`(입력 키 사전 검사): `g.rule()` 을 쓰는 곳(`ruleKeys`·`guardSure`·`guardAll`)은 `step` 이 TASK 면 읽는 이름·만드는 이름이 없는 것으로 본다. IF 의 `sure`(갈래 교집합)·`any`(갈래 합집합)와 `sureProduced`·`allProduced` 의 IF 계산은 **이어지는 갈래만** 센다. 끝내는 처리 갈래를 빼는 지금 `guardSure`·`guardAll` 과 같은 규칙이다. 끝내는 갈래 몸 안의 입력 키 검사는 그 갈래로 들어갈 때 지금처럼 한다.
- 서버 `RuleSetRunner.execute` 의 `RuleSetRunResult.path` 도 같은 이유로 MERGE 항목이 줄어든다. OASIS BPMN 은 `endedBy`·`caught`·`finalValues` 를 쓰고 `path` 의 MERGE 항목에 기대지 않는다(구현 때 `ruleSet*.bpmn` 을 한 번 확인한다).

## 6. 정적 검사

서버 `RuleSetAnalyzer`·`RuleSetPathState`·`RuleSetOrderCheck` 와 화면 `set-model.ts` 는 블록 트리만 걷는다. 옛 형식과 새 형식이 같은 블록 트리(같은 갈래 몸)를 만들므로 옛 형식에 있던 모양의 경로 검사는 바뀌지 않는다. 돌아오는 자리 뒤 정의된 변수는 지금 MERGE 뒤처럼 정상 갈래 끝과 **돌아오는** 처리 갈래 끝의 교집합이고, 끝내는 처리 갈래는 세지 않는다.

바뀌는 것은 끝내는 IF 갈래와 TASK 블록이다.

**끝내는 IF 갈래(B1)**

- 갈래 조건식 검사(`cond`)와 갈래 몸 검사는 끝내는 갈래에도 지금처럼 한다. 갈래 몸의 시작 상태는 IF 직전 상태다.
- IF 블록 뒤 상태는 **이어지는 갈래만** 합친다. `RuleSetPathState.mergeIf(base, 이어지는 갈래 상태들)` 로 교집합은 `defined`, 나머지는 `maybe` 다. 끝내는 갈래에서만 만든 이름은 블록 뒤에 `defined`·`maybe` 어디에도 들지 않는다. 끝내는 처리 갈래를 빼는 지금 `guarded` 규칙과 같다.
- 분석기의 `prodBy`(이름 → 그 경로에서 마지막으로 만든 룰) 합치기도 이어지는 갈래만 쓴다. 그래서 끝내는 갈래와 블록 뒤가 같은 결과 변수를 써도 `DUP_RESULT` 가 아니다.
- `RuleSetPathState.Walk`(룰 확정 형제 판정용 노드별 직전 상태)는 끝내는 갈래 안 노드도 지금처럼 적는다.
- 블록 뒤 룰이 끝내는 갈래에서만 만드는 이름을 읽으면 블록 트리 관계(`FlowTree.relation`)로는 "앞 경로"(AFTER)라 `IF_SIBLING` 이 되지 않는다. 그 이름의 출처가 사전(DICT)이면 지금처럼 지나가고, 프로그램 입력(PROG)이면 세트 입력으로 보아 검사 없이 지나가며, 그 밖이면 `UNKNOWN_INPUT` 이다. 지금 끝내는 처리 갈래가 만든 이름을 받는 노드 블록 뒤에서 읽을 때와 같은 결과다. 관계 계산을 고쳐 더 맞는 문구를 내는 것은 미룬다(§16).
- 하위 세트 호출 스펙의 `always`(END 에서 반드시 정의되는가)는 루트 순차 끝 상태와 **모든 끝냄 지점**(끝내는 처리 갈래 끝, 끝내는 IF 갈래 끝)의 상태를 합쳐야 한다(§13).

**TASK 블록**

- `guarded` 의 룰 검사(`rule(g.step())`)는 `step` 이 RULE 일 때만 한다.
- `never(g)` 는 `step` 이 TASK 면 받는 노드마다 `CATCH_NEVER`(경고) 한 줄을 낸다. `ruleId` 는 null, 노드 위치는 받는 노드, 문구는 "{t}는 빈 단계라 {c}가 받는 예외가 일어나지 않는다". 받는 종류 수와 상관없이 한 줄이다. RULE 은 지금 규칙 그대로다.
- 처리 갈래 경로 상태(룰 직전 + `CATCH_*`)와 교집합 규칙은 TASK 에도 그대로 쓴다. 실제로는 타지 않는 갈래지만, 나중에 룰을 지정하면 탈 수 있으므로 미리 같은 기준으로 본다.
- `EMPTY_TASK` 경고("빈 단계 n개 — 실행 때 그냥 지나간다")는 지금처럼 따로 난다.
- `RuleSetOrderCheck`·`RuleSetPathState` 의 `g.rule()` 은 `g.step()` 으로 바꾸고 TASK 는 건너뛴다.
- `RULE_IDS` 펼치기는 그대로다(TASK 는 룰이 아니다).

## 8. 편집기 연산

### 8.1 공용 도우미

`flow-model.ts` 가 해석과 같은 알고리즘의 관대한 도우미를 내보낸다. 구조 오류가 있어도 던지지 않고 null 을 돌려준다(편집 연산은 깨진 흐름에서도 돈다).

| 도우미 | 돌려주는 값 |
|---|---|
| `joinOf(flow, splitId)` | IF 는 옛 짝 MERGE 또는 §2.2 의 모이는 자리, PARALLEL 은 짝 MERGE. 순환·분기 아님이면 null |
| `endingBranches(flow, splitId)` | §2.2 의 끝내는 갈래 선 ID 목록(실행 순서). 옛 IF·PARALLEL 은 빈 목록, 못 정하면 null |
| `handlerTarget(flow, catchId)` | 처리 갈래 도착(END ID 면 끝내는 갈래). 정상 줄기는 둘러싼 끝을 모르므로 END 까지 본다(§2.3 의 `stop` 없음). 못 정하면 null |
| `returnOf(flow, nodeId)` | 그 노드의 돌아오는 자리 `J`(노드 배열 순서로 첫 돌아오는 처리 갈래의 도착). 없으면 null |

`flow-edit.ts` 의 블록 도우미는 다음처럼 바뀐다.

- `blockMembers(f, splitId)`: IF 는 분기 + 안쪽 노드(이어지는 갈래 몸과 끝내는 갈래 몸, 모이는 자리와 END 는 넣지 않는다), PARALLEL 은 지금처럼 분기 + 안쪽 + 짝 합류.
- `blockNodes(f, splitId, joinId)`: `reach` 의 멈춤 노드가 모이는 자리다. 끝내는 갈래에서 시작한 경로는 처리 갈래처럼 END 에 닿으면 그 경로만 멈춘다. "합류로 들어오는 선도 분기·안쪽에서만 와야 한다" 검사는 PARALLEL 에만 남긴다. IF 의 모이는 자리는 블록 밖(바깥 IF 의 다른 갈래, 돌아오는 처리 갈래)에서도 선을 받을 수 있다.
- `tailsOf(f, splitId)`(새로 둠): 블록 멤버(분기 자신 포함)에서 모이는 자리로 가는 선, 선 배열 순서. IF 블록의 "출구"는 하나의 선이 아니라 이 목록이다. 끝내는 갈래가 END 로 가는 선(**끝 선**)은 꼬리가 아니라 블록 안 선으로 본다.
- **빈 갈래 둘 막기(B2)**: 연산 결과에 짝 MERGE 없는 IF 의 같은 from→to 선이 둘 생기면 그 연산을 거부한다. 문구 `IF_EMPTY_TWICE` "IF {s}에 같은 노드로 가는 갈래가 이미 있다. 빈 갈래는 하나만 둔다". 변환(§12.2)과 `changeSplitKind`(병렬 → IF)는 거부하지 않고 빈 단계를 채운다.
- `dissolveMerge(g, m)`(새로 둠): MERGE m 으로 들어오는 선을 모두 m 의 나가는 선 도착으로 옮기고(선 ID·`order`·`cond`·`otherwise`·`label`·이름표 오프셋 유지, 꺾는 점은 지움), m 과 그 나가는 선을 지운다. §12.2 변환과 `changeSplitKind`(병렬 → IF)가 함께 쓴다.
- `handlerNodes(f, nodeId, stop)`: `stop` 은 `returnOf` 다.
- `handlerTrail`·`returnRuleFor`·`returnTargetOf`·`ensureReturnMerge`·`connectReturn`·`unwindReturnMerge` 와 문구 `RETURN_MERGE_NOT_ONE`·`RETURN_MERGE_STUCK` 은 없앤다. 처리 갈래의 맨 바깥 끝은 `handlerTarget` 과 "처리 갈래 노드에서 도착으로 가는 선" 으로 구한다. 지금 `handlerTrail` 의 "들어오는 선이 하나가 아니면 열린 갈래" 판정은 처리 갈래 안 IF 의 모이는 자리에서 틀리므로 쓰지 않는다.

### 8.2 연산별

| 연산 | 바뀜 |
|---|---|
| `insertSplit`(IF) | 선 e(A→B) 에 IF s 와 빈 단계 t(`TASK_LABEL`, ID 접두어 `r`)를 끼운다. 갈래 `{s→t, order 1, "갈래 1"}`·`{s→B, 그 외, "그 외"}`, 선 `{t→B}` 를 이 순서로 e 바로 뒤에 넣고 e.to = s. 노드는 A 뒤에 s, t 순서. MERGE 와 합류 출구 선은 만들지 않는다. 빈 갈래는 "그 외" 하나다(B2). **B 가 END 면** 모이는 자리 빈 단계 j(`TASK_LABEL`, ID 접두어 `r`, t 다음 ID)를 하나 더 두어 갈래 `{s→t}`·`{s→j, 그 외}`, 선 `{t→j}`·`{j→END}` 를 이 순서로 e 바로 뒤에, 노드는 A 뒤에 s, t, j 순서로 넣는다. 그러지 않으면 두 갈래가 따로 END 로 가 J-D19 로 "갈래 1" 의 빈 단계가 모이는 자리, "그 외" 가 끝내는 갈래가 되어 팔레트 기본 위치에서 블록 연산(지우기·「그 외」 풀기·병렬로 바꾸기·갈래 더하기·옮기기·접기)이 옛 판보다 나빠진다(J-D10 과 같은 근거, 수정 판정 2026-10-02). 이 모양에서 IF 를 지우면 j 가 남는다(되돌리기는 정확하다). PARALLEL 은 지금과 같다 |
| `addBranch` | IF 는 새 갈래 `s→t→모이는 자리`(t 는 새 빈 단계), 선 순서는 지금처럼 "그 외" 앞. 빈 갈래를 하나 더 만들지 않는다(B2). PARALLEL 은 지금처럼 `s→MERGE`. 모이는 자리를 못 정하면 "분기 {s}의 갈래가 모이는 자리를 찾지 못했다" |
| `removeBranch` | 이어지는 갈래 안쪽 = `reach(e.to → 모이는 자리)`, 끝내는 갈래 안쪽 = `reach(e.to → END)`. 선과 안쪽을 지운다. 빈 갈래는 선만 지운다 |
| `moveBranch`·`reorderBranches` | 순서 값만 바꾸므로 그대로. 짝 합류 확인(`splitAndMerge`)은 IF 에 대해 모이는 자리 확인으로 바꾼다 |
| `dissolveSplit` | 남길 갈래 k: 분기로 들어오는 선을 모두 k.to 로(빈 갈래면 모이는 자리로) 옮긴다. k 안쪽 꼬리 선은 이미 모이는 자리로 가므로 고치지 않는다. 분기·다른 갈래 안쪽(끝내는 갈래 몸 포함)·다른 갈래 선을 지운다. 끝내는 갈래를 남기려 하면 거부한다: "끝내는 갈래만 남기면 뒤 흐름에 닿을 수 없다"(메뉴에서는 그 항목을 흐리게 둔다). PARALLEL 은 지금처럼 합류도 지우고 꼬리를 합류 출구 도착으로 옮긴다 |
| `changeSplitKind` IF → 병렬 | 새 MERGE m(`splitId` = s, ID 접두어 `m`)을 모이는 자리 바로 앞(노드 배열)에 넣는다. `tailsOf(s)` 의 선을 모두 m 으로 옮기고(꺾는 점 지움) 출구 `{m → 모이는 자리}` 를 마지막으로 옮긴 선 바로 뒤에 넣는다. 그 뒤 갈래 `order`·`cond`·`otherwise`·라벨 처리는 지금과 같다 |
| `changeSplitKind` 병렬 → IF | 갈래 처리 뒤 `dissolveMerge(짝 MERGE)`. 단 짝 MERGE 의 나가는 선이 하나이고 그 도착이 END 면 지우지 않고 같은 ID 의 빈 단계(`splitId` null, `TASK_LABEL`, 위치 지움)로 바꿔 모이는 자리로 둔다(J-D10, 수정 판정 2026-10-02 — END 앞 병렬 ⇄ IF 가 왕복되고 빈 단계 한 칸이 더해진다). 그 결과 같은 도착으로 가는 IF 갈래 선이 둘 이상이면(병렬의 빈 갈래 여럿) 실행 순서 마지막 선만 빈 갈래로 두고 나머지 선마다 빈 단계를 끼운다(선 e: e.to = 새 빈 단계, 새 선 {빈 단계 → 도착} 을 e 바로 뒤). 병렬 갈래가 끝내는 갈래로 바뀔 일은 없다(병렬 갈래는 모두 합류로 갔다) |
| `changeSplitKind` IF → 병렬(끝내는 갈래가 있을 때) | 거부한다: "끝내는 갈래가 있는 IF 는 병렬로 바꿀 수 없다. 병렬 갈래는 모두 합류로 모여야 한다". 병렬 갈래는 직접 END 로 갈 수 없기 때문이다 |
| `removeNode` RULE·TASK | 들어오는 선이 없으면 지금처럼 나가는 선과 함께 지운다. 나가는 선이 하나가 아니면 거부한다(`RULE_EDGES_NOT_ONE` 문구 → "룰 노드의 나가는 선이 하나가 아니라 지울 수 없다. 선을 먼저 정리한다"). 들어오는 선은 여러 개여도 된다. 들어오는 선을 모두 나가는 선 도착으로 옮기고(선 ID 유지) 노드·붙은 받는 노드·받는 노드의 나가는 선을 지운다. 처리 갈래 안 노드는 남긴다(받는 노드 스펙 §8). 단, 그 노드가 다른 노드의 돌아오는 자리이고 나가는 선 도착이 END 면 거부한다: "처리 갈래가 돌아오는 자리라 지우면 그 처리 갈래가 끝내기로 바뀐다. 앞에 빈 단계를 두거나 선을 먼저 정리한다"(`RETURN_JOIN_END`). 돌아오는 합류를 걷어 내는 단계는 없어진다 |
| `removeNode` IF | 들어오는 선을 모두 모이는 자리로 옮기고 분기·안쪽 노드(끝내는 갈래 몸 포함)를 지운다(꼬리·끝 선은 노드와 함께 지워진다). 블록 단위 지우기라 끝내는 갈래 몸도 함께 지우고, 되돌리기로 돌린다(J-D13). 모이는 자리를 못 정하면 "분기 {s}의 갈래가 모이는 자리를 찾지 못해 지울 수 없다". 돌아오는 자리 + END 거부는 RULE 과 같다 |
| `removeNode` PARALLEL | 들어오는 선이 여러 개여도 된다. 나머지는 지금과 같다 |
| `removeNode` MERGE | "합류 노드는 분기를 지워서 없앤다"(돌아오는 합류 경로를 없앤다). 단 `splitId` 가 RULE·TASK 인 MERGE(받는 노드가 없어 §12.2 변환 대상이 아닌 옛 돌아오는 합류)는 `dissolveMerge` 로 걷어 낸다. 나가는 선이 하나가 아니면 "합류의 나가는 선이 하나가 아니라 지울 수 없다. 선을 먼저 정리한다"(수정 판정 2026-10-02) |
| `removeNode` CATCH | 받는 노드와 그 나가는 선만 지운다. 합류를 걷어 내는 단계가 없다 |
| `moveNode` RULE·TASK | 떼어 낼 때 들어오는 선을 모두 나가는 선 도착으로 옮긴다(지우기와 같은 `RETURN_JOIN_END` 거부). 돌아오는 처리 갈래가 있는 노드(`returnOf` 가 있음)는 지금처럼 `MOVE_GUARDED` 로 거부한다 |
| `moveNode` IF 블록 | 떼어 낼 때 분기로 들어오는 선을 모두 모이는 자리로 옮긴다. 놓을 선 t(X→Y): `tailsOf(s)` 를 모두 Y 로 옮기고(꺾는 점 지움) t.to = s. 새 선을 만들지 않는다 |
| `moveNode` 병렬 블록 | 들어오는 선 여러 개를 허용하는 것 말고는 지금과 같다 |
| `moveExcludedEdges` | IF 는 분기로 들어오는 선 + 블록 멤버에서 나가는 모든 선(꼬리 포함). 룰은 처리 갈래 범위를 `returnOf` 로 정한다 |
| `copyFragment` IF 블록 | `Fragment` 에 `tails`(꼬리 선 사본, `to` 는 빈 문자열)와 `endTails`(끝 선 사본, `to` 는 빈 문자열)를 더하고 `exit` 는 null. 룰·병렬은 지금처럼 `exit` 하나에 둘 다 없음. 받는 노드가 든 블록은 지금처럼 복사하지 않는다 |
| `pasteFragment` | `tails` 는 새 ID 를 주고 `to` = t.to 로, `endTails` 는 새 ID 를 주고 `to` = 붙여 넣는 흐름의 END 로 잇는다. 조각 선·꼬리 선·끝 선을 원래 선 배열 순서대로 t 바로 뒤에 넣는다. `wellFormed` 는 "`exit` 가 null 이면 `tails` 가 하나 이상이고 모든 꼬리·끝 선의 `from` 이 조각 안" 과 "MERGE 의 `splitId` 는 조각 안 PARALLEL" 을 본다 |
| `duplicateNode` IF 블록 | 원래 블록의 꼬리 선을 모두 복제 블록의 분기로 옮기고(꺾는 점 지움), 복제 블록의 꼬리를 원래 모이는 자리로 잇는다. 그래서 복제는 "원본 바로 뒤" 에 선다. 룰·병렬은 지금과 같다 |
| `connect` | 돌아오기 특례를 없앤다. 받는 노드·처리 갈래 노드에서 정상 경로 노드로 이으면 그 선이 곧 돌아오는 선이다. 같은 from→to 거부, 받는 노드로 들어가는 선 거부, 받는 노드 나가는 선 하나 규칙은 그대로다 |
| `reconnectEdge` | 돌아오기 특례를 없앤다. 나머지 규칙은 그대로다 |
| `addCatch(nodeId, to)` | RULE·TASK 에 붙인다(`CATCH_ONLY_RULE` 문구 → "룰·빈 단계 노드에만 예외 받기를 붙인다"). 선은 늘 `{c → to}`(to 가 null 이면 END). 정상 다음 노드로 놓으면 빈 돌아오는 갈래다 |
| `returnCatch`(「흐름으로 돌아오기」) | 끝내는 처리 갈래(`handlerTarget` 이 END)의 맨 바깥 순차에서 END 로 가는 선 하나(빈 갈래면 받는 노드의 선)를 돌아올 자리로 옮긴다. 처리 갈래 안 IF 의 끝내는 갈래 끝 선은 그대로 둔다(그 갈래는 계속 끝내는 갈래다). 돌아올 자리는 `returnOf(노드)` 가 있으면 그것, 없으면 노드의 나가는 선 도착이다. 그 도착이 END 면 거부하고 메뉴 항목을 숨긴다: "노드 다음이 끝 노드라 흐름으로 돌아올 자리가 없다. 노드 뒤에 빈 단계를 넣은 뒤 다시 한다"(`RETURN_TO_END`, J-D10). `RETURN_ALREADY`·`RETURN_OPEN`·`RETURN_NO_EXIT` 는 그대로 둔다 |
| `assignRule` | 그대로. 노드 ID 가 그대로라 받는 노드가 남는다 |
| `updateNodeDesc`·`groupable`·`MOVE_FIXED` | MERGE 관련 규칙은 병렬 합류에 그대로 쓴다. `NO_COPY` 문구 → "시작·끝·합류는 복사하지 않는다. 병렬 분기를 복사하면 합류가 함께 복사된다" |

### 8.3 메뉴·패널

- 편집 메뉴 「분기 풀기」의 "(빈 갈래)" 표시는 `e.to === joinOf(s)` 로 정한다(`canvas/menus/edit-menu.ts`). 끝내는 갈래는 "(끝냄)" 을 붙이고 항목을 흐리게 둔다(§8.2 `dissolveSplit`).
- IF 속성 패널의 갈래 목록에서 끝내는 갈래 옆에 "끝냄" 표지를 보인다. 갈래를 END 로 이으면(`reconnectEdge`·`connect`) 바로 끝내는 갈래가 된다. 따로 메뉴를 두지 않는다.
- **이어지는 갈래 안내(작업 항목, J-D19·Q9)**: 두 곳에 같은 뜻을 적는다.
  - 화면 도움말: IF 속성 패널 갈래 목록 아래에 한 줄 "흐름을 이어 갈 갈래는 「그 외」로 둔다. 끝낼 갈래는 조건 갈래로 두고 끝 노드로 잇는다." 를 보인다(IF 에 끝내는 갈래가 하나라도 있을 때만).
  - 영역 가이드: `docs/guide/FrontEnd/Local-Rules.md` 의 룰 세트 흐름 캔버스 절에 같은 규칙과 까닭(J-D19, 어긋나면 안쪽 IF 에서 S5)을 짧게 더한다.
- 빈 단계 노드 우클릭에도 「예외 받기 추가」를 둔다. 빈 단계 노드에도 예외 연결점(`CatchHandle`)을 그리고 `handlesOf("TASK")` 가 그 손잡이를 낸다.
- 속성 패널 MERGE 설명: "병렬 합류 — 병렬 {splitId}의 갈래가 모두 끝나면 결과를 갈래 순서대로 합친다. 병렬 분기를 지우면 함께 없어진다". 패널 머리 기본 이름: "병렬 {splitId} 합류".
- 받는 노드 속성 패널의 `CATCH_NEVER` 표시는 TASK 경고도 같은 자리에 보인다.

### 8.4 접기

- 접힌 IF 블록은 분기 + 안쪽(끝내는 갈래 몸 포함)을 감춘다. 모이는 자리는 블록 밖이라 남는다. 끝 선(끝내는 갈래에서 END 로)도 감춘다.
- 블록에서 모이는 자리로 가는 선(꼬리·빈 갈래)은 모두 빼고, 그 대신 그리기 전용 대표 선 하나 `{id: "fold:{s}", from: s, to: 모이는 자리}` 를 넣는다. 대표 선은 고르기·지우기·다시 잇기·[+] 를 하지 않는다(J-D14). 실제 선이 아니라서 편집 연산에 넘어가면 "선을 찾지 못했다"로 끝나지만, 캔버스가 처음부터 손잡이를 그리지 않는다.
- 접힌 병렬 블록은 지금과 같다(합류 출구를 분기에서 나가는 것으로 바꾼 사본).
- `blockInfo` 의 `count` 는 IF 가 멤버 수 − 1(분기만 뺌), 병렬이 − 2(분기·합류) 다. `ran` 계산에서 합류를 빼는 것은 병렬에만 해당한다.

## 9. 자동 배치

dagre 그래프에서 IF 합류 노드가 사라지는 것 말고는 배치 방식이 같다.

- `bodyIds`: 분기는 자기와(병렬이면) 합류, 받는 노드 블록은 `step` 과(옛 형식이면) 합류를 넣는다. 모이는 자리·돌아오는 자리는 블록 밖이라 넣지 않는다.
- `placeSplit` 의 빈 갈래 자리: `g.edge(분기, 모이는 자리)` 의 점과 `g.node(모이는 자리).y` 를 쓴다(지금은 합류).
- **끝내는 갈래**: `placeSplit` 의 갈래 자리 나누기에서 뺀다. 이어지는 갈래만 왼쪽부터 갈래 순서대로 놓는다. 끝내는 갈래 몸은 끝내는 처리 갈래와 같은 규칙(`clearEnding`: 몸 세로 범위와 겹치는 다른 노드 오른쪽 끝 + NODESEP 너머로 통째로 민다)으로 오른쪽에 비켜 놓는다. 한 IF 의 끝내는 갈래가 여럿이면 실행 순서대로 왼쪽부터다. END 로 바로 가는 끝내는 갈래는 몸이 없어 자리를 두지 않는다. 이렇게 하면 dagre 가 끝내는 갈래를 END 바로 위까지 늘려도 뒤 흐름과 겹치지 않는다. `hasGuarded` 처럼 "끝내는 갈래가 든 몸" 도 안쪽부터 맞춘다.
- `placeGuarded`: 돌아오는 MERGE 를 룰 가운데 아래에 두는 줄을 없앤다. 돌아오는 자리는 바깥 순차 노드라 dagre 자리 그대로다(지금 MERGE 다음 노드가 dagre 자리였던 것과 같다).
- 받는 노드 가상 선의 "빈 처리 갈래" 판정: 지금은 도착이 END 이거나 그 룰의 돌아오는 MERGE 인가로 본다. 바꾼 뒤에는 블록 트리의 `handler.body` 가 비었는가로 본다. 트리를 만들지 못하면 도착이 END 인 것만 빈 갈래로 본다.
- `endingRoutes`: 끝내는 처리 갈래의 끝 선에 더해 **끝내는 IF 갈래의 끝 선**(몸 마지막 출구에서 END 로, 몸이 없으면 IF 에서 END 로 가는 갈래 선)에도 같은 비켜 가기 규칙을 쓴다. 처리 갈래 끝 선은 지금처럼 `lastExit` 로 찾는다(맨 바깥 순차 끝 하나).
- 캐시 키(`layoutKey`)는 노드·선 칸을 그대로 적으므로 바꿀 것이 없다.

## 10. 그리기

- **병렬 합류(이중선 막대)**: `NODE_SIZE.MERGE` 를 `{ w: 200, h: 14 }`(병렬 분기와 같은 크기)로 바꾼다. `.rsf-merge` 는 배경 없이 위·아래 테두리 두 줄로 그린다(예: `border-top: 4px solid var(--rsf-par-bar); border-bottom: 4px solid var(--rsf-par-bar); border-radius: 0`, 가운데 6px 빈 줄). 실행됨(`data-state="run"`)이면 두 줄을 `--color-success` 로, 고름은 병렬 분기와 같은 바깥선으로 그린다. 연결점은 지금처럼 위 가운데(들어옴)·아래 가운데(나감)다. 검사 표시 점(`rsf-mark`)은 그대로 둔다. 라벨은 두지 않고 툴팁 "병렬 합류" 를 단다. 밝은·어두운 테마 모두 기존 토큰만 쓴다.
- **병렬 분기**: 그대로(채운 막대 `.rsf-par`).
- **IF**: 그대로(176×44 모양·라벨). 갈래 선은 다음 노드로 바로 들어간다.
- **모이는 자리 노드**: 따로 표시하지 않는다. 들어오는 선 여럿이 한 연결점(위 가운데)으로 들어간다.
- **빈 단계**: 예외 연결점을 그린다(§8.3).
- 원 모양 MERGE(28×28)를 쓰던 스타일·테스트 기대는 이중선 막대로 바꾼다.

## 11. 디버거

- `trace-view.ts` `scopePaths`: `guardMerges`(합류 → 받는 노드)를 `guardJoins`(돌아오는 자리 → 받는 노드 목록, 안쪽 블록 먼저)로 바꾼다. 옛 형식 트리(`mergeId` 있음)는 지금처럼 합류에 묶는다. 분기·받는 노드 블록의 `mergeId` 가 null 이면 `paths.set(mergeId, …)` 를 하지 않는다(모이는 자리는 바깥 순차 노드로 자기 경로를 따로 갖는다).
- `frames`: 기록 노드가 어떤 받는 노드 블록의 돌아오는 자리면, 고친 값을 넣기 **전에** 그 블록들을 안쪽부터 차례로 보면서 그 블록의 룰 직전 `CATCH_*`(`outerCatch`)가 적혀 있는 것만 되돌리고 적힌 값을 지운다. 되돌리는 범위는 돌아오는 자리 기록의 범위가 아니라 **받는 노드의 범위**(`scopeOf(paths.get(R))`)다. 병렬 갈래 안 받는 노드가 병렬 합류로 돌아오면 합류 기록의 범위는 바깥이지만, 엔진은 갈래 범위에서 되돌린 뒤 합친다. 합칠 때 `CATCH_*` 는 `made` 에 없어 바깥으로 가지 않는다.
- `overlayAt` 선 색칠은 바꿀 것이 없다. 고른 IF 갈래 선은 `chosen`, 안 고른 갈래 선은 `dim`, 모이는 자리로 들어가는 선은 출발 노드가 실행됐으면 `run`, 아니면 `idle` 이다. 받은 룰(CAUGHT)의 정상 선은 지금처럼 `idle` 이다.
- 모임은 따로 단계가 없다. 디버거는 모이는 자리 노드를 실행된 노드로 칠하고, 실제로 탄 갈래의 선만 실행 색으로 보인다. [한 단계]는 IF·돌아오는 갈래마다 한 번씩 덜 멈춘다.
- **끝내는 갈래로 끝난 실행**: 기록은 고른 갈래 몸 다음에 바로 END 다. 병렬 갈래 안에서 끝났으면 지금 `frames` 의 END 처리(R5: 열린 병렬 갈래를 안쪽부터 합친다)가 그대로 맞다. 끝 선은 출발 노드와 END 가 실행됐으므로 `run` 으로 칠해진다. 결과 머리는 `endedBy` 가 없으므로 "완료" 다. 대신 화면이 기록과 블록 트리에서 끝낸 갈래를 찾아 결과 머리와 END 노드 상세에 "IF {제목}의 「{갈래 이름}」 갈래에서 끝냈다" 를 보인다. 찾는 규칙: `endedBy` 가 없고, 기록의 IF 가운데 고른 선이 끝내는 갈래인 마지막 IF. 계약 칸이 아니라 화면 계산이다(J-D17). `endedBy` 가 있으면(처리 갈래 안 끝냄) 지금처럼 "예외로 끝남: {받는 노드 제목}" 만 보인다.
- 값 표 열(RULE 결과 + 병렬 합류)과 `TraceDetail` 의 합류 칸(합친 변수)은 병렬 합류에만 쓰이므로 그대로다.
- 중단점: MERGE 는 병렬 합류에만 남는다. 열 때 바꾼 흐름에 없는 노드의 중단점은 지금 코드가 버린다(`useSimulation` 의 `breakableIn` 이 흐름에 있고 중단점을 걸 수 있는 종류인 노드만 남기고, 세트를 열 때와 흐름 구조가 바뀔 때 부른다). 빈 단계로 바꾼 옛 돌아오는 합류는 ID 가 그대로이고 TASK 도 중단점 대상이라 그 중단점은 남는다.

## 12. 옛 형식

### 12.1 엔진·해석기가 받는 옛 형식

- IF 에 `splitId` 가 그 IF 인 MERGE 가 하나 있으면 그 MERGE 가 모이는 자리다(§2.2 1). 실행은 지금처럼 MERGE 기록을 남긴다.
- 받는 노드가 붙은 노드를 `splitId` 로 가리키는 MERGE 는 정상 줄기 위에 있으므로 처리 갈래 도착 계산(§2.3)이 그대로 그 MERGE 를 `J` 로 정한다. 실행은 지금처럼 `CATCH_*` 를 되돌리고 MERGE 기록을 남긴다.
- 옛 형식으로 지금 받는 흐름은 결과·기록이 그대로다. 옛 형식으로 지금 거부되는 흐름 가운데 새 규칙으로는 맞는 것이 있다. 예를 들어 처리 갈래가 그 노드를 감싼 IF 의 합류로 바로 가면 지금은 "처리 갈래 c1가 끝에 닿지 않고 m9로 나간다" 이지만, 새 규칙에서는 둘러싼 끝으로 돌아오는 갈래라서 받는다(§14.2 바뀌는 사례).
- 서버 저장은 옛 형식도 지금처럼 받는다. 편집기만 흐름을 저장하고 편집기는 새 형식만 보낸다.

### 12.2 편집기 변환(`upgradeLegacyMerges`)

`toEditFlow` 가 칸을 채워 복사한 뒤 부른다. 순수 함수이고 같은 입력이면 같은 결과다.

1. **대상**: MERGE m 가운데 `splitId` 가 IF 인 것(IF 합류)과, `splitId` 가 받는 노드가 붙은 RULE·TASK 인 것(돌아오는 합류). PARALLEL 합류와 `splitId` 가 맞지 않는 MERGE 는 그대로 둔다(검사가 알린다).
2. **END 로 바로 나가는 합류는 빈 단계로**: 대상 m(IF 합류·돌아오는 합류 모두)의 나가는 선이 하나이고 그 도착이 END 면 m 을 빈 단계로 바꾼다. 합류가 연쇄로 END 에 닿으면(예: 돌아오는 합류 → IF 합류 → END) END 바로 앞 합류 하나만 빈 단계가 되고, 앞 합류들은 3 에서 지워지며 그 빈 단계로 이어진다. 종류 `TASK`, `splitId` null, 제목 `TASK_LABEL`("빈 단계"), ID 그대로, `view.positions[m]` 은 지운다(28×28 자리라 232×68 상자와 맞지 않는다). 대상 목록에서 뺀다. 들어오는 선·나가는 선은 그대로다. 그래서 처리 갈래는 그 빈 단계로 돌아오고 끝내기(`endedBy`)로 바뀌지 않는다(J-D10). IF 합류였다면 모든 갈래가 그 빈 단계로 모여 끝내는 갈래가 생기지 않고, 블록 트리가 옛 형식과 같다(뒤에 빈 단계 한 칸만 더해진다).
3. **나머지 대상 지우기**: 노드 배열 순서로 대상 m 마다, 그때의 나가는 선이 정확히 하나이고 그 도착 T 가 m 이 아니면 다음을 한다(아니면 m 을 그대로 둔다).
   - m 으로 들어오는 선을 선 배열 순서로 모두 `to = T` 로 바꾼다. 선 ID·`order`·`cond`·`otherwise`·`label` 과 이름표 오프셋(`view.labels`)은 그대로이고, 꺾는 점(`view.routes`)은 지운다(끝점이 바뀌었다).
   - m 의 나가는 선과 m 을 지운다. `dropNodes` 와 같은 정리로 `view.positions[m]` 을 지우고, 그룹 `nodeIds` 에서 m 을 빼고(비면 그룹을 지운다), m 에 붙은 메모는 `attach = null` 로 둔다. 나가는 선의 꺾는 점·이름표는 `done` 정리가 버린다.
   - T 가 나중에 처리할 대상이면 그때 다시 옮겨진다. 이미 지운 대상을 가리키던 선은 그 대상을 처리할 때 옮겨졌으므로 처리 순서와 상관없이 결과가 같다.
4. 노드 배열은 지운 노드만 빠지고, 선 배열은 지운 선만 빠진다. 다른 순서는 바뀌지 않는다.
5. **빈 갈래 하나로 맞추기(B2)**: 지운 뒤 같은 도착으로 가는 갈래 선이 둘 이상인 IF(옛 IF 합류의 빈 갈래 여럿, 흔히 `insertSplit` 기본 모양)는 실행 순서 마지막 선(대개 "그 외")만 빈 갈래로 남기고, 나머지 선마다 빈 단계를 끼운다. 새 빈 단계는 ID 접두어 `r`, 제목 `TASK_LABEL`, 노드 배열에서 IF 바로 뒤, 위치 없음이다. 갈래 선 e 는 ID·`order`·`cond`·`otherwise`·`label` 그대로 `to` 만 새 빈 단계로 바꾸고(꺾는 점 지움), 새 선 {빈 단계 → 도착}(ID 접두어 `e`)을 e 바로 뒤에 넣는다. 실행 결과는 같고(빈 단계는 아무것도 하지 않는다) 기록에 TASK 항목, 검사에 `EMPTY_TASK` 경고가 생긴다.
6. 옛 형식에는 끝내는 갈래가 없고, 2 덕분에 변환 결과에도 끝내는 갈래가 생기지 않는다. 그래서 변환 전후 블록 트리는 빈 단계 칸만 다르고 경로 검사 결과도 `EMPTY_TASK` 경고 말고는 같다(A5 "저장된 세트가 그대로 검사된다").

예: 시드 `E2S_FLOW`(`if1` 갈래 `e3: if1→r2`, `e4: if1→m1`(그 외), `r2→m1`, `m1→r3`)는 `e4: if1→r3`, `r2→r3`(선 ID 그대로)이 되고 `m1` 과 `m1→r3` 선이 빠진다. 노드는 7개에서 6개가 된다.

### 12.3 저장·dirty·서버

- `toEditFlow` 안에서 바꾸므로 기준 흐름(`baseJson = flowJsonOf(toEditFlow(서버 흐름))`)과 편집 흐름이 같다. 열기만 해서는 dirty 가 아니다. 다른 편집을 해서 저장하면 새 형식으로 남는다.
- 서버에 저장된 글자는 다음 저장까지 옛 형식이다. 그동안 OASIS 운영 실행은 옛 형식으로 돌고 기록에 MERGE 항목이 남는다. 결과는 같다(§5 결과 불변).
- 열 때 바꾼 것이 있으면 메시지 줄에 한 번 알린다: "옛 합류 노드 {n}개를 없앤 형식으로 바꿔 열었다. 저장하면 새 형식으로 남는다." 개수는 `upgradeLegacyMerges` 가 지운 수 + 빈 단계로 바꾼 수다. 알림 문구를 정하려고 `load` 가 같은 함수를 한 번 더 부르거나 개수를 돌려받는다.
- 보기 모드에서도 바꾼 흐름을 보인다.

## 13. 하위 세트 호출 스펙에 주는 영향

`2026-10-01-rule-set-flow-subset-call-design.md` 를 이 모델 위로 옮길 때 고칠 점이다(그 스펙을 쓸 때 반영한다).

- §1 "돌아오는 MERGE 의 `splitId` 도 SET 노드 ID 일 수 있다" 를 지운다. SET 노드의 처리 갈래도 §2.3 처럼 정상 경로로 바로 돌아온다.
- §1 "흐름 구조에서는 RULE 과 같다(들어오는 선 1, 나가는 선 1)" → 들어오는 선 1 이상(모이는 자리일 때만 2 이상), 나가는 선 1.
- `CATCHABLE`·`FlowParser.catchable` 은 RULE·TASK·SET 이 된다. h2 문구도 "룰·빈 단계·룰 세트 노드에만" 으로 넓힌다.
- 블록 트리 `Step` 에 `SetStep` 을 더한다. `Guarded.step` 이 그대로 받는다(이름을 다시 바꾸지 않는다).
- 끝내는 IF 갈래(B1)와 처리 갈래 안 끝냄 규칙(J-D9·J-D18)이 SET 받는 노드에도 그대로 쓰인다. 하위 세트의 `endedBy` 판정(`SUBSET_ENDED`)은 `endedBy` 가 있는 끝냄만 본다. 하위 세트가 끝내는 IF 갈래로 끝나면(`endedBy` 없음) 부모에게는 **정상 완료**다(J-D17 과 같은 판단).
- §2 겉모양 `always` 계산의 "END 직전 경로 상태" 는 루트 순차 끝 상태와 모든 끝냄 지점(끝내는 처리 갈래 끝, 끝내는 IF 갈래 끝)의 상태를 IF 합치기 규칙으로 합친 것이다. 하위 세트 스펙의 "END 로 가는 모든 경로를 센다" 와 같은 뜻이고, 끝내는 IF 갈래를 빠뜨리지 않게 적는다.
- 병렬 갈래 안 끝냄(X-D11)이 하위 세트 안에서 나도 하위 세트 안의 일이다. 부모 병렬 갈래에는 번지지 않는다(하위 세트는 정상 완료이거나 `SUBSET_ENDED` 다).
- e2e 시나리오 수·노드 수 기대는 새 형식(합류 없음) 기준으로 쓴다.

### 14.3 퍼즈(`RuleSetFlowFuzz`)

- `Emit` 이 "보류 중인 선" 을 하나(`Pending`)가 아니라 목록으로 갖는다. IF 는 합류를 만들지 않고 갈래 끝 보류 선들을 다음 노드(없으면 END)가 한꺼번에 받는다. 빈 갈래는 IF 에서 나가는 보류 선이다. 중첩 IF 가 갈래 끝이면 그 보류 선들이 바깥 갈래 보류 목록에 합쳐진다.
- 한 IF 에 빈 갈래는 하나까지 만든다(둘째 빈 갈래로 뽑히면 룰 하나를 넣는다, B2).
- IF 갈래의 15% 는 끝내는 갈래로 만든다. 몸(없을 수 있음) 끝에서 바로 END 로 잇고 보류 목록에 넣지 않는다. 한 IF 에 이어지는 갈래가 적어도 하나 남게 하고, 끝내는 갈래를 실행 순서 마지막("그 외")에 두지 않아 §2.2 5 의 모호한 모양을 피한다(그 모양은 코퍼스 N20·N21 이 고정한다).
- IF 의 20% 는 옛 형식(MERGE)으로 만들어 옛 형식 받기도 두 구현에서 비교한다. 병렬은 늘 합류를 만든다.
- 구조 깨뜨리기 셋째 방법("그 외" 선 하나 더)은 `ifMerge` 대신 IF 의 모이는 자리(다음에 놓인 노드 ID 를 기록해 둔다)로 선을 더한다.
- 기대는 Java 결과이므로 구현 때 시드 그대로 파일을 다시 만든다(`-Dfuzz.write=true`). `MIN_FUZZ_CASES`(200)는 그대로다.

| J-D4 | 받는 노드를 TASK 에도 붙이고, TASK 인 동안 받는 노드마다 `CATCH_NEVER` 경고(A4) | 사용자 승인. 그림 먼저 그리고 룰을 나중에 채우는 흐름(D-125)에 예외 처리도 먼저 그릴 수 있다. 새 코드 대신 같은 뜻의 기존 경고를 쓴다 |
| J-D5 | 엔진·TS 해석기는 옛 형식을 받고 편집기는 열 때 바꾼다(A5) | 사용자 승인. 저장된 세트가 그대로 돌고, 다음 저장 때 자연히 새 형식이 된다 |
| J-D6 | "들어오는 선 2개 이상은 모이는 자리만" 을 따로 검사하지 않는다 | 블록 트리 만들기가 이미 보장한다(§2.5). 검사를 하나 더 두면 같은 결함에 문구가 둘이 된다 |
| J-D7 | 새 형식 IF 는 같은 도착으로 가는 갈래 선을 하나만 둔다(1단계 f4). 그래서 빈 갈래는 하나다. END 로 바로 가는 끝내는 갈래는 빈 갈래로 세지 않는다. 옛 IF 와 병렬은 지금처럼 받는다. 편집기 `insertSplit`·`addBranch` 는 빈 단계를 넣고, 변환·병렬 → IF 는 남는 빈 갈래에 빈 단계를 채운다 | 사용자 추가 결정 B2. 같은 두 노드를 잇는 선 둘은 그림에서 겹쳐 어느 갈래인지 알기 어렵고, 편집기는 이미 같은 from→to 를 막는다. END 직행 갈래를 빈 갈래로 세면 가장 흔한 "조건이면 끝내고 그 외는 계속" 모양(§1 둘째 예)을 그릴 수 없다. 옛 IF·병렬까지 막으면 저장된 세트(A5)와 지금 병렬 기본 모양이 깨진다 |
| J-D8 | 돌아오는 자리는 둘러싼 끝(IF 모이는 자리·병렬 합류)이어도 된다 | 한 노드가 블록 여럿을 닫는다는 A2 와 같은 규칙이다. 옛 형식의 "합류 → 합류" 연쇄를 변환하면 이 모양이 된다 |
| J-D9 | IF 갈래 중간 끝내기(끝내는 갈래)를 허용한다. 끝내는 갈래 = 다른 갈래와 노드를 함께 지나지 않고 END 로 가는 갈래, 모이는 자리는 이어지는 갈래끼리 계산한다. 처리 갈래 안·병렬 갈래 안·중첩 IF 안 어디서나 쓴다. 받는 노드 X-D6 은 없어진다 | 사용자 추가 결정 B1. "다른 갈래와 함께 지나지 않음" 은 그래프만으로 정해져 Java·TS 가 같게 계산하고, 끝내는 갈래가 뒤 흐름을 삼키지 않는다. 옛 형식 변환은 J-D10 으로 끝내는 갈래를 만들지 않는다 |
| J-D10 | 정상 다음 노드가 END 인 노드에는 돌아올 자리가 없다. 변환은 END 로 바로 나가는 옛 합류(IF 합류·돌아오는 합류)를 빈 단계로 바꾼다. 「흐름으로 돌아오기」는 그때 거부한다 | A3("END 는 끝냄")의 결과다. 돌아오는 합류를 그냥 END 로 이으면 `endedBy` 가 생겨 OASIS 가 보는 결과가 바뀐다. IF 합류를 그냥 END 로 이으면 B1 규칙으로 끝내는 갈래가 생겨 블록 모양·검사 결과가 바뀐다. 빈 단계 한 칸이면 둘 다 막는다 |
| J-D11 | 블록 트리에 `Step`(RULE·TASK, 뒤에 SET)을 두고 `Guarded.rule` → `step`, `Split`·`Guarded` 에 `joinId` | TASK 와 하위 세트 SET 을 같은 자리로 받는다. 이름을 바꾸면 RULE 만 가정한 코드를 컴파일이 모두 찾는다 |
| J-D12 | 변환은 `toEditFlow` 안에서 하고 열기만 해서는 dirty 가 아니다 | 기준 흐름과 편집 흐름이 같아야 자동 저장 불변식(`baseJson`)이 지켜진다. 보기만 하는 사람에게 저장 확인을 띄우지 않는다 |
| J-D13 | IF 지우기·접기·복사·옮기기는 끝내는 갈래 몸을 블록에 넣어 함께 다룬다. 「분기 풀기」로 끝내는 갈래만 남기기와 끝내는 갈래가 있는 IF 의 병렬 바꾸기는 거부한다 | 끝내는 갈래 몸은 그 IF 에서만 닿는 노드라 블록의 일부다. 끝내는 갈래 규칙(J-D9·J-D19) 때문에 올바른 흐름에서는 IF 모이는 자리가 END 가 되지 않으므로, 앞 판의 "모이는 자리 END 인 IF 지우기 거부" 는 필요 없다. 끝내는 갈래만 남기면 뒤 흐름에 닿을 수 없고, 병렬 갈래는 END 로 갈 수 없다 |
| J-D14 | 접힌 IF 블록의 대표 선은 그리기 전용이다 | 출구 선이 여럿이라 한 실제 선에 묶으면 편집이 한 갈래에만 걸린다 |
| J-D15 | `version` 1 유지 | X-D7, D-125 와 같은 판단 |
| J-D16 | 문구 "짝 합류 밖에서" → "모이는 자리 밖에서", 처리 갈래 침범 전용 문구 S8, 도착 불일치 S7, 같은 도착 IF 갈래 f4 | 새 모델에 맞는 말로 원인을 바로 알린다. 코퍼스가 두 구현의 문구를 묶는다 |
| J-D17 | 끝내는 IF 갈래로 끝난 실행은 정상 완료다. `endedBy` 를 쓰지 않고 `RuleSetResult`·`RunTrace` 에 새 칸도 두지 않는다. 디버거만 기록에서 끝낸 갈래를 찾아 보인다 | `endedBy` 는 "예외를 처리하다 끝났다" 는 뜻이라 OASIS 가 예외 끝냄으로 갈라 쓴다. IF 갈래 끝냄은 작성자가 그린 업무 흐름이므로 지금 IF 갈래가 END 로 가는 흐름처럼 정상 완료가 맞다. 어느 갈래로 끝났는지는 `path` 의 IF `chosenEdgeId` 로 이미 알 수 있어 계약을 늘릴 까닭이 없다 |
| J-D18 | 처리 갈래 안에서 IF 갈래로 끝나면 `endedBy` 는 끝난 지점을 감싼 가장 안쪽 처리 갈래의 받는 노드다. 병렬 갈래 안 IF 끝냄은 받는 노드 끝냄(X-D11)과 같이 남은 형제를 실행하지 않는다 | 처리 갈래 안 끝냄은 처리 갈래가 END 로 바로 가는 것과 뜻이 같다(예외 처리 중 끝냄). 끝냄 신호를 하나로 묶어 병렬·중첩 규칙을 한 벌로 둔다 |
| J-D19 | 모든 갈래가 서로 겹치지 않고 따로 END 로 가면, 실행 순서 마지막 갈래 가운데 END 로 바로 가지 않는 갈래가 이어지는 갈래다 | 그래프만으로는 어느 갈래가 흐름을 잇는지 정할 수 없고, 둘러싼 끝을 보면 모이는 자리 계산이 순환한다. 실행 결과는 어느 쪽이든 같다. 편집기 기본 모양("그 외" 가 이어짐)과 맞고, 갈래에 노드를 더해도 바뀌지 않는 규칙이다. 편집기는 END 앞에 IF 를 끼울 때 모이는 자리 빈 단계를 두어 기본 모양이 이 규칙에 기대지 않게 한다(§8.2 `insertSplit`, 수정 판정 2026-10-02) |

구현이 끝나면 `docs/mdm/decisions.md` 에 D-136 으로 J-D1~J-D19 를 남긴다. 받는 노드 스펙(D-134)의 X-D5("돌아오는 MERGE 의 `splitId` 는 RULE 노드 ID")·X-D6(처리 갈래 안 IF 갈래 END 금지)는 D-136 이 바꾼다고 함께 적고, 받는 노드 스펙 머리에 "§2·§3·§4·§8 의 돌아오는 MERGE 는 D-136 으로 바뀜" 한 줄을 더한다.

## 16. 미루는 것

- 모이는 자리·돌아오는 자리 강조 표시(노드를 고르면 그 블록이 모이는 자리를 표시)
- 접힌 블록 대표 선의 [+](블록 뒤에 끼우기)
- 서버에 저장된 옛 형식 세트 일괄 변환(마이그레이션)
- IF 조건식 오류(`BRANCH_EVAL_ERROR`)를 받는 노드(받는 노드 스펙 §12 그대로)
- 끝내는 갈래 안 노드와 IF 블록 뒤 노드의 관계를 EXCLUSIVE 로 계산해, 블록 뒤에서 끝내는 갈래 결과를 읽을 때 `UNKNOWN_INPUT` 대신 더 맞는 문구를 내기(끝내는 처리 갈래도 함께)
- 「이 갈래에서 끝내기」 메뉴(지금은 갈래 선을 END 로 다시 이어 만든다)
- §2.2 5 규칙에 어긋난 모양(안쪽 IF 에서 "그 외" 를 몸 있는 끝내는 갈래로 둠)을 편집기가 알아서 바로잡기
