## 0. 목표와 성공 기준

### 0.1 목표

1. 같은 양의 결과물을 만드는 데 드는 Claude 비용을 줄인다.
2. 사용자가 빠르게 해 달라고 하면 완료 시각을 앞당긴다.
3. opencode·GLM 워커에 구현까지 맡겨서 Claude 레인을 늘리지 않고 병렬 수를 늘린다.
4. 레인 안 서브에이전트를 최대한 병렬로 돌린다.

### 0.2 성공 기준

- 6절의 측정 도구로 회차를 잰다.
- 토큰 모드 회차의 목표는 6.2 표를 따른다. 핵심은 아래 세 가지다.
  - 1천 줄당 Claude 비용 $7 이하
  - 조정 세션 비중 10% 이하
  - 조정·레인 컨트롤러 컨텍스트 중앙값 12만 토큰 이하
- 시간 모드 회차의 목표는 활동 시간당 5,000줄 이상이고, 이때 1천 줄당 비용은 $10 이하다.

### 0.3 범위 밖

- 사용량 띠(G/Y/O/R) 계산 규칙은 바꾸지 않는다. 모드는 그 위에서 상한과 배정 순서만 바꾼다.
- 머지 게이트(`merge-gate.mjs`)와 무거운 명령 슬롯(`heavy.mjs`)의 동작은 바꾸지 않는다.
- Claude 리뷰를 머지 관문으로 두는 규칙은 유지한다. 비-Claude 워커의 결과도 Claude 리뷰를 통과해야 머지한다.

### 1.2 설계에 쓴 발견

1. **SDD가 가장 쌌다.** 1천 줄당 $6.9였고, 세션 1시간당 효율도 가장 높았다.
2. **레인을 늘려도 빨라지지 않는 경우가 있었다.** 레인 12개를 쓴 B의 활동 시간당 줄 수는 세션 1개인 A와 같았다.
3. **조정 세션 비용의 주된 원인은 컨텍스트 크기였다.**
   - 조정 세션과 SDD 컨트롤러가 호출할 때마다 컨텍스트를 중앙값 25만~33만 토큰씩 읽었다.
   - 30만 토큰이 넘는 호출이 43~57%였다.
   - 이 PC의 `.coord.local.json` 은 `compact.default_window` 가 1,000,000이다.
   - F 조정 세션은 이런 호출을 2,908번 했다.
4. **조정 세션 비용은 틱보다 요청 처리에서 나왔다.**
   - F 조정 세션 $233 가운데 73%가 사용자 요청 턴이었고, 23%가 작업 알림 턴이었다.
   - 진행표 요청이 12번, compact가 10번 있었다.
   - 틱 턴은 비용에서 따로 드러나지 않았다.
5. **Workflow가 작고 비쌌다.**
   - E의 Workflow 108회 가운데 1회당 agent 수 중앙값은 2였다.
   - Workflow 비용 $442 가운데 50%가 캐시 쓰기였다.
   - 모델 표의 기본값은 sonnet인데, Workflow agent 호출의 72%가 opus였다.
6. **도구 에러는 결함이 아니라 재시도였다.**
   - 도구 에러의 약 90%가 `Exit code`(빌드·시험·명령 실패)였다.
   - Workflow가 아닌 회차의 재시도율은 2.9~3.4%였고, Workflow agent는 5.2%였다.
7. **결함 양상이 방식마다 달랐다.**
   - SDD는 리뷰가 Important를 찾은 Task 6개가 모두 수정 1라운드에서 닫혔다.
   - 레인 회차는 환경 간섭 사고가 대부분이었다. node_modules 심링크, JDK 26 데몬, PDB 하니스 교착, Spotlight 색인이 그 예다.

## 2. 설계 1: 회차 모드

### 2.1 모드 선택

- 회차 모드는 `token`(토큰 우선)과 `time`(시간 우선) 두 가지다.
- 기본값은 `token` 이다.
- 사용자가 "빠르게 해 줘" 같은 요청을 하면 조정자가 `time` 으로 바꾼다.
- `start <run-id> --mode time|token` 으로 시작할 때 정할 수도 있다.
- 회차 도중에 모드를 바꾸면 이미 도는 일은 그대로 둔다. 다음 배정부터 새 모드를 적용한다.
- 모드는 state `run.mode` 에 기록한다.

### 2.2 모드 표

| 항목 | `time` | `token` |
|---|---|---|
| Claude 레인 수 상한 | 6 | 3 |
| 레인당 동시 서브에이전트 (G/Y/O/R 띠) | 6 / 5 / 3 / 0 | 4 / 3 / 2 / 0 |
| S/M 구현 첫 배정 | Claude agent와 풀 가운데 먼저 비는 쪽 | 풀 먼저 |
| 구현 모델 (Claude) | S/M sonnet/high. L·동시성은 opus/high | S/M sonnet/medium. L은 sonnet/high. opus는 판정에만 |
| 리뷰 | Task마다 바로. 다음 Task 구현과 겹쳐서 진행 | S는 몇 개씩 묶어서. M/L은 Task마다 |
| Workflow | 같은 흐름 M/L 항목 2개 이상 | 같은 흐름 M/L 항목 4개 이상 |
| 조정 세션 모델 | opus/medium | sonnet/medium |
| 하트비트 cron | 15분 | 30분 |

- 레인 상한 3은 레인을 늘려도 세션 효율이 떨어진 실측(1.2의 2)을 반영한다.
- 레인 상한 6은 이 PC의 메모리와 무거운 명령 슬롯으로 감당할 수 있는 선이다. **추정**
- 병렬도는 레인 수가 아니라 레인 안 서브에이전트 수와 풀 슬롯으로 높인다.
- `usage.relaxed` 가 켜져 있으면 지금처럼 Y·O 띠를 G로 내려서 계산한다.

### 2.3 설정

- `workflow.agents_by_band` 를 모드별 값으로 바꾼다: `{"time": {"G":6,"Y":5,"O":3,"R":0}, "token": {"G":4,"Y":3,"O":2,"R":0}}`
- `workflow.model_table` 에 모드 열을 넣는다. 모드 열이 없는 행은 두 모드에 같이 쓴다.
- `lanes.max_by_mode: {"time": 6, "token": 3}` 를 추가한다. `usage.md` 「새 레인 상한」과 함께 적용한다.

## 3. 설계 2: 레인 안 병렬 실행

원칙은 다음과 같다. 코드를 읽고 쓰는 일은 넓게 병렬로 돌린다. 무거운 명령은 슬롯으로 줄을 세운다.

### 3.1 항목 표에 의존 관계와 파일 소유를 적는다

- 레인 컨트롤러는 착수할 때 항목마다 `선행 항목` 과 `건드릴 파일` 을 적는다.
- 두 조건을 모두 만족하는 항목은 동시 상한까지 한꺼번에 띄운다.
  - 선행 항목이 모두 끝났다.
  - 다른 진행 중 항목과 건드릴 파일이 겹치지 않는다.
- 지금 지시문의 `수정분 확인이 clean 이 아니면 다음 항목 금지` 는 `그 항목에 의존하는 항목만 대기` 로 바꾼다.

### 3.2 격리: 같은 워크트리와 파일 소유 분리

- 구현 agent는 자기 항목의 파일만 고친다. 커밋은 하지 않는다.
- 컨트롤러가 그 항목의 파일만 골라 커밋한다(`git add <파일 목록>`).
- agent마다 워크트리를 따로 두지 않는다. node_modules와 Gradle 캐시가 추가로 들고, tooltip 회차에서 심링크 사고가 났기 때문이다. [근거: `docs/tooltip-2026-10/SUMMARY.md` §4]
- 파일 겹침을 피할 수 없는 항목만 순서대로 처리한다.

### 3.3 구현과 리뷰를 겹쳐서 진행한다

- 항목 A의 구현이 끝나면 컨트롤러가 커밋하고 리뷰 agent를 띄운다. 그동안 다른 항목의 구현은 계속 진행한다.
- 리뷰 지적은 수정 agent가 처리한다. A의 파일은 리뷰가 clean이 될 때까지 A의 소유로 잠근다.
- 리뷰 agent는 읽기 전용이다. 따라서 동시 상한 안에서는 몇 개를 띄워도 충돌하지 않는다.

### 3.4 시험

- 단일 시험 클래스·파일 실행이나 패키지 하나의 `tsc` 는 agent가 바로 돌린다.
- 모듈 전체 시험과 빌드는 `heavy.mjs` 슬롯을 거친다. 레인 안에서는 한 번에 하나만 돌린다.
- 동시에 진행한 항목 묶음이 끝나면 컨트롤러가 모듈 시험을 한 번 돌린다. 이것을 웨이브 끝 통합 시험이라고 부른다. 각자는 통과했지만 합쳐서 깨지는 경우를 여기서 잡는다.

### 3.5 컨트롤러 컨텍스트 보호

- agent는 보고를 파일(`task-<N>-report.md`)로 남긴다. 컨트롤러에게는 5줄 이하 요약만 돌려준다.
- 레인 컨트롤러는 컨텍스트가 `compact.lane_max`(기본 250,000)를 넘으면 5.1의 정리 절차를 따른다.

## 4. 설계 3: 비-Claude 워커 풀

### 4.1 구성

| 워커 | 맡는 일 | 동시 수 |
|---|---|---|
| opencode | S/M 구현·수정(TDD 포함), 조사, 문서. 풀의 주력이다. | 3 |
| GLM 5.3 | 본보기가 있는 패턴 반복, 정해진 형식의 문서·표 정리. opencode 슬롯이 꽉 찼을 때 넘치는 일을 받는다. | 1 (회사 PC는 0) |
| Claude | 분해, 리뷰(머지 관문), L·동시성·트랜잭션 구현, 실패한 묶음 이어받기 | 레인 상한(2.2) |

- 풀은 PC 전체에 하나다. 모든 레인이 함께 쓴다.
- 상태는 회차 폴더의 `pool/` 에 둔다. 회차가 없으면 `$TMPDIR/coord-pool/` 를 쓴다. 조정자 없이 SDD 세션 하나만 돌 때도 쓸 수 있게 하기 위해서다.
- 슬롯 수는 두 모드에서 같다. 모드는 배정 순서만 바꾼다(2.2).

### 4.2 실행 방식: 단발 실행

> **2026-10-11 변경(사용자 결정)**: 워커는 화면 없는 단발 실행 대신 **보이는 TUI 탭**으로 띄운다. 사람이 진행과 한도 오류를 화면으로 보기 위해서다. 실행기(Node)가 탭을 띄우고 지시를 넣고, 화면·보고 파일을 폴링해 판정하고, 어느 경로로 끝나든 탭을 닫는다. GLM 은 모델만 GLM 인 Claude Code 이므로 `launch.glm` 으로 띄운다. 현재 절차의 정본은 `references/pool.md` §1 이다. 아래 원래 설계는 기록으로 남긴다.

- 작업 묶음 하나마다 실행기를 한 번 띄우고, 일이 끝나면 프로세스가 끝난다.
  - opencode: `opencode run --standalone "<지시>"`
  - GLM: `glm` 환경으로 `claude -p "<지시>"`. 실행 전에 `glm-preflight.mjs` 가 `ok` 여야 한다.
- 진행 상황은 Orca 새 탭에서 보인다. `search.mjs --tab` 과 같은 방식이다. [근거: `references/contract.md` `search.opencode.tab_command`]
- 지금의 TUI 워커 방식(`worker-start`)은 쓰지 않는다. 지시문이 입력창에서 사라지거나 생존 판정이 영구 실패하는 문제가 있었다. [근거: `~/.claude/CLAUDE.md` 「Orca 로 opencode 워커 띄우기」]
- 단발 실행은 묶음 사이에 대화 맥락이 이어지지 않는다. 필요한 맥락은 묶음 파일에 모두 적는다.
- 슬롯 관리는 토큰을 쓰지 않는 Node 프로세스가 맡는다.
  - `submit` 할 때 빈 슬롯이 있으면 바로 실행한다. 없으면 큐에 넣는다.
  - 끝난 실행기가 큐에서 다음 묶음을 꺼낸다.

### 4.3 작업 묶음 형식

- 묶음 파일은 레인 워크트리의 `.pool/<id>.md` 에 둔다.
- `.pool/` 은 `.git/info/exclude` 에 넣는다.
- opencode에 넘기는 지시문은 `작업 지시 파일 .pool 폴더의 <id>.md 를 읽고 그대로 진행해` 로 짧게 쓴다. opencode 지시문에는 `!`·`/`·`@` 를 쓰지 않는다. [근거: `~/.claude/CLAUDE.md`]
- 묶음 파일 칸(`templates/packet.md`)
  - 목표
  - 작업 폴더
  - 건드릴 파일(3.1의 파일 소유)
  - 금지 사항: 커밋·push 금지, 소유 밖 파일 수정 금지
  - 완료 조건: 돌릴 시험 명령
  - 무거운 명령 규칙: 모듈 시험·빌드는 `heavy.mjs` 경유
  - 보고 형식: `.pool/<id>.report.md`

### 4.4 결과 반환

1. 워커가 `.pool/<id>.report.md` 를 남긴다.
2. 실행기가 종료 코드를 담은 `.pool/<id>.done` 을 만든다.
3. 실행기가 `term-send-safe.mjs` 로 레인 탭에 `[pool] <id> 완료 rc=<코드>` 한 줄을 보낸다.
4. 전송이 실패하면 레인이 다음 단계에서 `pool.mjs status` 로 확인한다.

### 4.5 풀에 맡기는 일

- 맡기는 일: 완료 조건 시험이 분명한 S/M 구현·수정, 조사, 문서, 본보기가 있는 패턴 반복
- 맡기지 않는 일: L 크기 구현, 동시성·트랜잭션, 보안, 공유 API 변경(merge-gate의 `SHARED_API`), 원인 모를 결함

### 4.6 검증과 실패 처리

1. 레인 컨트롤러가 보고 파일을 읽는다.
2. 완료 조건 시험을 직접 한 번 돌린다.
3. Claude 리뷰를 띄운다. 리뷰 기준은 2.2를 따른다.

| 상황 | 처리 |
|---|---|
| 종료 코드가 0이 아님 | 바로 Claude agent로 넘긴다. |
| 시간 초과 (S 20분, M 40분) | 바로 Claude agent로 넘긴다. |
| 한도 오류 (출력에 429, rate limit, quota) | 바로 Claude agent로 넘긴다. 그 워커 종류는 30분 동안 쉬게 하고 동시 상한을 하나 줄인다. |
| 완료 조건 시험 실패 | 바로 Claude agent로 넘긴다. |
| 리뷰 지적 | 풀에 다시 맡기지 않는다. Claude 수정 agent가 고친다. |

- opencode에서 GLM으로 넘기는 단계는 두지 않는다.
- 쉬는 동안 새 묶음은 다른 비-Claude 슬롯이 비어 있으면 그쪽에, 없으면 Claude로 간다.
- Claude로 넘어간 묶음은 실행기가 `FALLBACK` 으로 표시한다.

### 4.7 기록

- 묶음마다 `pool/log.jsonl` 에 한 줄을 남긴다.
- 칸: `id`, 레인, 워커 종류, 크기, 시작·끝 시각, 결과(`ok`·`fail`·`timeout`·`ratelimit`), Claude로 넘어갔는지, 리뷰 지적 수, 변경 줄 수

### 4.8 설정

| 키 | 기본값 | 뜻 |
|---|---|---|
| `pool.opencode.max` | 3 | opencode 동시 수 |
| `pool.glm.max` | 1 | GLM 동시 수. GLM 사전 확인이 실패하는 PC에서는 0으로 본다. |
| `pool.order` | `["opencode","glm"]` | 빈 슬롯을 찾는 순서 |
| `pool.timeout_min` | `{"S":20,"M":40}` | 묶음 시간 상한 |

## 5. 설계 4: 조정 세션 경량화

### 5.1 컨텍스트 상한과 정리 방식

- 조정 세션은 컨텍스트가 `compact.coordinator_max`(기본 200,000)를 넘으면 정리한다.
- 레인 컨트롤러는 `compact.lane_max`(기본 250,000)를 넘으면 정리한다.
- 정리 방식은 `/compact` 대신 아래 순서로 바꾼다.
  1. 정본 메모와 state를 갱신한다.
  2. `/clear` 를 보낸다.
  3. `resume.md` 의 재독 세트를 읽는다.
- `/compact` 는 큰 컨텍스트를 한 번 더 읽고 요약을 쓴다. `/clear` 는 재독 세트(수만 토큰)만 읽는다.
- 호출당 컨텍스트 중앙값이 30만에서 10만 안팎으로 줄면 캐시 읽기 비용이 약 3분의 1로 준다. **추정**
- 현재 `ctx-usage.mjs` 와 `CTX_OVER`·`CTX_OVER_SELF` 줄이 컨텍스트 감지를 맡는다. 판정 기준만 새 상한으로 바꾼다.

### 5.2 조정 세션이 직접 하는 일

- 새 요청이 들어오면 조정 세션은 크기를 한 줄로 산정한 뒤 레인·풀·서브에이전트로 넘긴다.
- 조정 세션이 직접 하는 일은 D0(git, 상태 확인, 짧은 확인)까지다. 조사는 검색 워커에 맡긴다.
- 구현은 조정 세션에서 하지 않는다.
- 진행표 요청에는 `coord-status.mjs` 출력을 그대로 보여 준다. `WBS.md` 와 오피스 화면 위치를 함께 알린다. 레인 화면을 다시 읽지 않는다.

### 5.3 이벤트 구동 틱

- `tick.mjs --watch` 가 백그라운드 셸에서 토큰 없이 돈다.
- 처리할 줄(IDLE, STALL, ESCALATE, 풀 완료 등)이 나올 때만 Monitor로 조정 세션을 깨운다.
- cron은 하트비트로만 남긴다. 간격은 2.2를 따른다.
- 이 항목의 목적은 절감보다 반응 속도다. 레인이 끝난 뒤 다음 일을 받기까지의 대기 시간을 줄인다.

### 5.4 조정 세션 모델

- `token` 모드는 sonnet/medium, `time` 모드는 opus/medium이다.
- 어려운 판단은 지금처럼 「판단 올리기」로 opus/high 서브에이전트에 넘긴다.
- 모드를 바꾸면 조정 세션 모델은 다음 `/clear` 재개 때 바꾼다. **미확인**: 실행 중인 세션의 모델을 바꾸는 방법은 구현 단계에서 확인한다.

### 5.5 레인 질문 처리

레인은 지금처럼 `질문: 배경 / 선택지 / 기본안` 형식으로 묻는다. 조정 세션이 종류를 판단한다.

| 종류 | 예 | 처리 |
|---|---|---|
| 사실·절차 | 어느 규칙 문서를 따르는가, 머지 순서, 시험 범위 | 조정 세션이 바로 답한다. |
| 영향이 작은 선택 | 기본안이 있고 레인 안에서 끝나는 선택 | `기본안대로` 한 줄로 답한다. |
| 설계·정합성 | 공유 API·스키마, 다른 레인과 겹치는 결정, 트랜잭션 | 「판단 올리기」로 opus/high에 넘긴다. |
| 제품 결정 | 화면 동작, 업무 정책 | 사용자에게 묻는다. 레인은 기본안으로 계속할 수 있으면 계속한다. |

- 답할 때마다 `coord-state.mjs decide <레인> "<질문 요약>" "<결정>"` 으로 state `decisions` 에 한 줄을 남긴다.
- 재개 재독 세트에 최근 결정 20개를 넣는다.
- 새 질문이 오면 결정 기록에서 비슷한 것을 먼저 찾는다. 있으면 그 답을 그대로 쓴다.

## 6. 설계 5: Workflow 사용 조건

### 6.1 사용 조건

| 조건 | `token` | `time` |
|---|---|---|
| 같은 흐름(구현 → 리뷰 → 수정)을 반복하는 항목 수 | 4개 이상 | 2개 이상 |
| 항목 크기 | M/L | M/L |
| agent 2개 이하로 끝나는 일 | 금지. Agent 도구(D2·D3)로 처리 | 금지 |
| 풀에 맡길 수 있는 S/M 항목 | Workflow에 넣지 않는다. 레인이 풀로 보낸다. | 같음 |

- Workflow 안에서는 풀을 부르지 않는다. Bash 도구는 10분을 넘으면 시간 초과가 나서, agent가 풀 결과를 기다리면 토큰과 시간을 낭비한다.

### 6.2 모델 규율

- `agent()` 마다 model·effort를 적는 규칙을 유지한다.
- opus를 쓸 때는 근거 한 줄(L 크기, 동시성, 판정 중 무엇인지)을 함께 적는다.
- `token` 모드에서는 opus를 판정 리뷰와 L 구현에만 쓴다. 실패 사다리에서도 sonnet/high를 한 번 더 시도한 뒤 opus로 올린다.

### 6.3 캐시 재사용

- 같은 단계의 agent들은 같은 모델로 동시에 띄운다.
- 지시문은 공통 부분을 앞에, 항목별 내용을 뒤에 둔다. 캐시는 앞부분이 같을 때만 재사용되기 때문이다.
- 효과는 7.2의 「Workflow 비용 중 캐시 쓰기 비중」으로 확인한다. **추정**: 같은 모델과 같은 앞부분이면 5분 캐시를 agent끼리 나눠 쓴다.
