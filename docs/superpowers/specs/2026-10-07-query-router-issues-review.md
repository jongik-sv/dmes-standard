# 조회 라우터 도입 문제점 검토

- 작성: 2026-10-07 (조정자, 회차 notice-fill2)
- 상태: 사용자 검토 중. 항목마다 「답변」 칸에 의견을 적어 주세요.

업무 모듈의 일반 조회를 MyBatis 조회 라우터로 BPMN 없이 처리할 때, 가장 큰 문제는 **보안**(지금도 존재)이고 그다음이 **DB 방언**과 **이중 관리**입니다.

## 0. 검토 대상 방침 (사용자 정리, 2026-10-07)

| 구분 | mcm·mdm | 그 밖의 업무 모듈 (mls·mpp·mqc·mas 등) |
|---|---|---|
| 일반 조회 | 지금처럼 BPMN → 서비스 → JPA | MyBatis 전용 조회 라우터(`/query/{queryId}`)로 BPMN 없이 바로 조회 가능 |
| insert·update·delete 등 트랜잭션 처리 | BPMN → 서비스 → JPA | 반드시 BPMN → 서비스 → JPA |

- MyBatis 는 업무 모듈의 읽기 전용 일반 조회에만 쓴다. MyBatis 로 데이터를 바꾸지 않는다.
- BPMN 에는 트랜잭션이 있는 실제 업무 흐름만 남는다.

## 1. 보안: 조회 라우터와 service 경로의 권한 검사 누락 (확인됨)

정책과 상관없이 지금도 있는 문제라서, 보안 레인 `route-guard` 가 먼저 고치고 있습니다.

- **조회 라우터에 권한 검사가 없습니다.** 로그인만 하면 누구든 등록된 쿼리 ID 를 아무거나 부를 수 있습니다. BFF(`m-mcm/proxy.ts`)는 `query`·`service` 를 예약어로 빼서 권한 키를 만들지 않고, `unmatchedDeny` 가 꺼져 있어 그대로 통과시킵니다. 백엔드 `EndpointPermissionFilter` 도 권한 키를 뽑지 못해 통과시킵니다.
- **조회 라우터로 쓰기도 됩니다.** 쿼리 ID 로 INSERT 문을 주면 그대로 실행되고 커밋됩니다. query-route 레인이 단위 시험으로 확인했습니다(행 0 → 1).
- **같은 계열 경로로 BPMN 도 우회됩니다.** `/api/{모듈}/service/{serviceId}` 는 화면 권한 없이 아무 BPMN 의 execute 를 실행합니다. 예: mdm `codeEdit` 의 execute = 「마루 코드 폐기」. 조정자가 BPMN 정의와 BFF 설정을 직접 확인했고, 실제 호출 시험은 하지 않았습니다.
- **파라미터를 사용자가 바꿀 수 있습니다.** 회사·공장·부서·사용자 ID 를 요청에서 받으면 남의 데이터를 볼 수 있습니다. 이런 값은 서버가 넣어야 합니다.
- **무거운 쿼리를 막을 장치가 없습니다.** 행 수 상한이 없습니다.

대책(route-guard 진행 중): 화면 권한과 쿼리 ID 묶기, SELECT 문만 허용, 없는 ID 는 404, 서버 주입 파라미터, 행 수 상한, service 경로 권한 판정 편입 또는 차단.

## 2. DB 방언: SQLite 로컬과 Oracle·PostgreSQL 운영의 SQL 차이

JPA 는 방언 차이를 대부분 대신 맞춰 주지만, 직접 쓴 SQL 은 그렇지 않습니다.

| 자주 깨지는 곳 | SQLite | Oracle | PostgreSQL |
|---|---|---|---|
| 페이징 | `LIMIT n OFFSET m` | `OFFSET m ROWS FETCH NEXT n ROWS ONLY` (12c 이상) | `LIMIT n OFFSET m` |
| NULL 대체 | `IFNULL`·`COALESCE` | `NVL`·`COALESCE` | `COALESCE` |
| 문자열 잇기 | `\|\|` | `\|\|` | `\|\|`·`CONCAT` |
| 날짜 | 문자열·`date()` | `TO_DATE`·`SYSDATE` | `TO_DATE`·`now()` |
| 빈 문자열 | NULL 과 다름 | NULL 로 취급 | NULL 과 다름 |

- 우리 시험은 SQLite 로만 돌기 때문에, 로컬에서 통과해도 운영에서 깨질 수 있습니다.
- 선택지: (A) 세 DB 공통 문법만 허용 (B) MyBatis `databaseId` 로 방언별 SQL 분리 (C) 둘을 섞어 공통을 기본으로, 꼭 필요한 곳만 분리.

## 3. 이중 관리: JPA 엔티티와 매퍼 SQL

- 테이블 구조가 바뀌면 엔티티와 매퍼 SQL 을 둘 다 고쳐야 합니다.
- 엔티티 잘못은 컴파일 때 드러나지만, 매퍼 SQL 잘못은 실행해야 드러납니다. 컬럼 이름 하나만 바꿔도 조회 화면이 운영에서 깨질 수 있습니다.
- 응답 키 이름(camelCase) 규칙이 두 곳에 생겨, 같은 데이터가 저장할 때와 조회할 때 다른 키로 오갈 수 있습니다.

대책(안): 매퍼 SQL 마다 실행 시험 의무화, 응답 키 규칙을 가이드에 고정.

## 4. 단순 조회와 업무 조회의 경계

- 지금은 조회 뒤 가공(코드 값을 이름으로, 마스킹, 행 단위 권한 필터, 계산 칸)을 서비스 코드에서 합니다.
- 라우터는 SQL 결과를 그대로 돌려주므로, 이런 가공이 SQL 로 들어가거나 화면 코드로 흩어집니다.
- 처음에 단순 조회였다가 가공이 필요해지면 라우터에서 BPMN 경로로 옮겨야 합니다.

대책(안): 「라우터로 해도 되는 조회」 판정 기준을 가이드에 고정. 예: 가공 없음, 권한 필터는 서버 주입 파라미터로만, 마스킹 대상 칸 없음.

## 5. 응답 모양과 화면 공통 기능 (추정)

- BPMN 경로는 cactus 표준 응답(meta·data·grids·errors), 라우터는 단순 목록(`ApiResponse`)을 돌려줍니다.
- 서버 페이징의 전체 건수, 오류 코드·메시지 모양, 그리드 공통 처리가 OASIS 응답 기준이라면 라우터용으로 따로 맞춰야 합니다. 아직 확인하지 않았습니다.

대책(안): 그리드·조회 영역·오류 표시 공통 부품이 두 응답을 모두 처리하는지 확인.

## 6. 감사·화면 사용 통계 누락 가능성 (추정)

- 화면 사용 통계(첫 업무 호출 기록)와 감사 로그가 OASIS 경로에 붙어 있다면, 라우터로 조회하는 화면은 통계에서 빠질 수 있습니다. 아직 확인하지 않았습니다.

대책(안): 기록이 붙는 위치를 확인하고, 필요하면 라우터에도 같은 기록을 넣음.

## 7. 개발 규칙이 두 갈래가 됨

- mcm·mdm 은 「모두 BPMN+JPA」, 업무 모듈은 「조회는 라우터+MyBatis, 변경은 BPMN+JPA」 입니다. 개발자와 AI 에이전트가 모듈에 따라 다른 규칙을 따라야 합니다.
- 지금 검사 도구(oasis-contract-check, dflow 게이트)는 BPMN 기준이고, 매퍼 SQL 을 검사하는 도구는 없습니다.

대책(안): 가이드·스킬에 모듈별 갈림길 명시, 매퍼 SQL 검사(SELECT 만인지·방언·허용 목록 등록)를 도구에 추가.

## 8. 얻는 것 (비교용)

- 실행 SQL 이 파일에 그대로 있어 디버깅이 쉽습니다. 로그의 SQL 을 그대로 DB 도구에 붙여 실행할 수 있습니다.
- 복잡한 조회·대량 조회에서 JPA 엔티티 생성·스냅샷 비용이 없습니다.
- 조회만 하려고 BPMN 을 만들 필요가 없어, BPMN 에는 실제 업무 흐름만 남습니다.

## 9. 설계 레인이 올린 결정 항목 (query-route, 추천안으로 진행 중)

설계 레인이 확인한 사실: 조회 라우터는 이미 mcm·mdm 에 등록돼 있고, MyBatis 는 JPA 와 같은 DB 연결·같은 트랜잭션을 씁니다. BPMN 안에서 매퍼를 부르는 기능도 이미 있습니다. 그래서 새로 「도입」 할 것은 거의 없고, 남은 일은 보호·방언·이름 규칙입니다. 설계 문서: `docs/superpowers/specs/2026-10-07-query-route-mybatis-design.md`(레인 브랜치).

| # | 결정할 것 | 추천안 | 답변 |
|---|---|---|---|
| Q2 | 라우터로 부를 수 있는 매퍼 범위 | `persistence/query/**` 아래 매퍼만 | |
| Q3 | 권한 검사 방식 | 쿼리 ID 를 `{화면 OBJECT}.{action}` 로 짓고, 기존 OASIS 화면 권한을 그대로 씀(새 권한 등록 없음) | |
| Q4 | 응답 키 이름 | SQL 별칭을 큰따옴표 camelCase 로(`AS "itemCd"`). 따옴표가 없으면 Oracle 은 대문자, PostgreSQL 은 소문자로 바뀌는데 SQLite 시험으로는 못 잡음. 기존 화면을 옮길 때는 기존 키 유지 | |
| Q5 | 방언 처리 | 공통 SQL 을 기본으로 하고, 꼭 필요한 곳만 `databaseIdProvider` 로 방언별 SQL. 페이징은 cactus 공통 조각 | |
| Q6 | 운영 방언 보증 | 정적 검사 필수 + 배포 전 운영 DB 에서 EXPLAIN 점검(도커 금지라 운영 DB 자동 시험은 불가) | |
| Q7 | 행 수 상한 | 넘으면 거절, 기본 10,000행 | |
| Q8 | SQL 로그 | 바인딩 값 로그를 INFO 에서 DEBUG 로 내림 | |

「단순 조회」 기준(설계 §3): 읽기만, SQL 한 문, 형식 수준의 검사만, 행 단위 권한은 서버가 넣는 값으로 표현, 행 수 상한 안. 해당하지 않는 예: 트리 조립, 잠금 판정, 캐시를 거치는 조회, 사용자 SQL 실행, SQL 로 할 수 없는 마스킹.
