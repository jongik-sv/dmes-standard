MCM 예약 작업 · 설계 1c6782c11 기준

예약 작업은 이렇게 실행됩니다

MCM 이 매분 실행할 작업을 골라 선점하고, 해당 모듈을 호출합니다. 모듈은 접수만 하고 바로 응답한 뒤 따로 실행하고, 끝나면 결과를 JOB 표에 직접 기록합니다. MCM 은 실행이 끝나기를 기다리지 않습니다.

1. 한눈에 보기

무엇을 언제 실행할지 정하고 선점하는 쪽은 MCM 하나뿐입니다. 모듈은 MCM 이 넘겨준 값으로 실행하고, 결과만 JOB 표에 직접 기록합니다. 모든 모듈이 같은 Oracle 을 쓰기 때문에 결과를 받는 API 가 따로 없습니다.

2. 매분 일어나는 일

판정·선점은 BPMN 안에서 하고 커밋합니다. 모듈 호출은 커밋이 끝난 뒤 BPMN 밖에서 합니다. HTTP 응답을 기다리는 동안 행 잠금이나 DB 연결을 쥐고 있지 않기 위해서입니다.

sequenceDiagram
  autonumber
  participant T as 매분 트리거 (MCM)
  participant B as 판정 BPMN job^^dispatch
  participant DB as JOB 표
  participant P as 호출 풀 (MCM)
  participant M as 모듈 진입점

  T->>B: 매분 0초에 실행
  B->>DB: 실행할 작업 조회 (USE_YN=Y, NEXT_RUN_AT 지남, 최대 50건)
  alt 실행할 작업 없음
    DB-->>B: 빈 결과
    B-->>T: 끝 (커밋 없음)
  else 실행할 작업 있음
    B->>DB: FOR UPDATE SKIP LOCKED 로 선점
    B->>DB: RUN 행 생성, NEXT_RUN_AT 을 다음 회차로
    B-->>T: 커밋, 선점한 목록 반환
    T->>P: 목록 넘김 (50건 넘으면 BPMN 다시 호출)
    P->>M: POST /internal/job/run (runId, serviceId, 입력값)
    M-->>P: 202 접수
  end

3. MCM 은 기다리지 않습니다

모듈이 「접수」로 응답하는 순간 MCM 의 호출은 끝납니다. 작업을 마친 모듈은 MCM 을 거치지 않고 자기 DB 연결로 RUN 행을 직접 갱신합니다. MCM 이 꺼져 있어도 결과는 기록됩니다.

sequenceDiagram
  participant MCM as MCM
  participant MOD as 모듈 진입점
  participant SVC as 대상 서비스
  participant DB as JOB 표

  MCM->>MOD: POST /internal/job/run
  MOD-->>MCM: 202 접수 (여기서 MCM 의 호출은 끝)
  MCM->>DB: 접수 기록 (서버 이름, service_tag)
  Note over MCM: 다른 일을 함. 붙잡고 있는 스레드·연결 없음
  MOD->>SVC: 자기 실행 풀에서 실행 (몇 초 ~ 몇 시간)
  SVC-->>MOD: 결과 (건수·메시지·수집 값)
  MOD->>DB: 짧은 별도 트랜잭션으로 RUN 행 갱신 (STATUS=RUN 일 때만)
  Note over MOD,DB: 수집 작업이면 같은 트랜잭션에서 수집 값 저장
결과 갱신은 대상 서비스와 분리된 짧은 트랜잭션입니다. 그래서 대상 서비스가 롤백되어도 FAIL 기록은 남습니다. DB 순간 오류로 갱신이 실패하면 5초 뒤 한 번만 다시 합니다. 모듈 서버가 도중에 죽어 기록이 끝내 없으면, MCM 의 정리 작업(5분마다)이 「시간 초과 + 여유 300초」가 지난 RUN 행을 TIMEOUT 으로 닫습니다. 이것도 기다리는 것이 아니라 주기적으로 확인하는 방식입니다.

4. 실행 기록(RUN 행)의 상태

  direction LR

  RUN --> SKIP: 모듈이 거절 (503 풀 가득, 409 이미 실행 중)
  RUN --> FAIL: 처리기 없음 (404), 연결 거부
  RUN --> OK: 모듈이 성공 기록

  RUN --> TIMEOUT: 모듈이 시간 초과 기록, 또는 기록 없이 여유 시간 지남
  OK --> [*]
  FAIL --> [*]
  SKIP --> [*]
  TIMEOUT --> [*]
상황상태누가 기록하나
모듈 실행 풀이 가득 참 (503), 같은 작업이 이미 실행 중 (409)SKIPMCM, 호출 응답을 받은 즉시
모듈에 해당 처리기 없음 (404), 연결 거부FAILMCM, 즉시
읽기 시간 초과, 5xxRUN 유지이미 접수했을 수 있으므로 닫지 않고 모듈의 기록을 기다림. MCM 은 재시도하지 않음

작업 시간 초과 (모듈의 Future 감시)TIMEOUT모듈 감시 스레드가 DB 에 직접
모듈 서버가 도중에 죽어 기록 없음TIMEOUTMCM 정리 작업(5분마다), 시간 초과 + 300초 뒤

5. 실패할 때의 트랜잭션

업무 처리와 결과 기록은 서로 다른 트랜잭션입니다. 대상 서비스가 실패하면 업무 변경만 롤백되고, 실패 기록은 별도 트랜잭션으로 커밋되어 남습니다.

sequenceDiagram
  participant E as 진입점 (트랜잭션 밖)
  participant S as 대상 서비스
  participant A as 트랜잭션 A (업무)
  participant B as 트랜잭션 B (결과 기록)

  E->>S: serviceStarter.start
  S->>A: 업무 데이터 변경
  S--xA: 예외 발생
  A-->>A: OASIS 가 A 롤백 (연결 서브서비스 단계도 함께)
  S-->>E: SYSTEM_ERROR 결과
  E->>B: REQUIRES_NEW 로 새 트랜잭션
  B-->>B: RUN 행을 FAIL 로, 코드·메시지 기록, 커밋
  Note over E,B: 업무 변경은 없어지고 실패 기록만 남음
경우업무 데이터기록
대상 서비스 실패롤백FAIL 과 메시지, 트랜잭션 B 로 커밋
QUERY·COLLECT 의 SQL 이 시간을 넘김Oracle 이 문장을 취소(ORA-01013)하고 롤백TIMEOUT. 남은 시간만큼 쿼리 시간 초과를 걸어 둠
진입점의 시간 초과 감시가 먼저 걸림인터럽트 뒤 롤백. 인터럽트를 무시하는 호출은 끝까지 돌 수 있음TIMEOUT. 쿼리 시간 초과와 겹쳐도 한 번만 기록하고, 늦은 결과는 덮어쓰지 않음
자기 트랜잭션을 가진 서브서비스, 묶음마다 중간 커밋하는 작업이미 커밋된 부분은 남음FAIL. 이런 작업은 다시 돌려도 결과가 같게(멱등) 만듦
결과 기록이 실패(5초 뒤 재시도도 실패), 모듈 서버가 도중에 죽음롤백RUN 으로 남았다가 정리 작업이 TIMEOUT 으로 닫음

6. MCM 이 여러 대일 때

모든 MCM 이 매분 같은 판정을 돌립니다. 중복 실행은 FOR UPDATE SKIP LOCKED 가 막습니다. 먼저 잠근 MCM 만 그 작업을 가져가고, 다른 MCM 은 잠긴 행을 건너뜁니다. 선점할 때 DB 행을 다시 읽으므로 캐시가 필요 없고, 화면에서 저장한 내용은 다음 분부터 모든 MCM 에 반영됩니다.

sequenceDiagram
  participant A as MCM 1
  participant DB as JOB 표
  participant C as MCM 2

  par 같은 분 0초
    A->>DB: 작업 X 선점 시도
  and
    C->>DB: 작업 X 선점 시도
  end
  DB-->>A: 잠금 성공, RUN 생성
  DB-->>C: 잠긴 행 건너뜀 (0건)
  A->>A: 커밋 뒤 모듈 호출
  Note over C: 이번 분에 할 일 없음

7. 모듈 안에서의 실행

예약 작업 정의의 실체는 serviceId + 입력 변수 하나입니다. 예약 실행 진입점이 그 서비스를 서브서비스로 부릅니다. OASIS 의 서브서비스는 함수처럼 몇 겹이든 감쌀 수 있으므로, 업무 BPMN 이 내장 서비스를 엮어 새 작업을 만들 수 있습니다. 실행 결과 기록은 가장 바깥 진입점만 한 번 합니다.

접수 · 감사 SCHEDULER · 시간 초과 감시 · 결과 기록"]
  E --> CODE["job^^code
등록된 ScheduledJob 빈"]
  E --> QUERY["job^^query

  E --> COLLECT["job^^collect

  E --> BPMN["업무 BPMN
serviceId 그대로"]
  BPMN -. "서브서비스" .-> QUERY
  BPMN -. "서브서비스" .-> COLLECT
  BPMN -. "서브서비스" .-> OTHER["다른 업무 서비스"]
화면 유형실제 실행비고
CODEjob^^code코드 실행 = 일반 클래스 실행. 등록된 빈만 실행하고, 화면에서 임의의 클래스 이름은 받지 않음
BPMN지정한 serviceIdBPMN 은 코드와 함께 배포되는 파일이라 실행 중에 고칠 수 없음
QUERYjob^^query트랜잭션 하나로 실행. 남은 시간만큼 쿼리 시간 초과를 검
COLLECTjob^^collect수집 값은 결과를 기록할 때 같은 트랜잭션에서 저장. SQL 읽기는 10초와 남은 시간 중 작은 값으로 쿼리 시간 초과. HTTP 는 첫 판에서 GET 만
(PURGE)CODE 로 대신기존 정리 작업(위젯 보관 삭제, 폐기 토큰 정리)을 코드 작업으로 옮김

내장 서비스와 job^^dispatch 는 웹 경로로도 불릴 수 있습니다. 그래서 진입점이나 트리거를 거치지 않은 호출은 거절합니다.

9. 서버 사이 API 와 DB 접근

경로방향하는 일
POST /internal/job/runMCM → 모듈실행 요청. 모듈은 접수만 하고 202 로 바로 응답
RUN 행 · 수집 값 표모듈 → DB실행 결과를 직접 갱신(cactus-core JobRunResultWriter 한 곳)
처리기 표 TB_MCM_JOB_HANDLER모듈 → DB기동할 때 자기 코드 작업(ScheduledJob 빈) 목록을 MERGE. 화면이 이 표로 목록을 앎(사용자 확정)

서버 사이 HTTP 경로는 /internal/job/run 하나뿐이고 BFF 를 거치지 않습니다. ClientKey 와 system 주체, SYSTEM 역할을 확인하고, 사용자 토큰으로 부르면 403 입니다. 모듈 호출 주소는 MCM 설정 dmes.job.modules.<모듈>.base-url 에 두고, 기본값은 기존 관례인 <모듈>_WAS_URL 환경 변수와 로컬 포트입니다.

10. 운영할 때 알아 둘 것

  • 모든 모듈이 MCMAPUSER 표에 닿는 같은 Oracle 을 쓴다는 것이 전제입니다. 운영 DBA 는 V3 끝의 GRANT 로 각 모듈 DB 사용자에게 권한을 줍니다(RUN: SELECT·UPDATE, 수집 값·정의·처리기: SELECT·INSERT·UPDATE, DELETE 없음).
  • MCM 이 모두 꺼지면 새 회차가 시작되지 않습니다. 놓친 회차는 따라잡지 않습니다. 이미 실행 중인 작업의 결과는 그대로 기록됩니다.
  • LB 는 /internal/job/run 을 다른 서버로 재시도하면 안 됩니다. 재시도하면 같은 회차가 두 서버에서 실행됩니다.
  • 이어 실행은 첫 판에서 뺍니다. 같은 모듈 안에서는 BPMN 서브서비스로 엮어 대신합니다.
  • 마스터코드·룰 같은 다른 캐시의 서버 간 동기화는 이번 범위가 아닙니다. 후속 과제로 남겼습니다(변경 기록 표 + 서버별 틱 확인).
